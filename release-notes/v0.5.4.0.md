# v0.5.4.0 — Base Recovery

This release completes the v0.5.x Base ownership-repair work by porting the legacy app's `DeleteBaseAndOwnedObjects` operation ("Recover Base") onto the same transaction pattern proven by v0.5.3.0's Base Ownership Transfer.

- Adds a Preview/Apply Recover Base pair to `HeadlessBaseOwnershipService`. Recovery removes the base's `base_ids` entry from its owning guild and deletes every structure/container/worker record tagged to it (`base_camp_id_belong_to`) outright, rather than reassigning them like Transfer Ownership does.
- Uses the same Preview → Safety Backup → Server-side Transaction → Validate → Journal/Audit → Refresh GUI implementation already proven by Base Ownership Transfer, Guild Ownership and World Transactions, and journals into the same transaction store. Preview decodes the save up front and reports the exact number of records that will be permanently removed before Apply, since this is a destructive operation beyond what a casual safety-backup restore undoes.
- **Removal only ever discards whole array elements, never a keyed object property.** An initial implementation deleted any JSON object that directly carried the `base_camp_id_belong_to` marker — this is safe for retagging (Transfer Ownership only overwrites a sibling field's value), but not for deletion: some record shapes (`MapObjectSaveData`, i.e. placed structures) carry the marker several levels below the record's own array element, nested under `Model.value.RawData.value`. Deleting that inner `value` key directly left a structurally required object empty and crashed the save encoder (`KeyError: 'value'` in `palsav/rawdata/map_object.py`) during initial testing against a real save. Fixed by scanning each array element's full subtree for the marker and removing the whole enclosing array element when found, never a property of a fixed-shape object.
- Desktop gets a real Base Recovery card on the Bases page (Preview Recovery, status text, an explicit "I understand this permanently deletes the base and its owned objects" confirmation checkbox, Apply With Fresh Safety Backup), replacing the disabled "Recover Base — BACKEND REQUIRED" stub. Wired through new `IMystTiqApiClient.PreviewBaseRecoveryAsync`/`ApplyBaseRecoveryAsync` and `/api/v1/bases/recovery/preview`/`/apply` routes.

Verified end-to-end on both Windows and Linux (Ubuntu 24.04.4 LTS, 192.168.1.144) against a real guild/base-populated save (copied into an isolated test environment, never against live/production data):

- **Windows**: Preview correctly identified owning guild MystTik and reported 132 tagged records for base `D04F779E4EF8578B7C8412B759E117E1` (matching the exact count independently confirmed by v0.5.3.0's retag test for the same base). Apply succeeded, reporting 132 records removed. Independent re-decode (not trusting the service's own report) confirmed zero occurrences of the base ID anywhere in the save and MystTik's `base_ids` retained only its other base.
- **Linux**: Same real save copied to an isolated standalone instance on the VM, reusing the already-installed `palsav`/`palooz` converter toolchain. Preview and Apply produced the identical result: 132 records removed, independently re-decoded and confirmed identical to the Windows outcome — zero remaining references, `base_ids` correct.
- The first Windows apply attempt failed and cleanly rolled back (see above) before the array-element-only fix was applied; the retry after the fix succeeded and was the run independently verified above.

While verifying on Linux, a stale ad-hoc test process from a prior session (`~/mysttiq-base-test`, working directory already deleted) was found still running on the VM and was cleaned up. This is unrelated to Base Recovery and is noted only for the record.

The standard automated Linux acceptance suite (`Test-v0.5.4.0-LinuxAcceptance.sh`) is expected to still fail the same pre-existing checks documented in v0.5.3.0's release notes (MOD inventory, UE4SS status, Production Doctor, monitoring metrics, PalServer status), due to the already-documented `User=root` systemd gap. This is unrelated to Base Recovery and remains explicitly deferred.

Promotion requires clean validation, logic, Windows/Linux desktop and headless builds, Windows runtime smoke, archive-entry verification, and SHA-256 verification.
