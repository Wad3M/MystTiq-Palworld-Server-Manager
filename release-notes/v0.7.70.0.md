# MystTiq v0.7.70.0 — Real Email Notification Dispatch

## Highlights

- **Implemented Email as a real notification channel** — previously a typed stub since v0.6.1.0
  that just logged "not implemented" and dropped the notification, unlike Webhook/Discord (both
  real). Now sends via plain SMTP (`System.Net.Mail.SmtpClient`), with the same retry-once shape
  the other channels already use.
- New configurable fields on the Email channel: `SmtpHost`, `SmtpPort` (default 587), `SmtpUseSsl`
  (default true, STARTTLS), `SmtpUsername`/`SmtpPassword`, `EmailFrom`/`EmailTo`.
- Verified with a real, minimal SMTP protocol stub server proving the exact envelope (from/to),
  authentication, subject, and body reach the wire correctly — and this test caught a real
  protocol-shape bug in its own first draft (`SmtpClient` sends the AUTH LOGIN username inline, not
  as a separate line) before it could hide a false pass.

## Upgrade notes

- No breaking changes — every existing `NotificationChannelConfig` construction elsewhere in the
  codebase still compiles unchanged; the new fields are all optional.
- No Desktop GUI yet for configuring this channel — same as Webhook/Discord, it's API-level only for
  now (`PUT /api/v1/notifications/channels`).
- `SmtpPassword` is stored in plaintext in `channels.json`, matching this project's existing
  local-secret convention (same threat model as RCON's `AdminPassword`, bearer tokens, etc.) — not a
  new or weaker practice.
- Only STARTTLS-style submission (typically port 587) is supported, not implicit TLS (port 465) —
  a `System.Net.Mail.SmtpClient` limitation, disclosed rather than silently unsupported.
- Not verified against a real mail provider (Gmail, Outlook, etc.) this pass — the wire protocol
  itself is proven correct against a real RFC 5321 server.
