# v0.2.15.8 — Runtime Evidence Engine Refinement

## Baseline
Official implementation baseline: **v0.2.15.7 — Unified Runtime State Architecture**.

## Objective
Refine runtime verification so every MystTiq surface interprets the same current-session evidence consistently. The immediate acceptance case is AntiDupe and PalImportFilter: when the MOD Library has authoritative **Loaded** evidence, the MOD Dashboard/verification report must not remain **Runtime Unverified**.

## Implementation
- Added `ModRuntimeEvidenceEngine` as the verification-side authority for mapping logical MOD identities to current-session runtime state.
- Added structured `RuntimeEvidenceAssessment` results: confirmed/unverified, evidence source, matched alias, and explanatory detail.
- RuntimeStateService now uses the evidence engine's positive-signature extractor rather than maintaining a single hard-coded `Starting Lua mod` parser.
- Added conservative recognition for `Starting Lua mod`, `Loading Lua mod`, explicit Lua-mod started/loaded/initialized/enabled/registered messages, and explicit loaded/initialized/registered mod messages.
- UE4SS verification first consumes the unified current-session snapshot and then honors the scanner-applied `LoadedByUe4ss` state. Historical log searches cannot override the current session.
- RuntimeStateService `StateChanged` now drives a non-recursive Library/Dashboard synchronization pass using the existing inventory snapshot.
- Verification/export details now identify the evidence source and matched runtime alias when available.

## Safety / compatibility
- No MOD files, `mods.txt`, `enabled.txt`, Workshop content, or server configuration are modified by the evidence engine.
- Current-session boundaries remain owned by RuntimeStateService; positive evidence is still cleared on stop/new session.
- Existing MystTiq dark-theme, button, tooltip, and layout standards are unchanged.
