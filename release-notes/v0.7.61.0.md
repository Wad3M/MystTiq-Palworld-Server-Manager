# MystTiq v0.7.61.0 — PalServer Launch Freeze Root Cause Fix

## Highlights

- **The PalServer launch freeze investigated since v0.7.57.0 is fixed.** Root cause, found live via
  a Process Explorer thread-stack capture on a genuinely frozen production process: PalServer was
  blocked inside a native Windows `MessageBoxW` call, waiting for a click that could never come
  because MystTiq launches it with no interactive desktop session. Every symptom this investigation
  ever chased — zero CPU, no crash, no port bind, nothing in any log — was this one missing launch
  argument. Unreal Engine's `-unattended` flag suppresses this entire class of dialog. Confirmed
  live: the identical production server, relaunched with the flag added, blew straight past the
  exact point it had always frozen at instead of sitting frozen.
- `-unattended` is now in both platform default launch-argument templates, and is automatically
  backfilled into every already-persisted server profile on load — existing installs are fixed
  without any manual edit required.

## Upgrade notes

- No configuration schema change, no new routes, no Desktop UI changes.
- **A separate, secondary finding, disclosed but not fixed here**: after clearing the freeze, both
  live test runs this session (production and its clone) took 10+ minutes of sustained, actively
  growing CPU use without finishing startup. This is categorically different from the freeze (real,
  continuous work vs. zero CPU growth) and doesn't block this fix, but means startup on this
  specific save/MOD combination may be unusually slow for a separate, not-yet-diagnosed reason.
  Worth its own follow-up.
- The still-running production headless host (v0.7.50.0) loaded its configuration before this
  session's direct edit to the live `mysttiq.json` — it needs a restart (ideally onto a build
  containing this fix) to actually launch with `-unattended` going forward.
- No way to visually render this app in the environment that built it, same standing limitation as
  every prior version.
