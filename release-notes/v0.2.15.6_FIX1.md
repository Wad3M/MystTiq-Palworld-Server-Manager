# v0.2.15.6 FIX1 — Runtime-Loaded Synchronization & Test Harness Correction

## Problem

The MOD Library could show every UE4SS/Lua MOD as `Not loaded` even while PalServer and the MODs were running correctly.

Two independent causes were identified:

1. `ModScannerService` consumed the session-cached `Ue4ssRuntimeResolver.Resolve()` snapshot. If that snapshot was created before PalServer started, its loaded-MOD list remained empty during later Library scans.
2. Workshop/managed package identity can differ from the actual UE4SS runtime folder name written by `Starting Lua mod '<name>'`. The Library matched only package/friendly names, so valid evidence could be missed.

The standalone logic harness also produced two false failures: it searched for the enum name instead of the `report.CanStart` gate used by `MainWindow`, and it treated a stale native `$LASTEXITCODE` as the result of a successful PowerShell `Build.ps1 Clean` call.

## Fix

- Runtime-loaded annotation now calls `Ue4ssRuntimeResolver.Refresh()` on each authoritative MOD scan.
- `ModRow` now carries runtime aliases derived from Workshop package structure and managed install destinations.
- Loaded-state matching uses package, friendly name, and runtime aliases.
- Logical-row merging preserves runtime presence, loaded evidence, and aliases.
- The 45-second startup MOD summary invalidates the inventory snapshot and refreshes the MOD Library automatically.
- The regression harness validates the real `report.CanStart` gate and treats PowerShell build scripts as successful when they complete without throwing.

## Safety

No MOD files are moved, deleted, enabled, or disabled by these changes. Runtime alias discovery is read-only.
