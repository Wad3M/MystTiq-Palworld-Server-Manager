# MystTiq Palworld Server Manager v0.3.0.6 FIX1

## Remote Enrollment Reliability Hotfix

Acceptance of the initial v0.3.0.6 package exposed a release-blocking enrollment defect.

The enrollment command appeared to complete, but the actual machine remained on schema-v1/local-only configuration, the TLS certificate/password were absent, and the API continued listening only on `127.0.0.1:8213`. The Windows acceptance runner also threw a PowerShell exception when prerequisite files/listeners were missing.

## FIX1 changes

`Configure-MystTiqRemoteApi.sh` is now staged and fail-fast:

1. explicit confirmation
2. one sudo authorization
3. verify the current binary actually contains the remote/TLS commands
4. prepare protected directories
5. backup the existing configuration
6. migrate/validate the configuration
7. create **and verify** the bearer token
8. normalize and verify token ownership/mode
9. create **and verify** the PFX and password secret
10. normalize and verify certificate/password ownership/mode
11. write the remote configuration
12. validate the written configuration
13. read the effective configuration back and verify bind/auth/TLS
14. install/restart the current build
15. verify systemd
16. verify the exact LAN listener
17. verify HTTPS health
18. verify unauthenticated HTTP 401
19. verify bearer-authenticated HTTP 200

If enrollment fails before final commit, the previous configuration is restored and the service is restarted.

`Test-MystTiqRemoteApi.ps1` now performs prerequisite checks and emits clean `[FAIL]` results for missing configuration, token, listener, or HTTPS connectivity instead of crashing on null values.

No core API security policy, schema, lifecycle, PalServer behavior, or Windows WPF behavior changed.
