# v0.6.3.0 — Windows Service Hardening, Character Migration & Setup/Update Cleanup

Three independent areas, each shipped as a real, working foundation rather than everything at full depth — see `docs/architecture/v0.6.3.0-windows-service-character-migration.md` for the full contract writeup and deferred list.

## Windows service hardening

`WindowsServiceManager` (an `sc.exe` wrapper that has existed since v0.4.0.0) is now actually wired into `service-status`/`service-install`/`service-uninstall`/`service-run` — those commands were previously hard-gated to Linux only. The auto-restart-on-crash loop, `LinuxHeadlessSupervisor`, turned out to contain zero Linux-specific code, so it's renamed to `HeadlessSupervisor` and shared by both platforms — this is what makes `RecoveryBackoffSeconds`/`MaximumRecoveryAttempts`/`RecoveryWindowSeconds` real on Windows for the first time. A new `Microsoft.Extensions.Hosting.WindowsServices`/`AddWindowsService()` integration makes `sc.exe stop` actually work (gracefully cancels the process instead of SCM eventually force-killing it), and a real `WindowsSystemServiceStatusProvider` replaces a hardcoded-false status stub.

## Character/account migration

New `HeadlessCharacterMigrationService`, following the exact Preview → Safety Backup → Server-side Transaction → Validate → Journal/Audit pattern already proven for guild ownership: migrate a source player's guild membership/leadership to an already-existing destination player identity (e.g. Xbox → Steam). Ships real Keep/Archive/Delete source-character disposition; `Reset` is explicitly rejected with a clear message rather than guessed. Full level/inventory/Pal/equipment transplant is explicitly deferred — nothing in this codebase decodes an individual player `.sav` file's internals yet, and the legacy WPF app's own migration tooling never implemented real mutation either.

## Server Setup vs. Update Center

Fixed a real bug: Server Setup's per-row action and "Install Missing" button silently triggered a full SteamCMD update/reinstall even when clicked on an already-installed row reading "Verify" — the same mutating route Update Center's own button uses. Setup now only mutates directly for genuinely-missing components; the ongoing-update case navigates to Update Center, which stays the one authoritative place that mutation happens.

## Verification

- `scripts/Test-v0.6.3.0-Logic.ps1 -RunBuild`: 21 contract-presence/regression checks, the frozen v0.6.2.0 checkpoint regression gate, `Build.ps1 Build -Configuration Release`, and the full v0.5.1.5 runtime smoke suite (28 checks) — all green.
- Manual, Windows: ran `service-run` in the foreground (not SCM-installed) against a scratch config and confirmed the API host, supervisor, and `AddWindowsService` lifetime wiring all start and shut down cleanly together. Full `sc.exe install`/`start`/`stop`/`uninstall` against a real registered service needs Administrator elevation this session didn't have, so that specific cycle is not yet live-verified — flagged in the checkpoint notes as a follow-up.
- Manual, against a real isolated copy of a live save: previewed and applied a real guild-membership migration, confirmed via safety-backup file-hash diff that `Level.sav` genuinely changed, confirmed the migration journal appears in Transaction Center history, and confirmed Archive and Reset disposition behavior. Found and fixed two real bugs in the process (a `canApply` computation bug and a missing JSON string-enum converter) — proof the verification was exercising real behavior, not just checking that code compiled.
- Manual, Desktop: confirmed Server Setup's per-row action navigates to Update Center instead of mutating when a component is already installed, and that genuinely-missing components still install directly.

Promotion requires clean validation, logic, Windows desktop and headless builds, and Windows runtime smoke. Linux deployment/verification for this milestone is a carried-forward gap from v0.6.2.0's checkpoint — the Windows-service work is Windows-only by nature, but the character-migration and Setup/Update-Center fixes are cross-platform and should be verified on the Linux VM in a follow-up session.
