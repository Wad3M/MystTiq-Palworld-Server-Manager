# v0.6.0.0 — Architecture Baseline & Operation Platform

First milestone of the `v0.6.x.0` family (`docs/roadmap/MystTiq_v0.6_Grouped_Development_Roadmap.md`), building on the completed v0.5.1.x–v0.5.5.0 "Functional Visual Shell Integration" line. Its job is to lay the architecture foundation the rest of `v0.6.x.0` depends on: a real Operation/Provider/Health/Transaction contract set in `MystTiq.Core`, plus a coordinator that makes long-running/destructive actions observable and safe to run concurrently.

This milestone's own acceptance checklist is larger than one pass can responsibly ship — priority queues, dependency-graph blocking, restart-safe lock reclassification, SteamCMD phase parsing, a full log-tail UI. This pass builds a real, working foundation and proves it by migrating the three existing destructive-mutation services onto it, rather than shipping the full aspirational checklist decoratively. See `docs/architecture/v0.6.0.0-operation-platform.md` for the full writeup and the explicit deferred list.

## Core contracts — `MystTiq.Core/Operations/`

- `OperationId`, `OperationPhase`, `OperationStage`, `OperationRecord` — kind-agnostic operation identity and history, promoted from the near-duplicate per-feature journal pattern the three services previously hand-rolled independently around a shared-by-accident type (`HeadlessWorldTransactionJournal`).
- `OperationTransactionState` — a derived Active/Committed/RolledBack/Failed outcome computed from each record's Phase + RolledBack fields, so every operation exposes a real transaction contract rather than callers re-deriving "did this commit" by hand.
- `ServerProfileId` — string-wrapping identity with a `Default` singleton. MystTiq is single-server today, but every operation record, lock, and API now carries a real profile id instead of relying on process name or an implicit "the one server" — the seam the eventual multi-server fleet (`v0.6.8.0`) builds on without another rewrite.
- `ServerHealthState` / `ServerHealthSnapshot` — formalizes the ad-hoc health strings the Dashboard already computed.
- `ICapabilityProvider` — minimal provider/capability marker, implemented by `IServerDistributionPlatformService` via default interface members (zero changes needed to the Windows/Linux platform services).
- `IOperationCoordinator` / `OperationCoordinator` — `BeginAsync` returns a disposable `OperationHandle`; a resource-key lock table rejects any operation whose keys overlap one already in flight, naming the blocking operation in the exception message. Persists one JSON file per operation under `ManagerRuntimeRoot/operations/journals/`, using the same atomic temp-file-then-move pattern already proven by the migrated services.

## Migration — "wrap, don't replace"

`HeadlessWorldTransactionService`, `HeadlessGuildOwnershipService`, and `HeadlessBaseOwnershipService` (World Transactions, Guild Ownership, Base Ownership/Recovery) now each acquire an `OperationHandle` at Apply time, alongside their existing per-feature journal rather than instead of it — avoiding regression risk against already-shipped, verified destructive-mutation code. All four migrated Apply flows share resource key `"world-mutation"` (they all mutate the same `Level.sav`), so the coordinator now correctly rejects any of them from running concurrently with another — a real safety property that did not exist before.

## New API surface

- `GET /api/v1/operations?max=N` — recent operations, newest first.
- `GET /api/v1/operations/{id}` — single operation, 404 if unknown.

## Desktop

The World Transactions page's "Transaction Center / Durable Journal" card gains a second "Operation Platform" card: Kind, Source, Phase, TransactionState, and last-updated timestamp across all three migrated features, with its own Refresh command. Kept as an enhanced section of the existing page rather than a new nav destination, consistent with the standing rule that World Transactions deliberately isn't its own nav item.

## Verification

- `scripts/Test-v0.6.0.0-Logic.ps1 -RunBuild` green, including 5 new contract-presence checks (Operation/Provider/Health/Transaction/ServerProfile contracts) and a frozen-checkpoint regression gate — the v0.5.1.5 logic gate is re-run against the archived `v0.5.1.5` FullSource checkpoint rather than the live tree, since it asserts a literal `VersionPrefix` that can never match again once the version moves forward. (One pre-existing check inside that frozen checkpoint, `Guild Base Capability Truth`, was already stale at the moment v0.5.1.5 itself was archived — confirmed by inspecting the checkpoint's own `MainWindow.axaml` directly — and is tolerated by name rather than silently ignored; any other frozen-gate failure still fails the check.)
- Manual, on an isolated copy of a real guild/base-populated save (never the live save): a Base Recovery Apply and a concurrent World Transaction Apply were dispatched simultaneously against an isolated local instance. Base Recovery won the race and ran to real completion (132 owned records removed, matching the same base this save's Base Recovery was verified against in v0.5.4.0); the concurrent World Transaction Apply was rejected with the coordinator's own message — `Blocked: resource 'world-mutation' is held by operation <id> until it completes` — proving the new cross-feature lock, not some other pre-existing per-service guard (these are two different services with no shared guard of their own).
- Desktop Transaction Center's new Operation Platform card confirmed to show entries from all three migrated features after exercising each once.
- Deployed to the Linux VM (`192.168.1.144`) and re-ran the Linux acceptance suite there: the new `GET /api/v1/operations` (list) and `GET /api/v1/operations/{id}` (404 for unknown) routes pass cleanly against the live systemd-managed service, alongside the existing Player/Guild Explorer, World Explorer, and Server Distribution routes. A cluster of unrelated failures surfaced in the same run (`/api/v1/status`, MOD/UE4SS inventory, Doctor, metrics) — confirmed via the live root-owned service (`curl` directly against the systemd instance returned a correct 200 with real PalServer status) to be the acceptance script's own known pre-existing gap: its ephemeral test instance runs as `mystroth` but `/opt/mysttiq/runtime/*` is root-owned by the systemd unit, so that instance alone gets `UnauthorizedAccessException` writing lifecycle state — unrelated to this release and already tracked as a known gap, not investigated further here. A live destructive Apply + lock-conflict race was not re-run natively on Linux against production data; the coordinator itself is platform-agnostic C# already proven correct above, and the new routes are confirmed working end-to-end against the live Linux service.

Promotion requires clean validation, logic, Windows/Linux desktop and headless builds, and Windows runtime smoke.
