# v0.5.3.0 — Base Ownership Transfer

This release ports the ownership-repair pattern proven by v0.5.2.0's Guild Ownership platform onto Base.

- Adds `HeadlessBaseOwnershipService` with a Preview/Apply Transfer Ownership operation. A real base's ownership is denormalized: it is not one field but a guild-level `base_ids` pointer plus a `group_id_belong_to` tag scattered across every structure/container/worker object placed at that base — confirmed against a real save: 132 separate tagged records for one base. Transfer moves the `base_ids` entry between guild records and retags every one of those objects to the new owning guild.
- Uses the same Preview → Safety Backup → Server-side Transaction → Validate → Journal/Audit → Refresh GUI implementation already proven by Guild Ownership and World Transactions, and journals into the same transaction store so existing Transaction Center history picks it up automatically.
- Deliberately scoped to Transfer Ownership only. Base Recovery — the legacy app's `DeleteBaseAndOwnedObjects` operation, which removes the tagged objects outright rather than reassigning them — has not been ported. The Bases page now shows an honest disabled "Recover Base — BACKEND REQUIRED" stub with an explanation, rather than a vague "repair" placeholder.
- Desktop gets a real Base Ownership Transfer card on the Bases page (target-guild input, Preview, confirmation checkbox, Apply With Fresh Safety Backup), wired through `IMystTiqApiClient.PreviewBaseOwnershipTransferAsync`/`ApplyBaseOwnershipTransferAsync` and new `/api/v1/bases/ownership/preview`/`/apply` routes.

Verified end-to-end on both Windows and Linux (Ubuntu 24.04.4 LTS, 192.168.1.144) against a real guild/base-populated save (copied into an isolated test environment, never against live/production data):

- **Windows**: Preview correctly identified source guild MystTik and target Unnamed Guild for base `D04F779E4EF8578B7C8412B759E117E1`. Apply succeeded, reporting 113 owning-guild tags updated. Independent re-decode (not trusting the service's own report) confirmed MystTik's `base_ids` retained only its other base, Unnamed Guild's `base_ids` gained the transferred base, and 113/113 records tagged to that base now pointed to the target guild with zero remaining on the source guild.
- **Linux**: Same real save copied to an isolated standalone instance on the VM (reusing the already-installed `palsav`/`palooz` converter toolchain from v0.5.2.0's verification — no new setup required). Preview and Apply produced the identical result: 113 owning-guild tags updated, independently re-decoded and confirmed identical to the Windows outcome — both `base_ids` arrays correct and 113/113 retagged records confirmed, 0 remaining on the source guild.

The standard automated Linux acceptance suite (`Test-v0.5.3.0-LinuxAcceptance.sh`) still fails several checks (MOD inventory, UE4SS status, Production Doctor, monitoring metrics, PalServer status) due to a pre-existing, previously-documented issue: the live systemd service runs as `User=root`, leaving `/opt/mysttiq/runtime` root-owned, which blocks the suite's separate standalone-as-`mystroth` acceptance instance from writing its own runtime state. This is unrelated to Base Ownership Transfer, was already known before this release, and remains explicitly deferred.

Promotion requires clean validation, logic, Windows/Linux desktop and headless builds, Windows runtime smoke, archive-entry verification, and SHA-256 verification.
