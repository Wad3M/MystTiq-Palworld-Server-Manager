# MystTiq v0.7.17.0 — Fix `api-remote-enable` CLI Bug

## Highlights

- **The documented CLI workflow for going remote now actually works.** `api-token-create` → `api-tls-create` → `api-remote-enable --bind-address <ip>` previously always failed on a fresh config, because a blanket pre-command validation check compared the new bind address against the old, not-yet-enabled authentication/TLS settings before the command that enables them ever ran.
- **No behavior change for any other command.** `api-run`/`service-run` still refuse to start listening on a non-loopback address without authentication and TLS both enabled — that safety check is unchanged.
- New permanent regression test exercises the real CLI end-to-end (fresh config → token → certificate → remote-enable → run) and confirms the resulting instance genuinely enforces authentication and TLS. Verified on both Windows and the real Linux deployment.
- **The Linux packaging/deployment pipeline (`Build.ps1 LinuxHeadless`) works again**, restored while verifying the above — it had been broken for every release since v0.6.1.0 for reasons unrelated to this fix. Then expanded to cover essentially the entire current read-only/safe API surface (previously it only tested what existed back in v0.6.1.0), turning up two more real bugs fixed along the way: a crash writing lifecycle state under a root-owned directory, and a config-defaults endpoint that crashed instead of cleanly rejecting an incomplete request. Full deploy against the real Linux VM now passes 118/118.
- **Went further still and manually verified the mutation endpoints** (guild/base ownership transfer, backup restore, MOD install/rollback, world import, config writes) that the automated script deliberately skips — using a real save copy in a fully isolated environment, with everything restored to its original state afterward. Found and fixed a fifth real bug: a backup-retention filter field that crashed instead of filtering, because its type wasn't actually JSON-deserializable.

## Upgrade notes

- Server-side (`MystTiq.HeadlessHost`) fix only, no configuration schema change and no Desktop change.
- If you previously worked around this by hand-editing a config's `Api.Authentication.Enabled`/`Api.Tls.Enabled`/`BindAddress`/`Port` fields directly, `api-remote-enable` can now be used normally instead.
