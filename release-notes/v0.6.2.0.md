# v0.6.2.0 — Multi-Server Fleet (Runtime Providers deferred)

Per `docs/roadmap/MystTiq_v0.6_Grouped_Development_Roadmap.md`, this milestone's literal scope bundles two largely orthogonal bodies of work: (a) server/profile identity threaded through paths/config/routes/coordinator/RBAC, and (b) a runtime-provider abstraction covering Docker and Wine-on-Linux. This pass ships (a) in full, real, working form, plus a genuine seam for (b) — explicitly deferred, not dropped, since Docker/Wine need real environments to verify against (this project's standing rule against shipping unverified "decorative" code).

## Config schema v3 — plural server profiles

`HeadlessConfiguration.Server` (one object) becomes `Servers` (`IReadOnlyList<HeadlessServerProfileConfiguration>`), each with its own `Id`/`Name`/`ServerRoot`/`SteamCmdPath`/`BackupRoot`/`RuntimeRoot`/`LaunchArguments`/`Runtime`. A new `MigrateV2` step wraps an existing single-server v2 config into one `"default"` entry — verified against a real legacy config file: migrates cleanly, and the resulting v3 file round-trips without any stray computed-property bloat (a real bug found and fixed: `HeadlessConfiguration.DefaultServer` was serializing into the persisted file until `[JsonIgnore]` was added).

## Composition, not rewrite

`IServerLifecycleService` and every `Headless*Service` already took an `IServerPathProfile` via constructor injection — none of them reached for global/static config. That meant per-server isolation could work the moment each server got its own `paths` object, with zero internal rewrites. `LocalManagementApiHost.Create` now loops over configured server profiles, constructing one full existing service graph per profile (bundled as `ServerProfileHost`). `OperationCoordinator`, `HeadlessRbacService`, and `HeadlessAuthAbuseGuardService` stay fleet-level singletons — one shared operation ledger, principal store, and auth-abuse guard for the whole process.

## Routes — profile resolution, fully backward-compatible

Every route is registered twice from one shared `MapProfileRoutes` method: once at its classic unprefixed path (resolving to the `"default"` profile only — zero change for a pre-fleet client) and once under `/api/v1/servers/{profileId}/...` for every profile, including `"default"`. A real bug was found and fixed during manual verification: the first implementation double-prefixed profile-scoped routes (`/api/v1/servers/{id}/api/v1/backups` instead of `/api/v1/servers/{id}/backups`) because each handler's literal path still carried its own leading `/api/v1`, redundant with the `MapGroup` prefix — caught by actually curling the new routes against a real two-profile instance, not by contract-presence regexes.

## Fleet-wide operation visibility and per-server locking

`OperationCoordinator.resourceLocks` is now keyed by `(ServerProfileId, resourceKey)` instead of `resourceKey` alone, with journal paths namespaced per profile. Verified live: firing `Server Start` on two profiles simultaneously failed each independently for its own real reason (missing executable) with neither reporting `lifecycle-operation-in-progress` from the other — proving locks no longer cross-block between servers.

## Compound process identity — closing a real cross-talk bug

`LocalManagementBootstrapper.EnsureAvailableAsync`'s "already reachable, reuse it" fast path previously trusted any process that answered `/healthz` with a compatible `component`/`apiVersion` — found during the previous session's screenshot work to silently attach to the wrong already-running MystTiq instance. `/healthz` now reports `serverProfileIds`; the bootstrapper checks the expected profile is actually present before reusing an instance (older pre-v0.6.2.0 instances with no `serverProfileIds` field are treated as compatible, so this doesn't regress against an older sidecar).

## Per-server RBAC and fleet bulk actions

`MystTiqPrincipal.ScopedServerProfileId` (nullable — null means full-fleet access) is checked by `RequireRole` against the route's resolved profile. New `GET/POST /api/v1/servers` and `DELETE /api/v1/servers/{id}` manage fleet membership (adding/removing a profile requires a process restart to take effect, same convention as every other config edit). New `POST /api/v1/fleet/{backup,doctor,update}-all` iterate every profile, staggered by `FleetStaggerSeconds` (default 5s) so N servers don't fire the same disk/network-heavy action simultaneously — verified live: `Backup All` against two profiles produced two isolated, correctly staggered backups (roughly 1s apart at a 1s test stagger), each in its own backup root.

## Runtime provider seam (Docker/Wine explicitly deferred)

`ServerRuntimeKind { WindowsNative, LinuxNative }` on each server profile — the two real values wrap the existing, already-verified `WindowsServerLifecycleService`/`LinuxServerLifecycleService` unchanged. Docker and Wine-on-Linux are not added as enum members yet; they need real Docker/Wine environments to verify against, and are picked up by a follow-up revision rather than shipped unverified.

## Desktop

New Fleet page listing every configured server profile with independent live status, plus Backup All / Doctor All / Update All buttons calling the new fleet routes. Existing single-server pages are unchanged in this pass — an optional per-page server selector is explicitly deferred alongside Docker/Wine, since threading `ServerProfileId` through the Desktop's 90+ existing API-client call sites is a large, separate mechanical pass better done once the server-side surface has settled.

## Explicit deferred list

- Docker and Wine-on-Linux runtime provider implementations (seam only).
- Docker-specific health/config checks (depends on the Docker provider).
- Per-page "current server" selector on existing Desktop pages beyond the new Fleet page.
- Direct single-server CLI verbs (`status`/`start`/`stop`/`restart`/`service-*`) stay scoped to the `"default"` profile only — `api-run`/the Management API is the fleet-aware surface.
- Crash-recovery auto-supervision (`LinuxHeadlessSupervisor`) stays scoped to the `"default"` profile only; additional fleet profiles are managed via the Management API's own lifecycle routes, not the systemd auto-restart loop.
- Cross-profile automation rules (a rule referencing another server).

## Verification

- `scripts/Test-v0.6.2.0-Logic.ps1 -RunBuild`: 22 contract-presence/regression checks, the full frozen v0.6.1.0 checkpoint regression gate, `Build.ps1 Build -Configuration Release`, and the complete v0.5.1.5 runtime smoke suite (29 checks) — all green.
- Manual, against a real two-server isolated instance (throwaway ports and directories, never the live save/config): confirmed independent config/backups/lifecycle status per profile via direct API calls; confirmed `/healthz` reports both `serverProfileIds`; confirmed the backward-compatible unprefixed routes resolve to `"default"` while `/api/v1/servers/{id}/...` resolves the named profile; confirmed `Backup All` produces two isolated, staggered backups; confirmed concurrent `Server Start` on both profiles fails independently without cross-blocking; confirmed a real legacy v2 config migrates cleanly to v3 with no stray fields. Two real bugs were found and fixed during this pass (the route double-prefix and the missing `JsonStringEnumConverter` on `ServerRuntimeKind`) — proof the verification was exercising real behavior, not just checking that code compiled.
- This checkpoint also carries forward the `RaisePageVisibility()` regression fix from the prior session (the Automation/Alert Center/Security pages rendering blank in the shipped v0.6.1.0 build) — folded in rather than shipped as a separate v0.6.1.1 patch, per explicit direction.

Promotion requires clean validation, logic, Windows desktop and headless builds, and Windows runtime smoke.
