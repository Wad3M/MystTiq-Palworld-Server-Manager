# v0.7.115.0 — Deficiency Fixes (the user's report, items 1–5)

## Why

After the 0.7.x pass (v0.7.111.0–v0.7.114.0), the user supplied a deficiency report and asked for it to be
checked. Every item was verified against the real code and the running app before anything was changed.
All six were confirmed. Item 6 (icon silhouettes and header art) was deferred by the user ("Skip item 6 for
now") and stays on the roadmap.

## 1. Map markers and labels can overlap

**Found:**
- v0.7.106.0 staggered labels by *distance between dots* (a 30px circle), pushing a label down one step per
  earlier dot inside it. That is not the question "does this text overlap that text":
  - A chain of markers 25px apart gave the 2nd and 3rd labels the same offset, so their text, much wider
    than 25px, overlapped.
  - A dot up-left of another put its pushed-down label on the other's.
- Looking at the live Map page found two more problems:
  - **Player names never rendered at all.** No name appeared even for an online player (also true of the
    v0.7.110.0 checkpoint screenshot). A diagnostic build with a red background on the label drew nothing,
    so the label was being laid out away or clipped, not merely coloured.
  - Every marker was a Button under the app-wide Button style (MinHeight 31, centred content,
    ClipToBounds). So each dot sat a few pixels off its computed point, and the label box on screen never
    matched the one the layout computed.

**Fixed:**
- `MapLabelLayout.ComputeLabelOffsets` now places each label as a rectangle: its own text width,
  estimated from length and font size, one line high. Labels are placed greedily in draw order at the
  nearest free spot (below, right, above, left, then further out one line at a time). A spot is free when it
  overlaps no label already placed and no other marker's dot. The result is bounded
  (`MaximumSteps`) and deterministic.
- Marker buttons now hold only the dot, with `MinWidth/MinHeight 0`. Labels are drawn in their own
  non-clickable layers at `LabelPosition`, which is exactly the rectangle the layout placed. Player names
  now appear.
- The harness checks placed rectangles for overlap directly: the chain, the diagonal case, stacked markers,
  five bunched markers, and 40 random clusters. It also checks that labels stay near their dots. Live
  screenshots (whole map and 2.4×) show every name next to its own marker with nothing overlapping.

## 2. Crash notifications can remain pinned after a backend restart

**Found:** the pinned "server is DOWN" notice's id (v0.7.110.0) was held only in memory. After a sidecar
restart nothing could unpin it.

**Fixed:** the id now lives in the profile's `crash-recovery/state.json` (`SupervisorRecoveryStateStore`),
which `CrashAlertObserver` reads and writes. A new observer after a restart unpins the notice that the
previous process pinned.

## 3. Recovery can report success before readiness is confirmed

**Found:**
- The v0.7.110.0 give-up watcher reported "back up" as soon as a PalServer process existed.
- The supervisor treated an `AlreadyRunning` restart result as recovered on sight.

**Fixed:** "back up" means **ready**, the same test a normal start uses: the process exists and its
configured UDP game port is up. The watcher waits for `Ready`. The supervisor, when a restart returns
without readiness, waits up to the startup timeout (`WaitUntilReadyAsync`); if the server never becomes
ready, that is a failed restart (`NotReady`), not a recovery.

## 4. Operation history and recovery state need stronger persistence

**Found:**
- `OperationCoordinator` journals were written but never read back. The history was empty after every
  restart, and an operation running when MystTiq stopped stayed "Running" on disk forever.
- The supervisor's restart window and give-up were memory-only. A MystTiq restart reset the "N restarts
  per window" limit, and treated a server that recovery had already given up on as a brand-new crash, which
  it restarted again.

**Fixed:**
- On start-up, the newest 500 journals are loaded. A Running or Queued one is closed as Failed with an
  `Interrupted` stage that says its outcome is unknown. It is saved, so this happens once. Resource locks
  are not restored.
- `SupervisorRecoveryState` (restart history, `GaveUpAtUtc`, pinned id) is saved on every change. After a
  restart, the supervisor starts with the remembered window. The fleet service resumes *watching* when
  recovery had given up, instead of restarting.
- `service-run` passes no store and keeps its own behaviour.

## 5. Outdated release version in docs; the full gate depends on an older backup archive

**Found:**
- `RELEASE_CHECKLIST.md` said "Current development candidate: v0.4.18.2".
- Every gate threw if the previous checkpoint ZIP was missing, so it could run on no machine but this one.
- The one "known residue" failure every gate carried since the v0.7.10x line came from
  `Validate-Release.ps1`'s hygiene check. It forbids bin/obj/artifacts folders, which the gate itself
  creates before validating.

**Fixed:**
- The checklist's current-release section no longer names a version. It points at `Directory.Build.props`,
  which validation already cross-checks.
- `Validate-Release.ps1 -AllowBuildOutputs` skips only the build-output hygiene check. Gates use it; the
  release pipeline still validates without it after Clean.
- The test framework has a SKIP state. A missing baseline archive is reported as SKIP with the path and how
  to point at a copy (`-FrozenBaselineZip`), instead of crashing the gate.

## Verification

- Logic harness: map-label scenario rewritten (rectangles), and 4 new scenarios:
  - readiness after a restart
  - readiness after a give-up
  - restart window, give-up and pinned id surviving a restart
  - operation reload with Interrupted
- `scripts/Test-v0.7.115.0-RouteSmoke.ps1` (5 checks) runs on the published exe, restarting the real
  sidecar mid-cycle, with its own FleetRoot:
  1. a planted Running journal comes back as Failed/Interrupted
  2. the real lifecycle gives up and pins DOWN (id saved)
  3. after a sidecar restart, no new crash is reported and DOWN stays pinned
  4. a real `PalServer.exe` process not on its game port is NOT "back up"
  5. binding the port gives "back up", and the old DOWN notice unpins
- `scripts/Test-v0.7.110.0-RouteSmoke.ps1` was updated to the corrected contract: its fixture has its own
  game port, which it binds once the fake PalServer starts.
- Live Desktop map screenshots: before (no player names) and after (whole map and 2.4×).
