# v0.7.24.0 — Roadmap Doc Audit

## Goal

Close the last item in the approved v0.7.20.0–v0.7.24.0 backlog plan: two rows in `docs/roadmap/WINDOWS_BACKPORT_REGISTRY.md`, both labeled "Discovery backlog" since the registry was created, flagged during the v0.7.19.0 backlog-triage audit as likely stale. Rather than trusting that suspicion, each row was independently re-verified against the current code before touching the doc — the same discipline v0.7.11.0's own doc-consistency audit established (four stale labels found and fixed there by checking real shipped state, not by pattern-matching the doc's own wording).

## What was found

### Row: "Service-style watchdog/recovery behavior inspired by Linux/systemd supervision"

Stale. `HeadlessFleetCrashRecoveryService` (`MystTiq.HeadlessHost`, shipped v0.6.13.0) wraps one `HeadlessSupervisor` per profile — the exact crash-detect/backoff/window-polling loop `service-run`'s systemd-style supervision already used, extracted unchanged into `RunCrashRecoveryLoopAsync` and reused verbatim. `ServerProfileHost` carries a `CrashRecovery` property; `LocalManagementApiHost.Create` starts one per profile, right alongside `Automation`. This means every profile under `api-run` — the mode Desktop's own sidecar actually runs, not just the installed-service `service-run` path the row's original wording implied — has had the same auto-restart safety guarantee since v0.6.13.0, including the "an intentional stop is never treated as a crash" guard, verified live against two real running PalServer instances (see `docs/architecture/v0.6.13.0-fleet-wide-crash-recovery.md`'s own verification section).

Flipped from "Discovery backlog" to "Shipped ... — see `docs/architecture/v0.6.13.0-fleet-wide-crash-recovery.md`".

### Row: "Improved structured log rotation/retention if Linux implementation proves useful"

Genuinely still open — not stale. The row's own premise (checking whether a Linux-specific implementation exists worth backporting) doesn't apply: `HeadlessConsoleLogWriter`, the only structured-log writer in the codebase, lives in `MystTiq.HeadlessHost` and is shared unmodified by both platforms. It appends every line (`[timestamp] [LEVEL] [CATEGORY] [SUBCATEGORY] message`) to `MystTiq-PalServer-Console.log` via a plain `File.AppendAllText` inside a lock, with no size check, no rotation, and no retention/cleanup anywhere in the method or anywhere else in the codebase (confirmed via a targeted search across both `MystTiq.HeadlessHost` and the Linux/Windows lifecycle services for rotation-adjacent terms — none found beyond unrelated `.Trim()` string calls).

Left as "Discovery backlog," with the registry entry updated to record that this was actually checked and confirmed open (not an untouched guess), so a future pass doesn't have to re-derive the same finding. No implementation attempted here — an unbounded log-management feature is real, scoped work, not a side effect of a doc-label fix, matching this plan's existing precedent of deferring genuinely-new-scope items (theme variants, whitelist join-requests) to their own dedicated passes rather than bundling them.
