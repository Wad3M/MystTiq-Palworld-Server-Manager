# Slow-Startup Investigation (Not Reproduced) — Session Following v0.7.70.0

## Goal

The last structurally-blocked item from the original roadmap audit: *"Palworld dedicated server
slow-startup (10+ min active CPU, never completes) — disclosed but NOT diagnosed or fixed"*
(`docs/architecture/v0.7.61.0-palserver-launch-freeze-root-cause-fix.md`'s own known-gaps section).
v0.7.61.0 fixed a genuine launch *freeze* (a Win32 message box blocking forever without
`-unattended`); this was a separate, still-open issue: on both production and its clone, PalServer
was observed taking 10+ minutes of sustained, growing single-thread CPU use without ever completing
startup, for the same save/MOD combination.

## What was tried

Cloned the real production install (robocopy, ~11 GB, same isolation technique as v0.7.65.0's Linux
verification and v0.7.68.0's RCON A/B test above — never touching the live `ServerRoot`/process) to
an isolated location, with offset game/RCON/REST ports and a throwaway `AdminPassword`. Ran it under
an isolated `mysttiq-server api-run` instance. This is the exact real production save and the exact
real installed MOD set (UE4SS + 6 mods: PalImportFilter, AntiDupe, BetterBaseRange, AdminCommands,
BetterBaseBuilding, MystPalIntelligence) — the same combination the original issue was reportedly
observed against.

Ran 5 full start/stop cycles (plus one additional start as part of the v0.7.68.0 RCON A/B test, 6
total). Every single one reached `ready: true` (UDP port confirmed bound) in **6–7 seconds** — not
10+ minutes. Checked Windows Defender real-time protection status (`Get-MpPreference`): enabled,
consistent with a fresh, unscanned clone being at least as likely to hit AV-scanning-related slowness
as production, if that were the cause — no slowness observed regardless.

One real, environmental difference was noted in the clone's own UE4SS log output: a "Runtime Health:
Degraded — UE4SS Mod Root Mismatch" warning, because UE4SS's own config still pointed at the
*original* production path (`C:\GameServers\Palworld\Server\...\ue4ss\Mods`) rather than the clone's
path — an artifact of the clone/relocate technique itself (UE4SS's own settings weren't rewritten to
the new path), not a MystTiq bug. This didn't block startup (`"Startup health gate: Ready. Normal
modded startup may continue."`) and isn't relevant to the slow-startup question, but is worth knowing
if anyone re-runs a similar clone-based test and sees the same warning.

## Result: not reproduced

Six consecutive clean starts, 6–7 seconds each, zero instances of the reported slow/hanging
behavior. This is a genuine negative result, not a fix — the underlying issue (if it's still present
under some other condition not exercised here) remains undiagnosed. Plausible explanations for the
non-reproduction, none confirmed:

- The original occurrences may have depended on a transient environmental condition at the time
  (disk contention, a concurrent SteamCMD update, antivirus definition-update scanning, or something
  else time-of-day/system-load-specific) rather than a deterministic property of this save/MOD
  combination.
- The issue may require a longer-running world/more accumulated save state, more concurrent players,
  or a specific MOD version that has since been updated, none of which this test's static clone
  captured.
- It's possible whatever caused it was already fixed as a side effect of an unrelated later change
  (e.g., a MOD update, a UE4SS update) — genuinely unknown without a way to reproduce the original
  conditions precisely.

## Disposition

Not closed. If this recurs, the most useful next step is capturing it *while it's actively
happening* on a real instance (a live thread-stack/CPU-profile capture, the same technique that
successfully root-caused the v0.7.61.0 freeze) rather than attempting to reproduce it cold — this
session's attempt to reproduce it on demand, on the exact same save/mods, did not succeed, so the
next real occurrence is more valuable evidence than another synthetic attempt.

## Cleanup

The diagnostic clone (~11 GB) and its isolated `mysttiq-server` instance were fully torn down after
this investigation (`taskkill` on the api-run process, `rm -rf` on the clone directory). The real
production install and its configuration were confirmed unchanged throughout.
