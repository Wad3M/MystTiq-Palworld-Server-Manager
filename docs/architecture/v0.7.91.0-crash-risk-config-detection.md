# v0.7.91.0 — Crash-Risk Configuration Detection

## Direct live feedback

Following a competitive feature review (researching other Palworld server managers on GitHub and
Nexus Mods, cross-checked against MystTiq's actual code rather than trusting marketing claims), one
concrete, well-evidenced finding stood out: multiple independent community sources flag
`BuildObjectDeteriorationDamageRate = 0` as a known cause of long-running server instability. It
disables automatic cleanup of decayed base structures, letting entity/object counts grow unbounded
over time. Checked MystTiq's own bundled QoL presets (`PalworldConfigPresets`,
`MainWindowViewModel.cs`) and confirmed two of them set this exact value to `0` — a real,
self-inflicted risk MystTiq's own Doctor never surfaced.

User: "add the crash-risk-config Doctor check first."

## Change

New `HeadlessDiagnosticsService.BuildCrashRiskFindings()`, added to the same unified report the
Doctor page (and Dashboard health rollup) already consume — no Desktop-side changes needed, since
`DiagnosticFindings` is already a generic, data-driven `ItemsControl` binding.

- Loads the active `PalWorldSettings.ini` via the existing `PalworldSettingsConfigurationService`
  (already an injected constructor dependency — no new wiring).
- Reads `BuildObjectDeteriorationDamageRate` via a new `GetDouble` helper, mirroring the existing
  `GetBool`/`GetInt` helpers already used by `BuildConfigurationFindings()`.
- `= 0` → `DiagnosticState.Warning`, with evidence/recommendation text explaining the specific risk
  and naming MystTiq's own presets that currently set it that way.
- Anything else (including "not set to a readable number") → `DiagnosticState.Pass`.
- `PalWorldSettings.ini` missing → `DiagnosticState.Skipped`, matching `BuildConfigurationFindings`'s
  own not-exists handling exactly.

## Scope decision: only this one setting

Community sources also describe `bEnableInvaderEnemy` (enemy raid events) as a crash contributor —
deliberately **not** included. That setting defaults to enabled in vanilla Palworld and the risk is
described as player/base-count-dependent, not universal; flagging a default-on setting
unconditionally would produce a wall of false-positive warnings on ordinary, healthy servers. Kept
the check narrow to the one setting with strong, specific, non-default-value evidence.
