# v0.7.0.0 — Themes, Skins, UI Personalization & Custom Icon Set

## Goal

The next roadmap line, present since v0.3.0.4 and never yet scoped: "Themes, skins, UI personalization and original Palworld-inspired MystTiq icon set."

## Grounding

Investigating `App.axaml` + `Styles/DesignSystem.axaml` found: a single hardcoded dark palette (89 `DynamicResource` keys — 15 base colors/brushes plus ~55 gradients), no theme-swap mechanism of any kind (no `MergedDictionaries` toggling, `FluentTheme`'s built-in `RequestedThemeVariant="Dark"` only affects Avalonia's own chrome, not MystTiq's custom palette), and the ~55 gradients' `GradientStop` colors were hardcoded hex rather than referencing the base palette — changing one base color would not have re-tinted anything built from it. `MainWindow.axaml` additionally hardcoded ~85 distinct inline `Foreground`/`Fill` colors for status/severity coding, bypassing the resource system entirely. No prior version built any of this — v0.4.0.2 only established the current single dark theme's resource foundation.

Two scope questions were asked before implementation, given the size of "full theme system" and the ambiguity of "original icon set" (no image-generation tool is available in this environment):

1. **Light mode or accent-only?** A true light mode roughly doubles the palette work (a second full background/text palette, contrast-auditing every inline color). The user chose to include it.
2. **How to handle "original icon set" without image-generation access?** Not photorealistic art — but a small set of hand-authored, original vector icon glyphs (Avalonia `StreamGeometry`/`Path` resources: paw print, wrench, capture-sphere, etc.) was offered and accepted. These are generic monster-taming/base-building iconography, not any specific Palworld character or logo art.

## What shipped

### A. Palette architecture (`Styles/DesignSystem.axaml`, `Services/ThemeCatalog.cs`, `Services/ThemeApplier.cs`)

Every resource that can be swapped at runtime is listed in `ThemeCatalog.cs`, keyed by resource name → theme → variant → `Color`:

- **Structural** (9 keys: `Bg0/Bg1/Bg2/Card/CardStrong/Border/BorderSoft/Muted/Text`, plus 5 input/list-row surface keys added for this release): identical across all 4 accent themes, differ Dark vs Light. The Light palette uses an *order-preserving* remap for background/card "elevation" colors (a card stays visually elevated/lighter relative to the window backdrop in both variants, rather than flipping to read as recessed just because the whole palette moved from dark to light) and a real semantic inversion for `Text`/`Muted` (which must actually go dark-on-light, unlike backgrounds).
- **Semantic** (3 keys: `Green/Amber/Red`): fixed hue (success/warning/danger meaning doesn't change with the chosen theme), only the Light variant darkens them enough to stay readable on a light background.
- **Accent** (5 keys: `Blue/Cyan/Violet/Magenta/Orange`): the five hues that actually change identity per theme (Default/Emerald/Crimson/Violet). Each theme keeps the same five *named slots* recognizably in that hue family — hand-authored per theme rather than a blind hue-rotation formula, after an early rotation experiment produced results like "Orange" rendering as purple in one theme, which would be a confusing resource name/color mismatch for future maintainers.
- **Gradient stops** (~76 keys across the ~20 gradients that define the app's primary chrome — `ButtonGradient`/`SuccessGradient`/`WarningGradient`/`DangerGradient` families, `PrimaryGradient`, `CommandSurfaceGradient`, `CategoryActiveGradient`, `NavSurfaceGradient`, `StatusSurfaceGradient`, `CardGradient`, `ServerTabGradient`/`ServerTabActiveGradient`): each `LinearGradientBrush`'s `GradientStop`s now reference a `{DynamicResource}` per-stop color instead of a literal hex value. **The Default+Dark value of every one of these is byte-for-byte identical to the pre-v0.7.0.0 hardcoded hex** — the baseline look is unchanged unless a different theme/variant is actually selected. The other 7 combinations (3 alt accent themes × Dark, 4 themes × Light) were derived mechanically (hue-rotation for accent-tied stops, order-preserving lightness remap for structural stops) rather than hand-guessed one at a time, then spot-checked by rendering actual swatches as SVG in the browser pane and inspecting the screenshot before committing the values.
- `ThemeApplier.Apply(accentTheme, variant)` writes every one of these directly onto `Application.Current.Resources`; since every consumer already binds via `DynamicResource`, the whole UI re-flows live with no restart and no `ResourceDictionary` swap.
- `Services/LocalThemePreferencesStore.cs` (new): persists the selection at `%AppData%\MystTiq\theme-preferences.json`, following the exact same constructor-less/atomic-write/try-catch-swallow pattern as `LocalMapPreferencesStore`/`LocalConfigPresetStore`.
- `MainWindowViewModel`: new `SelectedAccentTheme`/`IsLightMode` properties (each setter calls `ThemeApplier.Apply` and `_themeStore.Save`), `AccentThemeOptions` for the picker, `SetAccentThemeCommand`. `App.axaml.cs` applies the persisted theme once at startup, before the window is constructed.
- Settings page gained a new "Appearance" card: a light-mode checkbox and a row of accent-theme buttons.

### B. Inline color migration (`MainWindow.axaml`)

The ~85 distinct hardcoded `Foreground`/`Fill` hex values (status/severity text and dots) were mapped to the closest existing semantic/accent brush (`{DynamicResource GreenBrush}`/`RedBrush`/`AmberBrush`/`BlueBrush`/`CyanBrush`/`VioletBrush`/`OrangeBrush`/`MutedBrush`) via `replace_all` per distinct value, so status text now follows the selected theme instead of staying a fixed dark-tuned color that could read poorly (or invisibly) against a light background.

### C. Custom vector icon set (`Styles/IconGeometries.axaml`)

8 hand-authored `StreamGeometry` icons: monitor+pulse-line (Dashboard), wrench (Server Setup), paw print (Players), hub-and-spoke network (Fleet), shield+checkmark (Security), tent (Bases), vault+download-arrow (Backup Center), and a two-part capture-sphere motif (ring + center dot) for the tab bar's "+" button — replacing the equivalent Segoe Fluent Icons/Unicode-glyph icon on each of those surfaces. Verified visually before committing: each icon was authored as SVG first, rendered in the Browser pane, and inspected via an actual screenshot (not just a text dump) — the same syntax carries over almost directly into Avalonia's `StreamGeometry` mini-language (`M`/`L`/`A`/`Z`, both absolute and relative commands), so what was confirmed on screen is what ships.

## Explicit non-goals / disclosed limitations

- **The many smaller decorative `BorderBrush`/`BoxShadow`/`Effect` colors** scattered through `DesignSystem.axaml`'s ~150 other `<Style>` selectors (hover/pressed/selected-state borders and glows) are **not** covered this pass. `BoxShadow`'s shorthand string syntax (`"0 0 22 2 #5A3ADF64, ..."`) cannot bind to `DynamicResource` at all — a hard Avalonia limitation, not an oversight — and the remainder are secondary accents rather than primary surfaces. They stay at their current dark-tuned literal values in every theme/variant. A light-mode user may see some hover-glow colors that look slightly dark-tuned rather than perfectly light-optimized; primary readability (backgrounds, cards, borders, text, status colors) is unaffected by this gap.
- **~17 of the ~25 nav-sidebar destinations** keep their existing Unicode-glyph icons rather than getting a custom vector icon this pass — restructuring each nav `ToggleButton`'s content model (single `TextBlock` → icon+label `Grid`) for all of them, plus authoring that many more original icons, was judged disproportionate to the rest of this milestone; the 8 shipped icons cover the highest-visibility surfaces (Dashboard, Server Setup, Players, Fleet, Security, Bases, Backup Center, the "+" button).
- Raster assets (the taskbar `.ico`, wordmark PNG, dashboard background image) are untouched — these need real image-generation/artist access, not hand-authored vector paths.
- The legacy `App.axaml` duplicate style definitions/`MystTiq*` resources (noted in earlier investigation as overlapping with `DesignSystem.axaml`) are untouched — separate tech debt, out of scope here.
- No server-side change — 100% `MystTiq.Desktop`.

## Verification

`dotnet build` (Release) across all three projects — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.6.19.1 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, larger here than any prior milestone**: no GUI click-through capability in this environment, and this is an inherently visual feature. Verification here is compile-clean plus static contract checks (every theme/variant/gradient-stop key present, the preference store round-trips correctly, the icon resources are defined and referenced) — not a full visual/behavioral confirmation of the finished app. The one partial mitigation used: proposed colors and icon shapes were rendered as actual SVG in the Browser pane and inspected via screenshot before being committed to the real files, rather than chosen blind. Actual on-screen contrast, readability, and icon appearance inside the real running app are the user's to confirm once built.
