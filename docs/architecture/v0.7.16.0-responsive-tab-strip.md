# v0.7.16.0 — Responsive Tab Strip

## Background

Raised directly, the third of a 3-item follow-up list delivered alongside other work this session: "the extra server tabs will need to be able to expand when full screen to utilize more room. If they run out of room then there should have a double arrow or icon pointing to the right that when clicked shows the hidden servers and the option to create new."

The tab strip's `ListBox` had a hardcoded `MaxWidth="720"`, set once and never revisited as the app's window-resize/maximize handling matured. On a maximized or ultra-wide window this left real, available space unused; more importantly, once more tabs were open than fit within that fixed cap, the extras were simply clipped off the edge of the `ListBox` — no horizontal scroll (the `ItemsPanelTemplate` override to a plain horizontal `StackPanel` has none), no visual indicator that anything was hidden, and no way to reach a clipped tab at all short of closing others first.

## What shipped

### Real measured width instead of a hardcoded cap

The tab strip's containing `StackPanel` (`x:Name="TabStripHost"`, in the title bar's `Grid.Column="1"` — the `*`-sized column between the fixed 430px brand column and the `Auto`-sized window-chrome column) now reports its own size changes via a new `TabStripHost_OnSizeChanged` handler in `MainWindow.axaml.cs`, which calls `MainWindowViewModel.UpdateTabStripWidth(double)`. This targets the strip's own panel specifically rather than `Window_OnSizeChanged` (already used for the maximize-button glyph) because the strip's actual available width also shifts independently of the window's total width — the brand column is fixed, but the window-chrome column's own width can vary slightly.

### `VisibleTabs` / `OverflowTabs`

`MainWindowViewModel` gained two new `ObservableCollection<TabSession>` properties alongside the existing `Tabs`, plus a `bool HasOverflowTabs`. `RecomputeTabLayout()` — called from `UpdateTabStripWidth`, from a `Tabs.CollectionChanged` subscription wired in the constructor (covers opening/closing tabs), and from `ActiveTab`'s setter — estimates how many tabs fit using fixed per-control width constants matching the actual XAML (`Border MinWidth="200"` + its own margin ≈ 204px per tab; the "+" button's own width+margin ≈ 52px; the new overflow chevron's ≈ 40px), then splits `Tabs` into the two collections accordingly. The tab `ListBox`'s `ItemsSource` now binds to `VisibleTabs` instead of `Tabs`.

This is a capacity estimate, not pixel-perfect layout measurement (Avalonia doesn't expose a clean "will these particular children actually fit" API without doing the arrange pass first) — but every tab has the same `MinWidth`, and long profile names are already `TextTrimming="CharacterEllipsis"`-clipped rather than growing the tab wider, so the estimate matches the real rendered width closely in practice.

### The active tab is never hidden

If `RecomputeTabLayout` would otherwise place `ActiveTab` in the overflow slice, it's swapped with the last "naturally visible" tab instead, so the visible count stays the same but the currently-focused tab is guaranteed to stay in `VisibleTabs`. Combined with `ActiveTab`'s setter itself triggering a recompute, switching to a tab from the new overflow flyout immediately pulls it back into the visible row rather than leaving it selected-but-still-hidden.

### The overflow flyout

A new chevron button (`»`, plain Unicode text rather than a Segoe Fluent Icons glyph — matching how several other ribbon/nav icons in this codebase are already done, e.g. `↻`/`▶`/`■`/`✚`) sits between the tab `ListBox` and the "+" button, `IsVisible="{Binding HasOverflowTabs}"`. Its `Click` handler (`TabOverflowButton_OnClick`, mirroring the existing `AddTabButton_OnClick`'s code-behind-builds-a-dynamic-`MenuFlyout` pattern exactly, since the same "this list changes as tabs open/close" reasoning applies) lists every tab in `OverflowTabs` by name — clicking one sets `ActiveTab` directly — followed by a separator and a "Set Up New Server" entry that invokes the existing `SetUpNewServerTabCommand`, so a new tab is reachable from here too without first needing to close something else to free up strip space.

## Explicit non-goals

- **Pixel-exact fit detection.** The per-tab/per-button width constants are estimates derived from the actual XAML `MinWidth`/`Width`/`Margin` values, not a live measure-and-arrange pass. Accepted as good enough given every tab shares the same `MinWidth` and trims its own text rather than growing.
- **Individually resizable tabs, or a second tab row.** Out of scope for what was asked — the request was specifically a chevron-and-flyout overflow pattern (the browser-tab-overflow model), not a wrapping or resizable-tab redesign.

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors, after fixing one instance of the recurring XML-comment-`--` AVLN1001 parse error in a new comment.
- No GUI click-through capability in this environment (unchanged, disclosed every version) — this is a pure layout/interaction feature with no server-side component and no new REST surface, so verification here is limited to static inspection of the resulting bindings/handlers and the arithmetic in `RecomputeTabLayout`. Confirming the chevron actually appears at the right tab count, the flyout's contents, and the active-tab-swap behavior on a real screen is left to the user, the same disclosed gap as every visual-only feature shipped this session.
