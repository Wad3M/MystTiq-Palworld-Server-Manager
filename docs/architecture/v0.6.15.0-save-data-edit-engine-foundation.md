# v0.6.15.0 — Save-Data Edit Engine Foundation (Pal Editor)

## Goal

The top finding from a user-requested, 21-repo competitive survey (`docs/architecture/v0.6.15-plus-competitive-survey.md`): three independent, actively-maintained tools with hundreds of stars each (PalworldSaveTools, Palworld Save Pal, Palworld Pal Editor) do real item/Pal-stat/inventory editing MystTiq couldn't do at all — a gap explicitly deferred since the v0.6.7.0 checkpoint for lack of a "Pal/inventory struct decoder" anywhere in the codebase. This milestone builds that foundation, scoped to real, individual **Pal** editing. Player inventory editing is a larger, separate follow-up (needs cross-file container resolution across `Level.sav` and each `Players/<uid>.sav`), explicitly not attempted here.

## Grounding

Before writing any code, the actual save JSON structure was confirmed two ways: external research into `palworld-save-tools`/`deafdudecomputers/PalworldSaveTools`'s real field-access source code, then cross-checked directly against a real, already-decoded production `Level.sav.json` on this machine (read-only inspection, no server action). Both players and Pals live in the same flat array, `worldSaveData.CharacterSaveParameterMap`, as `PalIndividualCharacterSaveParameter` structs distinguished by an `IsPlayer` bool. A Pal is addressed by a stable per-map-entry `InstanceId` GUID. Confirmed real field shapes: `Level`/`Rank`/`Talent_HP`/`Talent_Shot`/`Talent_Defense` are double-wrapped ByteProperty (`{"value":{"type":"None","value":N}}`); `NickName` is single-wrapped StrProperty; `IsRarePal` is single-wrapped BoolProperty; `Gender` is EnumProperty with a nested `{"type":"EPalGenderType","value":"EPalGenderType::Male"}` shape.

## What shipped

New `HeadlessPalEditService` (`MystTiq.HeadlessHost`), modeled directly on the already-proven `HeadlessGuildOwnershipService`: `ListPalsAsync` (decode + enumerate every non-player `CharacterSaveParameterMap` entry, optionally filtered by owner), `PreviewAsync` (locate by `InstanceId`, validate bounds, return a single-use hash-checked preview token + human-readable diff), `ApplyAsync` (decode → mutate only the supplied fields → encode → independently re-decode and verify → atomic commit → refresh the v0.6.12.0 explorer sidecar). Same safety guarantees as Guild Ownership throughout: refuses unless PalServer is stopped, rejects a stale preview if `Level.sav` changed since preview, stages through a fresh safety backup, and journals every stage.

Scoped to `NickName`, `Level`, `Rank`, the three `Talent_*` IVs, `Gender`, and `IsRarePal` (the "lucky" flag) — safe, high-value, low-risk fields. Active/passive skill lists and species (`CharacterID`) are explicitly not mutated this pass (see Explicit non-goals). New routes `GET /pals`, `POST /pals/edit/preview`, `POST /pals/edit/apply` (Admin role on apply, matching Guild Ownership's tier), and a new "Pal Editor" card on the Desktop's Guilds page — a Pal list (filterable by owner), an edit form pre-populated from the selected Pal's current values, and the same Preview → confirm → Apply flow already proven for guild/base ownership.

## A real bug found and fixed during this pass's own live verification

The first live test against real production-derived save data returned **zero** owned Pals — every one of 85 real Pals showed `ownerPlayerId: null`, even ones independently confirmed (via direct grep of the source save) to be owned. Root cause: the code read ownership from the map entry's `key.PlayerUId`, which is zero for every genuine Pal entry — that field only carries meaning for a *player's own character-body* entry (which uses the identical struct and is filtered out by `IsPlayer`). The actual ownership field is `OwnerPlayerUId`, inside `SaveParameter` itself. Fixed by reading from the correct field; re-verified live that all genuinely-owned Pals (76 of 85 in the test save) then resolved to their correct real owner name.

## Explicit non-goals (this pass)

- Active/passive skill-list editing (`EquipWaza`/`MasteredWaza`/`PassiveSkillList`) — needs a validated skill-ID catalog MystTiq doesn't have yet.
- Species swap (`CharacterID`) — read-only this pass; a materially different risk profile than adjusting an existing Pal's own stats.
- Player inventory / base-storage editing — the second half of the competitive survey's top finding, deferred to its own future milestone (needs cross-file container-GUID resolution).
- Anti-cheat scanning (v0.6.18.0 in the roadmap) — depends on this foundation but is a separate detection/response feature.

## Verification

**Live, end-to-end, against a real isolated copy of production-derived save data** (never the production directory or process): `GET /pals` returned 85 real Pal entries with field values matching direct inspection of the source save (species, level, IVs all confirmed byte-for-byte). Previewed and applied a real edit (Level 7→50, IsRarePal false→true, NickName → "TestEdit") against a real owned Pal; the apply committed successfully, and an independent fresh `GET /pals` call confirmed every changed field landed exactly as requested while every untouched field (Talents, owner) stayed byte-identical — genuinely surgical editing, not a wholesale rewrite. The explorer sidecar (`Level.sav.json`) was confirmed to contain the change immediately, with no extra regeneration step, reusing the v0.6.12.0 fix. Owner resolution was independently verified correct after the fix (76 of 85 Pals correctly attributed to their real owning player).

`dotnet build` (Release) across all three projects, and `scripts/Test-v0.6.15.0-Logic.ps1 -RunBuild` (15 static contract checks, the frozen v0.6.14.0 regression gate, and all 29 real v0.5.1.5 runtime-smoke checks) all pass.
