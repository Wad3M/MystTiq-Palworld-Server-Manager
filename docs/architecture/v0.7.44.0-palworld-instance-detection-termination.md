# v0.7.44.0 — Palworld Instance Detection & Termination Tool

## Goal

Detect any Palworld server process running on the machine — not just the one matching the
currently-configured install path — and provide a way to close it from the UI. A direct
mid-session request, not from the original 57-item findings log: *"i have also manually closed
the server. We need to add a tool to detect palworld instances and be able to close them."*

## Grounding: what already existed

- `IServerSessionInspector.FindProcessesByName(names)` — the raw, cross-platform, path-agnostic
  process enumeration primitive. Already existed; nothing new needed at this layer.
- `WindowsServerLifecycleService.FindManagedServerProcesses()` — filters the above down to
  processes whose `ExecutablePath` starts with this profile's own `NormalizedServerRoot()`.
  Drives `/status` and the v0.7.28.0 MANAGED PROCESSES panel + "Kill Processes" ribbon button.
- `FindProcessesWithMismatchedPath()` (v0.7.29.0) — the inverse filter, used only to distinguish
  "genuinely stopped" from "running at an unexpected path" in `GetStatusAsync`'s status text.
- `POST /server/force-stop` — already a safe, crash-recovery-aware stop (`StopAsync(TimeSpan.Zero)`),
  already reachable from the UI (v0.7.28.0). No change needed for this profile's own process.

None of the above lists *every* Palworld process on the machine, unfiltered by install path — the
missing piece this version adds.

## Why this matters: two real collisions this session

This exact gap was hit twice during this session's own `-RunBuild` verification gates:

1. **v0.7.42.0**: an unrelated, real PalServer process was running (the user's own live server),
   collided with an isolated runtime-smoke test's precondition check. No in-app way existed to see
   it or stop it — had to be identified and killed manually via `tasklist`/`Stop-Process`, outside
   MystTiq entirely, after explicit user authorization.
2. **v0.7.43.0**: the same collision recurred. This time, `ParentProcessId` traced back to the
   user's own real `mysttiq-server.exe` management service — meaning the raw `Stop-Process` kill
   from the first collision looked like an unexpected crash to that service's own crash-recovery
   (`HeadlessSupervisor.RunCrashRecoveryLoopAsync`, gated on `PersistedServerLifecycleState.
  StopRequested`), which auto-restarted it. The user had to stop it properly through their own
   MystTiq session's Force Stop button — this tool has no bearer token to do that itself.

This is the exact failure mode the new tool has to disclose, not hide: **a raw kill of a PID this
profile doesn't recognize as its own may belong to a different local MystTiq session's own
crash-recovery tracking, and killing it directly can trigger an auto-restart there instead of a
clean stop.** There is no way for this profile to know that in advance — state store and crash
detection are scoped per-profile/per-`ServerRoot`, not shared across sessions.

## What shipped

**Core (`MystTiq.Core`)**:
- `ServerInstanceInfo` (new model, `ServerLifecycleModels.cs`): `ProcessId`, `ParentProcessId`,
  `ProcessName`, `ExecutablePath`, `Responding`, `ManagedByThisProfile`. The last flag is
  deliberately more conservative than `FindManagedServerProcesses`'s own permissive rule (which
  treats an unreadable `ExecutablePath` as *managed*, for status-display purposes) — here, an
  unknown path means NOT managed, because this flag decides which stop path the UI offers, and a
  false "managed" claim would wrongly suggest the safe path applies.
- `InstanceTerminationResult` (new model): `Success`, `ProcessId`, `Message` — the result of a raw
  kill, distinct from `ServerLifecycleOperationResult` since it carries no lifecycle snapshot and
  doesn't touch this profile's own state store.
- `IServerLifecycleService.FindAllInstancesAsync()` — every process matching
  `platform.ProcessNames`, tagged via the same `NormalizedServerRoot()` check
  `FindManagedServerProcesses` already uses, just applied to the *unfiltered* result instead of
  filtering it out.
- `IServerLifecycleService.TerminateUnmanagedInstanceAsync(processId)` — raw termination by PID
  (`Process.Kill(entireProcessTree: true)` on Windows, `signals.TryKill` on Linux). Deliberately
  bypasses `stateStore` entirely: writing `StopRequested=true` here would be false bookkeeping for
  a process this instance never started, and the process's actual owning session (if any) needs to
  see an honest unrequested stop so its own crash-recovery still applies its own real policy.
- Implemented in both `WindowsServerLifecycleService` and `LinuxServerLifecycleService`, matching
  the existing per-platform split for every other lifecycle operation.

**Headless host (`MystTiq.HeadlessHost`)**:
- `GET /server/instances`, `POST /server/instances/{processId}/terminate` — both
  `RequireRole(MystTiqRole.Operator, p.Id)`, matching every other mutating lifecycle route.
  Deliberately **not** run through `RunLifecycleActionAsync`'s `IOperationCoordinator` lock: these
  don't mutate this profile's own lifecycle/world state, and a raw kill of an unrelated instance
  must not be serialized behind this profile's own in-progress lifecycle operations (which would
  be actively harmful if this profile's own server were mid-restart while an admin needed to kill
  an unrelated stuck process).

**Desktop (`MystTiq.Desktop`)**:
- `ServerInstanceDto` / `InstanceTerminationResultDto` (new, `Models/ServerInstanceDto.cs`) mirror
  the Core records; `DisplayText`/`ManagedText`/`PathText` are client-side display helpers, same
  convention as `ServerProcessDto.DisplayText` from v0.7.28.0.
  `IMystTiqApiClient.GetAllInstancesAsync` / `TerminateInstanceAsync` + `MystTiqApiClient`
  implementation, following the existing GET/POST client patterns exactly.
- New Server Doctor panel, "ALL PALWORLD INSTANCES ON THIS MACHINE": reuses the list-plus-
  details-panel pattern MOD Dashboard/MOD Library already established (v0.7.40.0/v0.7.43.0) — an
  `AllInstances` list bound to `SelectedInstance`, with a details panel that branches on
  `IsSelectedInstanceManaged`:
  - **Managed**: reuses `ForceStopServerCommand` unchanged (the existing safe stop).
  - **Not managed**: a new `TerminateSelectedInstanceCommand`, gated behind explicit on-screen risk
    text (the crash-recovery-collision risk described above) before the button is reachable at all
    — there is no confirmation-dialog infrastructure anywhere in this app (checked: none exists),
    so this mirrors the app's own established precedent of requiring an explicit row *selection*
    first (same friction level as every other selection-gated mutating action in this codebase,
    e.g. Delete/Rollback MOD) rather than inventing new dialog plumbing for one feature.
- New ribbon button "Detect Instances" (Doctor page group) triggers `RefreshAllInstancesCommand`
  directly; `RunDoctorCommand` also refreshes the list as a side effect (best-effort, same page,
  same "what's actually running" concern).

## Explicit non-goals

- No change to `/status`, `/server/force-stop`, or the existing MANAGED PROCESSES panel — this is
  additive, not a replacement for this profile's own process tracking.
- No cross-session coordination or shared lock file between separate local MystTiq sessions — the
  disclosed risk (raw kill may trigger another session's crash-recovery) is stated to the user, not
  engineered away. Building real cross-session coordination would need a shared, machine-wide lock
  or IPC mechanism between independent MystTiq processes — out of scope for this version, and not
  something the original request asked for.
- No confirmation-dialog/modal infrastructure added — none exists anywhere in this app today
  (checked); the selection-then-details-panel pattern already used for other destructive actions
  (MOD delete/rollback, Force Stop itself) is reused instead of introducing new UI plumbing.
