# v1.0.7.0 — Errors Stay Visible, Nothing Is Lost (internal)

Roadmap items Q-1, Q-2, Q-3 and Q-5 from the outside review (`docs/roadmap/ANALYSIS_REVIEW_2026-10-07.md`), and the
owner's decision D-10 (2026-10-08).

## Q-1 — A saved list that cannot be read is never overwritten

**Reproduced first** (2026-10-08), with the real `HeadlessUserAccountService` in process and then on a real, isolated
v1.0.6.1 service (`artifacts\publish`, port 18671, its own fleet folder, sign-in on):
- alice, bob and carol created; `users.json` cut in half; the service restarted;
- 0 accounts listed; creating dave answered 200; `users.json` then held only dave.

The same script on the new build: 0 listed, dave refused (400, with the reason), `users.json` unchanged.

**`SavedFiles`** (HeadlessHost) is the one way MystTiq's lists are read and saved:
- `Save` writes `.partial`, then `File.Replace` keeps the file it replaces as `.last-good`. A file known to be bad is
  never made the good copy (it is moved over instead).
- `Load` on a file that cannot be read copies it to `.unreadable-{time}` (once per distinct content, so a list read on
  every call keeps one copy), then:
  - loads `.last-good` when it reads (`LoadedFromCopy`, a warning);
  - else, for a list the owner made (`ownerData: true`), returns it empty and refuses changes (`Unreadable`);
  - else (a log or cache) returns it empty (`StartedEmpty`).
- A missing file with a readable `.last-good` loads the copy. `useGoodCopy: false` skips copies for the delivery pause,
  where an older pause coming back would silently stop outside alerts.
- A refused list: `Save` throws `SavedFileRefusedException`, `EnsureWritable` / `Refusal` let services refuse before
  changing anything in memory. The API turns the exception into HTTP 409 `{ error: "saved-file-refused", message }`; the
  desktop's `SavedFileRefusalHandler` shows that message for any call.
- A successful read closes whatever was reported for that file. A list read once at start-up never reaches that until
  the next start, so its empty in-memory copy can never be saved over a file put back meanwhile.
- **Repair** (the Server Doctor fix `repair-saved-file`, Admin): if the file reads correctly now (a good copy was put
  back by hand), nothing changes and the owner is told to restart the service; otherwise the file is removed (its
  unreadable copy stays) and changes are allowed, starting empty.
- **Alert**: `LocalManagementApiHost.WatchSavedFiles` alerts each state once on the server whose folder holds the file
  (users and API tokens on the default server): Unreadable is a pinned Critical notification, LoadedFromCopy a Warning,
  Repaired an Information; each carries `Link = "diagnostics:<finding id>"`. The desktop's **Open Repair** opens Server
  Doctor with that finding first and tagged FROM ALERT.

Owner lists (refused when unreadable with no copy): user accounts, API tokens, automation rules, kits, kit claims, alert
rules, anti-cheat rules, notification channels and templates, Discord bot settings, identity guard settings, unique-name
claims, whitelist, temporary bans, teleport points, player notes and flags, player history, process priority and eco
mode. Logs (start empty): sign-in sessions, automation runs, recently given items, anti-cheat findings, identity guard
and unique-name events, presence events, the delivery pause.

While refused: kits are not given and auto-gift is off (a kit could be given twice); a temporary ban is not applied (its
end could not be saved); the unique-names guard stands down (whoever joined first would take every name); the player
history keeps what it learns in memory only.

Evidence: LogicHarness (the account wipe, the last good copy, the repair, the log case, the eco-mode policy, the delivery
pause); `scripts/Test-v1.0.7.0-RouteSmoke.ps1` on an isolated service (copy loaded and a named account signs in; the
next change saves; a refused change inside a service comes back as 409 and leaves the file; with no copy users.json is
left byte for byte, the owner token works, the alert and the repair; after the repair changes work); ArtworkHarness
(Open Repair, the tag, the fix text, the desktop shows the refusal's reason).

## Q-2 — No error ends the app unrecorded

There was no `Dispatcher.UIThread.UnhandledException`, `AppDomain.UnhandledException` or
`TaskScheduler.UnobservedTaskException` handler in the desktop or the service, so an error escaping a fire-and-forget
command (19 `Dispatcher.UIThread.Post(async …)` sites) or an `async void` handler ended the process with no record.

- Desktop: `CrashRecorder` writes `%LOCALAPPDATA%\MystTiq\crashes\crash-{time}.log` (the newest 50) and raises
  `Recorded`; `App` marks UI-thread errors handled and shows them (`UnexpectedErrorBanner`, every page, Dismiss); the 19
  posts run through `RunUi`, which catches and records.
- Service: process and unobserved-task handlers write to the service's output; an unobserved task error also goes to
  the activity log.

Evidence: ArtworkHarness throws from a command through `RunUi`: the app stays open, the record is written, the banner
shows it, the busy state clears.

## Q-3 — Background work is named, logged and finished on shutdown

`BackgroundWork.Shared.Run(name, work)` replaces every `_ = Task.Run(...)` in the service: public address refresh,
Steam public build and UE4SS checks, Discord connection, teardown and live status, MOD safe start, the world clock,
outside notification sends, backup world days and automation rules. A failure is logged once per distinct message
(again after a success); `StopAsync` (from `LocalManagementApiHost.DisposeAsync`) cancels and waits up to 10 s and names
what is still running. The empty catches in the world clock and backup world-day readers are gone. `SingleRunGate` makes
an automation rule that is still running record Skipped instead of starting a second run.

## Q-5 — One retry rule for replacing files

`FileRetry` retries only Windows error codes that clear once the other program lets go (32, 33, 1175, 1176, 1177).
`ServerLifecycleStateStore` keeps retrying access denied (Windows reports a held file that way), and a failure that
outlasts 20 tries throws an `IOException` saying what to check (read-only, another program, the folder's permissions).
LogicHarness: concurrent writers, a leftover `.tmp`, a held file and a read-only file.
