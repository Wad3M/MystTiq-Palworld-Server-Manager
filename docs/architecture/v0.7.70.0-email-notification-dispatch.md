# v0.7.70.0 — Real Email Notification Dispatch

## Goal

Continuing autonomously through the roadmap audit's remaining concrete items: `NotificationChannel.
Email` had been a typed stub since v0.6.1.0's routing matrix shipped — enabling it just logged
`"{channel} channel not implemented"` and dropped the notification, unlike `Webhook`/`Discord`
(both real, v0.6.1.0/v0.6.17.0). This version implements it for real.

## The implementation

`NotificationChannelConfig` gained Email-specific optional fields (`SmtpHost`, `SmtpPort` — default
587, `SmtpUseSsl` — default true, `SmtpUsername`, `SmtpPassword`, `EmailFrom`, `EmailTo`), all
defaulted so every existing 3-arg construction of this record elsewhere in the codebase keeps
compiling unchanged. `HeadlessNotificationRoutingService.DispatchEmailAsync` sends via the BCL's own
`System.Net.Mail.SmtpClient` (`EnableSsl`, optional `NetworkCredential`, one retry on failure,
matching the existing Webhook/Discord retry shape) rather than hand-rolling the SMTP protocol —
unlike `PalworldRconService` (where no BCL client exists for Source RCON, forcing a from-scratch
implementation), `SmtpClient` already exists, is not obsolete, and correctly handles STARTTLS/auth
negotiation — safer to reuse than to hand-roll TLS handling for a feature with no live mail server
available this session to validate a custom implementation against.

`SmtpPassword` is stored in `channels.json` in plaintext, consistent with this codebase's own
established local-secret convention (RCON's `AdminPassword` in `PalWorldSettings.ini`, bearer tokens
in plain files under the runtime root) — protected by OS file permissions on the server's own disk,
the same threat model already accepted everywhere else in this project, not a new or weaker practice
introduced here.

**Known limitation, disclosed**: `SmtpClient` only supports STARTTLS-style submission (the
`EnableSsl` flag negotiates TLS mid-connection after `EHLO`, typically port 587), not
implicit-TLS-from-connect (port 465). A mail provider that requires 465 won't work with this
implementation; documented in the field comment, not silently unsupported.

## Verification

- `dotnet build` on `MystTiq.HeadlessHost.csproj` and the full solution: clean, 0 warnings, 0
  errors — confirms `SmtpClient` is not marked obsolete in .NET 10 and introduces no build-breaking
  warnings.
- New `scripts\Testing\MystTiq.LogicHarness` scenario (21/21 total, passing after one real
  debugging round — see below): a minimal, real SMTP server stub (just enough of RFC 5321 —
  greeting, `EHLO` advertising `AUTH LOGIN`, the auth exchange, `MAIL FROM`/`RCPT TO`/`DATA`, `QUIT`)
  proves the real `HeadlessNotificationRoutingService.Dispatch(...)` call sends a correctly
  authenticated, correctly addressed, correctly worded email over the real wire protocol — not just
  that the code compiles.
- **The stub server test itself caught a real protocol-shape assumption error before this was ever
  shipped**: the stub's first draft implemented the textbook three-step `AUTH LOGIN` exchange
  (server prompts for username, client sends it; server prompts for password, client sends it) —
  `SmtpClient` actually sends the base64 username *inline* on the same line as `AUTH LOGIN` (a SASL
  "initial response"), only the password arrives as a separate line. The stub hung waiting for a
  username line that was never coming, `SmtpClient` timed out after 10 seconds, and the real
  `HeadlessNotificationRoutingService` code correctly caught and logged that timeout — proving the
  application's own error handling works, while also surfacing that the *test's* assumption about
  the wire protocol was wrong, not the fix. Fixed the stub to parse the inline case (falling back to
  the two-step form for robustness); re-ran clean.

## Known gaps (disclosed)

- Not verified against a real SMTP provider (Gmail, Outlook, a real mail server) — the wire protocol
  itself is proven correct against a real, if minimal, RFC 5321 server; provider-specific quirks
  (app passwords, rate limits, DKIM/SPF requirements on the sending domain) are unverified.
- No Desktop GUI exists yet for configuring the Email channel (same as Webhook/Discord before it) —
  this ships as an API-level capability, matching the existing pattern for the other two channels.
- Implicit-TLS (port 465) is not supported by `SmtpClient` — disclosed above, not attempted.
