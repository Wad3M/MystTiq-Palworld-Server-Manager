# v0.7.25.0 — Ribbon Adaptivity

## Goal

First release of a broader GUI/workflow/UX overhaul: the user walked through MystTiq's pages one by one across an extended session, flagging 57 concrete fixes — layout, workflow (especially new-server setup), and outright bugs, several with root causes pinned down during the walkthrough itself (see the full findings log in the session's plan file for grounding on each). These were sequenced into a 21-version roadmap, ordered to front-load shared infrastructure and low-risk fixes before larger feature work.

This release is item 5 from that roadmap: the ribbon needs to shrink/adapt when it has more items than fit the actual window width. It's sequenced first because nearly every subsequent version in the roadmap (items 17, 23, 29-31, 33, 39, 46, 55, plus new buttons in 7/21/57) adds more buttons to the ribbon — without this infrastructure, those additions would risk silently overflowing the row exactly the way the ribbon already could before this release (`ClipToBounds="True"` with zero adaptive logic).

## What shipped

### Data-bound ribbon groups

`MainWindow.axaml`'s ribbon used to be two hand-authored `Border Classes="ribbonGroup"` blocks (Server Control: Refresh/Start/Restart/Stop; Quick Actions: Backup/Console/Doctor), each button individually wired to its command with inline icon glyph/color. New `Models/RibbonActionViewModel.cs` introduces `RibbonActionViewModel` (glyph, label, automation name, command, command parameter, icon color enum, success/danger flags) and `RibbonGroupViewModel` (title + list of actions) — both plain records, rebuilt fresh rather than mutated in place.

`MainWindowViewModel.BuildRibbonGroupsForActivePage()` constructs the current page's ribbon content (today: always the same two page-agnostic groups, byte-identical to what existed before — no new buttons in this release). Later roadmap versions extend this method to append page-specific groups based on `SelectedPage`, rather than hardcoding more per-page XAML the way the rest of the app does elsewhere — a deliberate architectural choice specific to the ribbon, since its content will keep growing across many future versions.

### Shrink-to-fit, mirroring the tab strip exactly

`RibbonHost_OnSizeChanged` (`MainWindow.axaml.cs`) feeds the ribbon's measured width to `MainWindowViewModel.UpdateRibbonWidth`, which calls `RecomputeRibbonLayout()` — this is the same measurement technique the tab strip already established in v0.7.16.0 (`TabStripHost_OnSizeChanged` → `UpdateTabStripWidth` → `RecomputeTabLayout`), reused rather than reinvented.

One real difference from the tab strip: tabs are uniform width (a single `perTabWidth` constant suffices), but ribbon groups vary — a group's width depends on how many buttons it holds. `RecomputeRibbonLayout` walks groups in declared order, accumulating an estimated width (`EstimateRibbonGroupWidth`: `Border.ribbonGroup`'s own `Padding="6"` + `Margin="0,0,5,0"` = 17px of chrome, plus `Button.ribbon`'s `MinWidth="68"` per button plus 5px inter-button spacing) until the next group wouldn't fit, then puts everything from there onward into `OverflowRibbonGroups`. Overflow happens at **whole-group** granularity, not individual buttons — a group's buttons are a semantic unit (e.g. "Server Control" shouldn't have Stop hidden while Refresh/Start/Restart stay visible), and this also keeps the split logic much simpler than trying to also account for a group's title label rendering.

`VisibleRibbonGroups`/`OverflowRibbonGroups` (`ObservableCollection<RibbonGroupViewModel>`) mirror `VisibleTabs`/`OverflowTabs` exactly: `MainWindow.axaml`'s ribbon `ItemsControl` binds to `VisibleRibbonGroups`; a new "»" `RibbonOverflowButton` (`IsVisible="{Binding HasOverflowRibbonGroups}"`) opens a `MenuFlyout` built in `RibbonOverflowButton_OnClick`, listing each overflowed group's title as a disabled header followed by clickable `MenuItem`s per action — mirroring `TabOverflowButton_OnClick`'s exact pattern of building the flyout fresh from whatever the ViewModel most recently computed, rather than a static XAML flyout.

`RebuildRibbonGroups()` (which reconstructs `_allRibbonGroups` and re-runs the layout) is called once at the end of the constructor (after every command it references is already initialized) and again from `RaisePageVisibility()` — the same hook `SelectedPage`'s setter already calls for every other page-conditional property — so future page-specific ribbon content automatically gets rebuilt on navigation without needing a new hook.

### Theme-safe icon colors

Ribbon icon glyphs used to set `Foreground="{DynamicResource AmberBrush}"` (etc.) directly per button. Since the button markup is now one shared `DataTemplate`, the color has to be data-driven — but binding a `DynamicResource` key directly from a bound string isn't how Avalonia's `DynamicResource` markup extension works (it requires a static key), and resolving the brush once in the ViewModel would freeze it at construction time, breaking live theme switching. Solved the same way several other conditional visual states already work in this codebase (e.g. `Classes.glowGreen="{Binding IsHealthGlowGreen}"` on Dashboard cards): `RibbonActionViewModel` exposes `IsAmberIcon`/`IsGreenIcon`/`IsBlueIcon`/`IsRedIcon`/`IsCyanIcon` bools from its `IconColor` enum, bound as `Classes.amber="{Binding IsAmberIcon}"` (etc.) on the icon `TextBlock`, with five new style rules in `Styles/DesignSystem.axaml` (`TextBlock.flatIcon.amber` through `.cyan`) each still setting `Foreground="{DynamicResource ...Brush}"` — so the actual `DynamicResource` binding lives in the stylesheet, unaffected by which button uses it, and keeps following live theme changes exactly as before.

## Explicit non-goals

- No new ribbon buttons this release — content is byte-identical to before. New buttons/groups are later roadmap items (v0.7.26.0 onward).
- No change to the tab strip itself, which already had this capability.
- No attempt at per-button (rather than per-group) overflow — see rationale above.
