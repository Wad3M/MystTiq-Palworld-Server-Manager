# v0.7.102.0 — Deficiency Fixes From Walking the Running App

## Context

After the "enhancements to existing features" list was finished (v0.7.101.0), the running app was walked page
by page and seven defects were recorded in the roadmap. This version fixes all seven. None of them was visible
to the static gates; each was found by looking at the real app.

## What changed

1. **Configuration phantom "unsaved change" (data risk).** Opening Configuration on a server whose
   `ItemCorruptionMultiplier` was 0.05 showed "1 unsaved setting change", prompted to save on leaving, and
   Save Changes would have overwritten 0.05 with 0.1. Cause: an Avalonia `Slider` clamps its Value into
   [Minimum, Maximum] and snaps it to the tick when bound, then writes the result back through the two-way
   binding. The slider minimum was 0.1. Fix at the root: `PalworldSimpleSettingItem.SliderValue` ignores a
   write that is only the slider's clamped/snapped echo of the current value (`IsCoercionEcho`), so a value the
   file holds is never rewritten by loading a page, in range or not; a genuine drag always differs from the
   echo and is still recorded, snapped and clamped. The readout now shows the file's real value (0.05×, 5% of
   default) instead of the coerced one. Separately the Item Corruption Rate range is now 0 to 10 in steps of
   0.05, since real servers run below 0.1 (the Relaxed preset uses 0.25).
2. **Alert Center repeated a persistent condition forever.** `Fire` only enforced a cooldown held in memory,
   so a condition that stayed true re-alerted every cooldown, each a pinned Critical, and forgot everything on
   restart: the test server had five identical "Low disk space" alerts among 83 unread. Alerts are now
   **episodes** (`AlertEpisodeTracker`): one alert when a condition starts, silence while it stays true, one
   "Resolved: ..." Success notice when it clears, state persisted in `alerts/episodes.json` so a restart does not
   repeat. The configured cooldown is kept as a flapping guard (a condition that clears and returns inside it
   does not alert again, and its clearing is not announced). A rule that is switched off closes its episode.
3. **Doctor and Alert Center disagreed about disk space.** The Alert Center raised a Critical below a percentage
   of the backup volume (5.4%, 51.9 GB free) while the Doctor, which only looked at absolute figures, said Pass.
   One shared rule (`DiskSpaceRules`): Critical under 2 GiB free or at or under the Alert Center's configured
   percentage; Warning under 5 GiB. The Doctor now fails what the Alert Center calls Critical, uses the same
   configured percentage, and states the percentage in its evidence.
4. **Diagnostics Center showed a stopped server as "Network: ERROR".** A server stopped on purpose is now
   `NotRunning` ("NOT RUNNING"), its process row is informational (Skipped, "there is nothing to check on the
   network yet"), and only a real crash stays an Error. The new enum member is appended so existing numbers keep
   their meaning. Restart Server on the Diagnostics ribbon now needs a running server, like the main Restart.
5. **Backups retention boxes clipped a two-digit value** ("10" read "1"). Both boxes are wider with a
   whole-number format.
6. **Update Center said "Up to date" when this install was newer than the latest published release**
   (0.7.x running, newest public release 0.2.16.4). The status stays UpToDate but the detail now says the
   install is newer than the latest published release, so it is a local or unreleased build.
7. **Automation had no rules and said nothing.** With no rules nothing is scheduled, backups included. The page
   now says so and points at the New Rule form, whose defaults are already a nightly 03:00 UTC backup. No rule is
   created for the user. The hint disappears the moment a rule exists.

## Deliberately not done

- Existing stale notifications are not deleted (83 on the test server); use Mark All Read or Dismiss.
- No default backup rule is created without being asked.
- No reminder re-alerts for a long-running Critical (the recovery notice is the only follow-up).
- The pinned original alert is not unpinned on recovery (the alert is not tracked by id).

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 8 new scenarios: sliders never rewrite a value the file holds (below the minimum, above the
  maximum, off the tick, trailing zeros, zero, repeated binding) and still record a genuine drag (snapped,
  clamped, back to original is clean); alert episodes (once, silent for hours of ticks, one recovery, flapping,
  new episode, switched off, persisted across a restart, damaged state file); the shared disk rule including the
  real 51.9 GB / 953 GB case and the Default Server's real 33.6%; a stopped server versus a crashed one; the
  version wording.
- New live route smoke `Test-v0.7.102.0-RouteSmoke.ps1`, on a real sidecar with the low-disk percentage set to
  99 and the evaluation interval shortened to 2 s (`MYSTTIQ_ALERT_EVAL_SECONDS`, 1 to 600, default 60): exactly
  one pinned Critical alert across about ten evaluations; the Doctor reports Fail with a percentage for the same
  disk; still exactly one alert after a sidecar restart with the state file persisted; then exactly one
  "Resolved: Low disk space" Success notice after the threshold is lowered, and nothing repeats.
- **Seen on the running app** (the clone tab of the real world): Configuration shows "No unsaved changes" with
  Save and Reset disabled and Item Corruption Rate reading 0.05× (5% of default); leaving Configuration opens
  the next page with no prompt; Diagnostics shows "NOT RUNNING", the process row "SKIPPED" and Restart Server
  disabled; Backups shows "10" and "30"; Automation shows the hint above the form; Update Center shows the
  newer-than-published wording.
- **NOT verified:** the Alert Center recovery and episode messages in the Notifications page (checked through
  the notifications route, not on screen); the Linux paths; the Discord/email delivery of the new "Resolved"
  notices.
