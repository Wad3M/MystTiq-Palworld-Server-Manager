# v1.0.6.1 — The Wrong Character Again (internal)

## The report (2026-10-06)

The owner joined from another computer with his own Steam account (`steam_76561197962020201`).

- The server logged `'WadeeRROR' (UserId=steam_76561197962020201) has logged in`, and AdminCommands logged it as
  `FFFFFFFFE290DA9A`. The `FFFFFFFF` is only the sign of an ID whose top bit is set; Melly's A3835C7B prints the same
  way.
- `SteamPlayerUid.FromSteamId(76561197962020201)` is `67D8D355`, Wade's character. `E290DA9A` is the same wrong ID he got
  in the v1.0.0.1 incident. The server gave the account a fixed second ID, not its Steam one.
- A hand start ("double-click or a PowerShell script") gave him Wade.

## What ran the server

The process list showed:
- `MystTiq.Desktop.exe` v1.0.6.0 (from the v1.0.6.0 checkpoint);
- `mysttiq-server.exe` **v1.0.0.0** (`MystTiqPalworldServer_v1.0.0.0_Windows-x64`, started 2026-10-05 18:36).

The desktop connects straight to its profile's address (`127.0.0.1:8213`). The bootstrapper's version check (v0.9.9.0)
runs only when it has to start a helper, so a reachable older service was used as it was. Nothing since v1.0.0.0
applied to the server, including the v1.0.0.1 identity guard (no `identity-guard-events.json` was ever written).

## What it started PalServer with

The main profile's saved arguments, from a Launcher preset saved earlier:
`-port=8211 -log -stdout -FullStdOutLogOutput -abslog=…\Identity-Diagnostic.log`.

- Every Launcher preset but Like double-click set those four options. The editor also defaulted them on, and showed
  them on for a profile with no saved launcher settings ("to match the previous manual-parity hotfix"), even though the
  service has started such a profile with no arguments since v1.0.0.1. Saving the page wrote them in, which is the
  likely way they reached the owner's main profile.
- v1.0.0.1 found that every wrong-character start had `-port=8211 -stdout -FullStdOutLogOutput` in common, while
  double-click starts with no arguments kept the characters.
- The AdminCommands history also shows a per-connection case before MystTiq's Launcher existed: on 2026-08-11, Wade got
  `67D8D355` and Melly `84544311` in the same session. The arguments are therefore the strongest lead, not a proven sole
  cause, and the evidence is recorded rather than claimed.

## The fixes

1. **`CheckLocalServiceVersion` on every connect.** A loopback service older than the app is shown on the Dashboard
   (`OutdatedServiceBanner`, red).
   - **Update Service To This Version** (after a confirmation) calls
     `ILocalManagementBootstrapper.StopOutdatedLocalServicesAsync(AppVersion)`.
   - That stops `mysttiq-server` processes on this PC whose file version is older than the app, never the app's own
     packaged one, then starts the app's own through `EnsureManagementConnectionForLifecycleAsync`.
   - A process running as another account (the Windows service) is named, not stopped.
   - A PalServer the old service ran keeps running; the new service adopts it.
2. **Launcher presets and defaults** no longer switch on `-log`, `-stdout`, `-FullStdOutLogOutput` or `-abslog`. The old "no -abslog"
   hint is replaced by a warning when any of them is on.
3. **`IdentityGuard.LaunchAdvice`** puts the server's saved arguments (without MystTiq's `@mysttiq:` options) into the
   Critical alert. When they include the suspect options, it says to choose Like double-click, save and restart.
