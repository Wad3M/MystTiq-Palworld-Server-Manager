# v0.7.30.0 — Confirmed Bug Fixes: Status Text

## Goal

Sixth version in the GUI/workflow/UX overhaul roadmap. Items 35, 47, 48, and 56 from the roadmap's findings log — three confirmed bugs to fix, plus one that needed re-investigating before touching any code.

## What shipped

### Bug 1: Backups summary cards always reading 0 (item 35)

**Root cause**: `BackupItems` (the `ObservableCollection` both the backup table and the three summary-card computed properties read from) was populated at three separate call sites in `MainWindowViewModel.cs`, each with its own `Clear()` + `foreach(Add)`. Only one of the three (`RefreshBackupsCoreAsync`) also called `RaisePropertyChanged` for `BackupArchiveCountText`/`BackupVerifiedCountText`/`BackupPendingCountText`. The other two correctly repopulated `BackupItems` (which is why the table itself always rendered correctly — `ListBox` observes the `ObservableCollection`'s own `CollectionChanged` event directly) but never told Avalonia's binding system the three *computed* properties needed re-reading, so the cards stayed at whatever they last showed — their unread startup default, 0.

**Fix**: new `PopulateBackupItems(IEnumerable<BackupItemDto> items)` does the clear/repopulate and all three notifications in one place; all three original call sites now call it instead of duplicating the logic. This can't drift out of sync again the way it did before, since there's only one implementation to update.

### Bug 2: UE4SS reporting "0.0.0.0" as its installed version (item 47)

**Root cause**: `DetectUe4ssVersion()` (`HeadlessModManagementService.cs`) falls back to `FileVersionInfo.ProductVersion`/`.FileVersion` on `UE4SS.dll`/`dwmapi.dll` when no version-marker file exists. A DLL can have a version resource that technically exists in its PE header but was never actually stamped with real numbers — `ProductVersion` then legitimately returns the literal string `"0.0.0.0"`, which is non-null and non-empty, so it passed the method's existing `!string.IsNullOrWhiteSpace(...)` check and was returned as if meaningful.

**Fix**: new `IsMeaningfulVersion(string? value)` — trims leading/trailing spaces, dots, and zeros; if nothing is left, the value was purely zeros (e.g. `"0.0.0.0"`, `"0.0.0"`) and is treated the same as "no version found." A genuinely low-but-real version like `"0.1.0.0"` still passes (trimming only strips from the string's outer edges, so the `1` in the middle blocks it). Both the marker-file path and the DLL-fallback path now use this check instead of a bare null/whitespace test.

### Bug 3: Server Doctor's unexplained "UNKNOWN" label (item 56)

**Root cause**: this label is *correct*, not a bug in the underlying logic — `HeadlessDiagnosticsService.BuildReport` (documented and unchanged since the codebase's own comments explain it) returns `Unknown` specifically when every check passes but the server isn't currently running, since calling that state "Ready" would be dishonest. The actual bug was narrower: the backend already computes a genuinely useful explanation for this exact case (`OverallHealthDetail`, e.g. *"Server is not running; no health issues detected."*), but `MainWindowViewModel`'s `DoctorSummary` only ever built itself from the raw pass/warning/failure counts, discarding `OverallHealthDetail` entirely.

**Fix**: `DoctorSummary` now appends `LatestDiagnosticsReport.OverallHealthDetail` (when non-empty) after the counts, so the page reads e.g. *"17 passed · 0 warning(s) · 0 failure(s) — Server is not running; no health issues detected."* instead of leaving "UNKNOWN" to speak for itself.

### Correction: item 48 (UE4SS "Unverified" / "Not reported") does not describe a real bug

The original roadmap finding assumed the console lines showing `[UE4SS] Runtime Mods Root: ...` / `[UE4SS] Runtime Verified: ...` in Pal.log were independent, UE4SS-native evidence that `TryReadRuntimeModsRoot()` (the method actually responsible for `RuntimeVerified`) wasn't consulting. Re-reading `HeadlessModManagementService.cs` this release found that assumption wrong: those exact console lines are written by `HeadlessModManagementService`'s **own** startup narrative (`consoleLog.Info("UE4SS", "UE4SS", $"Runtime Mods Root: {ue4ss.RuntimeModsRoot ?? "Not reported"}")`, line ~155) — a direct restatement of the same `ResolveUe4ss()` result the UE4SS page already displays, not a separate signal. Parsing Pal.log for this data would have been circular: reading back MystTiq's own prior conclusion as if it were new evidence.

The actual detection (`TryReadRuntimeModsRoot`, which looks for a real `UE4SS.log` file matching a `"Loading mods from: <path>"` pattern UE4SS itself writes) appears to work as designed — a later timestamp in the same session's log excerpt that originally prompted this finding showed `Runtime Verified: True` with a real path once UE4SS had actually started and written its log, confirming the mechanism does succeed when genuine evidence exists. "Unverified"/"Not reported" is the honest result when that evidence genuinely isn't there yet (e.g. checked before UE4SS's first startup, or a UE4SS build/layout that doesn't produce a matching log line) — not a detection failure to fix.

**No code change was made for this item.** It's recorded here, not silently dropped, so the roadmap's own history stays accurate about what was investigated and why it didn't need a fix.
