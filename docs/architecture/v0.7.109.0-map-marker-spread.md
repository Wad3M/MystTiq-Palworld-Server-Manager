# v0.7.109.0 — Map: Spreading Out Exactly-Coincident Markers

## Context

The one residual gap v0.7.106.0's own architecture doc named explicitly: two markers at (or extremely near)
the exact same screen position still rendered as a single visible icon, because that version only ever
staggered *labels*, never the dots themselves ("label staggering fixes the text, not two icons occupying the
same pixels"). This version closes it.

## What changed

- `MapLabelLayout` gained a second pure pass, `ComputeMarkerOffsets`, alongside the existing
  `ComputeLabelOffsets`. Deliberately a much tighter radius than label collision: `CoincidentRadius` is 3
  screen pixels (two icons on the same pixel), vs. `CollisionRadius`'s 30 (label text width) — these are
  different problems and the constants reflect that. A marker with any real separation (more than 3px) is
  never touched.
- For a genuinely coincident cluster, the first marker (by insertion order — bases before players, matching
  draw order) stays exactly on the real point; every marker after it fans out `SpreadRadius` (6px) away at an
  angle (`rank * 60°`, so up to 6 positions before the ring repeats). Confirmed live this is enough: a real
  cluster of 4 exactly-coincident offline players, previously a single ring, now shows as 4 distinct rings.
- `PlayerMapPointDto`/`BaseMapPointDto` gained `MarkerOffsetX`/`MarkerOffsetY` (default 0, so every existing
  caller is unaffected), folded directly into the existing `MarkerMargin` computed property
  (`CanvasX + MarkerOffsetX - 5`, ...). No XAML changes were needed — the same binding that always positioned
  the dot now just receives a slightly different number for a coincident marker.
- `MainWindowViewModel.ApplyMapLabelDeoverlap` (renamed in spirit, not in name — still the one place both
  passes run) now runs `ComputeMarkerOffsets` **first**, then computes label offsets against the *resulting,
  fanned-out* positions rather than the raw ones — so a spread-apart marker's label reacts to where it now
  actually sits, not to its original coincident position. Runs after every rebuild (every zoom and pan), same
  as before.

## Deliberately not done

- No cap on how many markers a single tight coincident cluster can fan out before the ring repeats positions
  (`rank * 60°` wraps after 6). Not expected to matter in practice, and a repeated angle at `SpreadRadius` is
  still strictly better than every marker before this version stacking on the exact same pixel.
- The fan-out is not itself de-overlapped against label collisions from *other*, unrelated markers beyond the
  existing pass — it composes with the existing label-staggering logic (which now runs against the
  post-spread positions) rather than introducing a second, separate collision system.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 1 new scenario: markers with real separation are never touched; two exactly-coincident dots
  fan out with the first undisturbed and the second exactly `SpreadRadius` away; three exactly-coincident dots
  fan out to three *different* points on the ring, not on top of each other either; a collision exactly at
  `CoincidentRadius` still fans out, just past it does not; the coincident radius is confirmed much tighter
  than the label collision radius.
- Live UI check (window rendered with PrintWindow; helper `ui-capture-helper.ps1`), on the clone's real Map
  page: a real cluster of exactly-coincident offline players — a single hollow ring before this fix — now
  renders as 4 distinct rings fanned out around the shared point, while the nearby base marker (which has real,
  if small, separation from the cluster) stays exactly where it was with its own clean label.
