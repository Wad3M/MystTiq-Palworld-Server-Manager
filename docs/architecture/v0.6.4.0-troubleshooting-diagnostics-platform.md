# v0.6.4.0 — Troubleshooting & Diagnostics Platform

## Goal

Make Server Doctor the single authoritative explanation for Overall Health, and extend diagnostics to the administrator's own machine, not just the server.

## Consolidation: composition, not rewrite

`HeadlessDoctorService` (production health: config validation, server root, executables, systemd, lifecycle readiness, disk space, journal errors, API bind security) and `HeadlessEnvironmentChecklistService` (setup/tooling completeness: Steam/Python/UE4SS/save-tools/C++-toolchain presence, ini flags) are both already correct and already covered by the runtime smoke suite. Rather than merging their internals (high regression risk for marginal benefit), a new `HeadlessDiagnosticsService` calls both unchanged and maps their output into one `DiagnosticFinding` list (`MystTiq.Core.Models`), reusing the existing `DiagnosticState` enum (`Pass`/`Warning`/`Fail`/`Starting`/`Skipped`, extended with `Unknown` — appended at the end, not inserted first, since the enum serializes as a plain numeric value with no `JsonStringEnumConverter` and the Desktop's existing `NetworkDiagnosticCheckDto.StateText` switches on that raw int by hardcoded position; inserting `Unknown` first would have silently relabeled every already-shipped Network Diagnostics result).

Three facts are checked independently by both source services against the exact same `IServerPathProfile` property (`SteamCmdExecutable`, `ServerExecutable`, `BackupRoot`), with different component names and severity vocabularies. `HeadlessDiagnosticsService`'s `OverlapMap` merges each into a single finding (Health-category framing wins, with Environment's `Location`/`Action`/`ActionSupported` merged in) — verified live against a real test instance: each fact appears exactly once, with correct rollup math (8 passed, 6 warnings, 2 failures, hand-verified against the 6 Health-only checks + 10 non-merged Setup-only checks).

## `ServerHealthState` becomes real

`MystTiq.Core/Operations/ServerHealthState.cs` has existed since v0.6.0.0 with a code comment explicitly framing it as the formalization seam for exactly this — "the ad-hoc READY/ATTENTION strings the Dashboard already computes... into a real Core-level contract" — but nothing consumed it until now. `HeadlessDiagnosticsService.GetUnifiedReportAsync` computes it from the merged findings plus current lifecycle status: any Fail → `Attention`; any Warning while the server is running → `Degraded`; running with neither → `Ready`; not running with neither → `Unknown` (the Desktop keeps its own existing neutral "STOPPED" label for that specific case, rather than forcing it into an enum value that doesn't fit).

The Dashboard's Overall Health badge (`DashboardHealthText`/`DashboardHealthDetail`) previously computed independently from `status.Ready`/`status.CrashDetected` alone — reflecting neither Doctor nor Environment findings regardless of what they showed. It now fetches the unified report (on the existing `RefreshDashboardBackendAsync` full-refresh path, not the fast silent poll tick, since Doctor's own checks — journalctl, `DriveInfo` — are too heavy to run every poll interval) and overrides the lifecycle-only default whenever a real Fail or Warning finding exists. This is the specific, literal fix for the roadmap's "no health deduction should exist without a corresponding visible Doctor finding."

## Fix Automatically and Recheck

Scoped to what already has a safe mutation path: `create-backup-root` (`Directory.CreateDirectory`, genuinely new and tiny) and `install-distribution` (SteamCMD/PalServer-missing, reuses the already-existing `HeadlessServerDistributionService.UpdateAsync`). Both verified live: deleting the backup root flipped the merged finding to a fixable Warning with `actionKind: "create-backup-root"`; calling Fix actually recreated the directory; calling Fix on SteamCMD genuinely attempted a real install and reported a real, honest failure message when it couldn't complete (missing steamcmd path in the test config) rather than pretending success. Every other Environment check that's `UnavailableReason: "BACKEND REQUIRED: ..."` (Python/UE4SS/save-tools/C++ toolchain) stays exactly that — `FixAsync` returns the real reason, never a silent no-op, for anything without a recognized `ActionKind`.

`RecheckAsync(id)` re-runs the whole owning source (Doctor or Environment — both cheap filesystem/config scans) and returns just the one matching finding. This is pragmatically scoped, not literally isolated at the source-service level (would need decomposing ~25 checks into individually-callable methods), but is honest "recheck this one thing" from the user's perspective and was verified live to correctly reflect a fix that just landed.

## Local-PC diagnostics (new, entirely client-side)

Confirmed via direct research that `NetworkDiagnosticsService`/its platform implementations exclusively check the *server's own inbound* firewall/listener state — zero outbound/DNS/TLS/local-runtime checks exist anywhere in the codebase. `LocalManagementBootstrapper.ProbeAsync`, the closest existing analog, collapses every failure mode into one opaque `.NET` exception message, and that's exactly what `MainWindowViewModel.RefreshAsync`'s catch block shows the user today for any failed remote connection.

New `MystTiq.Desktop/Services/LocalDiagnosticsService.cs` runs a layered probe against the selected `ConnectionProfile`, entirely on the machine running Desktop (no server round-trip — the point is diagnosing why the server can't be reached): DNS resolution (`Dns.GetHostAddressesAsync`) → TCP connect (`TcpClient.ConnectAsync`, inspecting the real `SocketException.SocketErrorCode` to distinguish refused/timeout/unreachable) → TLS handshake for `https` profiles (`SslStream.AuthenticateAsClientAsync`, verifying the certificate against the configured pin using the exact same fixed-time comparison `MystTiqApiClient.BuildHandler` uses in real connections — extracted to a shared `MystTiqApiClient.VerifyCertificatePin` static method rather than duplicated) → HTTP `/healthz`. Each stage produces its own `DiagnosticFinding`-shaped result and short-circuits on failure, so the user sees exactly which layer failed and why, not one generic message. Two always-available local-machine checks (`.NET` runtime version/description, local disk space on the Desktop app's own local-app-data drive, using the same ≥5 GiB PASS / ≥2 GiB WARNING / else FAIL thresholds `HeadlessDoctorService`'s own disk check uses) round out the "Local Machine" category, all rendered through the same `DiagnosticFindingDto` shape as Doctor/Environment findings.

Surfaced as a new "Local Machine Diagnostics" card on the existing Diagnostics Center page, not a new nav destination.

## Deferred, not dropped

- Unifying `WorkspaceHealthText`/`EnvironmentHealthText`/`ModHealth` into the same model — three more independent page-local "health" computations were found during research; only the Dashboard's specifically-named Overall Health badge was in scope this pass.
- Safe headless install APIs for Python/UE4SS/save-tools/C++ toolchain.
- True per-check-isolated re-execution.
- Local outbound-firewall rule enumeration (`Get-NetFirewallRule` for outbound rules on the admin's own machine) — the TCP-connect stage's specific `SocketErrorCode` already gives a real, actionable signal without needing rule-level introspection.
- A JSON export format alongside the existing txt export.
