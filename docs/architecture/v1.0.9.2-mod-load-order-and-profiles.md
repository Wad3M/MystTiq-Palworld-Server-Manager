# v1.0.9.2 — MOD load order and profiles (internal)

Roadmap B-3 (scheduled by the owner 2026-10-12, D-11).

## Which order exists

- **UE4SS MODs:** UE4SS loads the MODs `mods.txt` lists, in that order; its documentation calls `mods.txt` the way
  that supports load ordering, and `enabled.txt` the one that does not (MystTiq already neutralises `enabled.txt`).
- **PAKs:** no order a file name sets. When two PAKs replace the same cooked asset, the result depends on the asset and
  the mount, and the PalMods 1.0 guide warns that renaming files is not a fix. MystTiq lists PAKs and says so instead of
  offering an order that would not hold.

## ModLoadOrder

`Parse(lines)` gives the entries in file order (comments `;`/`#`, blank and malformed lines skipped).
`Reorder(lines, first, strict)` puts `first` at the front and the other entries after in their current order, writing
each entry's own line into the entry slots, so comments and blank lines keep their places. `strict` refuses a name
`mods.txt` lacks (a stale list from the desktop); otherwise such names are skipped (a profile from another server).

## The service

- `GetLoadOrderAsync`: the UE4SS entries with on/off and whether the folder exists, and the PAK names.
- `SetUe4ssLoadOrderAsync(order)`: strict reorder; `mods.txt.previous` keeps the file before the change.
- `ExportProfileAsync`: `ModProfile` (format `mysttiq-mod-profile`, version 1): the UE4SS order and each MOD's type,
  package, on/off, UE4SS place, version, source (the description source) and SHA-256 over its files (names and
  content; `.disabled` and `enabled.txt` markers ignored).
- `ImportProfileAsync(profile, apply)`: the switches and the order a profile asks for on the MODs present; the missing
  MODs with their sources; a note for a MOD whose files differ. `apply: false` changes nothing. A newer format is
  refused.
- Every change goes through `RunWhileStoppedAsync` (the MOD gate, the coordinator's hold, the stopped-server check),
  as `SetEnabledAsync` does.

## Routes and roles

`GET /mods/load-order` and `GET /mods/profile` need Viewer; `POST /mods/load-order` and `POST /mods/profile/import` need
Admin (the default for a changing route, as every MOD route). The import route reads its own body, so a file that is not
a profile is answered "This file is not a MystTiq MOD profile." (409) rather than a bare 400.

## Desktop

The MOD Library's **Load Order and MOD Profiles** card. `ModsViewModel` keeps the list (`LoadOrderItem`), moves locally,
and saves on **Save Load Order**; it is refreshed with the MOD list on the MOD Library page. Export and import are
code-behind file dialogs (the file is the service's own JSON, at most 2,000,000 characters); the import shows a preview,
and **Apply Profile** sends exactly what was previewed. Saving the order and applying a profile are in the role table
(Admin); the Import button is enabled for Admin.

## Evidence

- LogicHarness: the reorder rules; saving on a temporary UE4SS tree (the new order on disk, `.previous`, a stale list
  and a running server refused); a profile exported, previewed, applied, missing MODs and changed files reported,
  non-profiles and newer formats refused.
- Route smoke on a real isolated service: the same through the API, plus a Viewer allowed to read and refused changes.
