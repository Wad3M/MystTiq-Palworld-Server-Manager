# v1.1.0.2 — The player ID check and move (internal)

Roadmap F-2. Owner, 2026-10-13: "write a test for the MystTiq to run when a user connects to ensure that the correct ID
is calculated", and when a player is not given their character "the system should automatically migrate to the new
user, backing up and cleaning up the list".

## What was found

The game itself gives Steam accounts new player IDs since its 1.0 update (between 2026-08-27 and 09-28). On the owner's
server: `steam_76561197962020201` was given E290DA9A (his character under 67D8D355) and `steam_76561198653223616` was
given 1467C601 (her older character under A3835C7B). The owner joined five test servers on 2026-10-13: started by
MystTiq, like a double-click, directly with Explorer's environment, with UE4SS off, and with UE4SS and PalDefender off
and MystTiq closed. Every one gave E290DA9A. No transformation of the Steam ID gives the new IDs, so they cannot be
calculated; they are learned from the game's own assignment. The launch arguments blamed in v1.0.0.1 and v1.0.6.1 were
not the cause.

## The join check and learned IDs

`HeadlessPlayerIdService.Observe` runs on the status poll before the identity guard. For each online Steam player with
a character (once per session) the expected ID is the learned one (`players/player-ids.json`), else the pre-1.0 formula
(`SteamPlayerUid`), each only when that character file exists. Same ID: correct; no known character: first seen (the ID
is learned); a different ID: new ID from the game, and a move is queued. The guard's `Judge` takes the learned ID; with
automatic moves on it lets the new-character screen through (the character made there is the move's target) and its
kick says the character is being moved.

## The move

`PlayerIdMove` (pure): the character under the new ID must be a throwaway (one body, at most a solo guild with no bases,
the new ID named nowhere else); it is removed and every value naming the old ID rewritten (the body, owned Pals, placed
buildings, previous-owner records, guild membership and markers); in the character file the two ID fields. The service:
server stopped (the lifecycle lock; a running server is stopped and started again around the move), the world-mutation
lock, a fresh safety backup, decode with the save's converter, rewrite, encode, decode again and `Verify`, replace
`Level.sav` atomically, write the moved character file, archive the old and the replaced character files under
`runtime\character-migration\archive`, learn the new ID, clear the queue entry, forget both IDs' level history
(the false "level 1 to 15 in 0 minutes" level-gap finding). A failure after replacing restores the originals.
Queued moves run when automatic moves are on and nobody is online (`RunPendingWhenIdle`), or from the card's button
(`POST /players/ids/move`, refused while players are online).

## Evidence

- LogicHarness: the move on a made-up world (8 references rewritten, the other player's 4 kept, the throwaway gone; a
  shared guild, a base, a stray reference and two old characters refuse; the character file; the verification); the
  join check with the guard (the owner's case queued and turned away with the move message, then first seen and
  correct after the move, a new player first seen, the new-character screen let through, the setting kept).
- LogicHarness on a copy of the owner's real world (`C:\GameServers\_Backups\world-before-uid-migration-20261013-114408`)
  with the real converter: the service moved Wade from 67D8D355 to E290DA9A, 216 references, Wade level 15 under the new
  ID, the same result as the move done by hand on 2026-10-13 (after which the owner joined as Wade).
- Live: the next player the game gives a new ID (carried).
