# v0.7.8.0 — RCON-Powered Admin Tools

## Background

Third release from the broader review requested this session: a codebase-wide bug scan (v0.7.6.0/v0.7.7.0) plus a competitive feature survey against other Palworld server-management tools (PalSupervisor, na-ji/palworld-admin, PalAdmin, AMP/Pterodactyl), cross-checked against the actual codebase rather than taken at face value.

The survey found several claimed competitor advantages were already built: scheduled restarts with in-game warning broadcasts (MystTiq's Automation `RestartServer` action already supports `WarningCountdownSecondsBeforeAction`), a raw RCON console (already in `MainWindow.axaml`'s Console/Monitoring area), RBAC with per-route role gating (`MystTiqRole`), and outbound Discord alert embeds (v0.6.17.0). Four gaps were confirmed genuine by direct code inspection — two of them (teleport, whitelist) already named in the codebase's own comments as an explicitly deferred roadmap item (`src/MystTiq.Core/Providers/ProviderModels.cs`'s comment listing "presence, world data, chat, whitelist, teleport, commands" as the full capability list MystTiq's Provider Framework was scoped down from). This release ships the three gaps buildable as thin wrappers around the existing `PalworldRconService.ExecuteAsync` primitive; whitelist (which needs new persisted state and an enforcement loop, not just a command wrapper) is deferred to v0.7.10.0.

## What shipped

### Unban + Ban List
Palworld RCON supports `UnBanPlayer <id>` and `BanList` (confirmed against current community documentation of the RCON command set before implementing). `RconPlayerModerationProvider.SupportsAction` gained `"unban"`; `ExecuteAsync`'s command-mapping switch gained the `UnBanPlayer` case. Palworld's REST API has no unban endpoint at all, so `HeadlessPalworldAdminService` (the REST provider) does not declare support for it — `PlayerModerationCoordinator`'s existing provider-filtering (`providers.Where(p => p.SupportsAction(action))`) means an unban request always resolves to the RCON provider without any new coordinator logic. `LocalManagementApiHost`'s `/players/{playerId}/action` route's `is "kick" or "ban"` branch gained `or "unban"` so it routes through the moderation coordinator instead of falling through to the REST-only `PlayerAdmin` provider (which doesn't support it and would reject it).

A new `GET /players/ban-list` route wraps `p.Rcon.ExecuteAsync("BanList", ...)` directly (not through the moderation-provider abstraction, since this isn't a per-player action) and returns the same `RconCommandResult` shape `/rcon/command` already returns. The Desktop side displays the raw response text in a read-only box rather than attempting to parse it into structured rows — the exact response format wasn't confirmed with enough certainty to risk a parser that silently drops or misreads entries if the server's actual output differs from assumption.

This un-stubs the "Unban" button that had sat `IsEnabled="False"` in `MainWindow.axaml`'s Players page since the surrounding buttons (Whitelist, Temporary Ban, Remove Admin) were first added as visible-but-disabled placeholders.

### Admin teleport
Palworld RCON supports `TeleportToPlayer <id>` (moves the RCON-issuing admin's own in-game character to that player) and `TeleportToMe <id>` (moves that player to the admin's location) — both operate relative to an admin character that must actually be present in the world, which a headless dedicated server has no way to guarantee. This is disclosed directly in both buttons' tooltips rather than papered over, since Palworld's RCON gives no distinct error for "no admin character in the world" versus "player not found" — the raw RCON response text is surfaced as-is so the operator can tell the two apart themselves from context.

New routes `POST /players/{playerId}/teleport-to-me` and `POST /players/{playerId}/teleport-to-player`, both thin `p.Rcon.ExecuteAsync(...)` wrappers, both requiring the target player currently online (checked client-side via the existing `SelectedPlayerRecord.Online` gate, same as Kick/Ban — teleporting an offline player has no meaning).

### Save World Now
New `POST /world/save-now` route wraps `p.Rcon.ExecuteAsync("Save", ...)`. Added to the Dashboard's existing SCAN/CLEANUP quick-action row. Previously the only way to force an immediate save was typing `Save` into the raw RCON console by hand.

### Desktop wiring
Four new `IMystTiqApiClient` methods (`GetBanListAsync`, `TeleportToMeAsync`, `TeleportToPlayerAsync`, `SaveWorldNowAsync`), all returning the existing `RconCommandResultDto` — no new DTO needed, since every new server route returns the identical shape `/rcon/command` already does. `RunSelectedPlayerAdminActionAsync` gained a `requireOnline` parameter (defaulting to `true`, preserving kick/ban's existing behavior) since gating unban behind "currently online" would make it permanently unusable — a banned player is by definition not online. A new collapsible "Ban List" card follows the `Button.sectionToggle` pattern introduced in v0.7.5.0 (collapsed by default, matching that release's no-scroll discipline rather than undoing it by adding more always-visible content to the Players page, which was that pass's single worst offender).

## Real bug found and fixed while wiring the above

Kick/Ban (and now Unban/Teleport) all read `SelectedPlayerRecord` — the Players page's "Directory" list selection, populated by `RefreshPlayersPageAsync` (a page-navigation trigger). v0.7.6.0's stale-tab-data fix cleared `SelectedOnlinePlayer` on every tab switch, based on the bug-scan finding that prompted it, which named `SelectedOnlinePlayer` as the property Kick/Ban read. Direct inspection while wiring Unban/Teleport onto the same buttons found that assumption was incorrect: `SelectedOnlinePlayer` is a *different* property (used elsewhere, for a whisper/online-players-focused panel), and `SelectedPlayerRecord` — the one Kick/Ban/Unban/Teleport actually use — was left completely unaddressed by that fix.

The staleness window here is worse than what v0.7.6.0 closed for `OnlinePlayers`: `RefreshPlayersPageAsync` only runs on Players-page navigation, not the 5-second background timer, so `SelectedPlayerRecord` stays showing the *previous* tab's player directory **indefinitely** if the user stays on the Players page across a tab switch — not just for up to 5 seconds. This is exactly the wrong-tab-action risk v0.7.6.0 set out to close, via a mechanism that release's own verification missed.

Fixed in this release:
- `ActiveTab`'s setter now also clears `SelectedPlayerRecord` (alongside the five selections v0.7.6.0 already cleared) on every tab switch.
- If the user is already on the Players page when switching tabs, `RefreshPlayersPageAsync()` is now triggered immediately for the newly active tab, closing the gap rather than leaving `SelectedPlayerRecord`/`PlayerRecords` empty until the next manual navigation.
- `RefreshPlayersPageAsync` itself gained the same stale-response-discard guard (`var requestTab = ActiveTab;` ... `if (!ReferenceEquals(requestTab, ActiveTab)) return;`) added to `RefreshAsync`/`RefreshStatusPollingAsync` in v0.7.6.0, so a slow directory fetch started for a tab the user has since left can no longer land its results on top of the newly active tab's data.

## Explicit non-goals

- **Ban list parsing into structured rows**: the exact RCON `BanList` response format wasn't confirmed with enough certainty before implementing to risk a parser that could silently misread it; the raw text is shown as-is instead.
- **Temporary ban with auto-expiry** and **investigating the disabled "Remove Admin" button**: remain backlog items, not part of this release.
- **Whitelist**: the other roadmap-named deferred item found by the survey — needs new persisted per-server state and an enforcement loop (auto-kick on join if not listed), not just a command wrapper, so it's sequenced to its own release (v0.7.10.0) rather than folded in here.
- **Give Items / Give Pals**: would need save-file writes (like the existing Pal Editor), not just RCON — bigger scope, remains backlog.

## Verification

`dotnet build` (full solution, Release) — 0 warnings/0 errors. The new HeadlessHost routes are exercised by the existing runtime smoke suite's RCON-adjacent coverage (`RCON status endpoint reports capability without exposing credentials`); a real Palworld dedicated server with RCON enabled is needed to verify the actual `UnBanPlayer`/`TeleportToMe`/`TeleportToPlayer`/`BanList`/`Save` command responses end-to-end, which is outside what this environment can run — the same disclosed limitation as every RCON-touching feature since the RCON provider was first added.

**Disclosed verification gap**: no GUI click-through capability in this environment, unchanged since v0.6.4.0. The tab-switch correction (`SelectedPlayerRecord` clearing + immediate `RefreshPlayersPageAsync`) was traced by hand against the same call graph verified for v0.7.6.0's original fix.
