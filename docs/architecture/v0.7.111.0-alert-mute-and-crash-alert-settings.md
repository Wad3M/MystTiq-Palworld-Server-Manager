# v0.7.111.0 — Alert Mute and Per-Profile Crash Alert Settings

## Why

Crash-recovery alerts (v0.7.101.0) had no settings at all: every crash, failed restart, give-up and recovery
sent a notification, with no way to switch them off or quiet them during planned maintenance. Whether this
was needed had been an open question since v0.7.101.0. On 2026-09-22 the user pulled it into 0.7.x.

## Design

Everything lives in the existing per-profile `AlertRuleSet` (`<RuntimeRoot>/alerts/rules.json`), which every
server profile already has on its own. No new file, no new store.

- `AlertRuleSet.CrashAlerts` — `CrashAlertRule(Enabled, RecoveryNotices)`, default `(true, true)`.
  `Enabled` switches crash-recovery alerts off entirely; `RecoveryNotices` controls only the two "server is
  back up" kinds (`RecoverySucceeded`, `ManualRecovery`).
- `AlertRuleSet.MutedUntilUtc` — an end time, not a flag, so a mute always ends by itself. While it is in
  the future, this profile sends no alerts at all: threshold rules and crash alerts.
- `AlertMutePolicy` (pure, harness-covered): `IsMuted`, `MuteUntil(minutes, now)` (0 or less unmutes,
  capped at 30 days), `ShouldSendCrashAlert(rules, kind, now)`. A client sending `"crashAlerts": null` gets
  the defaults rather than an exception in the recovery loop.
- `POST /api/v1/alerts/mute {minutes}` (Admin, same as `PUT /alerts/rules`). The end time is computed on the
  host's clock, so a remote Desktop with a skewed clock cannot mute for the wrong length.

### Threshold rules while muted

`EvaluateThrottledAsync` returns before evaluating anything. Episodes neither open nor close during a mute.
When the mute ends, a condition that is still true opens its episode then and alerts normally. One that
cleared during the mute is seen as recovered on the next evaluation, sends its "Resolved" notice and
unpins. The alternative, observing episodes but suppressing the notification, would have left a condition
that started during a mute silent until its 24-hour reminder.

### Crash alerts while muted or switched off

`CrashAlertObserver` now takes `Func<AlertRuleSet>` (this profile's `HeadlessAlertCenterService.GetRules`)
and reads it on every event, so a change applies to the very next crash. A suppressed alert is written to
the Activity log ("Crash alert not sent (muted or switched off)") so the history is not lost.
On `ManualRecovery`, the pinned DOWN notice from before the mute is **still unpinned** even when the "back
up" notice itself is not sent.

A give-up during a mute is not pinned (nothing is sent), so there is nothing to unpin later.

The crash recovery loop itself is unchanged: muting never stops MystTiq restarting the server.

### Host wiring

`HeadlessHistoricalMetricsService` and `HeadlessAlertCenterService` are now created before the crash
observer in `LocalManagementApiHost`, so the observer can be given that profile's rules.

## Desktop

Alert Center: a "Crash Alerts" block (two checkboxes, saved with Save Rules) and a "Mute Alerts" card (Mute
1 hour / 8 hours / 24 hours / 7 days, and Unmute while muted). Muting applies immediately, with no Save
needed. `AlertRuleSetDto` round-trips both new fields, because Save Rules sends the whole set back and a
missing field would reset it.

## Verification

- Logic harness: 3 new scenarios (policy, observer under mute including the unpin, per-profile persistence
  of `Mute`), 1 extended (an older rules.json loads with crash alerts on and nothing muted).
- `scripts/Test-v0.7.111.0-RouteSmoke.ps1`: a profile pre-muted through rules.json plus the real crash
  fixture. A real crash while muted sends nothing and writes the Activity line. A true low-disk rule does
  not alert, and Save Rules keeps the mute. Unmute through the new route, then both paths alert. Mute 60 is
  host-timed and a huge value is capped.
- Live Desktop: Mute 1 hour on the Clone profile showed the muted text and Unmute button. The Default
  profile was confirmed not muted, then Unmute returned it to "Alerts are on."

## Not done

- No mute for alert *delivery routes* only (Discord/email/webhooks) while keeping the Notifications page:
  a mute silences the notification itself.
- `service-run` (the OS-service supervisor) still sends no crash alerts at all, as before.
