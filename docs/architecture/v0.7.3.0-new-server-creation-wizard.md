# v0.7.3.0 — New-Server Creation Wizard

## Goal

Third slice of the broader v0.7.x UX plan: "when we create a new server, it should go through a wizard or a setting" — new-server creation should be a guided, stepped flow rather than one flat form.

## Grounding

Investigating the existing "Set Up New Server" flow found it already followed a natural 3-step sequence at the command level, just presented as one continuous flat form with no forced ordering:

1. Edit connection details (Name/URL/Bearer token/TLS pin) → click **Connect** → `ManagementApiConnected` becomes true.
2. *(Optional)* Fill in-game server defaults (name/description/passwords/players/ports) → click **+ Create Default Settings** → `CreateDefaultServerSettingsAsync()` writes a fresh `PalWorldSettings.ini` on the connected server.
3. Click **Save Profile** → `SaveProfile()` upserts the profile into `Profiles` and sets `SelectedProfile`, which is what flips `IsCreatingNewProfile` false and ends the "new server" state.

`OpenNewServerTab()` (bound to the tab bar's "+" → "Set Up New Server") already isolates this whole flow behind its own tab-open path, separate from `ConnectExistingProfileTab()` — confirmed this could be wizard-ized without touching the existing-profile-connection path at all.

## What shipped

- **`MainWindowViewModel`**: `NewServerWizardStep` (int, 1-3, private-set, reset to 1 by `BeginNewProfile()`), `IsWizardStep1`/`IsWizardStep2`/`IsWizardStep3` (each `IsCreatingNewProfile && NewServerWizardStep == N` — so none of this ever applies while editing an already-saved profile), `WizardAdvanceCommand`/`WizardBackCommand` (`AdvanceWizardStep()`/`GoBackWizardStep()`, simple clamped increment/decrement between 1 and 3).
- **Step 1 (`MainWindow.axaml`, the existing Connection Profiles card)**: unchanged fields. Header text swaps to "Step 1 of 3 — Connection Details" while creating a new profile. A new "Next: Server Defaults →" button appears (enabled once `ManagementApiConnected`) alongside the existing Connect button. **Save Profile**/**Delete Profile** — which only make sense for an already-selected profile — now show only `IsVisible="{Binding !IsCreatingNewProfile}"`; their role for a brand-new profile moves to Step 3's own Save Profile button (same `SaveProfileCommand`, not a new command).
- **Step 2 (the existing In-Game Server Defaults card)**: gating changed from `IsCreatingNewProfile` to `IsWizardStep2`. Header swaps to "Step 2 of 3." Gains a "← Back"/"Next: Confirm & Save →" row alongside the existing "+ Create Default Settings" button — Next is always enabled, since creating defaults here is explicitly optional (a target server might already have its own settings).
- **Step 3 (new)**: a short `Border.statuscard` summary (server name/address/connection state, all existing bound properties) plus "← Back" and "Save Profile" (`SaveProfileCommand` — the exact same command Step 1 always used, just also reachable from here).
- Since `SaveProfile()` already sets `SelectedProfile = profile` on success, which flips `IsCreatingNewProfile` false, all three wizard-step cards disappear automatically the moment the profile is saved — no extra "close the wizard" logic needed.

## Explicit non-goals

- No new save/connect/create logic — every wizard step reuses an existing command as-is.
- Existing-profile editing (the Connection Profiles card when `SelectedProfile is not null`) is completely unaffected; none of the new gating applies to it.
- Card flare and the no-scroll initiative (v0.7.4.x) remain queued as planned.
- No server-side change.

## Verification

`dotnet build` (Release) — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.7.2.0 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. Verified by direct code inspection that every new binding (`IsWizardStep1/2/3`, `WizardAdvanceCommand`/`WizardBackCommand`, the Step 3 summary bindings) resolves to a real, already-existing property/command with no typos, and that `IsCreatingNewProfile`'s existing behavior for editing a saved profile is untouched. Actually clicking through the three steps in the running app is the user's to confirm once built.
