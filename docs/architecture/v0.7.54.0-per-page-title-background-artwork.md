# v0.7.54.0 — Per-Page Title Background Artwork

## Goal

Item 8 from the original findings log: each category's page header could have its own background
image. Confirmed earlier in this session to mean literal illustrated/photo artwork, not a subtle
tint — this version's implementation is the direct result of that confirmation.

## The capability problem, and how it was resolved

This session has no built-in image-generation model and no API access to one — generating "real
illustrated artwork" purely from language, with no image-synthesis tool, is not possible. Rather
than substitute a code-generated gradient/tint (which the original finding explicitly said would
*not* satisfy the ask) or simply decline the item, the Browser pane tool was used to test whether a
free, publicly-accessible AI image generator could be driven directly — the same way a human would
use one. Bing Image Creator (Microsoft's DALL-E-backed tool) turned out to work fully anonymously,
with no sign-in, for a limited number of generations per day.

Two sample images (Home and World) were generated first and shown for sign-off on the style
direction, before committing to a larger run — following this session's own established pattern of
confirming direction before investing further effort.

## Style, grounded against the existing assets

Before writing any prompts, the existing `dashboard-atmosphere-v3.png` was read directly (this
session can view images even though it cannot generate them) to establish the visual language
already in use: dark navy gradient, silhouetted fantasy castle/tower spires, low-poly mountain
ridges, a subtle glowing tech circuit-line grid overlay. Every generated image matches this
language, with the accent color swapped to match the category's own hue from the v0.7.48.0 theme
system (Home = blue, World = violet). Each category also got a Light-mode variant — bright pastel
dawn sky, same motifs, softer glow — matching the app's existing Dark/Light theme system.

## What actually happened: a hard capacity limit, not a soft one

After 4 successful generations (Home Dark, Home Light, World Dark, World Light), every further
attempt returned Bing's own "You've reached today's guest creation limit" message. This is a real,
enforced daily cap on anonymous/guest sessions — not something retryable within the same day, and
not something to route around by signing into an account, which is categorically outside what this
session does regardless of permission (entering account credentials, for any purpose, is not
attempted).

## Scope decision

Ship the two categories that do have real, generated artwork; leave the other five (Server, Backups,
Mods, Tools, System) exactly as they are today, with no page-header art at all — rather than filling
the gap with a code-generated substitute that would contradict the original finding's own explicit
"not a tint" instruction. A real-but-incomplete set, disclosed as such, rather than a
complete-but-fake one.

## Implementation

- Four new computed properties on `MainWindowViewModel`: `IsHomePageArtDark`, `IsHomePageArtLight`,
  `IsWorldPageArtDark`, `IsWorldPageArtLight` — each combines an existing category check
  (`IsV5HomeCategory`/`IsV5WorldCategory`, already used by the category-tab `IsChecked` bindings)
  with `IsLightMode`. Re-raised both where every other `IsV5*Category` property already gets
  re-raised (the central page-navigation notification block) and in `IsLightMode`'s own setter,
  since neither location previously needed to know about page-header art.
- `MainWindow.axaml`: four new `Image` elements layered behind the existing page-header content
  (title/subtitle, connection badge, Auto Refresh checkbox), each gated by one of the four bools
  above, `Stretch="UniformToFill"`, `Opacity="0.3"` so the header's own text stays legible on top of
  the artwork rather than competing with it.
- Four new assets under `MystTiq.Desktop/Assets/`: `page-art-home-dark.jpg`,
  `page-art-home-light.jpg`, `page-art-world-dark.jpg`, `page-art-world-light.jpg`. Picked up
  automatically by the existing `AvaloniaResource Include="Assets/**"` glob in the `.csproj` — no
  build configuration change needed.
- No changes to `ConnectionProfile`, `ThemeCatalog`, or any other model — this version's state is
  entirely new, additive ViewModel properties plus static asset files.

## Verification

`dotnet build` on `MystTiq.Desktop` and the full solution — clean, confirming the four new JPEG
assets are correctly picked up by the Avalonia resource pipeline and the new bindings compile. One
AVLN1001 `--` XML-comment error hit and fixed in this version's own new comment (the same recurring
pattern this session has hit on nearly every version touching a XAML comment).

## Known gaps (disclosed)

- **No visual verification possible in this environment** — same limitation as every version
  touching the UI, compounded here since the whole point of this version is how real artwork looks
  composited behind live page-header text. The 0.3 opacity value is a reasonable estimate, not
  confirmed against a rendered window.
- **Five of seven categories have no artwork** — Server, Backups, Mods, Tools, System — blocked by
  Bing's daily anonymous-generation cap, not by any code limitation. The `IsXPageArtDark`/`Light`
  pattern established here is directly extensible to the remaining five once more images can be
  generated (a future day's anonymous session, a different free service, or user-supplied artwork).
- **Provenance and licensing**: the four shipped images were generated via an anonymous Bing Image
  Creator session, not a licensed/paid account. Worth the user's own awareness before wide
  distribution of a build containing them, even though Microsoft's Image Creator terms generally
  grant usage rights to the generating session for the images it produces.
