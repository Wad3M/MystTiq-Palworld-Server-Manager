# v0.7.105.0 — Doctor: Confirm Before Fix

## Context

A named follow-up since v0.7.103.0 ("Not built" in every checkpoint since: "a confirmation step for the
fix"/"a confirmation step before the Doctor's one-click fix"). The Doctor's Fix button (Create Nightly Backup
Rule, Create Backup Folder, Install / Repair Server Files) ran the moment it was clicked, with no chance to back
out. Backup Restore already solved exactly this for a different destructive action with a simple pattern: a
checkbox that must be ticked before the button works. This version applies the same pattern to every Doctor fix.

## What changed

- `DiagnosticFindingDto` (`src/MystTiq.Desktop/Models/DiagnosticFindingDtos.cs`) now implements
  `INotifyPropertyChanged` for one new client-side-only field, `FixConfirmed` — the same technique
  `PalworldSimpleSettingItem` already uses for its own live-bound state. Never sent to or read from the server;
  a fresh finding (a report refresh, or the instance `RecheckDiagnosticAsync` swaps in after a fix) always
  starts unconfirmed.
- New `FixConfirmText`: the same per-`ActionKind` switch `FixButtonText` already uses (v0.7.103.0), but phrased
  as what ticking the box means ("I understand this creates a nightly backup rule", "...creates the backup
  folder", "...downloads and installs server files", falling back to a generic "...runs the fix").
- `MainWindow.axaml`: the Fix button's `IsEnabled` is now bound to `FixConfirmed`; a `CheckBox` sits under the
  button row with short "Confirmed" text and `FixConfirmText` as its tooltip (kept short deliberately — the
  finding cards are compact list rows, not a dedicated detail panel like Backup Restore's, so a full sentence
  inline would have widened every row).
- `MainWindowViewModel`: `FixDiagnosticCommand`'s predicate and `FixDiagnosticAsync` both also check
  `finding.FixConfirmed` directly, not just the button's own `IsEnabled` — the same defense-in-depth
  `RestoreBackupCommand` already has via `BackupRestoreConfirmed`.

## Deliberately not done

- No change to the confirm-then-fix flow's server side at all: `/diagnostics/{id}/fix` still executes
  immediately on request, same as before. The confirmation is a client-side guard against an accidental click,
  not a new server contract — matching Backup Restore, which is the same shape (`BackupRestoreConfirmed` is
  Desktop-only; the restore route itself has its own separate `confirm` flag).
- No "confirmed" state persists across a refresh or a successful fix; ticking it again for a second fix on a
  different finding, or after a Recheck, is by design.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 1 new scenario, `DiagnosticFindingDto` compiled directly into the harness (same technique as
  `PalworldConfigurationDtos.cs`): a fresh finding starts unconfirmed; `FixButtonText`/`FixConfirmText` name the
  actual action for every recognised `ActionKind` and fall back to generic text for an unrecognised or absent
  one; setting `FixConfirmed` raises exactly one `PropertyChanged` per real flip and none for a no-op set to the
  same value.
- Live UI check (window rendered with PrintWindow; helper `ui-capture-helper.ps1`): opened Diagnostics on a
  profile with the "Scheduled backups" Warning finding, confirmed the Fix button is disabled and the Confirmed
  checkbox is unticked; ticked it and confirmed the button became enabled. Did not press it on a real profile.
