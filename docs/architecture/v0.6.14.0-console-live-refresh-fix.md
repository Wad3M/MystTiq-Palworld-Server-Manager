# v0.6.14.0 — Console Live-Refresh Fix

## Goal

A direct user report during the v0.6.13.0 pass: "the console does not seem to load anything when the server starts and stops." Queued as this milestone's sole scope. Continues the same `v0.6.x.0` versioning convention.

## Investigation

v0.6.13.0's checkpoint carried forward a bounded, non-fixing investigation: real narrative/stdout capture genuinely exists (`WindowsServerLifecycleService.StartConsoleCapture`/`AppendLifecycleConsoleLine`), so the write side wasn't simply missing. This pass found **two independent, compounding bugs**, both reproduced live against a real running PalServer instance before being fixed.

### Bug 1 — the passive auto-refresh timer skips its tick entirely during a Start/Stop/Restart

`MainWindowViewModel`'s 5-second `_refreshTimer` returns immediately whenever `IsBusy` is true. `RunLifecycleAsync` (the shared implementation behind Start/Stop/Restart) sets `IsBusy = true` for the operation's entire duration and, previously, called `ApplyLogs` exactly once — after the operation fully completed. A real Start can take anywhere from several seconds to the configured startup timeout; a Stop can take up to the stop timeout, longer still if it falls back to forced termination (observed directly during this session's own testing). For that entire window, the Console page received zero updates — frozen precisely during the moment its live narrative matters most, then dumped everything at once the instant the operation finished. This is a very literal match for "does not seem to load anything when the server starts and stops."

**Fix**: `RunLifecycleAsync` now runs a lightweight, console-only tail poll (`PollConsoleWhileBusyAsync`, a 2-second loop calling `_api.GetLogTailAsync` and `ApplyLogs`) concurrently with the main lifecycle operation, cancelled the moment the operation completes. The existing `IsBusy`-gated full status poll is untouched — this only adds a narrow, self-contained side channel for the one thing that needs to keep moving during the transition.

### Bug 2 — a real, independently-discovered starvation bug in the server-side log merge

Found while live-testing bug 1's fix, using an isolated instance with real modded pre-start diagnostics and a real, weeks-old `AdminCommands` server log both present. `HeadlessMonitoringService.GetLogTail`, when combining multiple console sources, concatenated each source's own chunk in a fixed order (MystTiq lifecycle/stdout first, then Pal.log, then any admin-command log) and applied `merged.TakeLast(maxLines)` to the whole concatenation. Because each source's own per-source floor (`Math.Max(12, maxLines / sources.Count)`) can independently exceed a small requested `maxLines`, a later source with enough historical volume could — and, reproduced live, did — completely evict an earlier source's content from the final `TakeLast` window, regardless of how chronologically fresh that earlier content actually was. In the live reproduction, real-time `[MYSTTIQ]`/`[OUT]` lines written seconds earlier were entirely absent from the returned tail, replaced end-to-end by weeks-old `AdminCommands` log entries.

**Fix**: removed the trailing `merged.TakeLast(maxLines)`. Each source is already independently bounded via `ReadTailLines(source.Path, perSource, ...)`, so the merged total stays naturally bounded (`sources.Count * (perSource + 1 header line)`) without a further blind global crop that can zero out an entire source.

## Verification

Both fixes verified live, end-to-end, against a real running PalServer instance on an isolated, full-fidelity copy of production-derived data (Tools + real MOD/UE4SS setup + real historical `AdminCommands` log):

- **Before the fix**: polled `/logs/tail?lines=10` four times across a real Start operation. Every poll returned exclusively weeks-old `AdminCommands` content; the MystTiq lifecycle/stdout section was entirely absent despite fresh lines genuinely being written during that exact window.
- **After the fix**: the identical test now shows real, live `[INFO]`/`[STATUS]` MOD pre-start diagnostic lines with the current session's timestamps, followed later in the same poll sequence by `[MYSTTIQ] PalServer ready. Managed PID {pid}; UDP 8211 verified.` appearing the moment it was actually written — alongside the historical `AdminCommands` section, which is no longer crowded out either.
- `dotnet build` (Release) across all three projects, and `scripts/Test-v0.6.14.0-Logic.ps1 -RunBuild` (12 static contract checks, the frozen v0.6.13.0 regression gate, and all 29 real v0.5.1.5 runtime-smoke checks) all pass.

Full interactive GUI confirmation (watching the actual Console page scroll live during a real click-through Start) was not performed — no capability exists in this session to drive the native Avalonia window directly, the same disclosed limitation carried through every checkpoint since v0.6.4.0. The underlying data-and-refresh mechanism this fix depends on was verified directly against the real API both fixes touch, which is the strongest verification available without that capability.
