# v1.0.2.0 — Unattended Reliability (internal)

The owner's roadmap (rewritten 2026-10-05) puts unattended reliability first (decision D-3): R-1 frozen-server
watchdog, R-2 alert delivery proof, R-3 the Linux headless service under systemd.

## R-1 Frozen-server watchdog

Crash recovery (`HeadlessSupervisor.RunCrashRecoveryLoopAsync`) only acted when no server process was left. A process
that hangs keeps its UDP game port, so `Ready` stayed true and nothing reacted.

- `IServerResponsivenessProbe` / `PalworldRestResponsivenessProbe`: GET `http://127.0.0.1:<RESTAPIPort>/v1/api/info`
  with the admin password, 10 s timeout. Any HTTP answer is `Answered` (even 401). A timeout or refused connection is
  `NoAnswer`. With REST off, no password or an unreadable settings file, the result is `CannotTell`.
- `FrozenServerWatchdog` (pure): per process id, it remembers the last answer. A process is frozen only when it has
  answered at least once, is ready, and has given `NoAnswer` for the whole limit. `CannotTell` never counts. A new
  process id starts with a clean record. It looks about six times per limit, at most every 30 s.
- The supervisor checks running servers when a look is due. A frozen one:
  - is restarted (`RestartAsync`: graceful 15 s, then the lifecycle's force kill), which counts toward the restart
    window, raises `FrozenDetected` first, then the usual RecoverySucceeded or RecoveryFailed;
  - when the window is used up, is announced once (`RecoverySuppressed`) and left alone until its process id changes,
    after which `ManualRecovery` is announced and it is judged afresh.
- `CrashAlertText` has its own `FrozenDetected` alert (Critical, not pinned). Unknown kinds otherwise fall to the
  pinned give-up text. `CrashAlertObserver` always writes "Frozen server restarted" to the Activity log.
- Setting: `lifecycle.unresponsiveRestartSeconds` (absent: 180; 0: off; otherwise at least 60, validated). The probe is
  wired into every supervisor: api-run per profile and service-run on Windows and Linux.

Live evidence (2026-10-05):
- The clone `second-local` was started through an isolated service: a config holding only that profile (as `default`),
  its own fleet root and port 18321, with a 60 s limit.
- Frozen with `NtSuspendProcess` at 16:23:07. The service logged "has not answered its REST API for 1 minute(s).
  Frozen-server restart attempt 1/5".
- A new process was ready 84 s after the freeze, and the frozen one was gone.
- Notifications: "server stopped responding, restarting (attempt 1 of 5)", then "server is back up (PID 18704)".
- Activity: "Frozen server restarted". The owner's live configuration and main server were not touched.

## R-2 Alert delivery proof

`HeadlessNotificationRoutingService` sent to Webhook, Discord and Email fire-and-forget. Only failures reached the
Activity log, so a channel that silently stopped working looked the same as a quiet one.

- Each send returns `(Success, Detail, Attempts)`: the HTTP status, "Accepted by <smtp host>", or the error. It is
  recorded in `NotificationDeliveryLog`: `notifications/deliveries.json` per profile, newest last, at most 500,
  written atomically.
- `NotificationDeliveryLog.Health` (pure), per outside channel:
  - Off: switched off;
  - Failing: tried in the window and the last send failed;
  - Delivered: a delivery in the window and the last send succeeded;
  - NotProven: nothing delivered in the window, which is 7 days.
  Everything switched on except Delivered is flagged.
- `GET notifications/delivery-health`. The desktop shows a Dashboard warning (polled at most once a minute) and the
  Alert Center Delivery card (channels with tags, the latest 20 sends). A test send refreshes it after 5 s.
- Live evidence owed: no outside channel is configured on this machine. The roadmap needs one real Discord and one real
  email send confirmed arrived (also E-3).

## R-3 Linux headless service under systemd

The unit already had `Restart=on-failure`, `WantedBy=multi-user.target` and a TERM stop. Each non-default profile has
its own unit name (`mysttiq-palworld-<id>.service`).

`scripts/Test-v1.0.2.0-LinuxSystemd.ps1` and `.sh` prove it on the VM in phases, using their own unit
(`mysttiq-palworld-r3test.service`), folder (`/opt/mysttiq-r3test`), config, ports 18431/18611 and a stand-in server:

- install: MystTiq's own `service-unit` text, pointed at the test folder; enabled and running without a desktop;
- crash: SIGKILL the main PID; systemd starts it again;
- reboot (the release run only): the service and the server come back at boot;
- stop: inactive with `Result=success`, and the server stopped with it;
- cleanup: the unit and folder are removed, and the production unit's SHA-256 is unchanged.

The gate runs it without the reboot whenever the VM answers on SSH. On 2026-10-05 the VM (192.168.1.122) did not
answer, so R-3 stays Built.
