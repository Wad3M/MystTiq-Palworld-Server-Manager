# v0.7.113.0 — Teleport Points (chat command)

## Why, and why a chat command

Asked 2026-09-22: "a setting that allows the clients to teleport from anywhere in the world to a teleport
point". Asked how players should trigger it, the user said: "through the internal game mechanic of
teleportation, if that doesnt work then a chat command".

The game's own mechanic cannot do it from the server. Researched and confirmed:
- `PalWorldSettings.ini` only has `bEnableFastTravel` and `bEnableFastTravelOnlyBaseCamp`. Fast travel
  still requires standing at a statue.
- "Fast travel from anywhere" exists only as client-side Nexus mods that every player installs.

So this is the fallback: a chat command.

## How it works

- Vanilla Palworld has no teleport command, and players cannot run PalDefender's commands themselves
  ("no command that non-admin player can use"). MystTiq reads chat and, as the admin, runs PalDefender's
  `tp <UserId> <X> <Y> [Z]` over RCON. It replies privately with PalDefender's `send msg <UserId> <text>`.
  It uses the same PalDefender-over-RCON runner as Starter Kits and Give Item.
- **Chat source** (`PalDefenderChatLogSource`): tails PalDefender's newest session log
  (`Pal\Binaries\Win64\PalDefender\Logs\*.log`) and MystTiq's captured console log.
  - A log that existed before MystTiq started is read from its end, so old commands are never replayed.
    A log created after MystTiq started (a new server session) is read from its start.
  - Only complete lines are consumed. A truncated or rotated file is re-read from the start.
- **Parsing** (`TeleportChat`, pure): only PalDefender's form is read:
  `[hh:mm:ss][level] [Chat::Global|Local|Guild]['Name' (UserId=..., IP=...)]: text`. It carries the UserId
  `tp` needs. The vanilla `[CHAT] <Name> text` form has no UserId, and PalDefender replaces it anyway.
  - The leftmost header wins, so a fake header typed into a message is attributed to its real sender.
  - A command is exactly the prefix (list the points) or the prefix plus one point name. Anything longer is
    ordinary chat and is ignored.
- **Identity check**: a command is acted on only if the Palworld REST player list shows a player online
  with exactly that name *and* UserId. With the list unavailable (REST off), nothing is done and the use is
  recorded as unconfirmed. The first build skipped the check when the list was unavailable; the route smoke
  caught that version teleporting an impostor, and it was changed before shipping.
- **Cooldown** per UserId (default 60 s, 0 to 3600), with a "please wait N seconds" reply. **Duplicates**
  (the same line in both logs) within 10 s are handled once. The duplicate key includes the name, so an
  impostor line cannot suppress the real player's command.
- The watcher polls every 2 s and always drains new lines, even while switched off. Turning it on later
  never acts on old lines.
- **Coordinates** are PalDefender's own. MystTiq never converts them. "Capture" runs `getpos <UserId>` for
  a selected online player and reads the numbers from the reply, ignoring digits glued to the UserId.

## Settings and routes

`<RuntimeRoot>/teleport/teleport.json`: `Enabled` (default off), `CommandPrefix` (default `!tp`; must be
`!` or `.` plus 1 to 16 letters/digits, so it never clashes with PalDefender's `/` commands),
`CooldownSeconds`, `Points` (at most 50; names are 1 to 32 of `[A-Za-z0-9_-]`, unique ignoring case, and
`list` is reserved).

- `GET /api/v1/teleport` (Operator): config, provider status, chat source, and up to 100 recent uses
  (newest first).
- `PUT /api/v1/teleport` (Admin): save, 400 on validation errors.
- `POST /api/v1/teleport/points/{name}/send {playerId}` (Admin): send an online player now.
- `POST /api/v1/teleport/capture {playerId}` (Admin): PalDefender `getpos`.

## Desktop

A "Teleport Points" card on the Map page:
- The on/off switch, command and cooldown.
- The points as text lines (`spawn -358 270`, optional height).
- Save Points, "Capture Selected Player's Position" (adds a `newpoint` line to rename) and Refresh.
- "Send selected player to <point>".
- The provider and chat-source status, and the recent uses.

The note under the Map's existing teleport buttons now points to it.

## Verification

- Logic harness: 5 new scenarios. They cover:
  - text parsing
  - chat parsing, including forged headers and comma-decimal cultures
  - the service end to end: off-switch, teleport + reply, cooldown, list, unknown point, impostor and
    offline senders, duplicates, no provider, no player list
  - the Send and Capture admin actions
  - log tailing: history skipped, partial lines, new session log, truncation
- `scripts/Test-v0.7.113.0-RouteSmoke.ps1` (9 checks) runs against the published exe.
  `scripts/Testing/FakePalServerEndpoints.ps1` stands in for PalServer's RCON (recording every command) and
  REST player list. A PalDefender-format chat line written into a fresh PalDefender session log produces
  exactly `tp steam_1 -358.5 270` and `send msg steam_1 Teleported to spawn.`, while an impostor line in the
  same log produces nothing. The smoke also covers the cooldown, recent uses, Capture, Send, validation and
  the off-switch.
- Live Desktop: the card renders on the Map page and loaded the Clone profile's real settings, provider
  status and the name of its real PalDefender session log.

## Not verified

- That the installed PalDefender (v1.8.3) writes chat lines in exactly this form to its log or the console.
  The format comes from another launcher's tests; nobody has chatted on this machine's servers.
- A real player actually moving, and the real reply text of PalDefender's `tp`, `send` and `getpos`.
  Until a real player tries it, treat it as proven on the MystTiq side only.
