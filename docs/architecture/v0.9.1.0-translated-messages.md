# v0.9.1.0 — Status and error messages in 12 languages

## Why

v0.9.0.0 made every fixed text in the window translatable, but the texts the code builds (server states, progress and
results, validation and error messages, drop-down choices, dialog texts) were still English. The inventory listed about
980 of them. Translating them at the source would mean changing hundreds of assignments in the view models, and the app
compares many of them (a status of "Stopped / Not ready", a history range of "1 Hour"). Logic and tests would break the
moment a language other than English was picked.

## Translate at display time

The view models keep English. Translation happens on the way to the screen:

- **The catalog.** Every message is a `msg.*` key in `Assets/i18n/<code>.json` (1,113 messages, English in `en.json`,
  every language complete; the gate's 12-language check covers them like every other key). The keys read like their text
  (`msg.stopped_not_ready`), with a hash suffix for long or colliding ones.
- **`MessageCatalog`** (`Services/MessageCatalog.cs`) is built from the English file and the chosen language's file on
  every language change (`Localizer.Messages`). For English it is empty, so English text passes through untouched.
  - A message without placeholders is an exact lookup. The fixed labels (`ui.*` and the other keys) count too, so a
    status that happens to equal a label is translated.
  - A message with `{n}` placeholders is a template. Its English becomes an anchored regular expression with a named
    group per placeholder (a repeated placeholder is a back-reference). The shown text is matched and the captured
    values are put into the translated template, so a translation may order them differently
    (`Sending {0} for {1}…` → `{1} に {0} を送信しています…`). A captured value that is itself a known message is
    translated too, two levels deep ("Status: Stopped / Not ready").
  - A message whose English ends in a space ("The history could not be read: ") is the start of a text the code
    completes (with an error); it matches that start and keeps the rest.
  - A multi-line status that matches nothing whole is translated line by line.
  - Templates are tried most specific first: the most fixed characters, and a closed template before an open-ended
    one on a tie ("Checked {0}." before "Checked "). A template needs at least four fixed characters, two of them
    letters, so "{0}{1}", "{0} MB" or "Up {0}" can never swallow unrelated text. Each regular expression has a 50 ms
    timeout.
  - Results are cached per language (up to 8,192 texts). Text that matches nothing is shown unchanged.
- **Where it applies.**
  - `{services:TrText Path}` is a MultiBinding of the value and `Localizer.Strings` (which changes with the language)
    through a converter that calls `Translate`. `Update-MystTiqUiText.ps1 -ConvertBindings` put it on every simple
    display binding (`{Binding Path}`, optionally `Mode=OneWay`): `Text` on TextBlock, Run and SelectableTextBlock;
    `Content` on buttons, check boxes, radio buttons and labels; `Header` on menu items, tabs and expanders; and
    `ToolTip.Tip`. Never on a TextBox or any other editable field, whose text must reach the view model as typed. It
    skips bindings with converters or string formats, and paths that are data by name (…Name, …Id, Url, Host, Port,
    Hash). 481 bound texts, with 7 list templates (`{services:TrText}` on `{Binding}`) for findings, warnings and accent
    names. Console, RCON and id lists stay as they are. `-Check` fails on an unconverted display binding.
  - A `DataType="{x:Type x:String}"` data template in `App.axaml` draws any plain string content (drop-down and list
    items, string button content) through TrText, so choices such as "All Players" or "1 Hour" follow the language
    while the view model's list stays English. No button uses an access-key underscore, so the default template's
    `AccessText` is not needed.
  - Code that sets text directly uses `Localizer.T(...)`: the confirmation and selection dialogs, the tray reminder
    and the 15 file-picker titles.

## What stays English, on purpose

Server and world names; the in-game restart command (`Shutdown 60 Server restarting` is sent to the server); date
formats; the default server name and the place names that match save data; product and technical names. Messages from
the MystTiq service itself (Doctor findings, server replies) arrive in English and are v0.9.2.0 work, as are the few
messages the app composes from several pieces (the map's marker summaries, uptime).

## Checks

The ArtworkHarness:

- checks exact, template, reordered, open-ended and multi-line messages in Japanese, and that unknown text and English
  are unchanged and the view models stay English;
- round-trips every message template in every language (English filled with sample values must come back as that
  language's text with the same values), which proves no template is shadowed by a wrong one; this found "Checked "
  catching "Checked {0}." and led to the tie rule;
- extends the every-page leftover scan to the messages, in all 11 translations, naming the element that shows each
  leftover. It found drop-down items ("All Players", "Balanced QoL"), which led to the String data template, and the
  UE4SS version and save-tool paths, which were wrongly skipped as data.
