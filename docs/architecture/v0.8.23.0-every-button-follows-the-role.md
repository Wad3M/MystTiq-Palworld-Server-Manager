# v0.8.23.0 — Every Button Follows the Role

v0.8.19.0 made the server refuse what a role may not do, and the Ribbon follows the signed-in role. Most page buttons did
not: a Viewer could press Enable on a mod, Save on the whitelist or Delete on a backup, and the server refused. This
version closes that. **Every command that needs more than Viewer is disabled below its role**, wherever its button is:
on a page, in a context menu or on the Ribbon.

## Derived, not hand-kept

`scripts/Testing/Get-MystTiqCommandRoles.ps1` works out which role each command needs from the code itself:
1. **Routes.** It lists the service's routes and the role each one needs (`LocalManagementApiHost.cs`). That is the
   declared `RequireRole`, or else, in a server's route group, Viewer to read and Admin to change, as the v0.8.19.0
   default does.
2. **Client methods.** It maps each API client method to the route it calls (`MystTiqApiClient.cs`), including paths
   built in a local variable first. A change whose path cannot be matched is reported, never guessed.
3. **Commands.** It follows each command's action through the ViewModel's methods to the client methods it reaches. A
   method passed on without being called (`RunLifecycleAsync(..., _api.StopServerAsync)`) counts. The command's role
   is the highest role those routes need. Two things do **not** decide a button's role:
   - a `Refresh`/`Load` method run after the action: it is a best-effort reload whose refusal for a lower role is
     expected;
   - the Ribbon builders and navigation: they only reference commands.
4. **Click handlers.** It does the same for the window's code-behind `Click` handlers (world edits, mod ZIP install),
   following their shared helpers.

**Result:** 112 commands (45 Operator, 58 Admin, 9 Owner) and 10 code-behind handlers (all Admin). One handler needs a
role but stays open to everyone: closing a tab, because it stops that tab's server only if you choose to in its dialog.

Examples of what this found beyond the Ribbon:
- the mod actions: enable, disable, delete, repair, roll back, update, and the ZIP install;
- saving the whitelist, alert rules, anti-cheat rules and the Discord bot;
- deleting, restoring and verifying backups;
- notification pin, read and dismiss;
- the world edits in the context menus: delete or copy a player, transfer or wipe a base, and the four guild
  operations.

## How it is enforced

- **The command classes.** `RelayCommand`, `RelayCommand<T>` and `AsyncCommand` take an optional role gate that is
  part of whether the command can run, so a bound button disables itself.
- **The table.** `MainWindowViewModel.CommandRoles.cs` lists each command with its role, installed once every command
  exists. Commands re-evaluate when the signed-in role changes.
- **The Ribbon** takes its "needs the X role" tooltips from the same table.
- **The code-behind controls** bind `IsEnabled` to `CanManageAdmin`.
- **Local, token-less use** keeps every command, as before.

## The gate keeps it true

The gate runs the audit and fails when:
- the table and the code disagree, whether a command gets a new route or a new command appears;
- a client change cannot be matched to a route;
- a code-behind control whose handler needs a role is not bound to it.

## Verification

- **ArtworkHarness** (offline), for local use and every role:
  - each of the 112 gated commands runs only where the role allows;
  - on every page, none of the 245 controls bound to a gated command is enabled below its role.
- **Remote sign-in** against the isolated instance on the Linux VM: **42/42 from Windows and 42/42 from Linux**. That
  includes the same page check with a real signed-in session (228 controls, each role).

## Not done

- **Disabled page buttons have no "needs the X role" tooltip.** The page's role notice explains it, and the Ribbon's
  tooltips say it.
