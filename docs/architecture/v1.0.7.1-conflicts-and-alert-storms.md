# v1.0.7.1 — Conflicts Refused, Alert Storms Bounded (internal)

Roadmap items Q-4 and Q-11 from the outside review (`docs/roadmap/ANALYSIS_REVIEW_2026-10-07.md`).

## Q-4 — One authority for conflicting work

**Reproduced first** (2026-10-08): `scripts/Test-v1.0.7.1-RouteSmoke.ps1` against the published v1.0.7.0 service.
- While a start was running (a stand-in PalServer that never becomes ready), a manual backup was written (200).
- A backup and a start sent together both ran.

The same smoke on the new build: the backup, a MOD change and a SteamCMD update are each refused (409, with the
reason), nothing is written, and a backup and a start sent together never overlap.

The coordinator's locks are per server (`world-mutation` and `lifecycle`), reject-if-held. `OperationHold.TryBeginAsync`
takes them for a piece of work or returns the refusal; disposing it completes the operation and releases the locks, so
each hold is in the operation history. Without a coordinator (a harness) it holds nothing, as before.

### Operation × lock table

| Operation | `lifecycle` | `world-mutation` | Where |
| --- | --- | --- | --- |
| server-start, server-restart (API, Discord, automation), diagnostics-restart | yes | yes | `RunLifecycleActionAsync`, `HeadlessDiscordBotService`, `HeadlessAutomationService` |
| server-stop, server-force-stop (API, Discord, automation) | yes | | the same |
| mods-safe-start (stuck-start test load and diagnostic) | yes | yes | `HeadlessModSafeStartService` |
| mods-\* (every MOD change) | yes | | `HeadlessModManagementService.HoldServerAsync` |
| ue4ss-install, ue4ss-rollback | yes | | the same |
| server-update (SteamCMD) | yes | | `HeadlessServerDistributionService.UpdateAsync` |
| paldefender-update | yes | | `LocalManagementApiHost` (the Update Center route) |
| console-capture-install, console-capture-uninstall | yes | | `LocalManagementApiHost` |
| backup-create (scheduled, manual) | | yes | `HeadlessBackupService.CreateAsync` |
| backup-restore | | yes | `HeadlessBackupService.RestoreAsync` |
| save edits: inventory, Pal box, Pal, player copy, player deletion, guild and base ownership, character migration, world transactions | | yes | each service |

Not locked, on purpose:
- **Safety backups** are taken by a save edit inside the `world-mutation` it already holds, so `CreateAsync` skips the
  lock for `BackupClass.Safety`.
- **Backup verify and Verify All** read archives only. They are serialised with create, restore and delete by the
  backup service's own gate, and edits call verify inside their lock. The roadmap's acceptance named verify too;
  locking it would only refuse checks during an edit, for nothing.
- **The pre-start MOD reconcile** runs inside the start that holds `lifecycle`.
- **Safe Start's MOD switches** run inside its own hold (`SetEnabledAsync(..., serverHeldByCaller: true)`).

**Unattended work waits:** automation's lifecycle actions and its scheduled backup retry every 15 s for up to 10
minutes when refused (`ConflictWaitLimit`, `ConflictRetryEvery`). The run record says how long it waited. A refused
backup is marked `IsConflict`, so only real conflicts are retried.

Evidence: LogicHarness (a backup refused during an edit while the edit's safety backup is not; a held backup blocks an
edit; another server never held up; a MOD change refused during a start, while Safe Start's switch is not; a scheduled
backup waits for an edit and then runs); the route smoke above.

## Q-11 — Alert storms stay bounded

`HeadlessNotificationRoutingService.Dispatch` used to start one background task per notification. Now:
- `Enqueue` writes to a bounded `Channel` (`SendQueueCapacity` = 200, `TryWrite`). When full, the send is dropped and
  a `Dropped:` delivery record is written per channel.
- `SenderCount` = 2 loops read it (`SendLoopAsync`, started on first use through `BackgroundWork`). A send that waited 5
  s or more has "waited N s in the send queue" in its record.
- **Repeats:** the key is severity, title and text. The first occurrence is sent; repeats within `RepeatWindow` (10
  min) are counted. When the window ends, at the next notification or on a sender's idle tick (`RepeatCheckEvery`, 30
  s), one summary goes out: "(repeated N more times)", with the time span. `combineRepeats: false` exempts the test
  notification.
- `GetQueueState` (waiting, the oldest's wait, capacity, senders, combined, dropped) is part of the delivery state, and
  the desktop shows it in Alert Center under Pause Discord, Email and Webhooks.

Evidence: LogicHarness against a real local webhook answering after 20 ms. 300 copies of one alert and 400 distinct
ones gave:
- 299 combined;
- the queue capped at 200, with the rest dropped and recorded;
- never more than 2 sends at once;
- every send delivered or dropped, none lost;
- the summary "repeated 299 more times";
- two test notifications both sent.

The ArtworkHarness checks the queue line.
