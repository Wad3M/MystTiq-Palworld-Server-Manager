# v0.7.63.0 — Central Theme System Audit: Status-Color Bypass Fix

## Goal

The user reported, from live use, that the theme/accent color system does not actually control
every resource the way it should — buttons, cards, and similar elements were suspected of staying
locked to one look regardless of the selected accent theme or Light/Dark variant. This is a real,
previously undiscovered gap in a feature line (`ThemeCatalog`/`ThemeApplier`) that shipped across
v0.7.48.0 (foundation) and v0.7.56.0 ("the rest of the theming gap is closed"), and whose own release
notes both disclosed the same limitation: *"No way to visually render this app in the environment
that built it"* — meaning neither prior pass was ever actually click-tested, only reasoned about
statically. This pass is a real audit of the shipped mechanism against the live XAML/C# source,
followed by fixes for every confirmed bypass found.

## Investigation

`ThemeCatalog`/`ThemeApplier` (`src/MystTiq.Desktop/Services/`) is a real, well-built mechanism: it
writes every resource key it owns directly onto `Application.Current.Resources` on
`ThemeApplier.Apply(accentTheme, variant)`, and any XAML consumer bound via `{DynamicResource ...}`
picks up the change live, no restart or page-reload needed. The question was not "does this
mechanism work" (it does) but "does everything that renders a color actually go through it."

Traced every color-bearing surface in `src/MystTiq.Desktop` back to its source and found four
confirmed, independent bypasses, all the same root cause: **a color computed once and cached or
returned as a literal is immune to a live theme switch, no matter how good the underlying resource
system is** — only `{DynamicResource}` (XAML) or an explicit re-resolve on every access (C#) responds
to `ThemeApplier.Apply` after the fact.

1. **`Border.statuscard` (the bare, non-accent-decorated class) had no themed style at all.**
   `App.axaml` — a leftover file from before `Styles/DesignSystem.axaml` existed — still declared a
   full parallel legacy system: `MystTiqBackground`/`MystTiqButtonMetal`/etc. hardcoded-hex resources,
   plus base `Window`/`Button`/`Border.card`/`TextBlock.muted` styles. For every one of those
   selectors that `DesignSystem.axaml` *also* declares (which is most of them), Avalonia's own
   equal-specificity tie-break rule (later declaration wins — `DesignSystem.axaml` loads via
   `StyleInclude` after `App.axaml`'s inline styles) meant the theme-aware version always won in
   practice, making the legacy copies dead but harmless. `Border.statuscard` was the one exception:
   `DesignSystem.axaml` only ever defined the *compound* `Border.card.accentXxx` / `Border.statuscard.
   accentXxx` variants, never a bare `Border.statuscard` override — so for the small number of
   `Classes="statuscard"` elements with no accent class (the sidebar's mini connection-status card,
   the duplicate-install-location warning banner), `App.axaml`'s hardcoded `#0E2133`/`#1E5279` was
   genuinely the only rule that ever applied, and never moved on any theme/variant switch.
2. **`ComponentStatusColorConverter`** (Update Center's component-version table) cached four
   `SolidColorBrush` instances built once from hardcoded Dark-theme hex literals at class load.
3. **`TabSession.StatusDotColor`** (tab-bar connection-status dot) and
   **`MainWindowViewModel.HealthStateColor`** (Dashboard health label) each computed a hex *string*
   from state, bound via a plain `{Binding}` — which, unlike `{DynamicResource}`, only re-evaluates
   when the source property itself re-raises change notification, not when the resource dictionary
   changes underneath it.
4. **`ServerProfileSummaryDto.StatusDotColor`** (Fleet page's server list) — the same pattern as #3,
   in a plain data DTO rather than a ViewModel.

None of these four were touched by v0.7.48.0/v0.7.56.0's work at all — they're a different failure
mode (computed-color bypass) from the ~530 hardcoded-gradient-literal problem those two passes
fixed, which is presumably why they survived two "central theme system completion" passes.

One correct precedent already existed in the codebase to follow: `TabSession.AccentBrush`
(v0.7.52.0, Per-Tab Color Coding) already resolves its brush via
`Application.Current?.TryGetResource(key, null, out var resource)` on every call, with an explicit
`RaisePropertyChanged` nudge from `MainWindowViewModel.RefreshTabAccentVisuals()` right after each
`ThemeApplier.Apply()` — exactly what a `{Binding}`-driven (not `{DynamicResource}`-driven) themed
value needs to keep working. The fix generalizes that same idiom.

## The fix

- New `Converters/SemanticStatusColorConverter.cs`: takes a semantic key (`"Green"`/`"Amber"`/
  `"Red"`/`"Muted"`/etc., matching `DesignSystem.axaml`'s existing `{Name}Brush` resources) and
  resolves it to the live brush via `Application.Current.TryGetResource` on every conversion — never
  cached, so it always reflects whatever `ThemeApplier` last wrote.
- `TabSession.StatusDotColor` → `StatusDotColorKey` (returns `"Green"`/`"Amber"`/`"Red"`/`"Muted"`
  instead of a hex string); `RefreshAccentVisual()` (already called on `Profile` set and after every
  `ThemeApplier.Apply()`) now also re-raises `StatusDotColorKey` so the converter re-resolves.
- `MainWindowViewModel.HealthStateColor` → `HealthStateColorKey`, same pattern;
  `RefreshTabAccentVisuals()` (the existing post-`ThemeApplier.Apply()` hook) now also re-raises it.
- `ServerProfileSummaryDto.StatusDotColor` → `StatusDotColorKey` — no explicit refresh hook needed,
  since this is a plain polled DTO that gets rebuilt from the next Fleet API poll regardless.
- `ComponentStatusColorConverter` now delegates to `SemanticStatusColorConverter` instead of caching
  its own static brushes.
- `MainWindow.axaml`'s four affected bindings (`Fill`/`Foreground`) now route through
  `{Binding ...Key, Converter={x:Static converters:SemanticStatusColorConverter.Instance}}`.
- `Styles/DesignSystem.axaml` gained the missing bare `Border.statuscard` style (using
  `CardStrongBrush`/`BorderSoftBrush`, both already theme-driven) and a `Button:focus-visible` style
  (using `BlueAccentHighlightBrush` — `App.axaml`'s old copy hardcoded `#75C8FF`).
- `App.axaml`'s entire legacy `MystTiqBackground`/`MystTiqButtonMetal`/etc. resource block and its
  now-fully-shadowed `Window`/`Button`/`Border.card`/`Border.statuscard`/`TextBlock.muted`/
  `Button.navitem`/`Expander.navgroup` styles were removed outright (`Button.navitem`/
  `Expander.navgroup` had zero live usages anywhere — the real nav uses `ToggleButton.nav`/
  `Border.navSurface` instead) rather than left in place as dead-but-technically-shadowed code. That
  shadowed state is exactly what let the `Border.statuscard` bug go unnoticed: a maintainer editing
  "the button style" would naturally reach for `App.axaml` without realizing it does nothing.

## Deliberately not changed

`ConsoleLineColorConverter` (log-line syntax highlighting in the Dashboard mini console, RCON
output, and the full Console page) still returns cached hardcoded brushes. This is intentionally
consistent with v0.7.48.0's own disclosed decision to keep all three terminal-style log views
dark/green in every theme, "matching how most apps keep a terminal panel dark regardless of the
overall UI theme" — reviewed during this audit and kept, not an oversight.

## Verification

- `dotnet build` on `MystTiq.Desktop.csproj` and the full solution: clean, 0 warnings/errors.
- `scripts\Test-v0.7.63.0-Logic.ps1` — see release notes for the check summary.
- **Not verified live in the GUI this pass** — same disclosed limitation as v0.7.48.0/v0.7.56.0: no
  way to visually render/click-test this app in the environment that built it. The fix is grounded in
  a real, traced defect (confirmed via Avalonia's own documented equal-specificity tie-break rule,
  the same rule this codebase's own comments already invoke elsewhere — e.g. the `Button.ghost:focus-
  visible`/`ToggleButton.categoryTab:focus-visible` overrides added in v0.7.14.0 for the identical
  reason) rather than a guess, but a user click-through across all four accent themes and both
  Light/Dark variants — specifically the sidebar's mini status card, the tab-bar status dots, the
  Dashboard health label, the Fleet server list, and Update Center's component table — is the only
  way to fully close this out. Flagged explicitly rather than claimed as done.

## Known gaps (disclosed)

- This audit traced every *computed-color* bypass (ViewModel/Model properties and IValueConverters
  producing colors outside the DynamicResource system) but did not re-run a full hex-literal sweep of
  `DesignSystem.axaml` itself — v0.7.48.0/v0.7.56.0 already covered that ground for gradients/glows,
  and this pass's four findings are a structurally different bug class, not a continuation of that
  same sweep.
- `ConsoleLineColorConverter` was reviewed and deliberately left as-is (see above); if that decision
  is ever revisited, it uses the exact same fix shape this pass already established.
