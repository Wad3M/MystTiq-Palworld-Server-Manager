# v0.7.52.0 — "+" Flow Restructure

## Goal

Item 53 from the original findings log: the "+" flyout has always had exactly one entry, "Set Up
New Server," which led into a wizard whose own step 0 then asked Local vs. Remote — one layer
deeper than the finding wanted. "Clone a server" already existed as a working feature (Fleet page's
Clone World card) but wasn't reachable from the "+" flyout at all.

## Investigation

Two open questions from the original finding, resolved by reading the actual wizard code before
changing anything:

**Does the Local branch already distinguish "install a fresh server" from "connect to an existing
one"?** No — `ChooseLocalConnection()` and the Local sub-view's `DetectLocalServiceAsync()` are one
single flow regardless of intent. There is no backend concept of "fresh install" vs. "existing
install" at this layer; Server Setup's own environment checklist handles that distinction
afterward, once connected, by simply reporting what it finds. So splitting "Set Up New Server" from
"Connect to Local Server" at the flyout level is a framing-text difference, not a different code
path — disclosed here rather than invented as a false distinction.

**Can Clone a Server work as a standalone flyout entry with no prior context?** No — cloning
duplicates an *already-connected* local server's installation (`CloneWorldCommand`'s own
`CanExecute` already requires `ManagementApiConnected`, and `BootstrapLocalCommand`/`IsLocalProfile`
confirm this whole feature is local-only). There is nothing to clone *from* without a source. The
flyout only offers this entry when `HasCloneableLocalTab` finds at least one open tab that
qualifies.

## Design

Four top-level flyout entries, in order:

1. **Set Up New Server** — unchanged (`SetUpNewServerTabCommand` → `OpenNewServerTab` →
   `BeginNewProfile()`, still landing on the step-0 choice cards).
2. **Connect to Local Server** — new (`ConnectLocalServerTabCommand` → `OpenConnectLocalServerTab`):
   opens a new tab, calls `BeginNewProfile()` then `ChooseLocalConnection()` directly, skipping
   step 0, with `Detail` set to "Connecting to an already-running local server."
3. **Connect to Remote Server** — new (`ConnectRemoteServerTabCommand` →
   `OpenConnectRemoteServerTab`): same shape, `ChooseRemoteConnection()`, "Connecting to a remote
   MystTiq server."
4. **Clone a Server** — new (`CloneServerFlowCommand` → `OpenCloneServerFlow`), shown only when
   `HasCloneableLocalTab` is true. Sets `ActiveTab` to the first eligible connected-local tab found,
   then navigates to the Fleet page (`NavigateCommand.Execute("Fleet")`) where the existing Clone
   World card already lives, unchanged.

The existing "Connect to {profile.Name}" list (per already-saved profile not currently open in a
tab) is unchanged and appears below the four new entries — reconnecting to a saved profile is a
distinct action from any of the four above, which all start a fresh wizard/navigation flow.

## What shipped

- `MainWindowViewModel.cs`: three new commands (`ConnectLocalServerTabCommand`,
  `ConnectRemoteServerTabCommand`, `CloneServerFlowCommand`), their backing methods
  (`OpenConnectLocalServerTab`, `OpenConnectRemoteServerTab`, `OpenCloneServerFlow`), and
  `HasCloneableLocalTab`.
- `MainWindow.axaml.cs`: `AddTabButton_OnClick` now builds four top-level `MenuItem`s instead of
  one, with the fourth conditionally added.

No changes to `MystTiq.Core` or `MystTiq.HeadlessHost` — every new entry point is a thin wrapper
around Desktop-side commands that already existed and were already correct.

## Known gaps (disclosed)

- No visual verification possible in this environment — the flyout's actual on-screen layout with
  four (or five, once a cloneable tab exists) entries was not confirmed visually.
- "Set Up New Server" and "Connect to Local Server" converge on the identical underlying flow, as
  documented above — a future version could make Server Setup itself aware of which entry point was
  used and tailor its own copy accordingly, but that's new scope beyond this restructure.
