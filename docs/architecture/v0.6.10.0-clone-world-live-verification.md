# v0.6.10.0 — Clone World & Extended Live Verification

## Goal

A direct user request, arriving after the full v0.6.0.0–v0.6.9.0 family shipped: build a real "Clone World" feature (duplicate a server profile's world so it can be run independently, both as a genuine admin capability and as a safer basis for testing), and use it to perform extended live verification this session hadn't yet done — a sustained real-time run, two genuinely simultaneous PalServer instances, and a real cross-machine connection test. Continues the same `v0.6.x.0` grouped-milestone versioning convention as every prior milestone.

## What shipped

### Clone World

- `HeadlessWorldCloneService` (new) — `POST /server/clone` (per-profile, reachable unprefixed for the default profile or under `/servers/{profileId}/server/clone`). Requires the source server stopped (files can't be safely copied while PalServer has them open — the same precondition every other save-mutating service in this codebase already enforces).
- Performs a **full, real copy** of the entire source `ServerRoot` (game binaries + `Pal/Saved` world/config data) into a new directory — not a shared junction — so future SteamCMD updates to one instance never silently affect the other. Uses `Parallel.ForEachAsync` over all source files for throughput; verified live against a real ~5.9 GB Palworld install (5,600+ files) in well under a minute.
- Assigns the new profile distinct ports (`PublicPort`/`RESTAPIPort`/`RCONPort`, offset by a configurable amount, default +100) so it can run alongside the source without a silent collision — directly reusing the same port-collision concept v0.6.5.0's Configuration Intelligence finding exists to catch, avoided proactively at clone time instead.
- Reuses the existing v0.6.2.0 `HeadlessFleetConfigurationService.AddServerAsync` path unchanged to register the new profile — inheriting its documented "requires a MystTiq process restart to take effect" convention rather than inventing a parallel one.
- New Desktop UI: a "Clone World" card on the Fleet page (new profile ID/name fields, a Clone button, and a status line).

### Real bug found and fixed during live verification (load-bearing for the whole feature)

The first live clone-and-run attempt found that editing `PalWorldSettings.ini`'s `PublicPort` alone does **not** control PalServer's actual UDP bind port. With both instances started, the clone's real process bound the *next free port* (8212) instead of its configured 8311, while `PalWorldSettings.ini` itself still correctly showed 8311 — confirmed by directly inspecting `Get-NetUDPEndpoint` against both running process IDs. The actual game port is controlled by the `-port=` command-line launch argument; `PublicPort` in the ini is not authoritative for the real socket bind (RCON's port, by contrast, *did* correctly follow its ini value in the same test). Fixed by having `CloneAsync` inject `-port={newGamePort}` into the new profile's `LaunchArguments` in addition to the ini edit. Re-verified live: both instances then bound their correct, distinct ports, confirmed at the OS level.

## Explicit non-goals

- Cloning to a different platform (Windows→Linux) or a different physical machine in one operation — the clone always targets a local sibling directory on the same host as the source; moving a cloned profile to another machine is a manual follow-up (copy + fleet-add there), not automated by this feature.
- Automatic conflict resolution beyond ports (e.g., MOD state, save-slot naming) — the clone is a byte-for-byte copy of everything else.

## Verification

All live, against a fully isolated environment (a complete, independent file-system copy of the real production Palworld install — never the production directory or process itself; the real production server was never started, stopped, or touched at any point):

- **Sustained real run**: started a genuine `PalServer.exe` via MystTiq's own lifecycle route (not a manual side-channel launch) against a real cloned save; confirmed via `Get-NetUDPEndpoint` and MystTiq's own UDP-confirmation readiness check that it was genuinely listening; ran metrics/Doctor/World Explorer/World Validator/RCON/backup-creation against it while live.
- **Two simultaneous instances**: used Clone World for real to produce a second, independent profile from the first; started both via their real per-profile lifecycle routes; confirmed via OS-level socket inspection that both bound distinct ports (8211/8311) and both real PalServer process trees were healthy and `ready:true` continuously across a 5-minute polling window (13 checks at ~20s intervals, `crashDetected:false` throughout both).
- **Idle Auto-Stop end-to-end** (the previously-disclosed v0.6.9.0 gap): with a real PalServer genuinely `Running` for the first time this session, created a live `IdleEmpty` automation rule (1-minute threshold) on the source profile. It correctly tracked idle time, fired its warning countdown, performed the final player recheck, and executed a real stop — the run record shows `State: "Completed"`, and clone1 (a separate profile) was completely unaffected, proving fleet isolation for real. **This closes the deferred verification gap from v0.6.9.0's checkpoint.**
- **Real cross-machine connection**: from this Windows machine, made an authenticated HTTPS call over the LAN to the existing, independently-running Linux MystTiq instance (a real system this session did not deploy anything to — read-only verification against its live `/api/v1/status`). Confirmed an unauthenticated request was correctly rejected (401 `missing-bearer-token`) and an authenticated request with the real bearer token succeeded (200, real live status data from the actual `PalServer-Linux-Shipping` process), over real TLS. This is a genuine, empirical "Windows head connecting to a Linux backend" proof — limited to the HTTP/API layer (this session has no way to drive the native Avalonia Desktop GUI directly), but exercising exactly the mechanism the Desktop app's own `MystTiqApiClient` uses for a remote connection.

## Real observations disclosed, not chased down this pass

- **Graceful shutdown consistently fell back to forced termination** across every stop performed this session against the cloned/sourced test instances (4 occurrences). The fallback worked correctly every time (`success:true`), so this isn't a defect, but the consistency is worth a closer look in a future session — possibly the configured `StopTimeoutSeconds` is too short for this particular save's exit-save duration, or there's a save-on-exit behavior specific to this environment.
- **A stale-crash-state edge case**: after forcibly killing the MystTiq *management* process itself (done repeatedly this session purely to reload fleet config after adding a profile — not something a normal admin workflow does), the next-launched instance's persisted status snapshot retained a stale `NativeProcessId` and `crashDetected:true`, which blocked Clone (and would block any other "must be stopped" operation) until an explicit `Start` was issued to refresh it — a plain `Stop` on the stale state did not clear it. Not encountered in any normal single-restart workflow; only surfaced because this session repeatedly force-killed the management process itself for config-reload purposes.
