# v0.7.33.0 — Home Dashboard Fixes

## Goal

Ninth version in the GUI/workflow/UX overhaul roadmap. Roadmap items 11, 12, and 14 — three fixes scoped to the Home Dashboard page.

## What shipped

### Removed the duplicate Online Players card (item 11)

Two player-facing elements existed on the Dashboard: the top-row "PLAYERS" summary card (`Classes="card glowPurple"`, online/known counts, an OPEN button to the Players page) and a second "ONLINE PLAYERS" card lower on the page (`Classes="card accentHome"`, a live `ListBox` of `OnlinePlayers` display names, no navigation of its own). The second card was `Grid.Column="1"` of a `Grid ColumnDefinitions="4*,1.2*"` shared with the "LIVE SERVER / MANAGER LOG" card at `Grid.Column="0"`.

Removed the ONLINE PLAYERS card and its enclosing two-column `Grid` entirely, replacing it with the log card alone (no `Grid.Column` needed, no `ColumnSpacing`) so it now spans the full row width. `OnlinePlayers` (the bound collection) is untouched — it still backs the Players page's own list; this only removes the Dashboard's redundant second consumer of it.

### Backup card gets an amber tint and an OPEN button (item 12)

The BACKUP card previously used the same generic `Classes="card accentHome"` styling as several unrelated cards, with no action button. The ACTIVE WORLD card right beside it already established the pattern to copy: `Classes="card glowDarkGreen"` plus a header-row `Button Content="OPEN" Command="{Binding NavigateCommand}" CommandParameter="..."`. An amber equivalent already existed in `DesignSystem.axaml` (`Border.glowAmber`, `CardAmberGradient` background, confirmed present before use) but was unused anywhere in the app. Swapped `accentHome` → `glowAmber` and added an `OPEN` button with `CommandParameter="Backups"`, matching the Backups category tab's own navigation target.

### Console log completeness at server start (item 14)

The roadmap's own finding for this item was explicit that it needed grounding before assuming a code change was required — the merge/read logic in `HeadlessMonitoringService.GetLogTail` had already been hardened once before (v0.6.14.0, fixing a source-eviction bug) and looked structurally sound. Re-investigation this release found the actual bottleneck one layer up, on the client side, not in that merge logic:

`GetLogTail(requestedLines)` clamps its own budget to `[10, 500]` and, when multiple log sources exist, divides that budget across them (`perSource = Math.Max(12, maxLines / sources.Count)`) — so the more sources merge (MystTiq's own stdout/lifecycle log, `Pal.log`, AdminCommands server logs), the smaller each individual source's slice gets. Every Desktop call site supplying `requestedLines`, however, was passing a hardcoded **120** — nowhere close to the server's real 500-line ceiling. With 3 sources merging, that works out to `Math.Max(12, 120/3) = 40` lines per source: nowhere near enough to carry a modded server's full startup diagnostics (raw `[UE4SS]`/`[MOD LOAD]`/`[MODS]` lines), which is exactly the kind of output the v0.2.16.4 reference screenshot that prompted this finding showed in abundance.

This is a real, groundable client-side tuning gap — confirmed directly from the request value versus the server's documented cap — not something that needed a live modded server to diagnose, even though the original finding correctly flagged that possibility as the likely outcome.

Fixed by raising the requested line count from 120 to 500 (the server's actual max) at every call site whose result feeds a log view a user can see:

- `RefreshMonitoringAsyncCore` (`MainWindowViewModel.cs`) — the shared core behind both the Dashboard's manual monitoring refresh and the Console page's `RefreshConsoleViewCommand`; both read from the same `LogLines` collection this populates.
- `RefreshStatusPollingAsync`'s aggregate poll — the recurring per-tab timer tick (~5s cadence) that normally keeps the Dashboard's log card current during ordinary viewing, not just right after an explicit action.
- `RefreshAsync`'s initial-connection poll — so a freshly opened tab's log view isn't starved from first paint.
- The post-lifecycle-mutation authoritative poll (`GetStatusPollingAsync`) and the `PollConsoleWhileBusyAsync` 2-second busy-loop poll — together these cover the entire window around and during a Start/Stop/Restart, the specific moment the original finding named ("we need to have that as well when a server starts").

Left unchanged: the Players page's own `RefreshPlayersPageAsync` call to the same aggregate endpoint, which fetches a log tail purely as a side effect of reusing that endpoint's shape — the Players page never renders log data, so raising its line count would add cost with zero visible benefit.

## Explicit non-goals

- No change to `HeadlessMonitoringService.GetLogTail`'s own merge/read/cap logic — the v0.6.14.0 hardening already there is correct; this release only changes what the client asks for.
- No live click-through against a real modded, running server in this environment (disclosed, carried-forward gap, same as every prior version this session) — the fix is grounded directly in the request-value-vs-server-cap arithmetic, not a rendered comparison against the reference screenshot.
