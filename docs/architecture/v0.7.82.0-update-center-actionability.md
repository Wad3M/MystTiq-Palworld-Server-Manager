# v0.7.82.0 — Update Center Actionability & Server Setup Table Resize

Direct live feedback against an Update Center screenshot: "the update center where it says update
available should allow us to click on it to update. we have a couple that say unknown, we need to
do better and have a way to check." Follow-up on the same visit, against Server Setup: "the server
environment should expand or shrink to fill the screen."

## Update Center: pip becomes actionable

The whole page was purely comparison data (`ComponentVersionDto` had no action of any kind) — every
row, including ones showing "Update available," was informational only.

- **New: `HeadlessComponentUpdateService.UpdatePipAsync`** — runs `python -m pip install --upgrade
  pip`, reusing the exact python resolution `CheckPipAsync` already does. `RunProcessAsync` gained
  an optional `timeout` parameter (existing 8-second default unchanged for every other caller) since
  a real install needs more room than a `--version` query. New route:
  `POST /update-center/components/pip/update`, mutation-gated the same way
  `/server/distribution/update` already is.
- pip is the only row this version makes genuinely actionable — it's the one component with a
  single, safe, well-known upgrade command. No fabricated "Update" action for components this app
  can't safely update unattended (SteamCMD self-updates; the Palworld Dedicated Server and UE4SS
  already have their own dedicated update/install flows elsewhere; Python/VC++ Runtime/MSVC Build
  Tools/PIM-Oodle have no reliable programmatic install path at all).
- New `ComponentVersionDto.CanUpdateInPlace` (`Component == "pip" && Status == "UpdateAvailable"`)
  gates a new "Update" button per row, wired to `UpdatePipCommand` → `UpdatePipAsync`, which
  refreshes the whole component table afterward so the row reflects the real new version
  immediately.

## Update Center: "Unknown" rows get a real way to check

Several rows (Python Runtime, Visual C++ Runtime, Microsoft C++ Build Tools, PIM/Oodle Decoder)
genuinely have no reliable unattended "latest version" feed (already disclosed in
`HeadlessComponentUpdateService`'s own header comment) — rather than fabricate one, a new
`ComponentVersionDto.SourceUrl` maps each of these (and the GitHub:/PyPI:-sourced rows, parsed from
their own `Source` label) to the real official page a human can check manually, and a new "Open"
button opens it via the OS default browser
(`OpenComponentSourceUrl_Click`, mirroring the existing `OpenModDescriptionSource_Click` pattern,
but reading the URL from the clicked row's own `DataContext` since this is inside an `ItemsControl`,
not a page-level "selected item"). Keyed primarily by `Component` rather than `Source` text, since
two unrelated rows (Visual C++ Runtime and Microsoft C++ Build Tools) both report the identical
`Source` string ("Windows Registry (no reliable \"latest\" feed)") but need different URLs.

## Server Setup: table resizes with the window

`Border.statuscard`'s Padding fix (v0.7.79.0) already made this table's rows legible; the table's
own container still had a fixed `MaxHeight="405"`, artificially short on a taller window (wasted
space below) and potentially overflowing on a shorter one. New `MainWindowViewModel.ServerSetupTableMaxHeight`,
recomputed on every window resize (`Window_OnSizeChanged`, the same trigger `UpdateMaximizeGlyph`
already uses — same established "recompute on live window size" pattern as
`UpdateTabStripWidth`/`UpdateRibbonWidth`), subtracting an approximate fixed-chrome offset and
clamping to a sane min/max. Not pixel-perfect (the chrome height estimate is deliberately
approximate, not tuned to an exact count), but a real, live improvement over a hardcoded constant.

## Bug fix: Alert Center disk-space prediction crash

Found live while testing this release: Activity & Audit was flooding with a repeating
`[WARNING] [Alerts] Alert evaluation failed — Value to add was out of range` entry roughly once a
minute. Root cause: `HeadlessAlertCenterService.GetDiskSpacePrediction` divides free disk bytes by a
`growthPerDay` rate computed from two historical samples; when those samples are close together in
time with only a tiny size delta, `growthPerDay` can be a near-zero positive fraction, making
`daysRemaining = free / growthPerDay` astronomically large — then
`DateTimeOffset.UtcNow.AddDays(daysRemaining)` overflows `DateTimeOffset`'s year-9999 ceiling and
throws. Fixed with a `MaxProjectableDays` cap (100 years): past that, the prediction honestly reports
"Storage is growing too slowly to project a meaningful exhaustion date" instead of attempting an
unrepresentable date.

## Configuration page: Server Identity to the top, dirty-state highlighting

Direct live feedback: "the server identity should be moved to the top" (with the Simple/Advanced
toggle, QoL preset, and search bar moving down to just above World Settings instead), "the server
identity text needs some spacing," and "anything that has changed from the save[d] preset should
highlight in Amber or Green."

- `MainWindow.axaml`'s Server config `Grid` (row-indexed) flattened to a single `StackPanel` so
  Server Identity renders first, with the toolbar row relocated to just above the Simple/Advanced
  view split. Server Identity's own `Grid` gained more `RowSpacing`/`ColumnSpacing`/`Padding`.
- New `Border.statuscard.dirty` / `TextBox.dirty` styles (`DesignSystem.axaml`, declared after the
  existing `accentXxx` block so it wins the equal-specificity cascade tie) highlight unsaved edits in
  amber — distinct from Advanced Settings' existing `Border.differsFromDefault` (active-vs-default,
  regardless of save state); this is active-vs-last-saved, i.e. `PalworldSettingDto.IsDirty`.
  `PalworldSimpleToggleItem` gained an `IsDirty` passthrough (it was missing one, unlike its slider
  counterpart `PalworldSimpleSettingItem`). Applied via `Classes.dirty="{Binding IsDirty}"` on Server
  Identity's four `TextBox`es, the Network toggle/setting rows, and all three World Settings slider
  rows.

## Bug fix: Dashboard "Stopped" contradicting the ribbon

Live-reported: "why does it say under overall health the PalServer process is active. The server is
stopped and not ready, but the only option i have is to stop?" `MainWindowViewModel.ServerIsRunning`
already treats a detected-but-not-confirmed-ready native process as "running" (so Start correctly
stays disabled), but `ServerState`/`DashboardHealthText` collapsed that exact same state down to a
hardcoded "Stopped / Not ready" — directly contradicting the ribbon next to it. Fixed: when
`status.NativeProcessId.HasValue` but not yet `Ready`, these now show "Starting / Not Ready" /
"STARTING" (amber glow, extending `IsHealthGlowAmber`/`IsServerGlowAmber`) instead of falsely
claiming the server is stopped.

## Bug fix: Generate Server Name button stuck disabled

Live-reported: the Server Identity "🎲 Generate" button was greyed out even after Configuration
settings had visibly loaded. Root cause: `GenerateServerNameCommand`'s `CanExecute` depends on both
`PalworldConfigLoaded` and `!IsBusy`, but its `CanExecuteChanged` was only ever re-raised from the
`PalworldConfigLoaded` setter — which fires mid-load, while `IsBusy` is still `true`, so
`CanExecute()` evaluated `false` right then and was never re-queried again once `IsBusy` returned to
`false` (nothing else ever re-raised it). `SaveCurrentAsPresetCommand` had the identical bug. Both are
now included in `RaiseIsBusyDependents`, the same re-query list `SavePalworldConfigurationCommand`
already used to stay correctly synced.
