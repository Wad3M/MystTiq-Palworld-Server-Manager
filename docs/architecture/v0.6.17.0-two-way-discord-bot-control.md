# v0.6.17.0 — Two-Way Discord Bot Control

## Goal

Third item in the roadmap sequence from the v0.6.15.0 competitive survey (`docs/architecture/v0.6.15-plus-competitive-survey.md`). Before designing anything, the roadmap doc's premise was re-checked against the actual code, since it claimed MystTiq's Discord dispatch was "outbound-only today." **That premise was wrong**: the only Discord-related code in the whole solution was one unimplemented enum case — `HeadlessNotificationRoutingService`'s `NotificationChannel.Discord` value logged `"Discord channel not implemented"` and never sent anything. No Discord.Net/DSharpPlus or any bot/gateway library was referenced anywhere in the solution.

This milestone builds real Discord integration for the first time, in two parts that together earn the name "two-way":

1. **The outbound leg**: `NotificationChannel.Discord` now actually posts a Discord-formatted embed to a configured Discord webhook URL. No bot, no token, no new dependency — Discord webhooks are plain HTTPS POST endpoints, reusing the same retry-once HTTP pattern the existing generic `Webhook` channel already had.
2. **The inbound leg (the actual "two-way" part)**: a real Discord bot (bot token, guild-scoped slash commands) lets an authorized Discord user run server commands (`/mysttiq-status`, `/mysttiq-stop`, `/mysttiq-kick`, etc.) and get a reply in Discord, executed by calling directly into MystTiq's existing lifecycle/RCON/moderation services.

Slash commands, not a text-prefix bot reading every message, were chosen deliberately: they need only the `Guilds` gateway intent (no privileged `MESSAGE_CONTENT` intent to request/approve), they're guild-registered so they never fire on unrelated chatter, and Discord's own UI enforces typed parameters. The bot connects **outbound** to Discord's gateway (a normal WebSocket client, the same shape `PalworldRconService` already is as a plain TCP client) — it never needs MystTiq to expose a public HTTPS endpoint, matching the existing local/LAN-first security posture.

## What shipped

**Outbound**: `HeadlessNotificationRoutingService.DispatchDiscordAsync` builds a Discord embed payload (`{embeds:[{title,description,color,timestamp}]}`, color mapped from severity) and posts it to the configured Discord webhook URL with the same retry-once pattern the generic webhook channel already used.

**Inbound**: new `HeadlessDiscordBotService` (`MystTiq.HeadlessHost`, constructed per server profile alongside `Lifecycle`/`Rcon`/`PlayerModeration`), backed by `Discord.Net.WebSocket` (new package reference, `MystTiq.HeadlessHost.csproj` only). Connects only when `Enabled` and a bot token are configured; registers eight guild-scoped slash commands on `Ready`:

- **Viewer**: `/mysttiq-status`, `/mysttiq-players`
- **Operator**: `/mysttiq-start`, `/mysttiq-stop`, `/mysttiq-restart`, `/mysttiq-broadcast <message>`
- **Admin**: `/mysttiq-kick <player> [reason]`, `/mysttiq-ban <player> [reason]`

Every command composes directly onto existing services — `IServerLifecycleService.StartAsync/StopAsync/RestartAsync`, `PalworldRconService.ExecuteAsync($"Broadcast {message}")` (the same call `HeadlessAutomationService` already makes), `PlayerModerationCoordinator.ExecuteAsync`, `HeadlessMonitoringService.GetPlayersAsync` — no new game-control logic. A command's minimum role is checked against the invoking Discord member's real guild roles (read from the interaction's `SocketGuildUser`, never a client-supplied claim), mapped through a per-profile `RoleMappings` table (`discord-bot.json`, `{ManagerRuntimeRoot}/notifications/`, `Admin`-gated `GET`/`PUT /notifications/discord-bot`). The bot token is write-only over the REST API — `DiscordBotConfigurationView` returns only `TokenConfigured: bool`, never the token itself, and saving with a blank token field keeps whatever token is already stored.

Discord-triggered `/mysttiq-start`/`stop`/`restart` share `OperationCoordinator`'s lock with REST- and Desktop-triggered lifecycle actions (same coordinator, same `["lifecycle"]`/`["lifecycle","world-mutation"]` resource keys as `LocalManagementApiHost.RunLifecycleActionAsync`) — a `/mysttiq-stop` can never race a REST-triggered stop.

Desktop: a new "Discord Bot" card on the Alert Center page (enabled toggle, bot token field, guild ID, owner-user-ID bootstrap, role-mapping list editor with add/remove), reusing `MystTiqRoles`/`CanManageAdmin` and the existing card/list-editor conventions.

## A real bug found and fixed during this pass's own live verification

Live-testing the bot's connection path against Discord's real gateway (with a deliberately invalid bot token, since no genuine bot credentials were available in this environment) surfaced a real problem: Discord.Net's own connection manager retries a gateway 401 indefinitely by design (a transient auth hiccup is retryable) — but a genuinely bad token never recovers, so the original implementation would have hammered Discord's real API forever while `connectionState` stayed stuck at `Connecting`, never surfacing the failure. Fixed by counting consecutive 401 responses in the `Log` handler: three in a row is treated as "this token is bad," not "try again" — the service now marks `Failed`, logs a clear activity entry, and proactively logs out/stops the socket rather than retrying under a known-invalid token. Re-verified live: after the fix, a bad token now reaches `Failed` and stops retrying within seconds of the third real 401 from Discord's servers.

## Explicit non-goals (this pass)

- World/save mutation commands (Pal editing, guild/base ownership repair) via Discord — too high-stakes for a chat command.
- Backup/restore or MOD install/uninstall triggers via Discord — same reasoning.
- Configurable command→role mapping — fixed tiers only this pass, matching the REST API's own fixed gating.
- Cross-profile / fleet-wide single bot instance — each profile's bot config and connection are independent, consistent with every other per-profile service.
- Anti-cheat scanning integration (v0.6.18.0) — separate milestone.

## Verification

`dotnet build` (Release) across all three projects and the full solution — 0 warnings/0 errors, including the new `Discord.Net.WebSocket` reference. `scripts/Test-v0.6.17.0-Logic.ps1` (18 static contract checks) passes.

**Live, end-to-end, against Discord's real servers** (isolated `mysttiq-server.exe` instance, real production install never touched): `GET`/`PUT /notifications/discord-bot` round-tripped configuration correctly — a saved token is never echoed back (`tokenConfigured: true` only), a save with a blank token field correctly preserved the previously stored token on disk, and a role mapping persisted and reloaded correctly. Enabling the bot with a deliberately invalid token made genuine outbound calls to Discord's real REST/gateway endpoints and received real `401 Unauthorized` responses — confirming the connection path is real, not mocked — and, after the fix above, correctly reached `Failed` and stopped retrying. The outbound leg was verified by directly exercising the real `HeadlessNotificationRoutingService.Dispatch`/`DispatchDiscordAsync` code against a local mock HTTP listener (schema-accurate, honestly disclosed as synthetic since no real Discord webhook was available): the listener received a well-formed `{"embeds":[{"title","description","color","timestamp"}]}` payload with the correct severity-to-color mapping.

**Not live-verified**: actual slash-command execution (`/mysttiq-status` etc.) against a real valid bot token and guild — no genuine Discord bot application/guild was available in this environment. The command-dispatch, role-resolution, and lifecycle-locking code paths were verified by direct code review and by the fact that every command composes onto already-live-verified services (`Lifecycle`, `Rcon`, `PlayerModeration`, `Monitoring`), but the actual Discord-side slash-command registration and invocation flow was not exercised against a live guild.
