# v0.7.73.0 — Tray Icon Honestly Reflects Running State

## The problem

Direct live report: the user expected "no tray icon visible" to mean "nothing is running," found two
real PalServer processes running with no visible MystTiq indicator anywhere, and asked to confirm
nothing auto-starts them. Investigation found no auto-start mechanism anywhere — no Windows
Startup-folder entry, no `Run` registry key, no scheduled task, no Windows service, no configured
automation rule on either profile, and in code, tab-session restore
(`RestoreTabSessionAsync` → `ConnectExistingProfileTab`) only reconnects and polls an already-running
server's status; it never calls Start. The two processes were simply left running from an earlier
manual start.

The real gap was in the tray/exit design itself. `App.axaml.cs`'s tray menu has three exit paths:
- **Safe Exit** / **Force Exit** — stop PalServer and the Desktop-owned headless sidecar, then quit.
- **Exit GUI Only — keep services running** — deliberately leaves PalServer *and* the headless host
  running, by design.

`Exit GUI Only` always fully quit the Avalonia application — which takes the tray icon down with
it. So "no tray icon" could mean either "genuinely idle" or "something is running, but you chose
the one exit path specifically built to hide that." The window's own close button already avoided
this trap (`MainWindow_Closing` only allows a real exit when `Tabs.Count(t => t.ServerIsRunning) ==
0`, otherwise it shows the confirm-minimize dialog) — the tray menu's own "Exit GUI Only" item just
never got the same treatment.

## The fix

Asked the user directly how to reconcile this, since there were two legitimate designs (always keep
a tray icon up while running, vs. keep the hard-exit but warn hard). Chose: **the tray icon stays up
whenever anything is running, full stop.**

`ExitGui_OnClick` now checks `viewModel.Tabs.Any(t => t.ServerIsRunning)` first — the exact same
check `MainWindow_Closing` already uses for the window's own close button. If anything is running,
it calls `HideMainWindowToTray()` (the same minimize-to-tray path the close button's confirm dialog
uses) instead of exiting. Only a genuinely idle app — nothing running in any tab — still fully exits
with no tray icon at all. This makes "Exit GUI Only" converge with the window-close behavior instead
of being a separate, less-honest path to the same background-running state.

## Tray now actually says what's running

The tray icon's tooltip was a static string (`"MystTiq — Palworld Server Manager"`) regardless of
state — even once the icon reliably meant "check here," it didn't say anything useful once you did.
Added a lightweight 5-second `DispatcherTimer` in `App.axaml.cs` (`UpdateTrayStatus()`) that reads
`viewModel.Tabs.Where(t => t.ServerIsRunning)` and sets the tooltip to name what's actually running
("MystTiq — idle, nothing running" / "MystTiq — running: Default Server" / "MystTiq — 2 servers
running: Default Server, second-local"). 5 seconds matches this app's existing background-tab
polling cadence closely enough that the tray is never far behind what the tabs themselves would show.

## Headless logging continuity (confirmed, not changed)

Separately asked to confirm logging continues in headless mode. This was already true by
architecture, not something this version needed to add: console capture
(`HeadlessConsoleLogWriter`, `WindowsServerLifecycleService`'s stdout/stderr redirection, and
v0.7.72.0's native console-write hook) all run entirely inside `mysttiq-server.exe`, the headless
management host — a separate OS process from `MystTiq.Desktop.exe`. `ExitGui_OnClick` never called
`StopOwnedSidecarAsync()` even before this version; only Safe/Force Exit do. So a Desktop-owned
sidecar already kept capturing logs for any server it was managing regardless of GUI state, and this
version's fix makes that state additionally *visible* (tray icon + tooltip) rather than changing the
underlying guarantee.

## Not attempted this version

- No change to what counts as "running" (`TabSession.ServerIsRunning`, unchanged) — a real PalServer
  process running but not currently open in any tab still isn't reflected by the tray, the same
  known scope boundary `MainWindow_Closing`'s own check already has.
- No GUI click-testing was possible in this environment (no GUI-automation capability, a disclosed
  limitation consistent with the rest of this project's session history) — verified by code review
  and a clean build only; a live click-through of the tray menu is still owed.
