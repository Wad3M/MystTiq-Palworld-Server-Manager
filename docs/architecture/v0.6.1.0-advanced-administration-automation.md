# v0.6.1.0 Advanced Administration, Automation & Analytics Platform

## Problem

Before this pass, MystTiq had zero periodic/background execution — every service was purely request-driven, so nothing scheduled ever ran unless a Desktop client happened to be polling. Authentication was a single shared bearer token with exactly one implicit "full access" role and no concept of a user or a scoped grant. Backups were a flat list of `.zip` files with no distinction between a one-off manual copy and a routine scheduled one, so a retention cleanup could just as easily prune something the admin meant to keep forever. Analytics stopped at an in-memory CPU/RAM history graph — no alerting, no prediction. And the manual server start/stop/restart routes never touched the `OperationCoordinator` introduced in v0.6.0.0 at all, so a restart could race an in-flight World Transaction/Guild/Base Apply undetected.

## Automation engine

New `MystTiq.Core/Automation/`: `AutomationRuleId`, `AutomationTrigger` (`DailyTime` with time-of-day/day-mask, or `Interval`, both with optional jitter), `AutomationCondition` (`RequireServerRunning`/`RequireServerStopped`, checked at due-time against `IServerLifecycleService.GetStatusAsync()` — failing records `Skipped`, not `Failed`), `AutomationAction` (`CreateBackup`/`StartServer`/`StopServer`/`RestartServer`/`SendNotification`/`SendRconCommand`), `AutomationRule`, `AutomationRunRecord` (`Scheduled`/`Running`/`Completed`/`Failed`/`Missed`/`Skipped`/`Cancelled`).

`HeadlessAutomationService` is the one and only background loop in the app: a `PeriodicTimer` on a 15-second tick, started from `LocalManagementApiHost.StartAsync` and torn down in `StopAsync`/`DisposeAsync` via a linked `CancellationTokenSource`. Each tick finds due rules, dispatches their execution onto background tasks, and reschedules `NextDueUtc` immediately (so a still-running rule isn't re-triggered on the next tick). A rule more than `MissedGraceSeconds` overdue (the host was asleep) records `Missed` and reschedules from now rather than firing very late. Rules and run history (capped ~500) persist to `ManagerRuntimeRoot/automation/rules.json` and `.../runs.json`, the same atomic-write pattern every other runtime-state file in this app uses.

`StopServer`/`RestartServer` actions with `WarningCountdownSecondsBeforeAction` set broadcast an RCON message at each configured offset (substituting `{seconds}`) before acquiring the lifecycle lock — the same thing a human admin would do before restarting a populated server.

## The lifecycle/coordinator gap, found and fixed

`LocalManagementApiHost`'s manual `/api/v1/server/start|stop|restart|force-stop` routes previously guarded themselves with a private `SemaphoreSlim` field only — never the `OperationCoordinator` introduced in v0.6.0.0. That meant a restart could run concurrently with an in-flight World Transaction/Guild/Base Apply, which all require the server to already be stopped for their *entire* duration but never re-check that once running.

Fix: a new resource key `"lifecycle"`, distinct from `"world-mutation"`. `StopServer`/force-stop acquire `["lifecycle"]` only (stopping never conflicts with a mutation that requires the server already stopped). `StartServer`/`RestartServer` acquire `["lifecycle", "world-mutation"]` together, so `BeginAsync` correctly rejects them while a world-mutation is in flight. The three manual HTTP routes were retrofitted onto the same mechanism (`LocalManagementApiHost.RunLifecycleActionAsync` now takes a coordinator + resource-key list and maps `BeginAsync`'s `InvalidOperationException` to `409 Conflict`, the same catch-and-convert pattern `HeadlessWorldTransactionService.ApplyCoreAsync` already used), and the local semaphore was removed entirely rather than kept alongside the coordinator as redundant overlapping concurrency control.

Automation's `StartServer`/`StopServer`/`RestartServer` actions go through the identical coordinator path, so a scheduled restart is subject to the same cross-feature safety as a manual one.

## Backup classes

`BackupClass { Manual, Scheduled, Emergency, Safety }` on `HeadlessBackupService`, persisted via a `classification.json` manifest under the service's existing state root — the same shape as its pre-existing `verification.json`, not filename encoding (would break `ResolveManagedBackup`'s strict prefix/suffix path-safety check) and not per-file sidecars (easy for an admin to detach when manually copying a `.zip` elsewhere). Unclassified/legacy backups default to `Manual`, the most-protected class, so nothing pre-existing silently becomes prune-eligible. `HeadlessBackupRetentionRequest.IncludeClasses` defaults to `{Scheduled}` only — the actual mechanism that protects Manual/Emergency/Safety backups from routine pruning: the retention tool literally can't see them unless an admin opts a class in. Pre-restore and pre-transaction safety copies (the four existing `backups.CreateAsync` call sites inside `HeadlessWorldTransactionService`/`HeadlessGuildOwnershipService`/`HeadlessBaseOwnershipService`) now classify as `Safety`; the manual "Create Backup" button classifies as `Manual`; automation's `CreateBackup` action classifies as `Scheduled`.

## RBAC (minimal, backward-compatible by construction)

`MystTiq.Core/Security/`: `MystTiqRole { Viewer, Operator, Admin, Owner }` (an ordered enum so `<` comparisons gate correctly), `MystTiqPrincipal` (with an optional `ExpiresUtc` for a temporary guest grant), and `MystTiqPrincipal.LegacyOwner` — the singleton the existing shared bearer token resolves to. `HeadlessRbacService` persists additional named principals to `security/principals.json`, storing only a SHA-256 hash of each token, never plaintext; `CreatePrincipal` returns the plaintext exactly once, the same convention the existing `api-token-create` CLI command already uses.

**The critical invariant**: a request whose bearer token matches the existing `Api.Authentication.TokenFile` value resolves to `LegacyOwner` (full access) *before* the RBAC principal store is even consulted, and when `Api.Authentication.Enabled` is `false` (today's default) every request resolves to `LegacyOwner` unconditionally. Every existing zero-config deployment is completely unaffected by this feature's addition.

Enforcement is a `RequireRole(MystTiqRole minimum)` extension on `RouteHandlerBuilder` — a Minimal API `IEndpointFilter`, not `[Authorize]`/ASP.NET policy DI (this app has neither set up, and didn't need to gain them for this). The auth middleware stashes the resolved principal on `HttpContext.Items` after authenticating; `RequireRole` reads it and returns `403` if the principal's role is below the minimum. Gated today: lifecycle mutation routes and backup mutation routes at `Operator`; world/guild/base Apply, config writes, automation rule CRUD, and backup reclassification at `Admin`; principal create/revoke at `Owner` only. A lightweight in-memory `HeadlessAuthAbuseGuardService` locks out a remote IP for 15 minutes after 8 failed attempts in 5 minutes, logging through the existing activity/audit sink rather than a new one.

## Analytics — Alert Center, disk-space prediction, gap markers

`HeadlessAlertCenterService` evaluates on the automation loop's existing tick (self-throttled to ~60s internally — no second timer), reading from `HeadlessHistoricalMetricsService.Snapshot()`'s existing samples: `HighCpuSustained`/`HighMemorySustained` (average over the last hour vs. threshold), `LowDiskSpace` (`DriveInfo` on the backup volume), and `DiskSpaceExhaustionPredicted` — a real linear projection of world/backup byte growth over the last 7 days of samples, yielding `daysRemaining`. On a threshold crossing past its cooldown, it calls the one new public method added to `HeadlessNotificationService`: `Create(severity, title, message, pinned)`, which is the entire integration surface both the Alert Center and automation's `SendNotification` action need — no parallel notification pipeline.

`HeadlessHistoricalMetricsService.Snapshot()` also now detects sample gaps wider than 3× the ~50-second minimum sample interval, and uptime resets (restarts), returning `Gaps`/`RestartMarkers` — so a Desktop history chart no longer draws a misleading straight line across an offline period.

## Notification routing (a real slice, not the full matrix)

`HeadlessNotificationRoutingService`: `NotificationChannel { Desktop, Webhook, Discord, Email }`. `Webhook` is actually implemented — POSTs `{severity, title, message, createdUtc}` to a configured URL, retries once, logs failures. `Discord`/`Email` are typed stubs that log "channel not implemented" rather than silently dropping, so the schema is future-proofed without pretending they work. `NotificationTemplate` (`{placeholder}` substitution) is consumed by the automation `SendNotification` action when `NotificationTemplateId` is set — a real, load-bearing consumer, not decorative schema.

## Advanced administration (deliberately small)

One concrete addition to the already-mature `HeadlessPlayerMetadataService`: `PlayerFlag { None, Watchlisted, Banned, Trusted }` alongside its existing Notes/Warnings — data/annotation only in this pass, not auto-enforced against any live provider hook.

## Desktop

Three new nav pages under System — Automation, Alert Center, Security — following the exact existing page/DTO/API-client shape (`AutomationDtos.cs`/`RbacDtos.cs`/`AlertCenterDtos.cs`/`NotificationRoutingDtos.cs`, ~25 new `IMystTiqApiClient` methods). Backup classes and notification routing extend the existing Backups/Notifications pages rather than adding more nav entries. `WhoAmI` drives `CanManageAdmin`/`CanManagePrincipals` view-model properties that disable buttons the current principal's role can't use — the visible client-side payoff of RBAC.

## Explicit deferred list

- **Automation**: event-based triggers (on-crash, on-join/leave — nothing in the codebase emits these events yet; needs the Provider Framework in v0.6.5.0 first); webhook/MOD/update action types beyond what shipped; cross-rule dependencies; run state surviving a process crash mid-execution; fleet-awareness (single `ServerProfileId.Default` only — correctly deferred to v0.6.2.0).
- **RBAC**: per-server permission scoping (the roadmap itself schedules this under v0.6.2.0, once servers-plural exist); persisted/distributed rate-limit state; SSO/OAuth; permission bits finer than the 4-role hierarchy; token rotation UI (create-new + revoke-old only in this pass).
- **Notification routing**: real Discord/Email dispatch; per-channel-per-severity routing matrix; template versioning.
- **Analytics**: tiered/downsampled long-term retention beyond the existing flat 30-day policy; anomaly detection beyond fixed thresholds; a separate alert-acknowledgment workflow (fired alerts are just notifications — existing read/pin/dismiss covers it).
- **Backup classes**: a per-class retention *schedule* editor UI (still one keep-latest/max-age preview-apply flow, now filterable by class); cross-server sync.
- **Advanced administration**: the typed RCON command catalog/explorer (owned by v0.6.5.0's Provider Framework); `PlayerFlag` *enforcement* (no live provider hook yet); bulk guild disband/kick-all.
