# v0.7.48.0 — Central Theme System Completion, Foundation Pass

## Goal

A direct live bug report, jumped ahead of the roadmap queue at the user's explicit request: *"we
need to fix the different themes. First we need to have a central place where a variable can be
changed that sets the theme colour so that the background and buttons all change to that setting.
Right now it looks like some of it changes but not all. Same with the light. When switching to
light mode, text colour may need to change, background colours and images need to change. All of
that should be centrally managed."*

A small, unrelated fix was folded in first, per direct request: Update Center's UE4SS row was
reading a stale GitHub tag, following v0.7.47.0's own discovery that the fork changed release
strategy. Fixed to always fetch the full release list and pick the most recently published one.

## Investigation: does a central mechanism already exist?

Yes. `Services/ThemeCatalog.cs` defines every themeable color for every (accent theme x
Dark/Light variant) combination. `Services/ThemeApplier.cs`'s `Apply(accentTheme, variant)` writes
every one of those values directly onto `Application.Current.Resources`, and every XAML consumer
already binds through `{DynamicResource}`, so the whole UI re-flows live with no restart. This is
called unconditionally on every app start (`App.axaml.cs`) and whenever the user changes the
theme picker (`MainWindowViewModel.cs`). The mechanism itself was never the bug.

## Investigation: what's actually hardcoded

A full read of both `MainWindow.axaml` (2636 lines) and `Styles/DesignSystem.axaml` (1389 lines)
found:

- **26 hardcoded hex colors directly in `MainWindow.axaml`** — borders, card backgrounds, status
  badges, table headers, dividers, none touching `ThemeCatalog` at all.
- **~300 hardcoded hex colors in `DesignSystem.axaml`** — far more than `ThemeCatalog`'s own header
  comment implied ("the many smaller decorative BorderBrush/BoxShadow/Effect colors... secondary
  hover/glow accents rather than primary surfaces").

## Real finding that reframed the scope

Most of DesignSystem.axaml's ~300 colors are not arbitrary one-offs. They're the "card flare"
per-page accent system (`accentHome`/`accentServer`/`accentWorld`/`accentBackups`/`accentMods`/
`accentTools`/`accentSystem`, built in v0.7.4.0) and status glows
(`glowGreen`/`glowRed`/`glowAmber`/`glowPurple`/`glowDarkGreen`/`glowCyan`/`glowViolet`), and their
BoxShadow/BorderBrush literals already, by construction, duplicate `ThemeCatalog`'s own Accent/
Semantic hex values — e.g. `accentServer`'s glow color is literally `#35D5E8`, this catalog's own
Cyan, hardcoded instead of referenced. Confirmed by exact hex comparison against every one of
`ThemeCatalog.Accent`/`Semantic`'s values before writing any derivation code.

Also confirmed via a 29-of-30 exact-match count: nearly every `DropShadowEffect.Color` literal
scattered through button/tab/nav hover states across the file matches one of the same 8 base
colors (`#35B9FF` for the general interactive glow, plus the 7 Accent/Semantic colors) — these are
systematic reuses of a small color set, not independent design decisions, just hardcoded
per-instance instead of referenced.

## Scope decision (asked and answered directly)

Two questions were put to the user before writing derivation code:

1. **Should per-page accent tints shift with the chosen accent theme, or stay fixed?** Chosen:
   shift with the theme — the larger of the two options, meaning Server/World/Mods/etc.'s own
   identity colors now re-tint along with everything else when Emerald/Crimson/Violet is picked,
   not just Dark/Light.
2. **What did "images" mean?** Confirmed: both the nav pane icons (56x56 pre-rendered glossy
   sphere PNGs under `Assets/Icons/`, no vector source found) and background/atmosphere art
   (`dashboard-atmosphere-v3.png`, `server-card-art.png`, `world-card-art.png`,
   `mysttiq-wordmark-v5.png`). These are raster images with baked-in gradients/shadows/highlights,
   not simple tintable monochrome icons — real theme-awareness for them needs asset regeneration
   or runtime hue-shifting, a genuinely different kind of work than color-token plumbing. Disclosed
   as out of scope for this version rather than attempted.

## A real fix to a previously-disclosed "hard limitation"

`ThemeCatalog`'s own comment stated BoxShadow's shorthand-string syntax "cannot bind to
DynamicResource at all (a hard Avalonia limitation, not an oversight)," and that decorative glow
colors would "stay at their current dark-tuned values in every theme/variant." Researched directly
before accepting this as permanent:

- The shorthand-string limitation is real and confirmed via Avalonia's own GitHub discussions:
  embedding a `{DynamicResource}` reference *inside* the `"0 0 18 0 #hex, ..."` string syntax
  genuinely does not work, because that string is parsed by a type converter, not markup-extension-
  aware.
- **But binding the *entire* `BoxShadow` attribute to a resource of type `BoxShadows` is a
  different mechanism and works fine.** Verified by writing real `Avalonia.Media.BoxShadows`
  objects into `Application.Resources` from C# (`ThemeApplier`, using the confirmed
  `BoxShadows(BoxShadow, BoxShadow[])` constructor) and referencing them via
  `BoxShadow="{DynamicResource X}"` in XAML — this compiled and is live in this version.
- `DropShadowEffect.Color` was never actually blocked by this limitation either — it's a normal
  bindable property on a normal XAML object (`<DropShadowEffect Color="..."/>`), not the restricted
  shorthand string. The two had been conflated in the original disclosure.

## Architecture: a formula-driven derivation engine, not hand-authored values

With ~300 individual hand-tuned colors x 4 themes x 2 variants, and no way to render or screenshot
the native Avalonia app in this environment to visually verify results, hand-authoring every
combination was judged too risky (high chance of shipping something inconsistent or worse-looking
than today, with no way to catch it before the user sees it). Built a systematic engine instead:

- **`Services/ThemeColorMath.cs`** (new): `Blend`, `Lighten`, `Darken`, `WithAlpha` — simple linear
  RGB blending. Deliberately not perceptual-color-space math; consistency across ~300 derived
  values matters more here than perceptual accuracy for a handful of them, and the app's existing
  hand-authored palette shows no evidence of perceptual-space tuning either.
- **`ThemeCatalog.DerivedColorNames` + `ResolveDerivedBaseColor`**: 11 named base colors — the 5
  existing Accent slots (Blue/Cyan/Violet/Magenta/Orange), the 3 existing Semantic colors
  (Green/Amber/Red), "Purple" (confirmed an exact alias of Violet — identical hex, `#A96DFF`,
  everywhere DesignSystem.axaml uses either name), and two with no natural existing slot:
  "DarkGreen" (`Darken(Green, 0.32)`, used by a couple of "protected/settled" status cards) and
  "Neutral" (`Blend(Border, Muted, 0.5)`, a desaturated blue-gray "no strong opinion" tint).
- **`ThemeApplier.Apply()`** now also computes, per base color x theme x variant, after writing the
  existing dictionaries:
  - `{Name}AccentBorderBrush` — `Blend(base, Structural.Border, 0.55)`, a muted passive border
    tint (used by the accentXxx card-flare borders, ribbon context borders, status badges).
  - `{Name}AccentHighlightBrush` — `Lighten(base, 0.5)`, a bright hover/focus/checked highlight.
    **Confirmed these need separate derivations, not one resource reused for both purposes**: the
    app's existing bright literals (`#91E4FF`, `#75C8FF`, `#72D0FF`) are meaningfully lighter than
    the muted border tint the passive accent system uses — conflating them in an early draft of
    this change produced a visibly wrong (too-dull) hover color, caught and fixed before shipping.
  - `{Name}AccentGlowShadowLow` / `{Name}AccentGlowShadowHigh` — two `BoxShadows` strengths (glow
    alpha `0x30`/`0x5A`), matching the app's own existing "passive decoration vs. active status
    signal" distinction between the accentXxx and glowXxx class families.
  - `Card{Name}Gradient` — a 3-stop tinted glass-card `LinearGradientBrush`, dark-blended toward
    black for Dark mode and light-blended toward white for Light mode, mirroring
    `ThemeCatalog.Structural`'s own existing Card/CardStrong Dark-vs-Light approach exactly, just
    tinted by the family's base color instead of neutral gray. **Overwrites the exact same resource
    keys** `DesignSystem.axaml` already statically declares (`CardGreenGradient`, `CardCyanGradient`,
    etc.) — confirmed via a clean build that Application-level resource overrides win over
    StyleInclude-declared ones, the same precedence every other resource this system already
    relies on, so no existing XAML reference needed to change.

## Disclosed exception: three terminal-style console views

`MainWindow.axaml`'s Dashboard mini-console preview, the RCON output panel, and the full Console
page's log view (lines using `Background="#07110A"`/`#0A1118"`, `BorderBrush="#214C2A"`,
monospace font) were deliberately left unchanged rather than converted. These are terminal-style
log displays; keeping them dark/green regardless of the app's overall theme matches a common,
widely-accepted convention (many IDEs and terminals keep a dark terminal panel even under a light
UI theme). Changing the background to a light tone while the log text's own color
(`{DynamicResource GreenBrush}`) is tuned for a dark backdrop risked a real, unverifiable-in-this-
environment contrast regression — disclosed as an intentional choice, not an oversight.

## Explicitly deferred, disclosed rather than silently dropped

- **~240 hardcoded colors remain in `DesignSystem.axaml`** after this pass, overwhelmingly the
  elaborate multi-stop translucent "glass" gradients: `GlassOptionHoverGradient`, the
  `PrimaryGlass*`/`SuccessGlass*`/`DangerGlass*` families, the four `Nav*Glass*Gradient` variants,
  `DashboardGlassGradient`, the `Context*Gradient` family (5), the `*GraphFill` family (5), the
  `Backup*Gradient` family (4), plus smaller one-offs (`worldTabHeader`, `modRow`, `dataRow`,
  `prototypeRow`, `disableAction`/`updateAction` buttons — the last few appear to be legacy
  prototype-page remnants, not confirmed still reachable from current navigation). These behave
  differently over a light vs. dark background than a simple lighten/darken swap can safely
  reproduce (translucent glass over white reads very differently than translucent glass over
  black) — real design judgment this session cannot verify visually. Tracked as its own follow-up
  version rather than risking a blind mass conversion of ~240 more values.
- **Nav pane icons and background/atmosphere art** — confirmed as part of what "images" meant, but
  out of scope for this pass: real theme-awareness needs either regenerated asset variants (no
  vector source exists to re-render from) or runtime hue-shifting (a custom rendering-pipeline
  effort, not evaluated in detail this version). Disclosed as deferred, not attempted.

## Real-world consequence, disclosed

`ThemeApplier.Apply()` runs unconditionally on every app start. The newly-computed derived
resources therefore replace today's hand-tuned static values immediately, for every user,
including the Default theme — a deliberate, disclosed deviation from `ThemeCatalog`'s own stated
"Default+Dark stays byte-for-byte identical" principle, for the specific ~11 base colors this
version touches. Hand-preserving exact byte-identical values for Default+Dark while still deriving
the other 7 (theme x variant) combinations correctly would have required reverse-engineering the
original hand-tuning with more precision than is practical without visual verification. The
computed values are designed to closely match the original spirit (same hue family, same
dark-tinted-glass structure) — any visual difference should be minor, but this is disclosed rather
than silently glossed over.
