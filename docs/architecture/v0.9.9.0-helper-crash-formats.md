# v0.9.9.0 — one helper, crash causes and local formats

The remaining roadmap items that needed no one but the code, and two bugs found on the way.

## The desktop's local helper

The desktop talks to a local headless service (the "helper", `mysttiq-server api-run --desktop-sidecar`). Two problems,
both found on 2026-09-29 while installing on the Linux VM, whose port 8213 is held by an older installed service:

- **Helpers piled up.** When the configured port is held by a MystTiq of another version, the desktop starts its own
  helper on a free port. It kept no record of that, so the next call, and every later app start, found the port held
  again and started one more. Two helpers ran on the VM within a minute, both supervising the same servers from the
  same configuration.
- **Restarting the helper took game servers down.** `StopOwnedSidecarAsync` killed the helper's whole process tree. A
  game server the helper started is its child, so the new-server wizard's restart (to bring a new profile online)
  ended every running server, and crash recovery then restarted them.

Now the desktop records the helper it starts (`desktop-sidecar.json` in its local runtime folder: process id, loopback
endpoint, executable) and reuses it while it answers with this version and the expected server. A recorded helper that
answers but cannot be used (an older version after an upgrade, or one that does not know a newly added server) is the
desktop's own, so it is stopped and replaced rather than left beside a new one. Only the helper process is stopped; game
servers keep running and the next helper adopts them (as seen all through 2026-09-28, when the clone server ran for
hours across helper restarts). A record that does not name a loopback address is ignored. A MystTiq the desktop did
not start is still never stopped; it is reported, as before.

One more case, from the VM check on 2026-09-30. The installed service there has TLS on, so it does not answer the
desktop's plain-HTTP health probe, and the port read as free. The desktop then started its helper on that port; the
helper could not bind it and exited, the connection timed out, and the record named a dead process. A port that
accepts a TCP connection now counts as occupied whatever the probe says (`PortAcceptsConnections`), so the helper
goes to a free port, and a helper that exited before answering is not recorded.

## A server that stops when a player joins

On 2026-09-28 PalDefender v1.8.3 on game v1.0.5 took the server down about 40 s after each join. PalDefender writes one
log per server start; that session's log simply ends on `steam_… connected to the server.`, where a healthy session goes
on to the login, the logout and `REST API stopped`. `ExitAfterJoinDetector` reads the newest session logs (last 7 days)
and reports a session whose last line is a player connecting or logging in, when the session ended within 5 minutes of
it: the next session's log began, or, for the newest log, the server is not running now. The player's address is left
out of the evidence. The new `exit-after-join` signature gives the cause and fixes. It comes from that one real case,
as the roadmap requires for crash signatures.

## UE4SS compared by content

Without a recorded install, UE4SS read "check manually". File dates cannot help: they are when the files were extracted,
not when UE4SS was built. The installed `UE4SS.dll` (the `ue4ss` folder first) is now hashed and compared with the
`UE4SS.dll` inside each download of the three newest releases (hashed once per asset and cached in
`ue4ss-release-hashes.json`). An identical file names its release: up to date, or update available. Live on the clone:
the four downloads of the two newest releases were hashed and the installed file matches none, so it still reads
"check manually", now saying why.

## Alerts for UE4SS and MOD updates

Requested on 2026-09-29: an alert when there is a new server version (v0.9.8.0), and also for UE4SS and for installed
MODs with updates. The Alert Center's out-of-date rule now tracks two more episodes:

- `ue4ss-outdated`, from the Update Center's UE4SS result. The result is cached (`PeekUe4ssStatus`) and refreshed in the
  background at most every six hours, or whenever the Update Center checks, so the once-a-minute evaluation never
  calls GitHub. Only "update available" and "up to date" decide; "check manually", "unreachable" and "not
  checked yet" leave the episode as it is.
- `mods-outdated`, from the MOD inventory's own per-MOD update flag (a local comparison, no network). The alert names
  up to five MODs and counts the rest.

Both use the same episode rules as every alert: one alert, reminders, one "Resolved" notice.

## The Doctor's port fix

`configuration-game-port` (v0.9.6.0) only reported a server that binds one port and advertises another. Fix now sets
PublicPort to the bound port (an ini change with a backup, no MystTiq restart). Moving the server to the advertised port
instead still means changing `-port=`, which applies when MystTiq restarts.

## Numbers, dates and times per language

Nothing set a culture, so formats followed the operating system's language whatever was chosen in MystTiq.
`DisplayCulture` now applies the chosen language's number and date formats on the system's own culture: text comparison
and casing stay as they were (a full switch to Turkish changes how "i" is cased, which can break comparisons of names
and ids). English keeps the system's formats. An audit found no culture-dependent parsing of decimals and no decimals
written into request URLs or commands; ISO-style dates written by the code (`yyyy-MM-dd`) stay as they are.
