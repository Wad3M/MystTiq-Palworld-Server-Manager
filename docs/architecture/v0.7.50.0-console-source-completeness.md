# v0.7.50.0 — Console Source Completeness (UE4SS.log)

## Goal

Not from the original findings log — found while scoping v0.7.51.0+ (Native Console Capture, the
native DLL-proxy project). Before starting that much larger, riskier project, its own premise was
worth checking against real data first: is the Console page's existing `GetLogTail` mechanism
actually missing a real source, or does the gap genuinely require native code?

## Investigation

`HeadlessMonitoringService.ResolveConsoleSources` has included a `"Pal.log"` source since early in
this session, with a code comment claiming it's "where PalServer/UE4SS write this exact kind of
native output." That claim was inherited from earlier investigation notes and never directly
verified against a real server's actual files.

Checked directly against this machine's real, actively-modded local Palworld install
(`C:\GameServers\Palworld\Server` — real production data per project memory, not a test fixture):

```
find "C:\GameServers\Palworld\Server\Pal\Saved\Logs" -maxdepth 1 -iname "*.log"
```

Result: only `MystTiq-PalServer-Console.log` (MystTiq's own file) — **no `Pal.log`**. A broader
recursive search of the entire server install tree for any non-MystTiq `.log` file found only
`PalDefender`'s own logs (a separate anti-cheat mod, unrelated to the base engine) and
`ue4ss/UE4SS.log`. `Pal.log` does not exist anywhere in this real install.

This is consistent with, and reinforces, the v0.7.46.0/v0.7.47.0 finding that `-ABSLOG` (the
standard Unreal file-logging flag) also produces no file on this server — Palworld's Windows
dedicated server build appears to have no working text-log output for the base engine at all on
this real install, not just a differently-named one.

`ue4ss/UE4SS.log`, by contrast, is real and substantial — 1947 lines from the current session alone:

```
[2026-09-10 06:29:23.7305354] [Lua] [AdminCommands] Registered command: goto
...
[2026-09-10 06:29:24.7538459] [Lua] [AdminCommands] Hooks registered
```

`ResolveConsoleSources` never looked for this file at all.

## Fix

Added `ue4ss/UE4SS.log` (`paths.Ue4ssRoot/UE4SS.log`) and its legacy-layout equivalent
(`paths.RuntimeBinaryRoot/UE4SS.log`) to `ResolveConsoleSources`'s candidate list, using the same
`Add()` dedup-by-full-path helper the existing sources already use. `Pal.log` was left in the source
list rather than removed — it costs nothing to keep checking for it (a future Palworld build or a
different install layout could still produce it), and removing a source that might exist elsewhere
isn't this version's call to make.

## Live verification (read-only, against the real install)

A throwaway console harness (not part of the shipped codebase, deleted after use) constructed
`HeadlessMonitoringService` directly, with a fake `IServerPathProfile` whose `RuntimeBinaryRoot`/
`Ue4ssRoot`/`LogsRoot` pointed at the **real** server directory — genuine read-only file reads
against real production data — while `ManagerRuntimeRoot` was redirected to an isolated temp
directory, so nothing wrote into or touched the live production MystTiq instance's own runtime
state (per this project's standing "never bind a test instance to the production port/state"
convention, documented in project memory).

Result: `GetLogTail(200)` returned `Available: true`, with `FileName` reporting all four merged
sources including `UE4SS.log`, and real UE4SS content (hook registrations, `[AdminCommands]` lines)
present in the returned lines.

**A second, larger finding surfaced as a side effect of this same verification, not from new code**:
the tail's last 20 lines were dominated by the already-existing "AdminCommands server log" source
(unchanged by this fix), and they contained genuine player connect/disconnect narration with real
names and timestamps:

```
[2026-08-27 13:22:31] Wade [67D8D355-...] has connected.
[2026-08-27 13:23:13] Wade [67D8D355-...] has disconnected.
```

This is exactly the kind of content the original v0.7.46.0 bug report ("console doesn't capture
events from Palworld server") was asking to see. It was always technically reachable through the
existing source list — this version didn't add it — but was easy to overlook when the console
otherwise looked thin without UE4SS.log's much larger volume of content alongside it.

## What shipped

- `HeadlessMonitoringService.cs`: two new candidate paths added to `ResolveConsoleSources`.

No Desktop changes were needed — the Console page already consumes `GetLogTail` via `/logs/tail`
and the aggregate `/status` route unchanged; this is a pure server-side source-list fix that the
existing UI picks up automatically.

## What this does NOT fix (disclosed, unchanged)

- Raw Palworld/Unreal engine `Print`/`UE_LOG`-level output (non-UE4SS, e.g. hypothetical base-engine
  warnings or errors) still has no accessible text-log path on this real install, confirmed again by
  this version's own investigation. That gap is exactly what v0.7.51.0+'s native DLL proxy project
  targets — this version does not reduce or change the scope of that work, it only makes sure the
  much smaller, safer fix available today ships first.
- `UE4SS.log` only exists once UE4SS has actually started (it's UE4SS's own log, not Palworld's) —
  a server with no UE4SS installed, or one where UE4SS hasn't started yet, still won't show this
  source; `Available`/the source list correctly reflect that (the file simply isn't found and is
  skipped, same as every other optional source already handled this way).
