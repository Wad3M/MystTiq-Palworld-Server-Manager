# v0.7.60.0 — Port Conflict Prevention & UE4SS Version Tracking

## Goal

Two direct requests, arriving in the same message while continuing to investigate the still-open
PalServer launch freeze: (1) prevent launching servers on a port that's already in use, with a
clear error instead of a silent hang; (2) fix UE4SS version detection, which had told the user
their install was current when it was not.

## Port Conflict Prevention

### The gap, found directly while investigating the freeze

`WindowsServerLifecycleService.StartAsync`'s only pre-launch guard was:

```csharp
if (FindManagedServerProcesses().Count > 0)
    return Failure(HeadlessExitCode.AlreadyRunning, ...);
```

This only catches a duplicate start of the *same profile's own already-tracked process*. It says
nothing about: another fleet profile configured for the same port, an unmanaged process outside
MystTiq's own tracking, or a leftover process from an unclean stop that hasn't fully released the
port yet. In any of those cases, `StartAsync` would launch PalServer anyway — and the result isn't
a clean failure. PalServer starts, spins up its full engine thread pool (confirmed via live thread
inspection during this session's own freeze investigation: 46 threads, every one in `Wait` state),
and then sits forever unable to bind the game port. That is *exactly* the symptom this session spent
many hours investigating as an unexplained "freeze" — genuinely indistinguishable from one without
deep diagnosis.

### Confirming the fix targets the right mechanism

Before writing the check, traced whether `GetGuardedListeningPorts()` (the existing mechanism
`GetStatusAsync`'s own readiness check already relies on) is actually per-profile-aware, or a
shared, hardcoded default that would silently fail to catch a conflict on a cloned/offset-port
profile. `ServerPlatformProfile.Windows/Linux.GuardedPorts` is indeed a static
`[8211, 8212, 25575]` — but every real construction site (`Program.cs`'s `LifecycleFactory`, used
by `api-run`, and `WindowsServiceRunLifecycleFactory`, used by `service-run`) already appends that
profile's own `GetConfiguredGamePort()` result before constructing the session inspector:

```csharp
var configuredGamePort = new PalworldSettingsConfigurationService(profilePaths).GetConfiguredGamePort();
var guardedPorts = platform.GuardedPorts.Append(configuredGamePort).Distinct().ToArray();
```

So `GetGuardedListeningPorts()` — a real `netstat -ano -p udp` scan filtered against this per-profile
guarded set — is safe to reuse directly for a pre-start conflict check, with no additional wiring
needed.

### The fix

`WindowsServerLifecycleService`/`LinuxServerLifecycleService.StartAsync`, immediately after the
existing `AlreadyRunning` guard:

```csharp
if (sessionInspector.GetGuardedListeningPorts().Contains(expectedGamePort))
    return Failure(HeadlessExitCode.PortConflict, $"UDP port {expectedGamePort} is already in use...");
```

New `HeadlessExitCode.PortConflict = 17`, mapped to HTTP 409 in `LocalManagementApiHost.MapStatusCode`
alongside the existing `AlreadyRunning`/`NotRunning` conflict codes. The message is clear about both
what happened and why: the port is taken, and starting anyway would produce an indistinguishable
hang rather than a clean failure.

### Surfacing to the user

No new UI was built. The Desktop's existing `RunLifecycleAsync`/`LifecycleStatusText`/`Detail`
mechanism already surfaces `result.Message` from any failed lifecycle operation, and that text is
already shown prominently on the Dashboard's SERVER card. A 409 response with a real JSON body
(matching `LifecycleOperationResultDto`'s shape) deserializes normally through the existing client
code path — no special-casing needed for this new exit code to reach the user.

## UE4SS Version Tracking

### The bug, as reported

Update Center could report UE4SS as up to date when it demonstrably was not (the user had just
installed a real, newer release and the app gave no indication anything had changed). Root cause:
`HeadlessModManagementService.DetectUe4ssVersion()` has never had a reliable source for the real
installed version — this fork ships no version marker file (`UE4SS.version`/`version.txt`), and the
installed DLL's own `FileVersionInfo` legitimately comes back as the unstamped literal `"0.0.0.0"`
(already filtered out by v0.7.30.0's own fix, falling through to a generic "Installed — version
metadata unavailable" placeholder). `HeadlessComponentUpdateService.CheckUe4ssAsync` had no way to
compare that placeholder against anything, so it always reported `Status = "CheckManually"` —
correctly honest in its own text ("compare dates/notes manually"), but easy to misread, and
genuinely uninformative regardless of what was actually installed.

### The fix: record what MystTiq itself already knows

The one place a real, trustworthy version identifier genuinely exists is the moment MystTiq's own
`ApplyUe4ssInstallAsync` (v0.7.49.0's real install flow) downloads and applies a specific release
catalog entry — it already knows exactly which `Source`/`TagName` that was. A new small manifest,
`ue4ss-install-manifest.json` under `ManagerRuntimeRoot` (not inside the UE4SS folder itself, so a
manual file copy over the top — bypassing MystTiq's own install flow entirely, exactly how this
project's own real server's UE4SS was actually installed until this session — correctly leaves no
manifest behind rather than silently reporting a stale recorded tag for files MystTiq never touched):

```csharp
internal sealed record Ue4ssInstallManifest(string Source, string TagName, DateTimeOffset InstalledAtUtc);
```

Written by `ApplyUe4ssInstallAsync` on success; deleted by `RollbackUe4ssInstallAsync` (the restored
snapshot could be from any earlier state, not necessarily a tracked release, so the recorded tag
would no longer describe reality after a rollback).

`DetectUe4ssVersion()` now checks this manifest first, returning `"{TagName} ({Source})"` — e.g.
`"2281fa31 (PalworldFork)"` — a real, human-readable, genuinely comparable identifier, ahead of the
existing marker-file/DLL-metadata checks (both left unchanged, still the fallback for installs this
manifest doesn't cover). A new `HeadlessModManagementService.TryGetInstalledUe4ssReleaseTag()`
exposes the raw tag (not the formatted display string) so `CheckUe4ssAsync` can compare it exactly
against the release catalog's own tag, rather than parsing it back out of a display string.

### The comparison itself

`CheckUe4ssAsync`, when a recorded tag exists: an exact, case-insensitive string match against the
latest release's own tag — genuine `Up to date` / `Update available` status, not a guess. When no
manifest exists, unchanged behavior: the same honest `CheckManually` status and message this always
had, now with an added note that reinstalling through MystTiq's own flow enables real comparison
going forward.

## Verification

`dotnet build` on the full solution — clean, 0 warnings/errors (one variable-name collision caught

method scope).

## Known gaps (disclosed)

- **No visual verification possible in this environment**, same standing limitation as every
  version touching the UI this session.
- **The port-conflict check has not been exercised against a genuinely live port conflict** (e.g.,
  two real servers actually racing for the same port) — this machine's own PalServer currently
  can't launch cleanly at all for the separate, still-unresolved reason investigated in v0.7.57.0/
  v0.7.59.0, so a full end-to-end live test of this specific fix wasn't possible this session.
- **The live production server's own UE4SS install manifest doesn't exist yet** — the real install
  performed earlier this session used the Apply flow before this version's manifest-writing code
  existed. Re-running the same install (now on a build that includes this fix) will backfill it.
- Port-conflict prevention here is scoped to the *game* port only, matching `expectedGamePort`'s own
  existing scope in `GetStatusAsync`'s readiness check — not the REST API or RCON ports, which have
  their own separate configuration and aren't part of this specific check.
