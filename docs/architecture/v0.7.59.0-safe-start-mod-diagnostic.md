# v0.7.59.0 — Safe-Start MOD Diagnostic

## Goal

Direct request, arriving mid-investigation of the PalServer launch freeze from v0.7.57.0: search
for whether others report similar crashes, and build an incremental MOD-loading safety feature that
detects and disables a crash-causing MOD automatically.

## Research first, before designing anything

Web research (see `CHANGELOG.md` for the full sourced summary) confirmed two things worth grounding
the design in, rather than guessing:

1. **"Remove mods one by one until the crash stops" is the standard, explicitly-documented
   community troubleshooting technique** for Palworld server crashes — this feature automates a
   real, proven practice, not a novel guess.
2. **Third-party AV false-flagging `PalServer-Win64-Shipping-Cmd.exe` is a widely-reported,
   separate issue**, consistent with this project's own Defender history — and a genuinely new lead
   surfaced too: some reports say PalServer needs the actual Steam client (not just SteamCMD)
   installed and run at least once on the server machine. Given this session's own `steamcmd.exe`
   crash (`STATUS_STACK_OVERFLOW`, independent of Palworld) and that Steam is installed but not
   running on this machine, that's a concrete, separate thing worth the user trying — unrelated to
   this version's own MOD-diagnostic work, noted for the record.

## Scope, confirmed directly before building

Two design questions were put to the user before writing any code:

1. **How should "crash" be judged?** Chosen: both an outright crash AND a startup hang that never
   reaches ready. This matters concretely — a crash-only check would have missed the exact freeze
   this session's own live investigation spent hours on (process alive, near-zero CPU forever, UDP
   port never binds, no crash at all).
2. **What happens to an implicated MOD?** Chosen: auto-disable it and auto-restart without it —
   full automatic recovery, reviewable afterward, not a "flag and wait for confirmation" design.

## A critical design addition, not asked for but necessary

Before writing the bisection loop, considered what would happen running this diagnostic against
*this exact machine's own current environment issue* (a freeze independent of any MOD, already
confirmed by direct testing in v0.7.57.0's own investigation). A naive per-MOD loop would report
every single candidate as "bad" — a wall of false positives, actively misleading. Added a
**baseline sanity check** as Step 0: disable every candidate, attempt one start with none of them.
If that also fails, stop immediately and report "not a MOD problem" rather than burning through
every candidate. This directly formalizes the exact manual test already run this session (disable
the whole UE4SS/PalDefender chain, confirm the freeze persists) as a permanent safety gate.

## Algorithm

1. **Precondition**: server must be stopped (same check `SetEnabledAsync` itself already enforces).
2. **Baseline**: disable every currently-enabled MOD. Attempt one start. If it fails (crash or
   hang), abort — restore every candidate to enabled, report "not a MOD problem," done.
3. **Incremental, cumulative testing**: for each candidate MOD (in inventory order), re-enable it
   *on top of* the already-confirmed-good set (not tested totally alone — real MOD ecosystems have
   dependencies, e.g. shared/core UE4SS libraries other mods rely on; isolated testing would
   produce false failures for anything depending on an earlier-tested MOD). Start. If healthy, stop
   cleanly and keep it enabled; move to the next candidate. If it fails, force-stop, disable just
   that MOD again, record the failure, and continue with the next candidate on top of the same
   still-good set.
4. **Final validation**: one more start with the surviving set, left running on success.
5. **Cancellable**: at any point, cancelling restores every originally-enabled candidate to
   enabled (a cancelled run is inherently incomplete, so it doesn't try to preserve partial
   progress) and stops whatever's running.

## A genuinely new pattern for this codebase: a long-running background job with polled status

Every existing multi-step operation in this codebase (World Transactions, UE4SS Install,
Guild/Base Ownership) follows a bounded preview-then-apply shape — each individual HTTP call
completes within seconds. This diagnostic can legitimately run for many minutes (a full start/stop
cycle per candidate MOD, each bounded by the configured startup timeout). Blocking an HTTP request
for that long is bad API design (client timeouts, zero progress visibility), so this is a real new
shape: `POST /mods/safe-start` kicks off a background `Task.Run` and returns immediately;
`GET /mods/safe-start/status` polls a lock-protected in-memory `SafeStartJob` for live progress;
`POST /mods/safe-start/cancel` signals a `CancellationTokenSource` held by that job.

**Concurrency safety, the part that needed real care**: `RunLifecycleActionAsync` (used by every
existing Start/Stop/Restart route) holds its `IOperationCoordinator` lock for exactly one
synchronous call. That pattern doesn't fit here — if `BeginAsync` released its lock as soon as it
returned (immediately, since it only kicks off a background task), a manual `/server/start` could
race the diagnostic's own start/stop cycles moments later, corrupting the whole test. Instead,
`HeadlessModSafeStartService.BeginAsync` acquires the `["lifecycle", "world-mutation"]`
`OperationHandle` itself and holds it for the *entire* background job — `Complete`/`Fail`/`Dispose`
only happen once `RunAsync` actually finishes, in every exit path (success, cancel, not-mod-related
abort, or an unhandled exception), via a `try/finally` wrapping the whole job.

## Implementation

- **Backend**: `HeadlessModSafeStartService` (new), composing `IServerLifecycleService` (for
  start/stop/status) and the existing `HeadlessModManagementService` (for enable/disable — reused
  unchanged, including its own precondition that the server be stopped before any MOD state
  change). `SafeStartJob`/`SafeStartStatus`/`SafeStartModResult` track progress; `SafeStartJob` is a
  small lock-protected mutable state object, not a database record — status is lost if the headless
  process restarts mid-run, an accepted limitation for a diagnostic tool (see Known gaps).
- **Wiring**: `ServerProfileHost.ModSafeStart`, constructed in `LocalManagementApiHost.Create`
  alongside every other per-profile service, given the fleet-level `IOperationCoordinator` and this
  profile's own `ServerProfileId` (needed to hold the lock across the whole job) plus the
  configured `StartupTimeoutSeconds`/`StopTimeoutSeconds` (reused from `HeadlessConfiguration
  .Lifecycle`, not a separate hardcoded value).
- **Routes**: `POST /mods/safe-start`, `GET /mods/safe-start/status` (404 when nothing has ever
  run for this profile), `POST /mods/safe-start/cancel`.
- **Desktop**: `SafeStartStatusDto`/`SafeStartModResultDto`, three new `IMystTiqApiClient` methods,
  `MainWindowViewModel.ModSafeStartStatus` polled by a dedicated `DispatcherTimer` (3s interval,
  started on a successful Begin, stopped once the status comes back `Completed`) — deliberately
  independent of `IsBusy`, since holding that flag for several minutes would disable unrelated UI
  the whole time. A new card in MOD Library shows live phase text, a progress count, a per-MOD
  pass/fail list as results land, and the final outcome; a "Safe-Start Diagnostic" button sits
  alongside the existing Enable All/Disable All/Repair actions.

## Verification

`dotnet build` on the full solution — clean, 0 warnings/errors.

## Known gaps (disclosed)

- **No visual verification possible in this environment**, same standing limitation as every
  version touching the UI this session.
- **Never run against a real PalServer.** This machine's own production server currently can't
  launch cleanly at all (the unresolved v0.7.57.0 freeze) — running this diagnostic against it
  right now would legitimately trigger its own baseline-failure path ("not a MOD problem"), which
  is the CORRECT behavior given the real environment state, but means the full incremental-testing
  loop itself has not been exercised against a real, healthy server this session.
- **Job state is in-memory only.** If the headless process restarts mid-diagnostic (a crash, a
  manual service restart), the running job's progress and cancellation token are lost — MOD state
  at that point reflects wherever the loop happened to be, not necessarily fully reverted. A
  `mods.txt`/`~mods` full-state snapshot-and-restore (matching `CaptureSnapshot`/`RollbackAsync`'s
  own v0.6.8.0 precedent) would close this gap but wasn't built here — the existing per-mod
  enable/disable calls already leave the on-disk state internally consistent at every step, so this
  is a "loses progress tracking," not a "corrupts MOD state," failure mode.
- **Ordering is inventory order, not dependency-aware.** If MOD B genuinely requires MOD A to be
  present to avoid a crash, and A happens to be tested after B in inventory order, B would be
  (correctly, if narrowly) flagged as bad on its own turn, then never get a chance to be retested
  once A is later confirmed good. A full dependency-aware re-test pass was judged out of scope for
  this version — the cumulative "build up a known-good set" design already covers the common case
  (a mod that depends on something tested earlier in the list) without it.
