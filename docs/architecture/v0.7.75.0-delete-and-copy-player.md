# v0.7.75.0 — Delete Player Completely / Copy Player

## What this ships

Two new destructive, byte-level player-save operations, direct user request following the same
session's investigation of a "right-click looks broken" report (that finding: Kick/Ban were
correctly wired all along, just correctly disabled with no visible disabled-state styling — fixed
separately with a real `MenuItem:disabled` style, since none existed anywhere in this app).

### Delete Player Completely

`HeadlessPlayerDeletionService`: deletes a player's own save file
(`Players/{PlayerUId}.sav`), then — as a genuinely separate, independent operation — reuses
`HeadlessGuildOwnershipService`'s own already-proven `RemoveBrokenMember` operation to clean up
their now-dangling guild reference, if any, and clears their `HeadlessPlayerRegistryService`
history. Deliberately two independent operations rather than one combined transaction: nesting a
second full Preview/Apply lifecycle inside this one's own held `IOperationCoordinator` lock would
deadlock against a non-reentrant coordinator (`"world-mutation"` resource key). Base ownership is
deliberately not special-cased — a base whose owning guild becomes ownerless as a side effect
already surfaces through this codebase's existing orphan-detection/Base Recovery flow.

### Copy Player

`HeadlessPlayerCopyService`: clones one player's build/progress onto another player's own save,
while the destination keeps its own identity. **Real investigation before writing any code**:
decoded a real production player's `.sav` file (read-only, via the exact same generic PlM/Oodle
converter this codebase already uses for `Level.sav` — confirmed it works unmodified on a
per-player save, the first time anything in this codebase has decoded one) and found a clean split
at `properties.SaveData.value`:

- **Copied** from source onto destination: `PlayerCharacterMakeData` (appearance), `InventoryInfo`,
  `UnlockedRecipeTechnologyNames`, `RecordData`, `SkinInventoryInfo`, `OrderedQuestArray_FullRelease`.
- **Left as the destination's own**, deliberately not overwritten: `PlayerUId`, `IndividualId`,
  `PlayerPlatform`, `LastOnlineDateTime` (copying these would make two save records claim the same
  identity), `LastTransform` (destination shouldn't teleport to source's last position), and
  `OtomoCharacterContainerId`/`PalStorageContainerId` (references to separate pal-party/storage
  container records likely stored elsewhere — blindly copying just the ID reference risked both
  players pointing at the same container with no way to verify that's safe).
- **Deliberately deferred**: the player's own in-world "character body" (`Level`, `Talent_*`,
  `Rank`) lives in `Level.sav`'s `CharacterSaveParameterMap` — a different file and decode target,
  per `HeadlessPalEditService` — and pal-party/storage contents themselves. A real scope decision
  matching how `HeadlessCharacterMigrationService` already disclosed the same boundary for its own
  guild-membership-only migration.

Both follow the exact same Preview → Safety Backup → Decode → Mutate → Encode → Verify → Atomic
Commit → Journal shape every other destructive save operation in this codebase already uses
(`HeadlessGuildOwnershipService`, `HeadlessPalEditService`), reusing `HeadlessSaveCodecService`'s
existing generic decode/encode (never previously pointed at a per-player file) and
`HeadlessBackupService` for the mandatory fresh safety backup.

## A real bug found and fixed during live testing

Live-tested against an isolated clone of the real production save (5 real players, 2 real guilds —
the established clone-and-isolate recipe, never touching the live install). First deletion test's
guild-cleanup follow-up failed with a lock-conflict error: `coordinator.Complete(operation.Id, ...)`
marks an operation's record complete but does **not** release its `"world-mutation"` resource lock
— only `OperationHandle.Dispose()` does. The follow-up `RemoveBrokenMember` call tried to acquire
that same key while the outer deletion operation's handle was still undisposed (disposal was
deferred to the method's `finally` block, which hadn't run yet). Fixed by explicitly disposing the
outer operation's handle immediately after `Complete()`, before attempting the follow-up call —
`Dispose()` is idempotent (its own `disposed` guard), so the `finally` block's catch-all dispose for
every other exit path stays safe unchanged.

Re-tested after the fix on a fresh player: deletion succeeded, the follow-up guild-cleanup
succeeded, and — independently re-verified by decoding the raw `Level.sav` a third way, outside
MystTiq entirely — the deleted player's entry was genuinely gone from the guild's real `players`
array on disk, not just reported gone.

Copy Player was independently verified the same way: after applying, re-decoded the destination's
`.sav` file fresh and confirmed `PlayerUId` was still genuinely the destination's own (not the
source's), while `InventoryInfo`/`PlayerCharacterMakeData` were present and matched the source.

## A known, disclosed read-side staleness (pre-existing, not introduced here)

After a successful deletion+guild-cleanup, `world/players-guilds` continued reporting the deleted
player as still a guild member for longer than expected, even though the real `Level.sav` on disk
was already correct (independently confirmed). This matches an already-documented, pre-existing gap
in this codebase (`Level.sav.json` read-side sidecar staleness, first noted at v0.6.3.0) — not
something this version introduced, and the underlying data mutation itself is proven correct.
Flagged here since this version's own testing is what surfaced it again; not fixed as part of this
change.

## Desktop UI

Players page's right-click context menu gains "Copy Player Data From…" and "Delete Player
Completely…". Delete shows a confirmation dialog (`ConfirmDeletePlayerDialog`) populated with the
real server-reported preview findings (not a generic warning). Copy first shows a populated
dropdown of known players to pick the source from (`SelectPlayerDialog` — a genuinely reusable
"pick one other player" component, built because the existing Base/Guild ownership cards still
require hand-typing a 32-hex ID and this shouldn't repeat that), then the same real-findings
confirmation shape (`ConfirmCopyPlayerDialog`).

Separately: `MenuItem:disabled` styling was added to `DesignSystem.axaml` (no `MenuItem` style
existed anywhere in this app before) — this is what actually explained the original "right-click
looks broken" report: Kick/Ban were correctly `CanExecute`-gated on the selected player being
online, just with no visible disabled look to distinguish "correctly disabled" from "broken."

## Deliberately not done this version

- **Base/Guild right-click convenience wiring, requested in the same conversation, is deferred to
  its own follow-up.** The underlying capability already fully exists and already works today
  (Base Ownership Transfer, Base Recovery/wipe, Guild Ownership Operations — all real, Preview →
  Safety Backup → confirm checkbox → Apply, already shipped) — what's missing is a right-click
  entry point that pre-selects a row and jumps to the relevant card, plus replacing free-text
  guild/player-ID entry with a populated dropdown the same way `SelectPlayerDialog` now does for
  players. Lower urgency than Player Delete/Copy, which had zero existing UI at all; scoped
  separately rather than rushed into this already-large change.
- No live GUI click-testing of the new dialogs themselves — no GUI-automation capability exists in
  this environment (disclosed consistently throughout this project). The backend was verified
  thoroughly and independently against real save data; the dialog code was code-reviewed against
  the same proven `ConfirmCloseTabDialog`/`ConfirmMinimizeToTrayDialog` shape already working in
  production.
