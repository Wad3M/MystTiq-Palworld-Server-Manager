# v1.0.4.0 — Guarded Save Edits: Items (internal)

The owner's roadmap milestone v1.0.4.0 (decision D-2: guarded edits only; D-7: remove an item, then add an item, then add
and remove a Pal). Every edit takes an automatic, verified backup first, runs on a clone first, and has a restore check.

## Where items live

Decoded production data (2026-10-05):
- `Players/<uid>.sav` holds `SaveData.InventoryInfo.CommonContainerId` (the main inventory).
- `Level.sav` holds `worldSaveData.ItemContainerSaveData`, a map from container id to `{SlotNum, Slots}`. Only filled
  slots are listed. Each is `RawData.value = {slot_index, count, item:{static_id, dynamic_id}, trailing_bytes}`, and an
  empty slot is simply absent.
- Items with their own record (tools, weapons, armour, eggs) have a non-zero `dynamic_id` that points into
  `DynamicItemSaveData`. Plain stacks have a zero one.

## The edit (`InventoryEdits`, pure)

- **Remove:** the slot entry is deleted. An item with its own record is refused, because its record would be left behind.
- **Add:** a plain-stack slot from the same world is deep-copied (so its layout and custom version data are the game's
  own), then given the free slot index, the id, the count and a zero dynamic id.
  - Refused for an id the world holds nowhere as a plain stack.
  - Refused when every index below `SlotNum` is taken.

## The guard (`HeadlessInventoryEditService`)

It follows the same shape as `HeadlessPalEditService`:
1. A single-use preview (15 minutes), with the change described.
2. At apply: PalServer is stopped, and Level.sav's hash is unchanged since the preview.
3. The world-mutation operation lock; a journal under `world-transactions/journals`.
4. A fresh safety backup, which must pass `VerifyAsync` before anything is touched.
5. Decode, change, encode.
6. An independent decode in which the container must equal the old one plus or minus exactly that slot
   (`VerifyOnlyThisChanged`).
7. `File.Replace`, and the explorer's sidecar refreshed.

Any failure copies the original back and checks its hash. The Players page shows the inventory, previews, asks for
confirmation (red for remove), then applies.

## Evidence

- LogicHarness, on a synthetic world shaped like the real decode:
  - remove and add;
  - the refusals (own record, absent item, item that only exists with a record, full inventory);
  - only that slot changes;
  - other players are untouched.
- `Test-v1.0.4.0-RouteSmoke.ps1`, on a copy of the clone's world with the real save tools: one stack was removed and one added through the API, each after a fresh safety backup that passed its check, with only that slot changed; an item the world holds nowhere as a plain stack was refused, as was any edit while a server ran; and restoring the first edit's safety backup gave the pre-edit Level.sav byte for byte.
- Owed for `Done`: on the clone server, a player confirms in game (S-1, S-2).

## Fixed on the way: a crashed server blocked restores

Found by the inventory smoke. After PalServer ended outside MystTiq (a crash, a kill), the status kept the process's
last-known id as `NativeProcessId`, and pressing Stop on the crashed server wrote it back again. The 23 guards that
refused on `NativeProcessId.HasValue || Ready` (backup restore, save edits, MOD changes, world clone and transactions,
player copy and deletion, guild and base ownership, character migration, server install) refused until the next start.
They now use `ServerLifecycleSnapshot.ServerMayBeRunning`: a live process or an open game port. The smoke kills its
stand-in server with crash recovery delayed, checks the status still names the dead process, and restores.

## S-3 (add and remove a Pal): moved

A Pal is two linked records: a `CharacterSaveParameterMap` entry, and a slot in the player's Pal box
(`CharacterContainerSaveData`, via `PalStorageContainerId`). Its many fields must agree with the game's own species
record. It is the larger part of D-7. Per the roadmap rule it moves to the next milestone with this note, rather than
shipping without its restore check.
