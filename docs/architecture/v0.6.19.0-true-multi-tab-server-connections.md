# v0.6.19.0 — True Multi-Tab Server Connections

## Goal

Direct user feedback: pressing "+" should open a new tab that either launches a new server or connects to an existing one, and should never let a tab connect to a server that's already connected in another open tab.

## Grounding

Investigating the current tab bar showed it wasn't really tabs at all — `Profiles`/`SelectedProfile` on `MainWindowViewModel` backed a single global connection. Switching which profile was "selected" tore down and replaced the whole connection (wiped the bearer token, reset `ManagementApiConnected`/`ConnectionState`). There was no concept of two servers being connected at once, so "don't let a tab reconnect to an already-open one" couldn't be answered honestly without first making tabs real. Presented as a scope choice — a smarter "one connection at a time" picker, or true simultaneous multi-tab connections. The user chose true multi-tab. A scoping pass found `SelectedProfile` referenced 169 times and `BearerToken` 131 times across the view model, confirming this needed its own milestone rather than a `v0.6.18.x` patch.

## What shipped

- **`ViewModels/TabSession.cs`** (new): per-tab connection state — `Profile`, `ProfileName`, `ServerUrl`, `CertificateSha256`, `BearerToken`, `ManagementApiConnected`, `ConnectionState`, `IsBusy`, `ServerIsRunning`, and its own `DispatcherTimer`. `ConnectionState`'s setter also raises a computed `StatusDotColor` (green/amber/red/grey) so the tab bar's status dot updates live even for a background tab.
- **The core trick**: `MainWindowViewModel`'s `SelectedProfile`/`ProfileName`/`ServerUrl`/`CertificateSha256`/`BearerToken`/`ManagementApiConnected`/`ConnectionState`/`IsBusy`/`ServerIsRunning` are now pass-through accessors over whichever `TabSession` is `ActiveTab`, via a new `SetActiveTabField<T>` helper that mirrors `SetField`'s exact contract (bool-returns-changed, `[CallerMemberName]`-derived property name). Every existing setter's side-effect body (CanExecute fan-out, glow-state notifications) is unchanged — only what backs the getter/setter changed. This is what turns "rewrite ~170 call sites" into "redesign about eight properties plus the tab list."
- **`RaiseActiveTabPropertiesChanged()`**: called when `ActiveTab` changes, it re-raises property-changed for every delegated property (so every bound control updates to the newly active tab's real state) and replays each property's own dependent-notification method (`RaiseManagementApiConnectedDependents`/`RaiseConnectionStateDependents`/`RaiseServerIsRunningDependents`/`RaiseIsBusyDependents`) — without re-running any value-dependent business logic. In particular, `SelectedProfile`'s setter body (which resets `BearerToken`/`ConnectionState` to "not connected" for a freshly *chosen* profile) does **not** replay on a bare tab switch — that would incorrectly wipe an already-connected background tab's state the moment it became active.
- **Two-tier polling**: `WireTabTimer(TabSession)` gives every open tab its own 5-second `DispatcherTimer` (replacing the single app-wide timer). The active tab's tick runs the exact same full-refresh body the old shared timer always ran — still correct, since it now operates through the `ActiveTab`-delegated properties. A background tab's tick calls `RefreshTabLightweightAsync`, which operates directly on that `TabSession`'s own stored fields (via a new `BuildProfileFromTab`, `BuildProfileFromEditor`'s tab-scoped counterpart) and calls the existing cheap `GetHealthAsync` — never through the delegated properties, since writing through them from a background tab would silently corrupt the focused tab's displayed state with a different tab's data.
- **New "+" flow**: `MainWindow.axaml.cs`'s `AddTabButton_OnClick` builds a `MenuFlyout` with "Set Up New Server" (`SetUpNewServerTabCommand` → `OpenNewServerTab()`, which opens a new tab and runs the existing `BeginNewProfile()` form-reset logic against it) and one "Connect to..." entry per saved profile not already open in a tab (`ConnectExistingProfileTabCommand` → `ConnectExistingProfileTab(profile)`). The duplicate-connection guard lives at this one "open a tab" step — filtered once when building the flyout, checked again defensively inside `ConnectExistingProfileTab` itself.
- **Tab bar** (`MainWindow.axaml`): the `ListBox` is now bound to `Tabs`/`ActiveTab` instead of `Profiles`/`SelectedProfile`; each item shows its own live status dot (`TabSession.StatusDotColor`) and a close ("×") button (`CloseTabCommand`, `CommandParameter="{Binding}"`). `RelayCommand<T>` gained a real `CanExecute`/`RaiseCanExecuteChanged` (it was previously a permanent-`true`, no-op-event stub — no existing usage needed more) so the close button can disable itself once only one tab remains.
- The Settings page's existing "Server Profiles" `ComboBox` (bound to `Profiles`/`SelectedProfile`) is unchanged — it still edits/reconnects the profile loaded into the *active* tab's editor, a separate concern from the tab bar's "which servers are simultaneously open."

## Explicit non-goals (this pass)

- Full live page data (Console, World Explorer, Player Registry, Configuration settings, etc.) kept warm per background tab — only the connection and a lightweight status summary stay live; the active tab's page data refreshes on focus, the same latency as clicking between nav pages today.
- A zero-tabs empty state — the last tab can't be closed.
- Any server-side (`MystTiq.Core`/`MystTiq.HeadlessHost`) change.
- Restoring every previously-open tab across an app restart — `Tabs` is in-memory only this pass; relaunch still opens with one tab (today's existing last-used-profile behavior).
- The two other queued-but-unscoped items from this session (ribbon items duplicating the nav sidebar; the Fleet page missing UI components) — separate, not touched here.

## Verification

`dotnet build` (Release) across all three projects and the full solution — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.6.18.4 regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. This is also the most GUI-interaction-heavy change made this session — verification here is compile-clean plus static contract checks (the property-delegation wiring is structurally correct, the duplicate-filter logic is present and correct by inspection), not a behavioral click-test. Actually opening two tabs, confirming both stay connected, confirming a third tab can't connect to an already-open profile, and confirming the status dots update independently is the user's to do once built.
