# v0.7.62.0 — Dashboard/Ribbon Layout Overlap Fix

## Goal

Fix a real, reported UI bug: after certain reconnect sequences, the ribbon and category tabs went
visually blank on every page (reported live on both Dashboard and Inspector), while the page title/
subtitle and connection badge kept rendering correctly throughout.

## Investigation

### Ruling out the data layer entirely

The first working theory — that `MainWindowViewModel`'s constructor never seeds the ribbon — was
checked against the actual source and found wrong: `RebuildRibbonGroups()` is already called once,
unconditionally, at the end of the constructor. A second theory (the ribbon's measured width never
gets set) was also checked and found wrong once live data was available.

With two speculative theories already disproven from static reading alone, the investigation moved
to live inspection instead of further guessing. `dotnet-sos` (Microsoft's official SOS debugging
extension) and Sysinternals `cdb` — both already installed earlier this session for the PalServer
freeze investigation — were used to attach non-invasively to the actual running, currently-buggy
`MystTiq.Desktop.exe` process and dump the real `MainWindowViewModel` instance's fields at the exact
moment the bug was visible on screen.

Findings, checked twice against two independently-reproduced instances of the bug:

- `VisibleRibbonGroups` (the `ObservableCollection` the ribbon `ItemsControl` binds to): **3 items**,
  not empty.
- `_allRibbonGroups` (the full, unfiltered source list): also 3 items.
- `_ribbonWidth`: `1403.2` — a real, healthy measured value, not the uninitialized `0.0` a "never
  measured" theory would predict.
- `_selectedPage`: `0` (`NavigationPage.Dashboard`) — correctly matching the displayed page.

This is conclusive: the ViewModel's data was completely correct at the exact moment of the visible
bug. Every explanation involving application logic, data binding, or missing property-change
notifications was ruled out categorically. The bug was never in "what the app knows" — only in how
that correct state was being rendered.

### Finding the actual mechanism

Directly asked, the user described the symptom precisely: "the Home Server World Backups Mods Tools
System part appears that it's in the background or something" — not missing, but *behind* something
else. That reframes it as a Z-order/overlap problem, not a visibility/data problem.

`MainWindow.axaml`'s outer layout Grid is declared as `<Grid RowDefinitions="66,42,Auto,*,44">` —
row definitions only, no `ColumnDefinitions` at all. Every child occupying rows 1-2 (the decorative
background panel, the category-tabs `Border`, the ribbon `Border`, and the page-header title/
subtitle `Border`) therefore shares a single, unbounded column. The only thing keeping the
page-header panel (declared *last* among these, at line 169, so it paints on top by default XAML
z-order) visually confined to "the right side" is its own `HorizontalAlignment="Right"` plus
`MinWidth="460"` — there is no real column boundary, and critically, **no `MaxWidth`**.

If an Arrange pass — plausibly one triggered by the `IsCreatingNewProfile`-gated visibility toggle
that every row-1/2 child shares, re-running during a reconnect — ever stops correctly respecting
`HorizontalAlignment="Right"` for this specific element, nothing prevents it from expanding to the
full row width. Its own explicit, opaque `Background="{DynamicResource CardGradient}"` would then
paint directly over the category tabs and ribbon beneath it in the same shared column. This matches
every observed detail: the page title/subtitle (this panel's own content) kept rendering correctly
throughout, since it was never actually hidden — everything *underneath* it was.

## The fix

Added `MaxWidth="620"` alongside the existing `MinWidth="460"` on the page-header `Border`
(`MainWindow.axaml`, the panel wrapping `PageTitle`/`PageSubtitle`). This bounds the panel to a
sensible size regardless of the precise Avalonia Arrange-pass condition that was letting it expand,
without needing to fully understand or reproduce that condition on demand.

A larger, more "structurally correct" fix — adding real `Grid.ColumnDefinitions` and assigning
explicit `Grid.Column` values to separate left (tabs/ribbon/nav) from right (header) — was
considered and rejected for this pass: it would also change the app's current intentional visual
design (ribbon and category tabs spanning the full row width, with the header floating on top in
the top-right corner) into a fixed side-by-side column split, a larger and riskier change than the
bug being fixed warranted.

## Verification

- Reproduced the original bug live (multiple times, across two separately-launched app instances).
- Live-inspected both instances via `cdb`+SOS, confirming the data-layer findings above on each.
- Applied the `MaxWidth="620"` fix, rebuilt (`dotnet build` clean, then `Build.ps1 DesktopWindows`
  for a runnable publish output).
- Launched the fixed build directly (existing PalServer processes from concurrent testing left
  fully untouched) and confirmed live: ribbon, category tabs, and nav pane all render correctly on
  both the Dashboard and Inspector pages after the same reconnect sequence that previously broke
  them.

## Known gaps (disclosed)

- The exact Avalonia-internal condition that lets the Arrange pass stop respecting
  `HorizontalAlignment="Right"` was never fully identified — `MaxWidth` bounds the visible damage
  regardless of the precise trigger, but the underlying Arrange behavior itself is unexplained. If a
  future Avalonia version or further changes to this page-header panel's content ever need more than
  620px, this ceiling would need revisiting.
- The broader structural fragility this bug exposed — no real `Grid.ColumnDefinitions` separating
  left-side and right-side chrome in this Grid, relying entirely on per-element alignment — remains
  in place. It was a deliberate, disclosed scope decision this pass, not an oversight.
