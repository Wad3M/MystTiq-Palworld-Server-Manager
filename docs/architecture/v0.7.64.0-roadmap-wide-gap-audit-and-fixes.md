# v0.7.64.0 — Roadmap-Wide Gap Audit and Fixes

## Goal

A direct follow-on to v0.7.63.0's theme-system audit: the user asked to "keep going on the rest of
the roadmap" — a full catalog of every gap this project's own documentation has already disclosed
(release-notes' "Known gaps" sections, docs/architecture/*.md, docs/roadmap/*.md, and TODO/stub
markers in current source), triaged into what's a real fixable defect versus honestly-scoped future
work, with the real, cheap-to-verify defects actually fixed this pass.

## What the audit found

A comprehensive sweep across ~90 release-notes files, the full roadmap doc set, and a source grep
for TODO/FIXME/"BACKEND REQUIRED"/stub markers turned up roughly 75 distinct open items. The large
majority are honestly-scoped, already-disclosed future work with no code defect behind them:
unbuilt features (web dashboard, mobile clients, Docker/Wine runtime providers, byte-level save
editing, event-based automation triggers, a full provider framework beyond the one slice v0.6.5.0
shipped), verification-only gaps that need resources this environment doesn't have (elevated Windows
Service install, a genuinely idle-vs-conflicting live port, real GUI click-through), and a handful of
deliberate non-goals. None of those needed "fixing" — they needed cataloging, which is now done.

A smaller set were genuine, concrete, fixable defects in already-shipped code:

1. **Automation rule validation was missing entirely.** `HeadlessAutomationService.CreateRule`/
   `UpdateRule` accepted any `int` for `Trigger.IdleThresholdMinutes`/`JitterSeconds`/`Interval` and
   any entry in `Action.WarningCountdownSecondsBeforeAction`, persisting and returning it verbatim —
   even though `ComputeNextDue`/the idle-tick path silently reinterpret invalid values
   (`Math.Max(1, idleThresholdMinutes)`, a non-positive `Interval` falling back to 1 hour) rather
   than honoring them. An admin creating a rule with `idleThresholdMinutes: -5` via the API got back
   HTTP 200 and a rule that claims to use a threshold it will never actually use.
2. **`MystTiq-PalServer-Console.log` had no size cap or rotation** on either of its two independent
   writers (`HeadlessConsoleLogWriter`'s structured lines, `WindowsServerLifecycleService`'s raw
   PalServer stdout/stderr capture) — `File.AppendAllText` forever, on a file this app's own design
   explicitly expects to live on a long-running production service.
3. **Three stale "BACKEND REQUIRED" disclosures** that no longer matched shipped reality:
   - `MainWindow.axaml`'s World Transactions/Repair Center page still claimed "Base ownership/Palbox
     binary repair remains BACKEND REQUIRED pending its own port onto the same save codec" — but
     Base Ownership Transfer (v0.5.3.0) and Base Recovery (v0.5.4.0) have both been live, fully-wired
     Preview/Apply cards on the Bases page for dozens of versions.
   - The Server Setup checklist's UE4SS Runtime row still said "UE4SS installation is scheduled for
     the MOD/UE4SS restoration phase" and marked its own action unsupported when missing — stale
     since v0.7.49.0 shipped a real `HeadlessModManagementService.ApplyUe4ssInstallAsync`, reachable
     from the MOD Dashboard/UE4SS page. `MainWindowViewModel.RunEnvironmentAction` already had a
     dedicated `"UE4SS Runtime" → Navigate(NavigationPage.Ue4ss)` case sitting unreachable behind the
     stale `ActionSupported=false`.
   - The same checklist's Backup Storage row claimed backup-root creation "must be performed by a
     server-side storage operation" as if none existed — stale since v0.6.4.0 shipped exactly that
     as Doctor's Fix Automatically (`HeadlessDiagnosticsService`, a real
     `Directory.CreateDirectory(paths.BackupRoot)` call). Unlike the UE4SS row, this checklist page's
     own action has no dedicated handler for "Backup Storage" (it would silently no-op on a generic
     re-verify), so only the note text was corrected here, not the disabled state.

Also noted but deliberately not fixed this pass: **`LinuxServerLifecycleService` has no PalServer
stdout/stderr console-capture at all** — `WindowsServerLifecycleService.StartConsoleCapture`/
`AppendConsoleLine` has no Linux counterpart, discovered while tracing the log-rotation fix's second
writer. This is a real, newly-surfaced gap (the Live Console page presumably shows less on Linux than
Windows as a result), but it's a new feature to build, not a rotation bug to fix, and is out of scope
for this pass — flagged here for a future session.

## The fix

- New `HeadlessAutomationService.ValidateTriggerAndAction` (public static, so it's directly
  unit-testable without constructing the service's 13-dependency graph), called from both
  `CreateRule` and `UpdateRule`, rejecting: negative `JitterSeconds`; a non-positive `Interval` on an
  `Interval`-kind trigger; `IdleThresholdMinutes < 1` on an `IdleEmpty`-kind trigger; any negative
  entry in `WarningCountdownSecondsBeforeAction`. `LocalManagementApiHost`'s `POST`/`PUT
  /automation/rules[/{id}]` routes now catch `ArgumentException` and return `400` with the message,
  matching this codebase's existing validation-error convention elsewhere.
- New `MystTiq.Core.Services.ConsoleLogRotation.RotateIfNeeded(path)`: renames the log to a single
  `.1` generation once it reaches 25 MB, so the next append starts fresh. Called from both writers
  immediately before their `File.AppendAllText`. Deliberately simple (one prior generation kept, no
  cross-writer lock coordination) — the failure mode of the inherent race between two independent,
  unsynchronized writers checking-then-renaming is at worst one extra or slightly-late rotation,
  never corruption, so added complexity wasn't justified for a non-critical log stream.
- The three stale-text fixes described above.

## Verification

- `dotnet build` on the full solution: clean, 0 warnings/errors.
- `scripts\Testing\MystTiq.LogicHarness` gained 11 new scenarios (17/17 pass): 8 direct calls to
  `ValidateTriggerAndAction` covering every reject/accept branch, and 3 for `ConsoleLogRotation`
  (under-threshold file left alone; an oversized file rotated with content preserved exactly and the
  next append starting fresh; a stale prior `.1` generation correctly overwritten rather than
  accumulating).
- New `scripts\Test-v0.7.64.0-RouteSmoke.ps1` (5/5 pass) — live HTTP checks against the real running
  sidecar, not just the pure-logic harness: `POST /automation/rules` rejects a negative
  `idleThresholdMinutes`/negative `jitterSeconds` with 400 and persists nothing; a valid rule is
  created and its values round-trip unchanged; `PUT /automation/rules/{id}` rejects a zero `Interval`
  with 400 and leaves the existing rule untouched; `GET /server/environment` confirms the UE4SS row
  now reports `actionSupported: true`.
- `scripts\Test-v0.7.64.0-Logic.ps1` (static contract-presence gate, matching this project's
  established per-version convention) and `-RunBuild` (strict validation, the frozen v0.7.63.0
  regression baseline, the full v0.5.1.5/v0.7.12.0/v0.7.15.0/v0.7.17.0/v0.7.64.0 smoke suites) — see
  release notes for the pass/fail summary.

## Known gaps (disclosed)

- The ~65 other cataloged items from this audit remain open, as documented future work or
  verification-only gaps — see the audit itself (not preserved as a standalone doc; summarized in
  the CHANGELOG entry and release notes) for the full triage. None of them are silent regressions;
  all were already disclosed somewhere in this project's own history.
- `LinuxServerLifecycleService`'s missing console-capture (noted above) is a newly-surfaced, real gap
  worth its own future session.
- This pass did not attempt the larger, resource-gated items from the audit (elevated Windows
  Service install-cycle verification, real Linux deployment of the very latest source, a genuinely
  live port-conflict test, GUI click-through of the theme fixes) — all carried forward as still-open,
  same as before this session.
