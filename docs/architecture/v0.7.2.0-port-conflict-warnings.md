# v0.7.2.0 — Port-Conflict Warnings for New-Server Creation

## Goal

Second slice of the broader v0.7.x UX plan: creating a new server should warn if a typed Game/REST port is already in use by another running server, and indicate that conflict before the user proceeds.

## Grounding

Investigation (carried over from the v0.7.1.0 planning pass) found a real, working OS-level "list every bound TCP/UDP endpoint + owning process" capability already existed: `INetworkDiagnosticsPlatformService.GetTcpListenersAsync`/`GetUdpEndpointsAsync`, with a Windows implementation shelling out to `netstat.exe -ano -p udp|tcp` and a Linux counterpart. It was only ever invoked by `NetworkDiagnosticsService.RunAsync`, scoped to one already-running, already-connected profile checking its own configured port — never for an arbitrary candidate port typed during new-server setup, and never before any profile exists. Neither new-server-creation path (`PalworldSettingsConfigurationService.CreateDefault`/`ValidateDefaultRequest` for the single already-connected-profile first-run flow, or `HeadlessConfigurationService.Validate`/`HeadlessFleetConfigurationService.AddServerAsync` for Fleet's add-profile flow) cross-checked a port against anything beyond internal request consistency (e.g. `GamePort != RestPort`).

Rather than thread a new dependency into those existing, already-validated synchronous methods (`CreateDefault` in particular is synchronous; a live port check needs async I/O), the port check is implemented as a standalone query the Desktop UI calls proactively while the user types — matching the plan's own framing of "not a hard block ... a clear, visible warning."

## What shipped

- **`MystTiq.Core/Models/NetworkDiagnosticModels.cs`**: new `PortCheckResult(int Port, string Protocol, bool InUse, string? ProcessName, int? OwningProcessId)`.
- **`MystTiq.Core/Services/PortAvailabilityService.cs`** (new): `CheckAsync(port, protocol)` reuses `INetworkDiagnosticsPlatformService.GetTcpListenersAsync`/`GetUdpEndpointsAsync` as-is (no changes to that interface or its Windows/Linux implementations), just filtering the returned endpoint list by an arbitrary port instead of one already-configured profile's port.
- **`MystTiq.HeadlessHost/LocalManagementApiHost.cs`**: new global route `GET /api/v1/diagnostics/port-check?port=N&protocol=UDP|TCP` (defaults to UDP), registered alongside the other unscoped `/api/v1/*` routes (not per-profile) since it needs no profile context and is most useful before any profile exists. Constructs its own fresh `PortAvailabilityService`/`NetworkDiagnosticsPlatformService.ForCurrentPlatform()` instance rather than sharing any per-profile `NetworkDiagnosticsService`.
- **`MystTiq.Desktop`**: `PortCheckResultDto` (mirrors `PortCheckResult`), `IMystTiqApiClient.CheckPortAsync`/`MystTiqApiClient.CheckPortAsync` (same `BuildClient(profile, bearerToken)` pattern as every other client call). `MainWindowViewModel.SetupGamePort`/`SetupRestPort`'s setters now trigger a best-effort async `CheckSetupPortAsync` (swallows any failure — a failed check must never block editing the form), populating `SetupGamePortWarningText`/`SetupRestPortWarningText` (and their `HasSetupGamePortWarning`/`HasSetupRestPortWarning` visibility booleans) when the port the user just typed is already bound, naming the process holding it where available. `MainWindow.axaml`'s "IN-GAME SERVER DEFAULTS" card shows these as amber warning text beneath the Players/Game Port/REST Port row.

## Explicit non-goals

- No change to `CreateDefaultServerSettingsAsync`'s actual validation/creation logic, or to `HeadlessConfigurationService.Validate`/`AddServerAsync` — the port check is a proactive UI warning, not a new hard gate on either creation path. A stale/zombie listener holding a port should not be able to block legitimate recovery.
- The new-server creation wizard (v0.7.3.0) and card flare / the no-scroll initiative (v0.7.4.x) remain queued as planned.

## Verification

`dotnet build` (Release) across all three projects — 0 warnings/0 errors.

**This is the one release in the v0.7.x plan with a real server-side change**, so verification went beyond the usual static-contract-check pattern: built the actual `mysttiq-server.exe` sidecar, started it against a scratch config (the same harness `Test-v0.5.1.5-RuntimeSmoke.ps1` uses), occupied a real TCP port (18999) with a plain `TcpListener`, and called the new endpoint directly — it correctly reported `InUse=true` with the real process name (`pwsh`) and PID. A second call against an unused port (19531) correctly reported `InUse=false`. This is live, end-to-end evidence, not just a structural/textual check — the strongest verification available in this environment for a server-side change.

The frozen v0.7.1.0 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite both passed, confirming no regression to existing server-side behavior.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. The live endpoint behavior was verified directly as above; the actual on-screen appearance of the warning text in the running Desktop app is the user's to confirm once built.
