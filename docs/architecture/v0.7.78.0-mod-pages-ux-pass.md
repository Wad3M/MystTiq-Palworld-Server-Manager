# v0.7.78.0 — MOD Pages UX Pass (Library redesign, Dashboard differentiation, UE4SS fixes)

Started as a single, narrow ask — "the whole page just looks odd" about the MOD Library button
row — and grew through several rounds of live, iterative feedback (build → relaunch → screenshot →
next round) into a full pass across MOD Library, MOD Dashboard, and the UE4SS page. Each round is
documented here in the order it actually happened.

## Round 1: MOD Library auto-load + button row redesign

Direct feedback against a screenshot: "there are a number of buttons for the installed mods and the
whole page just looks odd. Also the local steam Mods should load automatically."

- **Auto-load**: `MainWindowViewModel.SelectedPage`'s setter (the single funnel every page
  navigation already goes through) now fires `ScanWorkshopModsAsync()` when navigating to
  `NavigationPage.ModLibrary`, guarded by `WorkshopItems.Count == 0` so it only runs once per tab.
- **Button row** (superseded by Round 2 below, kept here for the record): initially regrouped the
  9-button flat row into 3 clusters with semantic `success`/`warning`/`danger` classes and dividers.

## Round 2: layout restructure, ribbon relocation, right-click, drag-and-drop

Follow-up feedback on the same page, treated as scope clarification of the still-open request
rather than a new topic: "under installed MODs card it should have the info if there is an updated
version... should we move the buttons to the ribbon? can we add a right click as well" — then,
separately, on the Install ZIP card: "i dont think we need a type box here... and there are 2
greyed out buttons that perhaps we should either get working or remove. We should also allow drag
and drop."

- **Layout**: Install Validated ZIP and Available Local Steam Workshop Mods now sit side by side in
  their own row at the top of the page (`Grid ColumnDefinitions="*,1.4*"`). Below that, Installed
  MODs takes 2/3 of the row width with MOD DETAILS at 1/3 (`Grid ColumnDefinitions="2*,*"`),
  replacing the earlier equal three-column split. The page's header text (description + ModState +
  ModSummary) moved into its own card above Install Validated ZIP; Available Workshop Mods
  naturally stretches to match that stacked pair's combined height since both sit in the same Grid
  row.
- **Ribbon**: page-level, no-selection-required MOD actions (Enable All, Disable All, Repair,
  Safe-Start Diagnostic) moved to a new "MOD Maintenance" ribbon group, gated to `IsModLibraryPage`
  specifically (not the shared `IsModInventoryPage` MOD Dashboard also uses, since Dashboard stays
  intentionally read-only).
- **Right-click**: the Installed MODs list gained a `ContextMenu` with Enable/Disable/Rollback/
  Repair/Delete Selected, matching the established Bases/Guilds/Players per-row pattern. The old
  in-card button cluster for these same selection-scoped actions was removed entirely — the ribbon
  now covers all-MODs actions, right-click covers per-mod actions, and nothing is duplicated.
- **ZIP card simplified**: the manual "Package name (optional)" override box was removed
  (`ModInstallPackage` property deleted end to end) — the package name always comes from the ZIP's
  own filename now, matching how PAK vs. UE4SS type detection already worked from the archive's own
  contents (v0.7.39.0). The two permanently-disabled "Legacy Migration"/"Workshop Information —
  BACKEND REQUIRED" buttons were removed rather than left as dead clutter, since no backend exists
  for either and none is planned near-term.
- **Drag-and-drop**: the ZIP card is now a real drop target (`DragDrop.AllowDrop="True"` on
  `ZipInstallDropZone`). `MainWindow.axaml.cs` wires `DragDrop.DragOverEvent`/`DropEvent` via
  `AddHandler` in the constructor (Avalonia's drag events are attached routed events, not plain CLR
  events, so they can't use a simple `Click`-style XAML attribute). Uses `e.DataTransfer.TryGetFiles()`
  (the current, non-obsolete Avalonia 11.3 API — `DragEventArgs.Data` is deprecated in favor of
  `DataTransfer`) to find a dropped `.zip`, then calls the exact same `InstallModZipAsync` path the
  file-picker button already used.
- **Per-mod version + update badge**: `HeadlessModItem` gained `UpdateAvailable`, `UpdateHint`, and
  `InstalledVersion` fields. `GetInventoryAsync` now calls the existing `CheckModUpdateAsync` once
  per installed mod during the regular scan (cheap, local, no network) and reads each mod's own
  `Info.json` directly out of its install folder via the already-existing `ReadWorkshopManifestVersion`
  helper — this reports the *actually-installed* copy's declared version, not the local Workshop
  cache's version, so it stays honest even when an update is available but not yet applied. Shown as
  a small version line + an "UPDATE AVAILABLE" badge per row on the Library list, and added to the
  MOD DETAILS panel's INSTALLATION section.

## Round 3: MOD Dashboard look-and-feel differentiation

Direct request after the Library redesign landed: "I need help with the MOD dashboard to change the
look and feel of it so it doesn't feel like it is essentially the same as the MOD library" — a real
observation once Library's read-only-list-plus-details-panel shape (from v0.7.40.0/v0.7.43.0) sat
right next to Library's own newly-redesigned version of the same shape.

- **Hero health banner** (new): a single large, color-coded card leading the page — green when
  `ModHealth == "Healthy"` (`IsModHealthGood`, a new computed property with matching
  `RaisePropertyChanged` calls at both `ModHealth` write sites), plain otherwise — showing the page
  description, `ModSummary`, and `ModState` together, replacing the old plain-text header every
  other page uses. Distinct from Library's own header-in-a-card treatment.
- **Stat cards recolored**: the 6 HEALTH/INSTALLED/CONFIRMED/UNVERIFIED/DISABLED/ISSUES cards
  previously all shared the identical flat `accentMods` look; now colored by what each represents
  (green for Health/Confirmed, cyan for Installed, amber border for Unverified, red border for
  Issues).
- **Installed MODs list intentionally thinner than Library's**: renamed to "MOD Overview" (direct
  follow-up: "change the Installed MODs title to something more specific" — it previously shared
  the exact same title as Library's card). Dropped install path, version, and the update badge from
  each row — Dashboard is a glance view; Library is where that detail actually matters and where you
  can act on it.

## Round 4: UE4SS page fixes

Live feedback against a UE4SS screenshot, unrelated to the MOD Library/Dashboard work above but
folded into the same in-flight version per this session's standing "mid-session feedback gets
applied directly when it's a live, concrete ask" practice:

- **Fixed: `Border.statuscard` had no `Padding` setter at all** (unlike `Border.card`, which has
  `Padding="11"`) — every statuscard's text sat flush against its own border. This is a shared style
  in `Styles/DesignSystem.axaml`, so the fix (`Padding="11"`, matching `Border.card`) applies
  app-wide, not just to the UE4SS page where it was first noticed.
- **Runtime Health no longer reverts to "Unverified" after a confirmed-good run just because its
  one-time evidence source disappears.** Direct request: "runtime health should capture after it
  has run one time... display something useful like no crashes or anything, or server ran without
  issue." Root cause: `HealthState` was computed purely from whether `TryReadRuntimeModsRoot()`
  found *current* evidence (a live UE4SS.log/Pal.log runtime-root line) — stop the server, rotate
  the log, or just revisit later, and the signal was gone even on an install that had already run
  cleanly. Fix: a new small persisted marker (`ue4ss-runtime-verification.json` under
  `ManagerRuntimeRoot`, following the exact same best-effort read/write pattern as the existing
  `Ue4ssInstallManifest`) is written whenever `verified && matches` is actually true. When current
  evidence is absent but this marker exists, `HealthState` reports
  `"Confirmed — ran without issue (last verified {timestamp})"` instead of "Unverified". A install
  that has genuinely never been confirmed still reports "Unverified", honestly — this only changes
  behavior for installs with real prior evidence.
