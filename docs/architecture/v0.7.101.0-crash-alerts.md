# v0.7.101.0 — Crash Alerts: Tell the Admin When the Server Crashes

## Context

Sixth of the "enhancements to features we already have", and the alerting follow-up listed after the Crash
Analyzer (v0.7.97.0) and Doctor (v0.7.98.0) work. Reading the crash-recovery loop showed a plain gap:
`HeadlessSupervisor.RunCrashRecoveryLoopAsync` detects a crashed or vanished server and restarts it, but it only
writes to the console. Nobody was told the server had crashed, that it came back, or that recovery had given up
and the server was down. The Crash Analyzer only ran when someone opened it.

## What changed

- **The recovery loop reports events** through an optional `ISupervisorObserver` (Core): `CrashDetected` (a
  restart is about to be attempted), `RecoverySucceeded`, `RecoveryFailed`, `RecoverySuppressed` (too many restarts
  inside the window, so the loop stops and the server stays down). An observer that throws can never stop
  recovery. The observer is optional, so the installed OS service path (`service-run`) is unchanged.
- **`CrashAlertObserver`** turns each event into a notification through the normal pipeline
  (`HeadlessNotificationService.Create`), so it appears on the Notifications page and reaches whatever routes the
  admin already configured (Discord, email, webhooks). Every profile's recovery loop gets one.
- **The alert says what an admin needs**, built by the pure `CrashAlertText`:
  - crash: Critical, "<server>: server crashed, restarting (attempt N of M)", when the restart happens, and the
    likely cause from the logs with the first thing to try and any mod the evidence names (a lead, not proof);
  - recovered: Success, "server is back up";
  - a failed restart: Warning, saying how many attempts remain;
  - giving up: Critical and **pinned**, "server is DOWN, automatic recovery gave up", telling the admin the server
    will not restart on its own until they fix the cause and start it.
- **The log analysis runs at the moment of the crash** (the logs are freshest then) and is recorded, so the Crash
  Analyzer shows the same finding. Because of the new-versus-already-reported logic from v0.7.97.0, a crash that
  leaves no new evidence says so ("no new crash evidence ... the newest finding was already reported earlier")
  instead of blaming a stale line. Giving up reuses the last analysis rather than re-reading and re-marking it.
  If the logs cannot be read the alert is still sent, without the analysis.

## Deliberately not done

- No change to when or how often MystTiq restarts a crashed server, or to the restart limits.
- No per-profile alert settings and no way to mute them yet; alerts follow the existing notification routes.
- A "server stopped on purpose" is never announced as a crash (the loop already ignores it).
- The Windows/Linux OS-service supervisor (`service-run`) has no observer, so it does not send these alerts.

## Verification

- Solution builds clean, 0 warnings/errors.
- Logic harness, 4 new scenarios. The first two run the **real** `HeadlessSupervisor` recovery loop against a
  scripted server: a crash gives CrashDetected then RecoverySucceeded after exactly one start; a server stopped on
  purpose gives no events and no start; an observer that throws still gets the server restarted; and when every
  restart fails the events run crash/failed twice then suppressed and the loop returns the crash exit code after
  exactly two attempts. The third covers every alert text (severity, pinning, titles, cause and first fix, a mod
  named as a lead, an already-reported finding not presented as the cause, no findings, no analysis, attempts
  remaining, blank server name). The fourth uses real notification and analysis services over fixture logs: the
  first crash carries the log analysis, the same logs again read as "no new crash evidence", giving up is pinned
  and critical, and only the two crash detections wrote an analysis.
- **Live, end to end, on a real sidecar** (`Test-v0.7.101.0-RouteSmoke.ps1`): an isolated sidecar over a fixture
  whose persisted state says the server was running with a process that does not exist. The real lifecycle service
  reported a crash, the real recovery loop announced it, the notifications route returned the critical alert with
  "Out of memory" and the first fix, then the genuinely failed restart (no PalServer.exe) was announced with "4
  attempt(s) left", and the Crash Analyzer history held the same finding.
- **NOT verified:** delivery to Discord, email or a webhook (the alert goes through the same pipeline as every
  other notification, whose routes were not configured here); how the alert looks on the Notifications page; the
  OS-service supervisor path; and a real Palworld crash (none was available). The give-up alert was verified in the
  harness against a scripted server and by text, not by letting a real sidecar exhaust its five attempts.
