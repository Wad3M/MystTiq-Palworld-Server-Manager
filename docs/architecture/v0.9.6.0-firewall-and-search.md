# v0.9.6.0 — firewall and server search

Requested on 2026-09-28, after a LAN join to the clone server needed a firewall rule typed by hand, and after a server
search that took about half a minute.

## The firewall check could not run, and would have been wrong

**What happened.** Diagnostics' firewall check and its repair started a bare `powershell.exe`. This machine's PATH has
`System32` but not `System32\WindowsPowerShell\v1.0`, so the start failed ("cannot find the file specified") and the
check always read "inspection unavailable".

**What else was wrong.** Once PowerShell ran, `Get-NetFirewallPortFilter` took about 27 seconds on this machine
(775 rules), and a silenced error still left exit code 1, which the runner treated as a failure. The check also counted
any enabled rule whose port was "Any" as opening the server's port. On this machine that included the Palworld game
client's own rule, Steam's, and Store apps' rules (Xbox, ChatGPT). It also included a "Palworld Server EXE" rule for
`PalServer.exe`, which is only the launcher: the game binary it starts (`PalServer-Win64-Shipping-Cmd.exe`) owns the
socket, and a program rule covers only the process that owns it. So a port with no usable rule would have read
"allowed".

**Fix.**

- Rules are read through the firewall's own COM API (`HNetCfg.FwPolicy2`): every rule in about 0.2 s.
- A rule counts for the server's port only when all of these hold:
  - it is inbound and covers the protocol (17, or 256 for any);
  - it covers the port (a number, a list, a range, or `*`);
  - it is not limited to another program, a Windows service, or app containers. A rule with a `LocalAppPackageId` or a
    `LocalUserOwner` applies only to Store apps.
- A program rule counts only for the server's own binary. `FirewallRules` holds this matching as plain functions, and
  the logic harness tests it without touching the firewall.
- Changes still go through PowerShell (`New-NetFirewallRule`), now by its full path and with `-EncodedCommand`, so a
  quote in a server id cannot break the script. `netstat` is also started by its full path.

## A rule that follows the server's port

- Each rule MystTiq makes is named `MystTiq Palworld Server - Game UDP <port>` and tagged in its description with
  `MystTiq server: <id>`.
- Allowing a port creates or repairs that rule (enabled, inbound, allow, every profile). It then removes that server's
  tagged rules for any other port, so a port change doesn't leave the old port open.
- Rules made before this version carry no id. They still count for their port and are never removed.
- The port is the one the server binds (`ServerGamePort.Expected`: the `-port=` argument, else 8211), not PublicPort.

`GET /diagnostics/network/firewall` returns the state without changing anything:
- allowed, blocked, turned off, or missing;
- the rules that cover the port;
- this server's rules for a port it no longer uses.

`POST /diagnostics/network/firewall/repair` (Admin) makes the change.

**Administrator rights.** Adding a rule needs an administrator. The Desktop's own service runs as the signed-in user,
so Windows refuses the change. The refusal comes back with the script. When the server is on this computer (a loopback
address), the Desktop runs that same script through Windows' administrator prompt (`runas`). If the prompt is declined,
it says so and nothing changes. A remote server's owner is told to run MystTiq's service as an administrator there, or
to add the rule there.

**Where.**

- Diagnostics has a Windows Firewall card with the state and **Allow through Firewall**.
- Settings shows the same beside the launch arguments, where `-port=` is set.
- The new-server wizard shows it on its last step, for the server it just set up.
- Fleet's Clone World card reminds you that a clone needs its own rule once it is online.
- The Doctor has a `network-firewall` finding with an `allow-firewall` fix.
- On Linux nothing changes the firewall. The card and the finding show the `ufw` and `firewalld` commands instead.

## A second server bound the first one's port

The wizard registers a second server with the current server's launch arguments. Those arguments carried the first
server's `-port=`, so both servers used one port. Without a `-port=`, the new server bound 8211 whatever port the wizard
was given, because PublicPort binds nothing.

- `LaunchArgumentsText.WithPort` drops any `-port=` from the copied arguments and adds the wizard's port.
- A new Doctor finding, `configuration-game-port`, warns when a server's bound port and its advertised PublicPort
  differ. It is not fixed automatically, since launch arguments apply when MystTiq restarts.

## Server search

The search used to send an HTTPS and then an HTTP `/healthz` request to every address, 700 ms each, 32 at a time. With
three adapters that was about 760 addresses and half a minute.

**Now.**

- **First pass: a TCP connect only.** It runs 256 addresses at a time with a 600 ms timeout. A computer without MystTiq
  refuses at once; an address with nothing on it stops at the timeout.
- **Second pass: the identity probe.** Only the addresses that accept get it. The harness searches 255 unused addresses
  plus a stand-in service in about 0.6 s.
- **Progress.** Reports carry the plan, the count checked and each service the moment it answers. The window lists
  each service as it arrives, shows the ranges and a progress bar, and has **Cancel**. The window stays usable during a
  search.
- **Ranges.**
  - This computer comes first, then the `/24` around each adapter address, each range once.
  - Virtual adapters (WSL, Hyper-V, Docker, VMware, VirtualBox, libvirt) are listed as "not searched" unless ticked:
    their ranges hold this computer's own guests. An adapter counts as virtual only when it also has no default gateway:
    on this machine the real LAN runs through a Hyper-V external switch, "vEthernet (MystTiq External)", with the router
    as its gateway. The first build skipped it by name, and dropped the physical card on the same /24 as a duplicate, so
    only 127.0.0.1 was searched (seen live). Real adapters now claim their range first.
- **The tab stays connected.** A search used to select the first service it found, which rewrote the tab's address and
  marked it "Not connected" (seen live on the clone tab; v0.9.5.0 did the same). A connected tab now only lists what
  was found; a tab that isn't connected still picks a service as before.
  - Typed ranges (single addresses or `/24` to `/32`) are added. Entries that can't be read are named.

## A stop taken for a crash

This version's full gate failed once, in the v0.9.5.0 fleet smoke: a server stopped on purpose was restarted as
crashed. Run on its own, the smoke failed about one run in three. The logs showed the crash detected about a second
*after* the stop had completed and recorded "Stopped".

**Why.** A trace of a failing run (the state file and the process list every 100 ms) showed it: the stop recorded
"Stopped" when the process list came back empty, and 17 ms later a status read listed the same process at its own path
and recorded "Running"; a second later it was gone and the supervisor restarted the server as crashed. The inspector read
each process's details inside one `try`, and `Process.Responding` throws for a process that is terminating, so the
`catch` dropped a process that was still alive. The stop's wait took that as "exited"; the next read, a moment later,
listed it again. With that fixed, a second trace showed a narrower window: a status read listed the process just
before it exited, but read the state file just after the stop wrote "Stopped", and wrote "Running" over it.

**Fix.**

- A process is listed until Windows reports it has exited (`WaitForSingleObject` on a limited handle) and never after:
  an unreadable detail no longer drops it, and an exited process that something still holds a handle to is skipped (its
  path stays readable, so since v0.9.5.0 it could otherwise read as running).
- Status reads (list, read, write) and a stop's state writes take one lock, so a read sees the process and the state
  from the same moment; a read during a stop also leaves the stop request as it is (Windows and Linux).
- The state file is written by one writer at a time (two shared one `.tmp` file), and a replace that Windows refuses
  because something has the file open is retried briefly. The trace's own reader, ten reads a second, made a start fail
  with "Access to the path is denied" before this; a virus scan or a backup could do the same.

The logic harness replays the stop sequence, and a crash without a stop request is still detected. After the fix the
fleet smoke passed six runs in a row under a tracer reading its state file ten times a second.
