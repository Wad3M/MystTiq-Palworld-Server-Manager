# v0.7.13.0 — New-Server Workflow Redesign

## Background

Raised mid-session, explicitly framed as "the next 0.7 task": the existing "Set Up New Server" flow lived inside the Settings page's normal card stack, gated by `IsCreatingNewProfile`/`IsWizardStepN` bindings mixed in among the controls used to edit an already-saved profile. Nothing distinguished "you are mid-setup, this connection doesn't exist yet" from ordinary navigation — a user could freely click away to any other page while a new profile was half-configured, and the wizard itself never asked the most basic question first: is this server on this machine, or somewhere else? The request was to redesign this after how other connection-manager-style applications (SSH clients, database clients, remote-desktop clients) handle "New Connection" — a focused, separate sequence, Local-or-Remote as the very first choice, a network-scan option for the Remote branch, and the regular ribbon/nav chrome hidden until a tab is actually connected or a brand-new server has been created.

The existing 3-step wizard (Connection Details → In-Game Server Defaults → Confirm & Finish), built in v0.7.3.0 entirely from fields/commands that already existed for editing a saved profile, was sound and did not need replacing — the ask was about *where it lives* and *what comes before it*, not the steps themselves.

## What shipped

### The wizard now has its own dedicated host, not a page among many

`MainWindow.axaml`'s outer `Grid` (`RowDefinitions="66,42,Auto,*,44"`) previously showed the category tabs (Row 1), ribbon toolbar (Row 2), and nav-sidebar-plus-page-content (Row 3) unconditionally, with only individual wizard *steps* inside the Settings page hidden behind `IsWizardStepN` bindings. Those three chrome elements are now all gated behind `IsVisible="{Binding !IsCreatingNewProfile}"`, and a new sibling `Grid Grid.Row="3" IsVisible="{Binding IsCreatingNewProfile}"` hosts the entire wizard instead — background image, its own `ScrollViewer`, and every step centered in a single column. While a tab is mid-setup, there is no nav sidebar to navigate away with and no ribbon to accidentally act on a connection that doesn't exist yet.

The Settings page's old "Connection profiles" card is simplified back to handling only an already-saved profile's editing (Connect/Save Profile/Delete Profile) — every `IsCreatingNewProfile`/`IsWizardStep1`-conditioned branch that used to live there was removed rather than left as dead, permanently-false conditions, since `IsCreatingNewProfile` can no longer be true while that page's content is even visible.

### New Step 0 — Local or Remote

Before Connection Details, a new first step (`NewServerWizardStep == 0`, `IsChoosingConnectionKind`) presents two cards: **Local** ("Runs on this computer. MystTiq finds or starts its own local management service.") and **Remote** ("Runs on another machine. Scan your LAN or enter its address directly."). Picking either sets a new per-tab `TabSession.ConnectionKind` field ("Local"/"Remote"/empty — mirroring why `WizardStep` is per-tab rather than a single shared field: two tabs can each be mid-setup with a different choice open at once) and advances to Step 1, which now shows one of two sub-views instead of a single undifferentiated form:

- **Local**: an "Auto-Detect Local Service" button (new `DetectLocalServiceAsync`, calling the same `ILocalServiceDiscoveryService`/`ILocalManagementBootstrapper` pair the pre-existing "Bootstrap Local Service" button on the Settings page has always used — this is not new plumbing, just newly reachable during profile creation, where `SelectedProfile` is still null) plus manual Name/Service URL fields, pre-filled to the default loopback endpoint, for opening a second or third tab against a different local sidecar port.
- **Remote**: the pre-existing LAN-scan button (`DiscoverServicesCommand`) and discovered-services picker, plus manual Name/Service URL/Bearer token/TLS certificate pin fields, with the default loopback URL cleared out since a remote server has no reason to default there.

Steps 1 (Connection Details, now specialized as above), 2 (In-Game Server Defaults), and 3 (Confirm & Finish) are otherwise unchanged from v0.7.3.0 — same fields, same commands, same `CreateDefaultServerSettingsCommand`/`SaveProfileCommand` wiring, just relocated into the new host and renumbered so the whole sequence runs 0→3 instead of skipping straight to 1.

### Clicking "+" already launches this correctly — no change needed

The "+" tab button's flyout has an existing "Set Up New Server" entry that calls `OpenNewServerTab()` → `CreateTab()` + `BeginNewProfile()`. `BeginNewProfile()` now sets `NewServerWizardStep = 0`, which is exactly the Step 0 Local/Remote choice — this was verified against the actual code path (not assumed) after a mid-session note asked for it explicitly; the existing wiring already does this without any additional glue.

## Explicit non-goals

- **Tab-bar overflow behavior for many open tabs, and duplicate-player-name deduplication on the Players page** — both raised in the same mid-session note as backlog items, but distinct features unrelated to the new-server workflow itself. Deliberately not folded into this release to keep it scoped to what was actually redesigned; queued as follow-up work.
- **Fixing the `api-remote-enable` CLI bug found while building this release's live remote-connection test** (see Verification below) — confirmed real, but it's `MystTiq.HeadlessHost` CLI dispatch, unrelated to this release's Desktop-only scope. Flagged as a separate task rather than patched here. **Fixed in v0.7.17.0** — see `docs/architecture/v0.7.17.0-api-remote-enable-cli-fix.md`.
- **A second physical machine for the Remote test** — this environment is a single machine. The Remote branch was verified against a sidecar deliberately rebound to the machine's own LAN interface with authentication and TLS enabled (see Verification), which exercises the identical code path (LAN IP, self-signed certificate pin, bearer token, non-loopback transport) a genuinely separate remote machine's connection would use, but is not a substitute for a true cross-machine test.

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors, after fixing two instances of the recurring XML-comment-`--` AVLN1001 parse error introduced while writing new XAML comments in this file.
- No GUI click-through capability in this environment (unchanged, disclosed every version) — verification is at the service/API level the wizard's own new code calls into, using real running processes rather than mocks:
  - Two ordinary `--desktop-sidecar` loopback instances started on different ports (8213, 8214) with isolated server/backup/runtime roots, both answering `/healthz` simultaneously with distinct process IDs — re-confirming multi-server operation still holds after this restructuring (no product code in `MystTiq.Core`/`MystTiq.HeadlessHost` changed this release, so this is a regression check, not new ground).
  - A third instance deliberately run *without* `--desktop-sidecar` (which force-binds loopback by design — confirmed by reading `Program.cs`, not a bug), configured with a generated bearer token (`api-token-create`) and self-signed TLS certificate (`api-tls-create`) for `192.168.1.5`, bound directly to that LAN address. `GET https://192.168.1.5:8215/healthz` correctly reports `api:"remote-secured", authentication:true, tls:true`; an unauthenticated `GET /status` correctly returns `401` with `{"error":"missing-bearer-token"}`. This is the same transport (non-loopback IP, self-signed cert requiring a pin, bearer token) the Remote branch's Connect action exercises against a real separate machine.
  - Attempting the documented `api-remote-enable --bind-address 192.168.1.5 ...` CLI path directly (rather than hand-writing the config as above) failed with "Non-loopback API binding requires api.authentication.enabled=true / api.tls.enabled=true" — a real, confirmed bug in `Program.cs`'s command dispatch (its blanket pre-command validation runs before `api-remote-enable`'s own handler, using the *old* auth/TLS flags against the *new* bind address). Not fixed here (out of this release's scope, see Explicit non-goals) but flagged as a separate follow-up task with full repro steps.
  - All three instances stopped and their scratch directories removed after verification; no test artifacts left behind.
