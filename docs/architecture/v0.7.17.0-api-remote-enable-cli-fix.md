# v0.7.17.0 — Fix `api-remote-enable` CLI Bug

## Background

Found (but explicitly not fixed) while building v0.7.13.0's remote-secured verification rig, and recorded there as a follow-up: `mysttiq-server.exe api-remote-enable --bind-address <LAN-IP> ...` could not actually be used to promote a fresh config to a secured remote binding, even though `HeadlessRemoteApiEnrollmentService.EnableRemoteApi` — the service the command is supposed to call — was itself correct. This made the documented `api-token-create` → `api-tls-create` → `api-remote-enable` workflow (`docs/linux/COMMAND_REFERENCE.md`, `README.md`) non-functional from the CLI: there was no way to transition a fresh config from loopback to a real remote (LAN/WAN) binding in one step.

## Root cause

`Program.cs` builds an `effectiveHeadlessConfiguration` (the loaded config with CLI overrides like `--bind-address`/`--api-port` applied) and validates it once, unconditionally, **before** the command switch statement — for every command, including `api-remote-enable`/`api-remote-disable`. That effective config took the CLI's *new* `--bind-address` but the *old*, not-yet-updated `Api.Authentication`/`Api.Tls` flags from the config as loaded from disk. A fresh or loopback config always has both disabled, and the validator rejects any non-loopback `BindAddress` unless both are enabled — so the pre-check always failed for exactly the one command whose entire purpose is to flip those flags on, before its own case handler (which calls `EnableRemoteApi`) ever ran.

Reproduced directly: `config-write-default` then `api-remote-enable --bind-address 192.168.1.5 --api-port 8215` exited 2 with "Non-loopback API binding requires api.authentication.enabled=true"/"...api.tls.enabled=true", never reaching `EnableRemoteApi`.

## What shipped

`Program.cs` now computes a `skipsEffectiveValidation` flag (`command` equals `api-remote-enable` or `api-remote-disable`, case-insensitive) and wraps the existing pre-command validation block in `if (!skipsEffectiveValidation)`. Neither of those two commands ever reads `effectiveHeadlessConfiguration` — each already builds and validates its own result internally via `HeadlessRemoteApiEnrollmentService` (`EnableRemoteApi`/`DisableRemoteApi`). Every other command that does consume the effective configuration (`api-run`, `service-run`, `service-status`, `service-install`, `service-uninstall`) is untouched — the same blanket check still runs for them, so a fresh config still cannot be told to start listening on a non-loopback address without authentication and TLS both enabled. `LocalManagementApiHost.Create` also independently throws if handed such a configuration, an unrelated pre-existing guard that provides defense in depth regardless of this fix.

## Explicit non-goals

- **No change to `api-run`/`service-run`'s own validation.** Those commands still reject an unsafe non-loopback override exactly as before — only the two enrollment commands that don't need the check were exempted.
- **No config schema or API surface change.** This is a CLI command-dispatch fix; `HeadlessRemoteApiEnrollmentService` itself was already correct and is unchanged.

## Critical files

- `src/MystTiq.HeadlessHost/Program.cs` (the `skipsEffectiveValidation` gate around the effective-configuration validation block)
- `src/MystTiq.Core/Services/HeadlessRemoteApiEnrollmentService.cs` (unchanged — `EnableRemoteApi`/`DisableRemoteApi`, now actually reachable for a non-loopback bind on a fresh config)
