# v0.6.0.0 Operation Platform Architecture

## Problem

Before this pass, `HeadlessWorldTransactionService`, `HeadlessGuildOwnershipService`, and `HeadlessBaseOwnershipService` each hand-rolled their own near-duplicate "journal" (create → advance → commit/rollback, written to a JSON file), sharing a type by accident (`HeadlessWorldTransactionJournal`, despite the name). There was no shared operation identity, no cross-feature visibility, and no protection against two conflicting mutations running at once — e.g. a Base Recovery Apply and a Guild Ownership Apply both racing to mutate the same `Level.sav`.

## Core contracts — `MystTiq.Core/Operations/`

- **`OperationModels.cs`** — `OperationId` (string-wrapping id, `OperationId.New()`), `OperationPhase` (Queued/Running/Completed/Failed/Cancelled/RolledBack), `OperationStage` (free-form State/Detail/TimestampUtc, preserving the granular per-milestone naming the three services already used), `OperationRecord` (OperationId, ServerProfileId, Kind, Source, ResourceKeys, Phase, timestamps, SafetyBackup, RolledBack, Stages, JournalPath).
- **`ServerProfileId.cs`** — string-wrapping identity with a `Default` singleton. MystTiq is single-server today, but every operation record, lock, and API now carries a real profile id instead of relying on process name or an implicit "the one server" (programming rule: multi-server identity never relies only on process name). This is the seam v0.6.8.0 (multi-server fleet) builds on without another rewrite.
- **`ServerHealthState.cs`** — `ServerHealthState` enum (Unknown/Ready/Degraded/Attention/Transitioning) + `ServerHealthSnapshot` record, formalizing the ad-hoc health strings the Dashboard already computed.
- **`ICapabilityProvider.cs`** — minimal `ProviderId`/`IsAvailable` marker. Implemented by `IServerDistributionPlatformService` (default interface members, so `WindowsServerDistributionPlatformService`/`LinuxServerDistributionPlatformService` needed zero changes) as the first real provider.
- **`IOperationCoordinator.cs` / `OperationCoordinator.cs`** — `BeginAsync(profile, kind, source, resourceKeys, ct)` returns a disposable `OperationHandle`; disposing it releases the resource locks. `Advance`/`Complete`/`Fail` update phase, append a stage, and persist. A `Dictionary<string, OperationId>` resource-lock table behind a single `lock` rejects `BeginAsync` when any requested key is already held, throwing with a message naming the key and the holding operation. Each operation persists as one JSON file under `ManagerRuntimeRoot/operations/journals/`, using the same atomic temp-file-then-move pattern already proven by the three migrated services.

## Migration — "wrap, don't replace"

Rather than ripping out the proven journal mechanics (regression risk against already-shipped, verified destructive-mutation code), each service's Apply method now *also* acquires an `OperationHandle` via `coordinator.BeginAsync` at the point it previously created its journal, calls `coordinator.Complete`/`coordinator.Fail` at the same points it already logged final success/failure, and disposes the handle in `finally`. The existing per-feature journal keeps running unchanged; the coordinator layers cross-feature resource-locking and visibility on top of it.

All three migrated services use resource key **`"world-mutation"`**, since all three mutate the same `Level.sav`:

| Service | Method | Kind |
|---|---|---|
| `HeadlessWorldTransactionService` | `ApplyCoreAsync` | `world-transaction` |
| `HeadlessGuildOwnershipService` | `ApplyAsync` | `guild-ownership` |
| `HeadlessBaseOwnershipService` | `ApplyTransferAsync` | `base-ownership-transfer` |
| `HeadlessBaseOwnershipService` | `ApplyRecoveryAsync` | `base-recovery` |

Preview/Analyze phases are unchanged — no operation is opened until Apply actually commits to a mutation. Because all four share the same resource key, the coordinator now correctly rejects any of them from starting while another is in flight, which did not exist before.

## API surface

- `GET /api/v1/operations?max=N` — recent operations, newest first.
- `GET /api/v1/operations/{id}` — single operation, 404 if unknown.

Desktop: `OperationRecordDto`/`OperationStageDto` (`Models/OperationDtos.cs`), `IMystTiqApiClient.GetOperationsAsync`. The World Transactions page's existing "Transaction Center / Durable Journal" card gained a second "Operation Platform" card listing Kind/Source/Phase/UpdatedUtc across all three migrated features, with its own Refresh command — kept as an enhanced section of the existing page rather than a new nav destination, consistent with the standing rule that World Transactions deliberately isn't its own nav item.

## Deferred (explicitly, not silently dropped)

- Priority-ordered queueing — today a conflicting `BeginAsync` is rejected outright, not queued.
- Dependency-graph blocking beyond a single resource key.
- Restart-safe reclassification of operations interrupted by a process crash — a fresh process starts with an empty lock table, which is safe but does not retroactively re-classify what an old interrupted operation's journal file says.
- SteamCMD phase/progress parsing.
- A dedicated full log-tail UI — per-feature status text remains the log surface for now.

These are the larger items in `docs/roadmap/MystTiq_v0.6_Grouped_Logic_Acceptance_Test_Plan.md`'s v0.6.0.0 checklist not covered by this pass; later `v0.6.x.0` milestones pick them up as the fleet-management features that need them land.
