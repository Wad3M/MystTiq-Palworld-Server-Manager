# v0.7.71.0 — Console Source: PalDefender Log

## Problem

Direct follow-up to the still-open console-capture investigation (v0.7.46.0 → v0.7.57.0). The
user provided a real screenshot of a visible Windows Terminal console window for the
`second-local` clone server, showing:

```
Starting PalDefender Anti Cheat v1.8.3 (console)
...
REST API started on port 8212
PalDefender Anti Cheat v1.8.3 loaded!
Running Palworld dedicated server on :8311
```

and asked for this exact content to be redirected into MystTiq's own Console page. v0.7.57.0's
own investigation concluded that *live, ongoing* console capture needs a native DLL-proxy hook
(large effort, disclosed as low realistic payoff since the PalServer binary is `NO_LOGGING`
compiled) — but the *startup banner* content in the screenshot is a different, much smaller
problem: is it written to disk anywhere MystTiq isn't already reading?

## Finding

Checked directly against the real production install (`C:\GameServers\Palworld\Server`) rather
than assuming: **PalDefender (a UE4SS-loaded anti-cheat mod) writes its own timestamped
per-session log file** at `Pal\Binaries\Win64\PalDefender\Logs\{dd.MM HH.mm.ss}.log` — one file
per server session, created fresh on every PalServer start. Confirmed the current session's file
contains exactly the screenshot's content, including `Running Palworld dedicated server on
:8211` — PalServer's own startup banner apparently reaches PalDefender's own logger too, which is
why the visible console window showed both. `HeadlessMonitoringService.ResolveConsoleSources`
never looked for this file.

(PalDefender also writes a separate `Logs\RESTAPI\RESTAPI_{dd-MM-yyyy}.log` for its own local REST
API — not wired in here, since it's PalDefender's own admin-API traffic log, not general console
narration, and out of scope for this fix.)

## Fix

`HeadlessMonitoringService.ResolveConsoleSources` gains a new source, following the exact same
`FindNewestTextLog` pattern already used for AdminCommands' own per-session log directory: newest
file under `RuntimeBinaryRoot\PalDefender\Logs`, added as `"PalDefender log"`.

## Verification

Live, against the real running production (`default`) and clone (`second-local`) profiles, not
just a static check: rebuilt via `Build.ps1 DesktopWindows`, relaunched the local API host,
confirmed `/api/v1/servers/{id}/logs/tail` reports `PalDefender log` as a merged source and that
its actual PalDefender-content lines (startup, REST API port, wiki URL, the version-mismatch
warning) now appear for both profiles.

## Disclosed, unchanged scope

This does **not** address ongoing/ambient console output during a running session — PalDefender's
own log, like every other source `ResolveConsoleSources` reads, only ever carries the startup
banner for that session and then goes silent, the same disclosed gap v0.7.46.0/v0.7.57.0 already
documented. The native DLL-proxy hook remains the only path to genuinely live, ongoing capture,
and remains unimplemented (small disclosed payoff, per v0.7.57.0's own findings) and blocked on
this machine's unrelated PalServer-launch freeze investigation (see
`docs/architecture/v0.7.70.0-slow-startup-investigation.md` and the project memory's own notes on
it). This version closes a real, narrower gap — a genuine missing source of real startup
diagnostics — not the larger live-capture problem.
