# v0.6.16.0 — Live World Map (Player Positions)

## Goal

The second finding from the v0.6.15.0 competitive survey (`docs/architecture/v0.6.15-plus-competitive-survey.md`): six separate competitor tools ship a live world map showing player positions — the single most common feature MystTiq lacked entirely. This milestone closes that gap, scoped explicitly to **player positions only**. Wild Pal positions and base coordinates are deferred, disclosed, not silently dropped — see Explicit non-goals.

## Grounding

Before designing anything, Palworld's own official REST API (`GET /v1/api/players`) was confirmed — against the official docs (`docs.palworldgame.com/api/rest-api/players`) and cross-checked against a second, independent OpenAPI spec that lands on the identical field set — to already return real, live `location_x`/`location_y` doubles per online player. This is the exact endpoint `HeadlessMonitoringService.GetPlayersAsync` already polls every status tick; the fields were simply never captured. No mod, no save-file decoding, and no new data source were needed for player positions.

The same research found no equivalent live source for wild Pals (not exposed by the API at all) or base coordinates (would need new, unverified `Level.sav` decode work this codebase doesn't currently do). Per explicit user scope decision, this pass covers player positions only.

## What shipped

`HeadlessMonitoringService.HeadlessPlayerSnapshot` gained `LocationX`/`LocationY` (string, matching the record's existing all-string convention), populated in `GetPlayersAsync` via the existing `GetAny(player, "location_x"/"location_y")` helper — no new parsing logic, since `GetAny` already round-trips a JSON number through `GetRawText()`. Desktop's `PlayerSnapshotDto` mirrors both fields; no new route, no new DTO type — this rides the exact same poll path already running every 5 seconds.

Screen-ready coordinates are computed once, in the ViewModel (`RebuildPlayerMapPoints`, called at the end of `ApplyPlayers`), matching the existing `MetricHistoryPoint.CpuGraphHeight` convention rather than an XAML value converter. A new Desktop-only `PlayerMapPointDto(Name, CanvasX, CanvasY)` carries the plotted result. Coordinates auto-fit every currently-online player with a valid, parseable position into a fixed 480x480 canvas (min/max bounds + padding, `TryParseCoordinate` returning `double?`) rather than hardcoding Palworld's absolute world-coordinate range, which isn't reliably documented. A player with a missing or unparseable coordinate is excluded from the map entirely, never plotted at a wrong default.

The map background is a Desktop-local preference, never a server-side concept — `LocalMapPreferencesStore` mirrors `JsonConnectionProfileStore`'s exact storage pattern (`%AppData%\MystTiq\map-preferences.json`, atomic temp-file-then-move writes, corrupt-safe defaults). Palworld's actual in-game map art is Pocketpair's copyrighted asset, so this ships with a plain coordinate grid; a "Browse for Map Background" button lets the user drop in their own sourced/licensed image at any time, and "Clear Background" reverts to the plain grid. A missing or invalid configured file falls back to the plain grid, never a broken-image state.

Surfaced as a new "World Map — Live Player Positions" card on the existing Players page (`IsPlayersPage`), not a new nav destination, consistent with how every other diagnostics/monitoring addition this session has been placed.

## Explicit non-goals (this pass)

- Wild Pal positions — not exposed by Palworld's REST API at all; fabricating data is never done in this project.
- Base positions — needs real investigation into `Level.sav`'s map-object save structures, which nothing in this codebase currently decodes; deferred pending that investigation.
- Any game-accurate map background image — ships as a plain coordinate grid; the rendering is built so a user-supplied image can be dropped in later without touching the plotting logic.
- Historical/replay position tracking — this is a live snapshot on the existing poll cadence, not a stored movement trail.

## Verification

**Live, end-to-end**, using a synthetic-but-schema-accurate REST mock (an `HttpListener`-based script simulating `/v1/api/players` with a response body matching the confirmed real Palworld API schema exactly, since no genuine connected player was available in this environment and the real production server was confirmed not running): `GetPlayersAsync`'s new `LocationX`/`LocationY` fields populated with real, non-empty coordinate values end-to-end through the existing poll → REST route → JSON serialization path, confirming the real code path works, not just that it compiles.

`dotnet build` (Release) across all three projects — 0 warnings/0 errors — and `scripts/Test-v0.6.16.0-Logic.ps1 -RunBuild` (13 static contract checks, the frozen v0.6.15.0 regression gate, and the full v0.5.1.5 runtime-smoke suite) all pass.
