# v0.7.97.0 — Crash Analyzer: Known Causes, Fixes, and No More Repeats

## Context

Third of the "enhancements to features we already have". The competitive review had put "troubleshooting
tools" on the list, and reading the headless analyzer showed it was a keyword counter:

- Six needles matched by substring. `"oom"` (meant as OOM) also matches "room", "zoom" and "boom".
- Any line that merely mentioned `ue4ss` or `dwmapi.dll` became a "UE4SS context" warning. On a real,
  healthy server's console log (342 lines) the old logic would have raised that warning on 130 lines of
  ordinary start-up output; the new analyzer reports nothing for the same log.
- A finding was only a title and up to five lines. It never said what the problem usually means or what to do.
- Every run re-read the same logs and re-reported the same lines, so a crash from three weeks ago looked
  as current as one from five minutes ago.
- The exit code MystTiq itself logs when the server process ends (`process exited with code -1073741819`)
  was ignored, though it is the clearest evidence there is.
- It never said which installed mods the evidence names. (The older WPF-era analyzer did weigh mods, but the
  headless service the Desktop uses did not.)

## What changed

- **Signature catalog** (`MystTiq.Core.Services.CrashSignatureCatalog`, pure): 12 known failure signatures,
  each with a severity, a plain-language cause and concrete fixes: missing runtime library, out of memory,
  stack overflow, access violation, disk full, port already in use, save read/write failure, shutdown
  failure, hang, UE4SS or mod script error, Steam initialisation, and a fatal-engine-error catch-all.
- **One signature per line, most specific first**, so a native crash whose stack names UE4SS is one access
  violation finding rather than three overlapping ones. Patterns are word-anchored and have match timeouts.
  UE4SS is only a finding when the same line also reports an error.
- **Exit codes are translated**: the NT status codes that mean access violation, stack overflow, missing DLL
  and fatal failure, and Linux 137/139/134. Exit code 0, -1 (Windows reports it when the real code is
  unavailable) and unknown codes mean nothing. 137 is described honestly: a SIGKILL, most often the kernel
  OOM killer, but anything that force-kills the process gives it.
- **Mods named in the evidence** (`CrashAnalysisBuilder`): the installed mod names are matched against each
  finding's lines (alphanumerics only, names of 4+ characters), shown as "a lead, not proof of cause", and
  put first in the isolation plan ("Disable X first"). If the inventory cannot be read, analysis still
  completes and just names no mods.
- **New versus already reported**: each finding has a key (signature, match count, last matching line). A
  finding whose key appears in an earlier report is "already reported". Analyzing the same logs twice
  raises nothing new; a fresh crash line changes only its own signature's key. New findings sort first, the
  summary counts them, and the activity log only warns for a new Critical finding.
- **First seen / last seen** from the matching lines' own timestamps (UE and MystTiq formats). Lines with no
  stamp of their own are not guessed at.
- **Desktop page**: pick a finding to see what it usually means, what to try, the mods named, when it was
  seen, whether it is new, and its evidence. New findings are marked in the list and history.
- **Stale-data fix**: crash findings, plan and history are per-server, so they are cleared on a tab switch
  and reloaded if the Crash Analyzer page is the one open (the same bug class as the v0.7.89.0 Active World
  card and the v0.7.92.0 base markers).
- Reports saved before this version still load: the new fields are optional. The first analysis after
  upgrading treats everything as new, because old reports carry no keys.

## Deliberately not done

- No claim of root cause. A finding says what the log line usually means and what to try; the mod
  naming is a correlation lead and is labelled that way.
- No automatic disabling of mods, and no change to the crash-recovery supervisor.
- Palworld-specific messages were not invented: signatures use generic Unreal, Windows and Linux patterns
  that are well established, plus MystTiq's own exit-code line. New Palworld-specific signatures should be
  added only from real log evidence.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness: 7 new scenarios pass. They cover catalog integrity (unique ids, cause and fixes on every
  signature), "room", "zoom" and "boom" never matching, a plain UE4SS mention not being a finding, one line
  claimed once, the runtime-smoke fixture still yielding two findings, exit-code translation, timestamp
  parsing in both formats, mod naming and the 2-letter-name guard, first/last seen, new-versus-repeated
  including a fresh crash line, and loading a report saved before this version.
- New live route smoke `Test-v0.7.97.0-RouteSmoke.ps1` (isolated sidecar, fixture log): first analysis returns
  exactly the three expected signatures with causes, fixes and keys and ignores the "room" line; the
  `-1073741819` line becomes an access violation and exit code 0 is ignored; re-analysis reports all three as
  already reported; a new crash line makes only its own signature new; history persists and reloads with the
  new fields.
- Real-data check: the Default Server's real console log copied into an isolated fixture analyzes to no
  findings, where the old logic would have flagged 130 lines. The real server was not touched.
- **NOT verified:** the rendered page. No GUI automation is available here, so the list-plus-detail layout was
  checked through the compiled bindings and code review, not on screen. No real crash was available to
  analyze, so the catalog's cause and fix text is checked for presence and correct matching, not against an
  actual Palworld crash.
