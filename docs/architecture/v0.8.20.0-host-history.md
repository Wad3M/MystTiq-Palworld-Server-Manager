# v0.8.20.0 — Host History

This is a v0.8.17.0 follow-up ("host history"): the HOST tab shows how the machine has been doing, not only how it is
doing now.

## Recording

`HeadlessHostHistoryService` (one per MystTiq, since it is the same machine for every server):
- takes a reading at start and then **once a minute**, from the same `HeadlessHostMonitor` the page reads;
- each reading holds:
  - processor %;
  - memory used %;
  - the **busiest** network adapter's send and receive rates. It is not the sum of the adapters: on a virtual switch
    the physical adapter and the switch carry the same traffic, and adding them would count it twice.
- keeps **7 days** in `FleetRoot/host/history.json`, written at the first reading and then every five minutes, and on
  stop. An unreadable file starts empty instead of stopping MystTiq.

## Serving

`GET /host/history?hours=` (Viewer, scoped like every route):
- the range is clamped to 1 hour .. 7 days;
- the points are thinned to at most 600 by averaging equal slices;
- the **averages and peaks come from every reading**, so a one-minute spike is not averaged away;
- with no readings, the numbers are absent, not zero.

## The card

**History**, on the HOST tab right after "This machine":
- a range picker: last hour, last 24 hours (the default), last 7 days;
- a chart (`HostHistoryChart`):
  - processor (blue) and memory (violet) on one 0–100 % scale;
  - upload (green) scaled to its own peak;
  - a reading without a value (the first processor reading of a session has none) leaves a gap instead of a false
    zero;
- a summary, for example "Processor 27 % on average, peak 80 % · memory 61 % used on average, peak 70 % · busiest
  upload 9.6 Mbit/s";
- a coverage line: how many readings, since when, and what each colour is.

The history loads with the page and when the range changes, then about once a minute (every 12th 5-second refresh),
matching how often a reading is taken.

## Verification

- **Logic harness:**
  - a reading from a snapshot (memory %, the busiest adapter only);
  - a day of minute readings thinned to at most 600 points, with peaks and averages from every reading;
  - no readings gives no numbers;
  - the service drops readings older than 7 days, picks by range (capped at 7 days), writes the fleet file, reloads
    it after a restart, and starts empty from a damaged file.
- **Windows route smoke** (4 checks, published exe): a reading at start with real processor and memory values; the
  file in the fleet folder; ranges clamped; the history kept across a restart, with a new reading added.
- **Linux, isolated on the VM** (4 checks): the version, a first reading from `/proc` in range, the fleet file, and a
  restart.
- **ArtworkHarness: 513 checks.** The summary text, the chart's points, the coverage line, "no readings yet", and the
  three ranges. Render: `host-history`.

## Not done

- There is no per-server history of the server's own traffic (not counted per process by the operating system); the
  Dashboard already keeps the server process's own CPU and memory history.
- History is fleet-wide (one machine). A remote server's history is the remote machine's, recorded by the MystTiq
  running there.
