# v0.8.21.0 — The Linux Service Can Raise the Server's Priority Again

This fixes the limit v0.8.17.0 found on Linux. An unprivileged MystTiq can lower the Palworld server's priority
(niceness 10 for eco mode or below normal) but cannot raise it again. So once eco mode switched on, a player joining
did not bring the server back to full speed. The HOST tab said so, but the only remedies were root or `CAP_SYS_NICE`.

## Why a limit, not a capability

When one process lowers another's niceness, Linux checks the **target** process's `RLIMIT_NICE`, or the caller's
`CAP_SYS_NICE`. The Palworld server is started by MystTiq's service and inherits the service's resource limits.

So the unit `service-install` writes now sets:

```
# MystTiq v0.8.21.0: lets MystTiq raise the Palworld server's priority again after eco mode (HOST tab).
LimitNICE=-11
```

That allows niceness down to -11, which is High, the highest priority MystTiq offers (`ProcessResourceControl.Niceness`).
**No capability is added**, and `NoNewPrivileges=true` stays.

- An existing service keeps its old unit until `service-install` is run again.
- The refusal message and the HOST tab's Linux note now say so.

## `service-unit`

`mysttiq-server service-unit [--config …] [--service-user …]` prints exactly the unit `service-install` would write,
without installing anything or needing sudo. An admin can inspect it first, and the Linux check uses it. On Windows the
command explains that MystTiq installs a Windows service there.

`LinuxSystemdServiceManager.BuildUnitText` is now public and static (the constructor refuses to run off Linux), so the
unit can be checked on any OS.

## Test runs no longer touch the real fleet folder

v0.8.20.0 found that **19 older smokes** (v0.5.1.5, v0.7.12.0 to v0.7.113.0) started `api-run` without their own
FleetRoot. They used the default, the real `ProgramData` fleet folder, so for many versions their API audit lines went
into the real fleet activity log, and since v0.8.20.0 they also added host history readings (of this same machine).

- **`--fleet-root <path>`** (new, any command): overrides the configuration's FleetRoot for that run only. It is
  validated like the file's value (an absolute path, or the command refuses to start) and never written back.
- **All 19 smokes pass it** (`<their temp folder>\fleet`).
- **The gate checks it:** every smoke the gate starts `api-run` from must pass `--fleet-root` or write its own FleetRoot
  into its configuration.
- **New smoke** (`Test-v0.8.21.0-RouteSmoke.ps1`, 3 checks): the host history lands in the given folder, the
  configuration file still names the default FleetRoot, and a relative path is refused.
## Verification

- **Logic harness:**
  - the unit has `LimitNICE=-11`, `NoNewPrivileges=true` and the given user;
  - no `AmbientCapabilities` or `CapabilityBoundingSet`;
  - `ExecStart` is unchanged, and a second server still gets `--server-id`;
  - the limit covers High.
- **Linux VM, isolated** (5 checks; installs nothing):
  - `service-unit` runs as the ordinary user;
  - the printed unit has the limit and keeps `NoNewPrivileges`;
  - no capability is added;
  - **`systemd-analyze verify` accepts it**, `LimitNICE` included (exit 0, no notes);
  - nothing was written outside `/tmp`.
- The gate runs that check in `-RunBuild` when the VM answers, SKIP otherwise.
- **Windows smoke** for `--fleet-root`: 3/3 on the work build.

## Not done

- **Raising a priority through a service actually installed with this unit was not exercised.** That needs
  `service-install` with sudo, and the VM's installed service is off limits for these checks.
  - The kernel rule it relies on is documented behaviour (`setpriority(2)`, `RLIMIT_NICE`).
  - v0.8.17.0 showed the opposite side: without the limit, the raise is refused.
- The installed `mysttiq-palworld` service on the VM keeps its current unit until it is reinstalled.
