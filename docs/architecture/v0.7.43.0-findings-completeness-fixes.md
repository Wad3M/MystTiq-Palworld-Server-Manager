# v0.7.43.0 — Findings Completeness Fixes

## Goal

Nineteenth version in the GUI/workflow/UX overhaul roadmap — a direct mid-session request: *"i also need you to review the required changes from all my previous commands to ensure they are done. For instance the MOD dashboard."* This is not a finding from the original 57-item log; it's a request to audit whether earlier findings actually shipped as intended.

## Audit method

Cross-checked the roadmap's 22-version-slot-to-finding mapping for completeness first: every one of the 57 findings maps to exactly one version, is explicitly folded into a broader item (item 4 into item 51's Update Center Overhaul; item 43 into v0.7.40.0's "Install Validated ZIP moved to top" note), is explicitly deferred and documented as such (item 8; the website-description half of item 40), or needs no code change (item 49, a direct-answer explanation, not a bug). One finding — item 6 — was in none of those categories: it had no version slot, wasn't folded into anything else, and wasn't documented as deferred. A genuine gap, the same shape as item 13's mid-session-discovered missing slot back in v0.7.32.0.

Separately, re-read the *content* of each shipped version's own finding against current code, not just its slot assignment — this is where item 40's MOD Dashboard gap surfaced: v0.7.40.0's roadmap entry itself said "foundation also used by MOD Dashboard's item 40 ask," but the actual implementation only ever touched MOD Library.

## What shipped

### MOD Dashboard's missing mods list (items 21, 40)

Confirmed against the live `MainWindow.axaml`: MOD Dashboard (`IsModDashboardPage`) had a header, 6 summary cards, and a "Needs Attention" card — no list of installed MODs at all, despite the original ask literally being "all of the running Mods should be here listed like the old version. So the Mod on the left and then the description of the MOD on the right" (item 21), echoed independently in item 40's own grounding.

Added a new `Grid ColumnDefinitions="1.6*,*"` section (list left, details right) using the exact same binding pattern already proven on MOD Library (`ModItems`/`SelectedMod`, `HasSelectedMod`, the same per-field details layout: Overall Health/Installation/Runtime/Evidence) — but deliberately **read-only**: no Enable/Disable/Delete/Rollback/Update actions, no Install Validated ZIP card. This matches Dashboard's own pre-existing framing, already present before this release, that the page itself states: *"Open MOD Library to browse, install, or change enabled state."* Dashboard shows the same live data at a glance; MOD Library stays the only place to mutate anything.

The website-sourced description (the other half of item 40, and the "description... grabbed from the website" clause of item 21) is **not** part of this release — the user was asked directly how to scope it and chose designing for multiple sources up front (Steam Workshop plus at least one more), which is real new work (per-source fetch logic, a uniform display contract, caching, an outbound-request security/scope conversation) deserving its own version, not something to improvise here. Evidence surfaces MystTiq's own already-real evidence field in the meantime, same as MOD Library's details panel.

### Footer elapsed-time and server context (item 6)

`IsBusy` turned out to already be per-tab (`get => ActiveTab?.IsBusy ?? false`, backed by `TabSession.IsBusy`) — but `BusyReason`, the descriptive text shown in the footer, is a flat `MainWindowViewModel` field, not tab-scoped. Combined with the original finding's core complaint (no elapsed time, no indication of which tab/server), this meant a busy operation's footer text could look stale or ownerless.

Added:
- `_busyStartedAt`/`_busyServerName` fields, captured together whenever `IsBusy` transitions to `true` (`RaiseIsBusyDependents`), cleared together when it goes `false`.
- A dedicated `DispatcherTimer` (`_busyElapsedTimer`, 1-second interval, wired in the constructor) that only runs while busy, updating a new `BusyElapsedText` property (`"12s"`, `"1m 34s"`, etc.).
- `StatusBarText` now appends the captured server name in parentheses when known: `"Creating backup… (my-server)"`.
- Footer XAML gained a new column showing `BusyElapsedText` (visible only while `IsBusy`), between the reason text and the existing "last updated" timestamp.

Real sub-step/percent-complete progress remains explicitly out of scope — the original finding's own grounding already noted this would likely need backend changes (most operations here are all-or-nothing REST calls, not streamed progress), not something this client-side-only fix attempts to fake.

### Nav pane icons doubled again (direct mid-session request)

"The icons should be 2x the size they are right now" — interpreted as the nav pane icons (the same 25 destinations already resized once in v0.7.32.0, the app's most prominent icon system). Doubling 28×28 to 56×56 in the existing 58px-tall row would have clipped (`Border.navSurface` has `ClipToBounds="True"` and only 2px of vertical border thickness to spare in a 58px row). Scaled the row height (58→72px) and icon column (32→60px, `ColumnSpacing` 10→12) together, the same paired-scaling approach v0.7.32.0 established for the first resize.

## Explicit non-goals

- No change to `IsBusy`'s per-tab architecture — it was already correct; only `BusyReason`'s missing elapsed-time/server-context was the real gap.
- No website-sourced MOD description work — scoped separately, own future version.
- No further findings-completeness audit beyond what's reported here — if more gaps surface later, they'll be handled the same way (documented, then fixed), not retroactively squeezed into this version.
