# v0.7.57.0 — Native Console Capture, Proxy DLL Foundation

## Goal

Surfaced by a live bug report during v0.7.46.0 (no PalServer console output captured), scoped in
detail at v0.7.51.0, and picked up here. Three faster options were already ruled out by direct live
testing before this version:

- **`-ABSLOG="path"`**: no file was ever created, even minutes after UE4SS finished loading mods.
- **Launching `PalServer-Win64-Shipping-Cmd.exe` directly**, bypassing the `PalServer.exe` wrapper:
  zero lines captured even with the process's stdio pipes redirected and the process confirmed alive.
  Unreal appears to allocate and write to its own internal console object, independent of inherited
  OS stdio handles.
- **UE4SS's Lua API**: no hook into Unreal's own engine log exists, only UE4SS's own mod-loading
  diagnostics. Confirmed via UE4SS's own documentation and source (zero references to
  `FOutputDevice`/`GLog`/`LogfImpl` anywhere in its signature-scanning code) that this specific ask
  has been raised by the wider community before and never implemented.

The one proven, working technique other tools in this space use — PalServerLogger, and the same
category UE4SS/PalDefender's own loaders already rely on — is DLL proxy injection: ship a DLL with
the same name as one the game already imports, forward its real exports to the genuine system DLL so
the game behaves identically, and use the loader's own `DllMain` entry point to run arbitrary code
inside the game process.

## What this version actually builds

A new native C++ artifact, `native/MystTiqConsoleProxy/` — genuinely outside the `.NET` solution
(no `.csproj`, no reference from any C# project), built by a new standalone script,
`scripts/Build-ConsoleProxy.ps1`, using the MSVC toolchain confirmed present on this machine
(Visual Studio Community 18, MSVC v143 x86/x64 build tools, `cl.exe` 14.51.36231).

### Target: `DSOUND.dll`, re-verified against the real binary

`dumpbin /imports C:\GameServers\Palworld\Server\Pal\Binaries\Win64\PalServer-Win64-Shipping-Cmd.exe`
confirms the real production binary imports exactly 6 functions from `DSOUND.dll`, **all by
ordinal, not by name**: 11, 1, 3, 6, 8, 12. `dumpbin /exports C:\Windows\System32\dsound.dll`
against the real system DLL maps those ordinals to `DirectSoundCreate8`, `DirectSoundCreate`,
`DirectSoundEnumerateW`, `DirectSoundCaptureCreate`, `DirectSoundCaptureEnumerateW`, and
`DirectSoundCaptureCreate8`. `DSOUND.dll` was chosen (over `d3d9.dll`, which the third-party
PalServerLogger tool uses) specifically because it doesn't collide with anything already loaded on
a real install — confirmed live on this machine's own production server: `PalDefender.dll` already
uses its own `d3d9.dll`-based proxy, and `dwmapi.dll` (the legacy UE4SS proxy position) is present
but disabled (`.myst-disabled` suffix). A second `DSOUND.dll` proxy sitting alongside both is
inert with respect to either.

### Implementation

- `dllmain.cpp`: six `extern "C" __declspec(dllexport)` forwarding stubs, one per real export.
  Each lazily resolves the genuine system `dsound.dll` (loaded via `GetSystemDirectoryW` + a full
  path, never a bare `LoadLibraryW(L"dsound.dll")` — that would re-resolve to this same proxy DLL
  via the standard DLL search order and recurse) and tail-calls the real function with an identical
  signature, so PalServer's actual audio-init behavior is untouched.
- `MystTiqConsoleProxy.def`: pins each export to the **exact ordinal** the real system DLL uses —
  required because PalServer's import table references DSOUND.dll by ordinal, not name; getting
  this wrong would silently resolve the wrong function at runtime.
- `DllMain`: on `DLL_PROCESS_ATTACH`, opens a lifecycle log (`MystTiqConsoleProxy.log`, written next
  to wherever the DLL itself is loaded from — no dependency on any MystTiq-owned config path, since
  this DLL doesn't reference the .NET application at all), loads the real `dsound.dll`, and calls
  `TryInstallLogHook()`. On failure to load the real DLL, logs a fatal error but still returns
  `TRUE` from `DllMain` — a hard failure there would abort the entire host game process, which is
  strictly worse than a proxy that fails open and logs why.

### The actual log-capture hook: deliberately not implemented

`TryInstallLogHook()` is a real, callable function — it isn't a stub that silently does nothing
without saying so. It writes an honest line to the lifecycle log explaining that no hook was
installed, and why: finding `FOutputDevice::LogfImpl`'s real address (it isn't exported, and its
offset isn't stable across builds) requires a live memory signature scan against a running process,
and there is no safe way to test a scan-and-hook implementation without a working PalServer to
verify it against.

That inability compounds with a re-confirmed low-payoff finding: this session independently
re-ran the same check v0.7.51.0's investigation did — searching the current binary for standard
Unreal log category strings (`LogTemp`, `LogEngine`, `LogNet`, `LogPal`, `LogWorld`, `LogInit`) —
and found zero matches, all six. `NO_LOGGING` still appears to hold for this build. Even a
successfully-installed hook would likely capture very little beyond crash/fatal-path messages
MystTiq's own crash analysis already surfaces another way.

Writing untested, speculative memory-patching machine code and shipping it as if it were real
capability — especially code that gets injected into a live game process — is exactly the kind of
fabrication this project's whole session has avoided. The honest, disclosed scaffold here is worth
more than a plausible-looking hook nobody has verified doesn't crash the server.

## Why live testing wasn't possible this session

The same session that built this proxy also investigated, in parallel, why this machine's real
production PalServer can't currently launch cleanly at all — a separate, pre-existing issue, not
caused by this work. Findings, for whoever picks this up next:

- The production server (and a freshly-cloned second instance at a different path/port) both freeze
  identically on every launch attempt: process starts, the engine process (`PalServer-Win64-
  Shipping-Cmd.exe`) shows near-zero CPU growth indefinitely, the UDP game port never binds, no
  crash, no Windows Defender detection logged, nothing in the Application/System/Defender-
  Operational event logs.
- **Ruled out**: a device reboot (retried after, identical freeze). The entire injection chain —
  `UE4SS.dll`, `PalDefender.dll`, `d3d9.dll` and its proxy — temporarily disabled via a reversible
  rename, confirmed the exact same freeze still happens with none of them present, then fully
  restored.
- **New finding, still unexplained**: `steamcmd.exe` itself — with zero Palworld involvement,
  just `steamcmd.exe +quit` — crashes on this machine right now with a genuine Windows exception,
  `STATUS_STACK_OVERFLOW` (`-1073741571` / `0xC00000FD`), not a normal SteamCMD self-update signal.
  Checked and ruled out as explanations: `AppInit_DLLs` (empty, disabled), Controlled Folder Access
  (disabled), Attack Surface Reduction rules (none configured), third-party antivirus (none
  registered besides Defender), Winsock LSP corruption (checked, inconclusive), recently-installed
  services (Docker Desktop and Claude's own service, both routine, both unrelated).
- This points to something systemic on this machine outside Palworld/MystTiq entirely, needing
  tools this session doesn't have (Process Monitor, Process Explorer thread-state inspection, or
  WER crash-dump analysis) to actually diagnose. Left as an open, disclosed environment issue.

## Verification performed

- `scripts\Build-ConsoleProxy.ps1` builds `MystTiqConsoleProxy.dll` cleanly via the real MSVC
  toolchain (`cl.exe`/`link.exe`).
- `dumpbin /exports` against the built DLL confirms all 6 exports land at the exact ordinals the
  real system `dsound.dll` uses — an exact, verified match, not an assumption.
- Loaded the built DLL in complete isolation (a throwaway directory, `LoadLibrary`/`GetProcAddress`/
  `FreeLibrary` via a small P/Invoke harness) — confirmed `DllMain` runs, the real system DLL
  resolves and an export address is returned, the lifecycle log is written correctly with all four
  expected lines (inject → real DLL loaded → hook scaffold logs its own no-op status → detach), and
  the DLL unloads without crashing.

## Known gaps (disclosed)

- **Never loaded into a real PalServer process.** The isolated `LoadLibrary` test above proves the
  DLL is well-formed and its forwarding logic works; it does not prove the game itself loads and
  runs correctly with this DLL present in its own binary directory, since that requires the same
  production server that currently can't launch cleanly at all for unrelated reasons.
- **No log-capture hook.** `TryInstallLogHook()` is a real, honest scaffold, not a working
  capability. Finishing it needs: (1) a live, healthy PalServer to test a memory signature scan
  against, and (2) given the re-confirmed `NO_LOGGING` finding, a clear-eyed judgment call on
  whether the resulting payoff (likely crash/fatal-path messages only) justifies the remaining work.
- **Not wired into MystTiq's own install/deploy flow.** Deliberately — an unverified native
  component that gets injected into a user's live game process should not be silently bundled into
  a real release until it's actually been proven safe against a running server.
