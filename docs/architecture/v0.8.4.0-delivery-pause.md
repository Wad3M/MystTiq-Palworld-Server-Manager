# v0.8.4.0 — Pause Discord, Email & Webhooks

This closes the v0.7.111.0 follow-up: "muting delivery routes only (Discord/email) while keeping the Notifications
page". The v0.7.111.0 alert mute stops alerts from being raised at all. This adds the lighter option: keep every
notification in MystTiq, and stop the outside pings for a while (for example during maintenance, or at night).

## Design

- **One choke point.** Every notification is created by `HeadlessNotificationService.Create`. That method persists the
  notification, then hands it to `HeadlessNotificationRoutingService.Dispatch`, which forwards it to Webhook, Discord
  and Email. The pause is checked in `Dispatch` only, so:
  - alerts, crash alerts, automation "send notification" actions and the test notification are all covered;
  - the Notifications page is never affected;
  - each skipped send is written to the Activity log as "Not sent outside (delivery paused)", with its title and
    the channels it would have gone to.
- **Separate storage.** The pause is kept in `notifications/delivery.json`, apart from `channels.json`. Saving the
  channel list replaces that file whole, so a client could otherwise clear or set a pause by accident.
- **Same rules as the alert mute.** The end time is computed on the host's clock and capped at 30 days
  (`AlertMutePolicy.MuteUntil`); `minutes <= 0` resumes; `NotificationDeliveryPolicy.IsPaused` is the pure check.
- **Not queued.** Notifications from the pause are not sent afterwards. They are on the Notifications page already,
  and a burst of stale pings when the pause ends would be worse than none.
- **Per server profile**, like the channels themselves.

## Routes

- `GET /api/v1/notifications/delivery`: the end time (if paused), which outside channels are on, and a plain
  sentence describing the state.
- `POST /api/v1/notifications/delivery/pause` with `{minutes}`: Admin, the same role as the alert mute.
- `POST /api/v1/notifications/test` (Admin): creates a "Test notification" through the normal path. The reply says
  where it went: "sent to Webhook", "Notifications page only: outside delivery is paused", or "no outside channel is
  switched on". Sending is fire-and-forget, as before, and a failed send lands in the Activity log.

## Desktop

Alert Center has a new "Pause Discord, Email & Webhooks" card below Mute Alerts, with:
- the state in plain words (local time), which also says when no outside channel is on;
- Pause buttons for 1 hour, 8 hours, 24 hours and 7 days;
- Resume, shown only while paused;
- Send Test Notification.

The state loads with the Alert Center.

## Verification

- **Logic harness, 2 scenarios.**
  - The policy: the host-clock end time, the 30-day cap, 0 resumes, the pause surviving a restart and a channel
    save, and an unreadable file meaning "not paused".
  - A real `HttpListener` webhook: it receives while on, receives nothing while paused (the notification is kept and
    the skip is logged), and receives again after resuming, with nothing sent late.
- **Route smoke** (`scripts/Test-v0.8.4.0-RouteSmoke.ps1`). Runs the published exe against a localhost-only webhook
  receiver in the script, with its own FleetRoot. It checks:
  - a test notification arrives while on;
  - while paused, nothing arrives and both notifications are on the page;
  - the pause survives a sidecar restart plus a channel re-save;
  - after resuming, it arrives again, and nothing arrives late;
  - the 30-day cap.
- **Live Desktop** on the clone profile, which has no outside channels, so nothing could leave the machine: the card
  shows the state; Pause 1 hour sets it on the host for the clone only (Default untouched); Resume clears it
  (`delivery-pause-live.png` in the checkpoint).

## Not verified

- Real Discord or email delivery. No live endpoint was used; a webhook is the same HTTP path Discord uses.

## Also decided this version: teleport points on the map (not done)

PalDefender's documentation does not say whether `tp` and `getpos` use Unreal world units or the in-game map units
([Commands wiki](https://ultimeit.github.io/PalDefender/Commands/)). Its issue tracker also has a report of `getpos`
giving off coordinates over RCON ([issue #113](https://github.com/Ultimeit/PalDefender/issues/113)). No player was
online to measure it, so drawing points on the map would be a guess.

A sound way to do it later: when Capture runs for an online player, record PalDefender's position together with the
REST API's world position for the same player at the same moment. That pair tells MystTiq the conversion. See the
roadmap.
