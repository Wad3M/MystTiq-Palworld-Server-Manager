# v0.7.39.0 — Mod Install Type Auto-Detection

## Goal

Fifteenth version in the GUI/workflow/UX overhaul roadmap. Roadmap item 44 — the mod-install flow should detect PAK vs. UE4SS from the ZIP's actual contents, instead of requiring a manual dropdown pick.

## Grounding

Confirmed during the original walkthrough that the existing per-row "TYPE" column on the Installed MODs list already correctly distinguishes PAK vs. UE4SS for mods already on disk — that detection logic (`HeadlessModManagementService.ScanPakMods`/`ScanUe4ssMods`) was never the gap. The gap was specifically in *installing a new mod*: `ModInstallType` (`MainWindowViewModel`) was a plain `ComboBox` bound to `["PAK", "UE4SS"]`, defaulting to `"PAK"`, sent as-is to `InstallModZipAsync` with zero inspection of the actual ZIP contents. Forgetting to flip the dropdown silently installed the wrong type.

## What shipped

### Server-side detection (the real fix)

`HeadlessModManagementService.InstallZipAsync` already extracts the uploaded archive to a staging directory before deciding how to install it (`extracted`, populated by the existing traversal-safe extraction loop). A new `DetectModType(string extracted)` helper inspects that extracted tree directly: any `.pak`/`.ucas`/`.utoc` file anywhere in it (recursively) is an unambiguous PAK signal — no UE4SS/Lua mod ever ships those file types. Everything else installs as UE4SS; `InstallUe4ssFiles`' own pre-existing "archive is empty" check still catches a genuinely empty upload, now surfaced as a UE4SS-specific message rather than a generic "unsupported type" error (which, in practice, never used to fire anyway, since the client's fixed two-value dropdown always sent one of the two supported strings).

The detected type — not the caller-supplied `type` parameter — now drives which install branch runs (`InstallPakFiles`/`InstallUe4ssFiles`), what gets recorded in the activity log, and what `HeadlessModMutationResult.Type` the client gets back. When the detected type differs from what the client requested, the activity log records both (`requestedType=... (auto-corrected from archive contents)`), so a genuine mismatch stays visible in the audit trail rather than silently disappearing.

### Client-side: the dropdown is gone

The `ComboBox` in MOD Library's "Install Validated ZIP" card (bound to `ModInstallTypes`/`ModInstallType`) was removed entirely — there's nothing left for a user to pick, since the server decides for itself from real content. `MainWindowViewModel.ModInstallType`/`ModInstallTypes` were removed as dead properties (only ever referenced by that one binding and the install call site).

### What still sends a type on the wire, and why

`InstallModZipAsync`'s API surface still takes a `type` string parameter — `CaptureSnapshot(type, package)` runs *before* extraction (it needs to snapshot whatever already exists under that package name, for rollback safety, before the new archive overwrites it), so it has no way to know the new archive's real type yet at that point in the method. The client now sends a fixed `"PAK"` literal instead of a user-chosen value — byte-for-byte the same value most installs already sent by default before this release (the dropdown defaulted to `"PAK"`), so `CaptureSnapshot`'s existing pre-existing-mod lookup behaves identically to today for the common case. The one edge case this doesn't cover — re-installing a ZIP under a package name that previously existed as the *other* type — was already a narrow edge case unrelated to this item's scope (install-type correctness, not cross-type package-name collision handling), and is unaffected in practice: the new archive still installs at the correct (detected) location either way; only the rollback snapshot's search location could miss in that specific scenario.

## Explicit non-goals

- No change to the existing per-row Installed MODs Type detection (`ScanPakMods`/`ScanUe4ssMods`) — already correct, not part of this finding.
- No change to `DeleteAsync`/`RollbackAsync`/`CaptureSnapshot`'s own `type`-parameter-driven behavior beyond what's described above — those still require and trust an explicit type, since they act on an already-installed mod whose real type is already known from the inventory, not freshly-uploaded unknown content.
