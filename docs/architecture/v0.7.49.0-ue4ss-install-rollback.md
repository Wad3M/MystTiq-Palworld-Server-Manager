# v0.7.49.0 — UE4SS Install/Rollback

## Goal

v0.7.47.0 gave the UE4SS page's "Release source" dropdown real data for the first time (`GET /api/v1/ue4ss/releases`), but was deliberately listing-only — actually installing a selected release writes into the server's UE4SS binaries and was scoped as its own, higher-risk version. This is that version: real install and rollback, built on the release catalog v0.7.47.0 already shipped.

Mid-session, the user asked to push v0.7.48.0's remaining ~240 hardcoded "glass" gradient colors to the very end of the 0.7.x roadmap line (now v0.7.57.0+) so the rest of the new-capability roadmap ships first. The plan file was renumbered; this item moved up into the freed v0.7.49.0 slot.

## Investigation performed before writing any install code

The plan's own item 26 (the original slot for this work) explicitly flagged the release zip's internal structure as unverified: "verify the actual zip contents against both target layouts before deciding." That verification was done directly, live, against real GitHub release assets, before any design decision was made:

```
curl -sL -o fork.zip "https://github.com/Okaetsu/RE-UE4SS/releases/download/2281fa31/UE4SS-Palworld-g2281fa31.zip"
unzip -l fork.zip
```

Fork zip (`Okaetsu/RE-UE4SS`, tag `2281fa31`) — **modern layout**:
```
dwmapi.dll                          <- zip root
ue4ss/LICENSE
ue4ss/MemberVariableLayout.ini
ue4ss/Mods/...                      <- bundled default mods, mods.txt, mods.json
ue4ss/UE4SS.dll
ue4ss/UE4SS_SDK_Backends/UE4SS.json
ue4ss/UE4SS-settings.ini
```

```
curl -sL -o upstream.zip "https://github.com/UE4SS-RE/RE-UE4SS/releases/download/v3.0.1/UE4SS_v3.0.1.zip"
unzip -l upstream.zip
```

Upstream zip (`UE4SS-RE/RE-UE4SS`, tag `v3.0.1`) — **legacy flat layout**:
```
dwmapi.dll                          <- zip root
UE4SS.dll                           <- zip root
UE4SS-settings.ini                  <- zip root
Mods/...                            <- zip root, bundled default mods + mods.txt
Changelog.md, README.md             <- zip root, non-engine files
```

**This is the finding that shaped the whole design**: the two catalog sources are not the same file layout under different version numbers — they are genuinely different packaging conventions. `ResolveUe4ss()` in `HeadlessModManagementService.cs` already distinguishes "modern" (`Ue4ssRoot`/`ue4ss/Mods`) from "legacy" (`LegacyUe4ssModsRoot`, flat under `RuntimeBinaryRoot`) for *mod detection*, but nothing in the codebase had previously confirmed which packaging convention each release source actually ships. Guessing a flatten/nest transform between them — the approach originally sketched in the plan before this verification — would have been unverifiable without live testing against a real server, exactly the kind of guess this project's established discipline avoids (see the console-capture investigation in v0.7.46.0/v0.7.47.0, or the PalServerLogger license decision).

## Design decision: mirror, don't normalize

Rather than transform every release into one canonical on-disk layout, install faithfully mirrors whatever the selected zip's own root structure already is onto `RuntimeBinaryRoot`. This is not a simplification for its own sake — it is *exactly* what each project's own install instructions already tell a human to do by hand (extract to `Pal/Binaries/Win64`), so there is zero guessed transformation logic between "what the zip contains" and "what ends up on disk."

Consequence: install does not target "modern" or "legacy" as a policy choice. It detects which layout the *selected zip* uses (`zip.Entries.Any(e => path starts with "ue4ss/")`) and, separately, which layout (if any) is *already installed* (`Directory.Exists(Ue4ssRoot)` vs. legacy marker files `UE4SS.dll`/`UE4SS-settings.ini` directly under `RuntimeBinaryRoot`). If those disagree and something is already installed, install is refused with a clear explanation rather than silently leaving both layouts in place — directly motivated by the fork's own release notes warning that two copies of UE4SS loading at once **will crash the game**. A fresh server (nothing installed either way) accepts either source.

## Mod-state safety

Every zip entry whose normalized path contains a `Mods` path segment, at any nesting depth (`Mods/...` for the legacy layout, `ue4ss/Mods/...` for modern), is skipped outright during install — never extracted, never even creates the destination directory. This is enforced at the same point the path-traversal guard already established by `InstallZipAsync` runs, so it inherits that same defense. `mods.txt`, `mods.json`, and every user-installed mod folder are therefore structurally impossible for an engine install to touch, not just conventionally avoided.

`UE4SS-settings.ini` (wherever it appears in the zip) is skipped if the destination file already exists on disk — preserved rather than overwritten, since it is commonly hand-edited. This directly matches language in UE4SS's own real v3.0.1 release notes about "replacing files while preserving custom configuration settings." If it does not exist yet (fresh install), the zip's own default is installed normally.

## Preview → Apply → Rollback

Reuses the exact Preview-then-Apply token shape `HeadlessBackupService.PreviewRetention`/`ApplyRetentionAsync` already established, rather than inventing a new pattern:

- **`PreviewUe4ssInstallAsync(source, tagName)`** re-resolves the selection against the live GitHub catalog **server-side** — the client sends only `{source, tagName}`, never a raw download URL, closing what would otherwise be an SSRF-shaped gap (a client-supplied arbitrary download URL fetched server-side) before it was ever introduced. Returns a random 24-byte hex token (`RandomNumberGenerator`, same convention as the backup retention token), a 15-minute expiry, and a plain-language summary including the detected current layout.
- **`ApplyUe4ssInstallAsync(token)`** validates the token and its expiry, then requires PalServer stopped (`lifecycle.GetStatusAsync` — the same check `RejectWhenRunningAsync` already performs for mod mutations) since UE4SS's DLLs are loaded into the running process; overwriting them live would at best fail with a file-lock error and at worst corrupt a running process's mapped image. Downloads the release asset (200 MB cap, 3-minute timeout, streamed to a staging file — not buffered in memory), extracts to a staging directory with the same path-traversal guard `InstallZipAsync` already uses for user-uploaded archives, checks the layout-mismatch rule above, then takes a snapshot (see below) before writing anything into `RuntimeBinaryRoot`.
- **`RollbackUe4ssInstallAsync()`** restores the most recent snapshot on demand. Also invoked automatically from inside `ApplyUe4ssInstallAsync`'s catch block if any step after the snapshot fails, so a failed install cannot leave a half-overwritten engine on disk.

## Snapshot precision

Unlike the per-MOD snapshot mechanism (`CaptureSnapshot`/`RollbackAsync`, v0.6.8.0) which zips an entire package folder, the engine snapshot is scoped to **exactly the set of relative paths the current install is about to write** (`plannedWrites`, computed after the Mods-folder skip is applied) — nothing more. For each planned path, if a file already exists there, it's added to the snapshot zip and recorded in `existedPaths`; if not, it's recorded only in `plannedPaths`. On rollback, a path present in `plannedPaths` but absent from `existedPaths` is deleted (the install created it fresh, so "before" means "did not exist"); every path in `existedPaths` is re-extracted from the snapshot zip. This is deliberately more precise than a whole-directory backup: it can never restore into (or need to touch) `Mods/`, because paths under `Mods/` were never added to `plannedWrites` in the first place.

A snapshot failure (I/O error, disk full) does not block an install the operator already explicitly confirmed via Preview — same policy the per-MOD `CaptureSnapshot` already established, documented at both call sites.

## API surface

All under the existing per-profile `routes` group in `LocalManagementApiHost.cs`, alongside the existing `/mods/*` and `/ue4ss` routes:

- `GET /ue4ss/install/status` — `{ RollbackAvailable: bool }`.
- `POST /ue4ss/install/preview` — body `{ Source, TagName }`, returns `Ue4ssInstallPreview` (200) or 404 if the release has no clear primary asset or doesn't exist.
- `POST /ue4ss/install/apply` — body `{ Token }`, returns `Ue4ssInstallResult` (200 on success, 409 on failure — matching the existing `/mods/*` mutation routes' success/Conflict convention).
- `POST /ue4ss/install/rollback` — same result shape.

The three mutating routes are gated `RequireRole(Admin)`, matching how this route group already gates other destructive/install-class actions (e.g. principal management, Discord bot config).

## Desktop changes

- `SelectedUe4ssRelease` (new bindable property) backs the release list, now a `ListBox` with `SelectedItem` binding instead of the prior read-only `ItemsControl`.
- Three new ribbon buttons on the UE4SS page — Preview Install, Confirm Install, Rollback — replace the permanent "Installing a specific release isn't wired up yet" stub text that has been there since v0.7.47.0.
- `Ue4ssInstallState` shows the live preview summary (including detected current layout and expiry) or the last install/rollback result message.
- Changing `SelectedUe4ssRelease` invalidates any outstanding preview token (mirrors `BackupRetentionToken`'s own invalidate-on-change behavior for retention cleanup), so Confirm Install can never fire against a preview that no longer matches the current selection.
- `RefreshUe4ssReleaseCatalogAsync` (already wired to the existing "Refresh Runtime" button) now also calls `GET /ue4ss/install/status` to keep `Ue4ssRollbackAvailable` current.

## Live verification performed

Unlike a static-only gate, the actual install/preview/apply/rollback code path was exercised end to end against real GitHub release data, through a throwaway console harness (`HeadlessModManagementService` constructed directly against a fake `IServerPathProfile`/`IServerLifecycleService` pointed at a temp directory tree — not the shipped codebase, deleted after use) — the same "prove it against real data, not the shortest plausible story" discipline used for the console-capture investigation. Four scenarios, 21 assertions, all passed:

- **Fresh install, modern layout** (`Okaetsu/RE-UE4SS`, tag `2281fa31`): preview resolves, apply installs `dwmapi.dll` at the binaries root and `ue4ss/UE4SS.dll`/`ue4ss/UE4SS-settings.ini` under the subfolder, `ue4ss/Mods` is never created, rollback removes every file the install wrote (correct "didn't exist before" behavior).
- **`UE4SS-settings.ini` preservation**: a pre-existing settings file with a custom marker survives a real install untouched, while the engine DLL still installs normally alongside it.
- **Layout-mismatch refusal**: a fake legacy install (bare `UE4SS.dll`/`UE4SS-settings.ini` at the binaries root) correctly causes preview to report "Legacy (flat root)" and apply to refuse installing the fork's modern-layout zip, with the legacy files left completely untouched and no `ue4ss/` folder created.
- **Fresh install, legacy layout** (`UE4SS-RE/RE-UE4SS`, tag `v3.0.1`): apply installs `UE4SS.dll` directly at the binaries root (no `ue4ss/` subfolder), `Mods/` is never created.

## Known gaps (disclosed)

- **No visual verification possible in this environment** — same limitation as every prior version touching the UI. The ribbon buttons, ListBox selection, and status text were verified to compile and bind correctly, not verified to render correctly.
- **Not exercised against a real, already-populated Palworld server install** — the live verification above used a synthetic directory tree, not a real server with a real PalServer.exe and a real prior UE4SS install. The Windows file-lock behavior when PalServer is truly stopped vs. merely reporting stopped, and behavior against a real install's exact on-disk quirks, are still unverified against a live server.
- **`UE4SS-settings.ini` preserve-if-exists is a policy choice, not a detected fact** — there is still no way to distinguish "user customized this file" from "this is exactly the shipped default from a prior install," so a fresh install onto a server whose settings file was never touched keeps stale defaults from an older release rather than picking up the new release's defaults. Disclosed as the same "no existing code distinguishes default vs. user-edited content" gap the original research flagged.
- **Only one engine snapshot is kept at a time** (`UE4SS-ENGINE_current.zip`, overwritten on every install), matching the per-MOD snapshot's own "undo my last change" scope rather than a full history — consistent with, not a regression from, the existing pattern.
