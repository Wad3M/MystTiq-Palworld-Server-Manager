## Real bugs found and fixed

### 1. `Level.sav.json` explorer sidecar staleness (first disclosed v0.5.2.0, unfixed through v0.6.7.0)

`HeadlessPlayerGuildExplorerService`/`HeadlessWorldExplorerService` read a static `Level.sav.json` sidecar beside the active `Level.sav` for their read-only Players/Guilds/World Explorer views. Nothing ever regenerated it after a guild/base/character mutation committed, so those views could show stale data until something external re-decoded it — disclosed as a known gap in seven consecutive checkpoints across nine months without ever being fixed.

Root cause was pure oversight, not missing infrastructure: every guild/base/character mutation service (`HeadlessGuildOwnershipService`, `HeadlessBaseOwnershipService` x2, `HeadlessCharacterMigrationService`) already independently re-decodes the just-committed save as its own verification step (`verifyJsonPath`) before returning success — that already-produced, already-verified JSON was just being thrown away instead of also being persisted to the sidecar path the explorer services actually read.

Fixed with a new `HeadlessSaveCodecService.RefreshExplorerSidecar(levelSavePath, verifiedDecodedJsonPath)` — copies the already-verified JSON to `Level.sav.json` beside the committed save. Best-effort by design: it runs *after* the mutation has already committed and been independently verified, so a refresh failure must never fail or roll back a successful save mutation — worst case, the explorer view stays exactly as stale as it was before this fix existed, never worse. Wired into all four commit sites.

**Verified live, end-to-end, against a real isolated copy of production save data** (never the production directory or process): applied a real `TransferLeadership` operation via the actual API (`POST /guilds/ownership/preview` → `POST /guilds/ownership/apply`) against guild `11D02AC34634E88B6A9262A0C74FCD53` ("MystTik"), transferring leadership from Melly to Wade. Confirmed `Level.sav.json`'s modified timestamp changed from the original decode time to the moment of commit, and confirmed a fresh `GET /world/players-guilds` call immediately afterward — no other action taken in between — correctly showed Wade as Leader. This is the exact bug, closed for real, not just patched around.

### 2. `config-write-default` silently ignored its own documented CLI overrides

`--server-root`/`--steamcmd`/`--backup-root`/`--runtime-root` are documented, general CLI options (`mysttiq-server.exe --help`) and every other command applies them after loading the configuration. `config-write-default` returned early, before that override logic ever ran, and unconditionally wrote `HeadlessConfiguration.CreateDefaultForCurrentPlatform()`'s hardcoded built-in path regardless of what was passed on the command line — a real, confusing inconsistency for any scripted/unattended provisioning flow.

**Found by this session's own bug-testing methodology, not by the static audit**: setting up an isolated test environment with `config-write-default --server-root <scratch path>` produced a config file whose `ServerRoot` was still the hardcoded default (which, on this development machine, happens to be the real production Palworld install path) — a genuine near-miss caught before any mutating call was made against it.

Fixed: `HeadlessConfigurationService.WriteDefault` gained an optional `HeadlessConfiguration? configuration` parameter (defaults to the same built-in behavior when omitted, so every other caller is unaffected); `config-write-default` now builds the effective default with the same override-application pattern every other command already uses, and writes that. Verified: re-running `config-write-default --server-root <scratch path> --overwrite` now produces a config whose `ServerRoot` genuinely reflects the override.

## Real finding, documented but not fixed (low severity, not a safety defect)

Automation rule creation (`POST /automation/rules`) accepts negative/invalid numeric trigger values without validation — e.g. `idleThresholdMinutes: -5` is accepted and persisted as-is (HTTP 200). This is **not** a functional safety bug: the actual idle-evaluation path (`HeadlessAutomationService`, idle-rule tick) already defends against it with `Math.Max(1, rule.Trigger.IdleThresholdMinutes ?? 30)`, so a negative or zero value is silently clamped to a safe 1-minute minimum at evaluation time regardless of what was stored. The gap is purely display/data-integrity: the persisted and API-returned value doesn't match the value actually enforced, which could confuse an admin reading it back. Deferred rather than fixed this pass — closing it properly means deciding validation ranges across every trigger/action numeric knob (`idleThresholdMinutes`, `jitterSeconds`, `missedGraceSeconds`, `warningCountdownSecondsBeforeAction`), not a one-line change.
