# v0.7.46.0 — Console Newest-First Ordering

## Goal

A direct live bug report against the user's own real running server, not from the original
57-item findings log: *"console still does not capture events from palworld server file. Also
does not connect to the server backend, tells me operation failed."* This version documents the
live investigation of both, the fix that shipped for one of them, and a follow-on UI request made
while confirming the fix.

## Investigation: "operation failed" / doesn't connect

Investigated live, read-only, against the user's actual running instance (PID confirmed via
`Get-CimInstance Win32_Process`), never touching or restarting their real server without
authorization:

1. `GET /healthz` → healthy, reachable, `version: 0.7.45.0` (confirmed the user was running the
   just-shipped build).
2. `GET /api/v1/config` → effective configuration loaded correctly, `startupTimeoutSeconds: 90`.
3. `GET /api/v1/status` → `"ready": false"`, `"guardedListeningPorts": []`,
   `"detail": "PalServer process is active; UDP 8211 has not been confirmed."` — **10 minutes**
   after the process had started, still not ready.
4. `Get-NetUDPEndpoint` (direct OS-level check, not MystTiq's own view) → the real
   `PalServer-Win64-Shipping-Cmd.exe` process was bound to **UDP 27015**, not 8211. Nothing at all
   was listening on 8211.

## Root cause

`PalWorldSettings.ini`'s `PublicPort` setting does **not** control which UDP port PalServer
actually binds — only the `-port=` command-line launch argument does. This was discovered and
fixed for the Clone World feature in v0.6.10.0 (`HeadlessWorldCloneService` explicitly strips any
existing `-port=` argument and injects the correct offset one), but that fix was never backported
to the pre-existing "default" profile, which predates Clone World. Its `LaunchArguments` never
had `-port=8211` added, so PalServer fell back to Steam's own default (27015) instead.

Since MystTiq's own readiness detection (`WindowsServerLifecycleService.GetStatusAsync`) only ever
polls for `expectedGamePort` (8211 by default), it could never observe the real process as ready —
`ready` stayed `false` indefinitely, and any Start/Restart operation exhausted its
`StartupTimeoutSeconds` (90s) and returned `HeadlessExitCode.StartupTimeout` (`Success: false`),
which the Desktop UI renders as `ConnectionState = "Operation failed"` — even though the process
was alive and completely healthy the entire time. This is also a real, live-server-affecting bug:
if players were told to connect on port 8211 (the "advertised"/configured port), they may have been
unable to reach the actual running server on 27015.

## Fix applied (live, with the user's explicit approval)

Added `-port=8211` to the profile's `LaunchArguments` via a live `PUT /api/v1/config/editable` call
against the user's own running instance — the same safe, schema-validated route the Desktop app's
own Configuration page uses, rather than hand-editing the JSON file directly (avoids guessing at
install paths or risking a malformed write while a live process might have the file open).
Confirmed by re-reading the persisted `C:\ProgramData\MystTiqPalworldServer\mysttiq.json`
afterward — the new argument was present on disk.

**Applying the fix requires two restarts, both deliberately left to the user's own timing**:
1. The MystTiq backend service itself needs to reload the config from disk (a full
   close/reopen of the app, or equivalent).
2. PalServer needs its own restart afterward to actually bind the corrected port.

Neither was performed automatically — this is the user's live server with real players on it, and
the standing safety rule from this whole project (never touch the user's live PalServer process
without explicit, per-instance authorization) applied here exactly as it has all session.

## Investigation: console not capturing PalServer events (root-caused, not yet fixed)

Read the real `MystTiq-PalServer-Console.log` (`ServerRoot\Pal\Saved\Logs\`), spanning Aug 27
through Sep 10 across many restarts. Pattern, consistent across every single session: the initial
UE4SS/MOD-load startup banner (~20-30 lines: Win64 Root, UE4SS Root, Mods Root, Runtime Verified,
per-mod `ENABLED` lines) gets captured, then the file goes completely silent for the rest of that
run — regardless of how many hours the server then stayed up.

Cross-checked against `Pal\Binaries\Win64\ue4ss\UE4SS.log` (UE4SS's own log file, a genuinely
different source from MystTiq's redirected stdout capture): it stops updating at the **exact same
timestamp** as the console capture goes quiet. Both independently pointing at the same moment is
strong evidence this isn't "the server just doesn't produce much output" — it's that the specific
process MystTiq is capturing stops being the one doing real work.

**Root cause**: `WindowsServerLifecycleService.StartAsync` redirects stdout/stderr only from the
immediate child process it starts via `Process.Start` (`PalServer.exe`, a thin bootstrap wrapper).
The actual Unreal Engine dedicated-server work — and therefore essentially all ongoing gameplay
output — happens in `PalServer-Win64-Shipping-Cmd.exe`, a separate **grandchild** process with its
own console/window. This codebase already documents that grandchild's separate window in
`ApplyPostLaunchWindowPolicyAsync`'s own comment (written for the unrelated purpose of hiding its
window), but nothing had previously connected that fact to the console-capture gap.

This closes out item 14 from the original findings log, which was explicitly left as *"needs a
live check against an actual modded, running server before concluding any code change is
required"* — that live check has now happened, with a real, specific, previously-undiagnosed root
cause. **The actual fix (capturing the grandchild process's own stdout/console) is genuine new
feature work** — it needs design (does the grandchild process inherit a redirectable stdout handle
at all, or does capturing it need an entirely different mechanism, e.g. attaching to its console or
reading a log file it writes) that hasn't been done yet. Tracked as its own future roadmap item
rather than rushed into this version.

## What shipped: Console Newest-First Ordering

While confirming the port fix on the Console page, the user asked for the log view to show the
most recent activity at the top instead of the bottom.

- `MainWindowViewModel.ApplyConsoleFilter()` now builds `FilteredLogLines` by iterating
  `LogLines.Reverse()` instead of `LogLines` directly. `LogLines` itself is untouched and keeps its
  original chronological (oldest-first) order.
- `DashboardActivityLines` (the Dashboard's Live Activity panel) still reads from `LogLines`
  directly and is unaffected — this change was scoped to exactly what was asked (the Console page),
  not applied speculatively elsewhere.
- Export Console (`MainWindow.axaml.cs`'s `ExportConsole_Click`) reads from `FilteredLogLines`
  unchanged, so an exported file now comes out newest-first too — a deliberate choice, not an
  oversight: the button exports "the console view," and after this change that view is newest-first,
  so the file matches what was on screen when the user exported it.

## Explicit non-goals

- No fix for the grandchild-process console-capture gap in this version — tracked separately.
- No automatic restart of the user's live MystTiq backend or PalServer process — the config fix is
  saved and verified, applying it is the user's own decision on their own timing.
- No change to `LogLines`'s own ordering, `DashboardActivityLines`, or any other consumer of the
  console log data — scoped to exactly the Console page's own display order, as requested.
