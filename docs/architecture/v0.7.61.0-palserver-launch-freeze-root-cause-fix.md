# v0.7.61.0 — PalServer Launch Freeze Root Cause Fix

## Goal

Find and fix the actual root cause of the PalServer launch freeze investigated on and off since
v0.7.57.0, most recently reprioritized by the user as top priority: "keep working on the crash
fix. this is top priority to be able to start and stop servers individually."

## Investigation history (context)

Prior sessions ruled out, in order: the UE4SS/PalDefender/d3d9 injection chain (disabled entirely,
froze identically), a device reboot (retried, identical), game file corruption (SteamCMD validate
confirmed the full ~5.9GB install matches Steam checksums exactly), Windows Defender exclusions
(added, no change), a newer UE4SS install (installed, no change), and — earlier this session — a
Hyper-V networking theory: the host's default route ran entirely through Hyper-V External virtual
switches bound to the physical Realtek Gaming NIC (one deliberately named "MystTiq External"),
which is a documented source of UDP stalls under some Realtek driver/Hyper-V combinations. That
switch was live-reassigned to a spare USB NIC (`Set-VMSwitch -NetAdapterName "Ethernet 2"`),
confirmed via routing table that the physical Gaming NIC was fully freed from Hyper-V, and a
relaunch was retried — the freeze reproduced identically. That theory was correctly ruled out
before continuing.

Separately, this session also fixed a genuinely different SteamCMD `STATUS_STACK_OVERFLOW` crash
(corrupted internal SteamCMD state, unrelated to this freeze) and shipped v0.7.60.0's port-conflict
guard, which is a legitimate, independent fix but does not address the freeze itself (the guard
only catches a port already held by *another* process — the frozen process itself never got far
enough to hold a port MystTiq would treat as a genuine conflict for a subsequent attempt).

## The finding

With every I/O-adjacent theory (network, files, Defender, injection chain) exhausted, the
investigation moved to live, in-process diagnosis using two Sysinternals tools against a
genuinely-frozen production process, caught live rather than reproduced synthetically.

### Process Monitor: ruling out I/O entirely

A frozen `PalServer-Win64-Shipping-Cmd.exe` instance (the second-local-server clone, port 8311,
already 36+ minutes into the identical zero-CPU-growth freeze this investigation has chased for
weeks) was captured with Process Monitor, filtered to the PalServer process names. Out of 4.2
million total events captured system-wide during the capture window, exactly 11 matched the
filtered process — seven `Thread Create` events at process start, and nothing else, for the entire
remaining lifetime of the process. No file access. No registry access. No network activity of any
kind, not even a failed/pending one. This ruled out every I/O-stall theory in one step: the process
was not blocked on anything Windows would log as an operation. That points at a pure in-process
synchronization wait — a mutex, event, or condition variable never getting signaled — not an
external dependency.

### Process Explorer: the actual blocked call

With a fresh frozen instance live (this time two simultaneous instances — the production server and
its clone, both started independently and both frozen identically), Process Explorer's per-thread
**Stack** inspection was used on the highest-cumulative-CPU thread of each. The stack (ignoring a
long run of garbled `ImPlot::TagYV`/`png_get_io_chunk_name`-style frames — meaningless nearest-
export guesses from a symbol engine with no real PDB for this binary) showed, at the actual
top of the call chain:

```
win32u.dll!NtUserWaitMessage
USER32.dll!IsDialogMessage
USER32.dll!SoftModalMessageBox
USER32.dll!MessageBoxIndirectA
USER32.dll!MessageBoxTimeoutW
USER32.dll!MessageBoxW
```

The thread is blocked inside `MessageBoxW` — a native Win32 modal dialog — waiting for a click.
MystTiq launches PalServer with no interactive desktop session (headless, hidden-window launch).
A `MessageBoxW` call under those conditions still succeeds in creating the dialog at the OS level,
but nothing can ever see it or click it, so `NtUserWaitMessage` blocks forever. This explains every
symptom this investigation has ever observed: zero CPU (a message loop wait uses effectively none),
no crash (this isn't a fault, it's a legitimate — if unreachable — wait), no port bind (whatever
runs after the dialog is dismissed, including opening the game socket, never executes), nothing in
any event log (Windows Error Reporting doesn't fire for an un-dismissed dialog), and no Defender
detection (nothing malicious is happening).

The dialog's trigger condition was not identified (it could be an Unreal `ensure()`/fatal-error
path, or a Steamworks SDK error dialog — `steamclient64.dll`/`steam_api64.dll` are both loaded in
every affected process) and doesn't need to be: Unreal Engine's `-unattended` command-line flag
exists specifically to suppress this entire class of dialog, converting any of them into log output
instead of a modal box. It was absent from every launch argument set MystTiq has ever used — not
the Windows default, not the Linux default, not either of this machine's real persisted profiles.

## Live confirmation

Both frozen instances were killed, and the identical binaries/save files/ports were relaunched
directly with `-unattended` prepended to the same argument list:

- **The clone** (`Server-clone-second-local`, port 8311): reached UE4SS fully hooking all engine
  functions, all three MODs (BetterBaseBuilding, MystPalIntelligence, AdminCommands) loading
  successfully, and PalDefender anti-cheat starting cleanly — a point this investigation had never
  once reached in any prior attempt.
- **Production** (`Server`, port 8211): reached the identical checkpoint independently.
- Thread state was checked directly on both and found genuinely different from the freeze: one
  thread `Running` with real, continuously growing CPU time, the rest normally `Wait`ing — not
  every thread sitting in `Wait` with zero CPU growth, which is what every prior freeze attempt
  showed without exception.

This is treated as conclusive: the specific, well-understood, previously-undiagnosable failure mode
this investigation spent weeks chasing does not occur with `-unattended` present.

## A separate, secondary finding (disclosed, not fixed here)

Both live confirmation runs, after clearing the freeze, went on to take an unusually long time
(10+ minutes of sustained, continuously-growing single-thread CPU use) without ever completing
startup during this session's observation window. This is categorically different from the freeze
(active, growing CPU vs. zero growth; one thread genuinely `Running` vs. all threads `Wait`ing) and
is not blocking this fix from shipping, but it means startup on this specific save/MOD combination
may simply be very slow for a separate, not-yet-diagnosed reason (possibly related to one of the
two custom Lua MODs, `BetterBaseBuilding` or `MystPalIntelligence`, or UE4SS's own per-object hook
overhead scaling with a large, long-played, base-heavy save). Worth a dedicated follow-up once this
fix is confirmed live in production.

## The fix

- `-unattended` added to both platform default launch-argument templates in
  `HeadlessConfiguration.CreateWindowsDefault()`/`CreateLinuxDefault()` — every newly-created
  profile gets it going forward.
- `HeadlessConfigurationService.LoadOrDefault` now calls a new `EnsureUnattendedFlag` step after
  every load path (v1-migrated, v2-migrated, and current-schema deserialize alike): if a profile's
  `LaunchArguments` doesn't already contain `-unattended` (case-insensitive), it's prepended. This
  is deliberately not a schema version bump — the JSON shape is unchanged, only a content default is
  being defensively backfilled — and deliberately automatic rather than opt-in: `-unattended` isn't
  a discretionary tuning flag a user would reasonably think to add themselves, and leaving already-
  broken installs broken until someone manually diagnoses the same MessageBox stack trace again
  would defeat the point of fixing it here.
- The real, live `mysttiq.json` on this machine (both the `default` and `second-local` profiles)
  was also edited directly during the investigation, so the fix is already present in the file the
  next restart of the still-running old (v0.7.50.0) headless host process will read.

## Known gaps (disclosed)

- **No visual verification possible in this environment**, same standing limitation as every prior
  version.
- **The dialog's exact trigger condition was not identified.** `-unattended` suppresses the entire
  class of Win32 message-box dialogs Unreal (and linked SDKs) can show, which is sufficient to fix
  the freeze regardless of which specific condition was firing, but the specific condition itself
  remains unknown.
- **The secondary slow-startup finding (10+ minutes of active CPU without completing) is disclosed,
  not fixed.** It affects the same save/MOD combination on both the production server and its
  clone, so it's unlikely to be specific to one install, but needs its own dedicated investigation.
- **The still-running production headless host process (v0.7.50.0) has not picked up this fix** —
  it loaded its in-memory configuration before this session's direct `mysttiq.json` edit, so any
  server start through the currently-running app will still use the old, `-unattended`-less launch
  arguments until that process is restarted (ideally onto a build that includes this fix).
