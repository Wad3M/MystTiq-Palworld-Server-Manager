# v0.7.83.0 — New Server Wizard: Reordered Steps & Genuine Second-Server Support

## Context

Direct live feedback against the v0.7.81.0 wizard: the standalone "+" → "Clone a Server" menu
shortcut should be removed (it just jumped to Fleet's own Clone World card, competing with the
wizard's own Clone path instead of being part of it), and the wizard's own step order should change
to World Source (New World / Import / Clone) → Server Identity & Ports (with a live port-conflict
warning) → World Settings (preset or customize) → Install Directory → Download & Install, with the
directory defaulting to "the one we typically use unless it already exists, then the same root but a
different name based on the server's name."

Two constraints, confirmed by reading the actual code rather than assumed, meant the *displayed*
step order and the *execution* order couldn't be identical, and meant "Install Directory" turned out
to require far more than a path picker:

- `PalworldSettingsConfigurationService.CreateDefault` hard-requires
  `ServerRoot/DefaultPalWorldSettings.ini` to already exist — a file SteamCMD's install produces, not
  something present in an empty directory. So Identity/Ports and the World Settings preset choice are
  collected early (matching the requested order) but only actually *applied* automatically right
  after Install produces a real settings file.
- **"Local MystTiq" (the always-present built-in default profile) permanently owns the default
  ServerId.** Reusing it for a brand-new server collides with `BuildProfileFromEditor`'s own
  duplicate-connection guard (added in v0.7.63.0 for exactly this class of mistake) — confirmed live,
  not theoretically: the very first real Connect attempt from this wizard threw "already connects to
  this exact server" and could never get past Step 1. This meant every "Set Up New Server" completion
  must register a genuinely new fleet profile, not just when the target directory happens to be
  occupied — only the *directory* varies by occupancy (typical root if free, a derived sibling if
  occupied), registration always happens.

## New step order

1. **Local Service** (shared with Connect, unchanged) — now auto-triggers the same detection
   `DetectLocalServiceCommand` does instead of requiring a manual click, and auto-advances straight to
   World Source the moment it connects (`ApplyStatus`'s new complementary branch to the existing
   ServerIsRunning short-circuit). Direct live feedback: "this should not be the first screen... I am
   setting up a new one, not connecting to an existing service." Step 1's header and instructional
   copy are also reworded for this flow (`WizardStep1HeaderText`/`WizardStep1InstructionText`).
2. **World Source** — cards reordered to New World / Import / Clone, matching the requested order.
3. **Server Identity & Ports** (New World/Import) or **Clone source picker** (Clone, unchanged
   content) — Identity & Ports only *stages* values (`Setup*` fields); nothing is written yet.
4. **World Settings choice** (New World/Import only) — preset picker or "Customize after install."
   "Customize" can't show real slider values pre-install, so it defers to the existing, fully-live
   Configuration page after Finish rather than faking pre-install values.
5. **Install Directory** (New World/Import only) — see below.
6. **Download & Install** (New World/Import only) — unchanged SteamCMD install/environment-checklist
   content, moved here from its old step-3 position.
7. **Confirm & Finish** — reached from step 3 directly for Clone, or step 6 for New World/Import.
   Automatically applies Identity & Ports and any chosen preset before showing the summary (see
   below); Connect's own Confirm stays at its original step 5, untouched.

## Install Directory: always registers a new profile

`ContinueFromInstallDirectoryAsync` checks whether the currently-configured `ServerRoot` is occupied
(local `Directory.Exists`/`EnumerateFileSystemEntries` — safe since this flow is always local). If
occupied, a sibling directory is derived (`<parent>\<slug of server name>`, collision-suffixed),
mirroring `HeadlessWorldCloneService.CloneAsync`'s own pattern; if free, the typical root is used
directly. Either way, it then:

1. Registers a new fleet profile via the already-existing `POST /api/v1/servers`
   (`HeadlessFleetConfigurationService.AddServerAsync` — no file copying, it never did) — new client
   wrapper `AddFleetProfileAsync` on `IMystTiqApiClient`/`MystTiqApiClient`, copying
   `SteamCmdPath`/`LaunchArguments`/`Runtime` from the current config and only overriding
   Id/Name/ServerRoot/BackupRoot/RuntimeRoot.
2. **Restarts the Desktop app's own owned sidecar** — new `RestartOwnedSidecarAsync` on
   `ILocalManagementBootstrapper`, composing the already-existing `StopOwnedSidecarAsync` +
   `EnsureAvailableAsync` (which already verifies the new profile is actually present in the
   restarted instance's `/healthz` `serverProfileIds` list). A newly-added fleet profile is invisible
   to the running management process until it restarts — a real, previously undocumented-in-the-UI
   constraint.
3. Reconnects the wizard's in-progress connection to the new profile's scoped routes
   (`TargetServerId` set, `ServerScopedRoutingHandler` already routes on it).
4. Only ever offered for local desktop-sidecar connections and declines outright (with an honest
   message pointing to Fleet instead) if a real Windows Service install is detected, since the
   Desktop app has no code path to restart that.

**Clone gets the same treatment.** `CloneAsync` already registers its new profile server-side (via
the same `AddServerAsync`), but had the identical "needs a restart to come online" gap, previously
undisclosed — its own Confirm step never mentioned it. `CloneIntoNewServerAsync` now runs the same
restart-and-reconnect sequence before landing on Confirm.

## Real bugs found and fixed along the way

- **`BuildProfileFromEditor`'s duplicate-connection guard blocked the wizard's own Connect.** Fixed
  by skipping the check specifically while `IsNewServerSetupFlow && TargetServerId` is still blank
  (the wizard is inspecting state through the shared default connection, not saving a duplicate
  profile) — the guard re-applies normally once a real distinct `TargetServerId` exists.
- **Step 1's header text silently stayed blank.** The original 3-way `IsVisible`-toggled `TextBlock`
  row never updated after the tab's `ConnectionKind`/`IsNewServerSetupFlow` were set, reproduced
  live: every child started invisible on the very first layout pass, and the row never picked up the
  later `IsVisible` changes (a known Avalonia class of issue) — while `WizardStep1NextButtonLabel`, a
  plain string binding on the exact same underlying flag right below it, rendered correctly the whole
  time. Fixed by replacing the 3-`TextBlock` row with one `TextBlock` bound to a computed
  `WizardStep1HeaderText` string, the same reliable pattern the button label already used.
- **Confirm's summary showed the generic "New Server" placeholder.** `ProfileName` (the connection's
  own label) and `SetupServerName` (the Palworld server's in-game name) were two entirely separate
  fields with nothing syncing them. `SetupServerName`'s setter now auto-follows into `ProfileName`
  while it's still the `BeginNewProfile` default (or blank), never overwriting an explicit rename.
- **Alert Center disk-space-prediction crash, round 2.** The v0.7.82.0 fix's `MaxProjectableDays` cap
  alone did not actually stop the crash live — confirmed via the activity log, it kept recurring
  every ~60-75s across many rebuilds. A `NaN` `daysRemaining` compares false against every bound (a
  known floating-point trap), silently slipping past both guards. Added explicit `double.IsFinite`
  checks on both `growthPerDay` and `daysRemaining`, plus a last-resort `try/catch` around the
  `AddDays` call itself. Confirmed clean via the live activity log for hours after the round-2 fix.

## Removed: "+" menu's standalone "Clone a Server" entry

`AddTabButton_OnClick`'s `HasCloneableLocalTab`-gated menu item and its `CloneServerFlowCommand` /
`OpenCloneServerFlow` (which just navigated to Fleet's Clone World card) are removed. Fleet's own
Clone World card is untouched — its own redesign remains explicitly tabled per direct instruction
earlier this session.

## Verification

`dotnet build` on `MystTiq.Desktop` (excluded from the full-solution build, a confirmed pitfall from
this session) and the full solution — clean throughout every round of fixes. Live end-to-end
verification was driven directly against the real REST API (mirroring exactly what the wizard's own
code calls, since GUI automation isn't available in this environment): registered a new fleet profile
("MystTiqClaude") at a derived sibling directory, restarted the local sidecar and confirmed the new
profile appeared in `/healthz`'s `serverProfileIds`, installed Palworld Dedicated Server via SteamCMD
into the new directory, created default settings with offset ports, and confirmed the Fleet list
showed all three servers afterward — with the pre-existing "Default Server"'s own settings confirmed
untouched throughout. The wizard's own click-path in the live desktop UI was also driven by the user
directly; the collision-guard and Step 1 header bugs were found and fixed from that live session.
