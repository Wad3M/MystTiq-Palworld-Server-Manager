# v0.7.106.0 — Map: De-overlapping Marker Labels

## Context

A named follow-up since v0.7.100.0's map-zoom work ("de-overlapping labels of players standing together"),
carried in every checkpoint since as "not built." Two or more markers (players sharing a base, a base near the
default spawn plateau) drew their name labels directly under their dot at the same fixed offset, so close-
together labels rendered on top of each other and became unreadable.

## What changed

- New `src/MystTiq.Desktop/Services/MapLabelLayout.cs`: a pure, dependency-free pass,
  `ComputeLabelOffsets(IReadOnlyList<(double X, double Y)> points)`. For each point, counts how many earlier
  points (by insertion order) sit within `CollisionRadius` (30 screen pixels) of it, and returns that count
  times `LabelStep` (13px) as its label's downward offset. A marker with nothing close enough to collide with
  gets offset 0 — its label stays exactly where it always was. `CollisionRadius` started at 11 (roughly a bare
  dot's own size) and was raised to 30 after the live check below showed it was too tight: labels are
  left-aligned starting at their own dot, so what actually collides is rendered text width, not dot distance —
  two dots several pixels apart can still draw overlapping names.
- `PlayerMapPointDto`/`BaseMapPointDto` (`WorldMapDtos.cs`) each gained `LabelOffsetY` (default 0, so every
  other existing caller is unaffected) and a computed `LabelMargin` (`new Thickness(0, LabelOffsetY, 0, 0)`).
- `MainWindowViewModel.RebuildPlayerMapPoints`: restructured to a single exit (was three early returns) so a
  new `ApplyMapLabelDeoverlap()` always runs after every rebuild, over the current on-screen (view-space, i.e.
  post-zoom/pan) position of every base and player marker **together** — a base and a player standing on it
  can collide with each other's label too, not just marker-of-the-same-kind. Bases are listed first, matching
  their draw order, so a base keeps its label at the dot and whichever player is standing on it staggers.
  Existing DTO entries are replaced with a `with { LabelOffsetY = ... }` copy (the same pattern
  `RecheckDiagnosticAsync` already uses to swap a single `ObservableCollection` item), not mutated in place.
- `MainWindow.axaml`: each marker's name `TextBlock` now binds `Margin="{Binding LabelMargin}"` (dot position
  itself, via `MarkerMargin`, is untouched).
- Because `RebuildPlayerMapPoints` already runs again on every zoom and pan (existing wiring, unchanged), the
  de-overlap pass is naturally live: zooming in spreads real screen distance between dots, so a cluster's
  labels un-stagger back to 0 once the collision radius no longer applies, with no separate trigger needed.

## Deliberately not done

- No leader lines connecting a staggered label back to its dot. For a cluster of three or more, a label ranked
  low in the stack sits visibly below its own dot with nothing drawing the connection — acceptable at this
  scope; a leader-line renderer is a larger, separate piece of work.
- No cap on how many labels a single tight cluster can stagger before running off the bottom of the map frame
  (`ClipToBounds="True"` on the map's own border just clips it). Not expected to matter in practice — a real
  server's players and bases rarely cluster more than two or three deep at once — but worth knowing if it ever
  does.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 1 new scenario, `MapLabelLayout.cs` compiled directly into the harness (same technique as
  `MapViewport.cs`; `WorldMapDtos.cs` itself is NOT compiled in, since it needs `Avalonia.Thickness` and the
  harness has no such reference — only the dependency-free layout function is tested there): markers far apart
  never stagger; three dots stacked exactly on top of each other stagger 0, one step, two steps in insertion
  order; a collision exactly at the radius still counts, just past it does not; two separate clusters stagger
  independently of each other; zero or one marker never collides with anything.
- Live UI check (window rendered with PrintWindow; helper `ui-capture-helper.ps1`), on the clone's real Map
  page (2 bases and an offline player naturally close together near the same spot): before the radius fix, the
  base's "MystTik" label and the nearby offline player's ring both drew overlapping, unreadable text even
  though the dots themselves were not touching. After raising `CollisionRadius` to 30, the same cluster showed
  two fully legible "MystTik" labels stacked cleanly apart (screenshots kept: before/after). Zooming in to 3.8x
  spread the markers further apart in view-space and all three labels (two bases, one player) settled at
  distinct, non-overlapping positions.
- **Known residual, out of scope here**: two markers whose dots sit at (or extremely near) the exact same
  screen position still render as a single visible dot — label staggering fixes the *text*, not two icons
  occupying the same pixels. Not attempted this version; the complaint on file was specifically about labels.
