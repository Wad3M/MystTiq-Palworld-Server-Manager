# v0.7.15.0 — Temporary Bans & Historical FPS Charting

## Background

Continuing in order through a backlog list raised earlier this session: temporary bans with auto-expiry, "Remove Admin" feasibility, give-items/give-Pals, mod load-order/per-mod config editing, and historical FPS charting. Before implementing anything, a feasibility research pass read this session's own already-tested RCON/REST vocabulary (`RconPlayerModerationProvider.cs`, `docs/architecture/v0.7.8.0-rcon-admin-tools.md`), the existing mod-management code (`HeadlessModManagementService.cs`), and the existing history-persistence code (`HeadlessHistoricalMetricsService.cs`) to establish what was genuinely buildable versus blocked before committing scope.

The research found: Temporary Bans and Historical FPS Charting are both genuinely feasible now, with strong existing precedent to build from (Whitelist's poll-driven enforcement shape, and the FPS data v0.7.9.0 already collects live). "Remove Admin" turned out not to be a feature at all — it's an orphaned UI stub with no backend concept ever defined for it, and Palworld's RCON has no per-player admin grant/revoke command to build one against. Give-items/give-Pals and mod load-order/config editing are both large, open-ended, or outright blocked (see Explicit non-goals). This release ships the two feasible items plus the stub cleanup; the two blocked/large items remain backlog, unscoped.

## What shipped

### Temporary Bans

New `HeadlessTemporaryBanService` (`MystTiq.HeadlessHost`), built on the same shape as `HeadlessWhitelistService` (v0.7.10.0): a persisted per-profile JSON file (`players/temporary-bans.json`), enforced from the same `/status/poll` cadence the player registry and whitelist already use rather than a new background timer.

- `BanAsync(playerId, playerName, reason, duration, token)`: calls the *existing* ban path (`PlayerModerationCoordinator.ExecuteAsync("ban", ...)`, completely unchanged — no new RCON/REST command was needed) and only persists a tracked expiry (`DateTimeOffset.UtcNow + duration`) if that ban actually succeeded.
- `EnforceAsync(token)`: each poll tick, any entry whose expiry has passed is removed from the tracked list *before* attempting the unban (not after) — a permanently-failing RCON connection would otherwise retry the same expired entry every 5-second poll forever; a failure is still fully visible in the activity log, and the operator's existing manual Unban button remains available regardless.
- `ForgetIfPresent(playerId)`: called from the generic `/players/{playerId}/action` route whenever a manual `unban` succeeds, so an operator lifting a temp-ban early through the ordinary Unban button doesn't leave a stale tracked entry that the sweep would otherwise (harmlessly, but confusingly) attempt to unban again once its original timer elapses.

New routes: `GET /players/temp-bans` (list, Operator role), `POST /players/{playerId}/temp-ban` (create, Admin role — same role tier as the existing whitelist PUT and other admin-mutating routes).

Desktop: a duration-hours `NumericUpDown` + "Temp Ban" button sits next to the existing Kick/Ban controls in the Player Administration card (same selection/online gating as Kick/Ban — `SelectedPlayerRecord?.Online == true`). A new collapsible "Temporary Bans" card, placed directly after the existing Ban List card and matching its collapsed-by-default pattern, lists active entries (name, reason, time remaining) with a per-row "Lift Now" button that reuses the ordinary unban action path.

### Historical FPS Charting

`HeadlessHistoricalMetricSample` gained two new nullable fields, `ServerFps`/`ServerFrameTimeMs`, threaded straight through from the `HeadlessRuntimeMetricsSnapshot` the existing `/status/poll` handler already fetches every cycle — no new polling, no new REST call. Kept nullable rather than coalesced to 0, matching the exact convention `RuntimeMetricsSnapshotDto.ServerFps` established in v0.7.9.0: the Palworld REST API being disabled is a common, valid configuration, and a real 0 FPS reading must never be confused with "no data for this sample."

`HeadlessHistoricalMetricsSnapshot.Snapshot(...)` gained `AverageFps`/`PeakFps`, computed only over samples that actually have a value — both are `null` (not 0) when nothing in the selected range ever reported real FPS data.

On the Desktop side: `HistoricalMetricPointDto`/`HistoricalMetricsSnapshotDto` gained matching fields; the live-append path (`AppendLiveResourceHistory`) now carries `ServerFps`/`ServerFrameTimeMs` through from each live poll too, so the short-term in-memory buffer and the persisted 30-day history both show FPS consistently. `ResourceHistoryChart` (the custom-drawn dual-series control already plotting CPU/Memory) gained a third series in green, with its own independent min/max normalization — drawn only between two consecutive samples that *both* have a value, so a REST-disabled stretch reads as a visual gap in the FPS line rather than a misleading straight line down to zero. A new `HistoryFpsSummary` text line ("FPS Avg X · Peak Y", or an explicit "not recorded" message when the whole range has no data) sits alongside the existing CPU/Memory summaries.

### Stub cleanup

Two stale, permanently-disabled buttons were sitting in the Player Administration card's button row:

- **"Whitelist — BACKEND REQUIRED"** — genuinely stale dead UI. Whitelist shipped a complete, working implementation (its own collapsible card, further down the same Players page) in v0.7.10.0, but this stub was never removed from where it had originally sat before that work existed. Removed.
- **"Remove Admin — BACKEND REQUIRED"** — investigated, not built. Traced to a placeholder carried forward from the pre-rewrite legacy GUI with no concept ever defined for what it should actually do in the current architecture. Palworld's admin model is a single server-wide RCON `AdminPassword`, not a per-player permission grant — there is no per-player "admin" state to add or remove in the first place. Removed outright rather than left as a permanently-disabled promise with nothing behind it.

## Explicit non-goals

- **Give-items / give-Pals to a player.** Confirmed via this session's own prior research (`docs/architecture/v0.7.8.0-rcon-admin-tools.md`'s own non-goals) and re-confirmed here: no `GiveItem`/`GivePal` command exists anywhere in Palworld's RCON/REST surface as tested throughout this session. The only proven path is offline save-file container/inventory mutation — the same class of work as the existing v0.6.15.0 Pal Editor, but for a struct this codebase has no decoder for yet. Materially larger and riskier than either feature shipped this release; left as unscoped backlog.
- **Mod load-order editing and/or per-mod config editing.** `HeadlessModManagementService` has no concept of ordering today, and none of Palworld's mod ecosystem conventions (PAK load order, Lua/UE4SS per-mod config formats) share a single schema a generic editor could target. Building this well would mean inventing an ordering model and a heterogeneous per-mod-type config editor, not extending the existing install/inventory/rollback pipeline. Left as unscoped backlog rather than shipping a narrow, likely-wrong-for-most-mods first cut.

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors, after fixing one instance of the recurring XML-comment-`--` AVLN1001 parse error in a new comment.
- Live-verified against a real isolated sidecar (no GUI click-through capability in this environment, unchanged, disclosed every version): `GET /players/temp-bans` returns the correct empty default; `POST /players/{id}/temp-ban` correctly resolves to the underlying `ban` action and fails gracefully with a structured 422 when RCON is genuinely unconfigured (no `PalWorldSettings.ini` present, the same constraint every RCON-touching feature this session has had) — and, critically, does **not** leave behind a phantom tracked entry when the underlying ban fails, confirmed by re-querying the list afterward; `GET /history` reports the new `averageFps`/`peakFps` fields as `null` (not `0`) with zero samples recorded, matching the intended null-means-unavailable convention.
- New `scripts/Test-v0.7.15.0-RouteSmoke.ps1` (3 checks) passed standalone against the `Build.ps1 DesktopWindows` sidecar output before being wired into the release gate.
- Testing the actual auto-expiry-unban behavior over real elapsed time, and the FPS chart's real visual rendering, both require either a long-running live session or GUI click-through this environment cannot provide — the same disclosed gap as every prior UI/timing-dependent feature this session.
