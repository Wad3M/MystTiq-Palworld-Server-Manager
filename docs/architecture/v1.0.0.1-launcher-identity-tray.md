## The identity bug (reported 2026-10-04)

"When I launch the server through MystTiq it changes the user information and doesn't load the correct profile."

What the evidence shows:

- A Palworld server derives a Steam player's ID from the Steam ID: CityHash64 of the decimal SteamID64 in UTF-16LE, folded
  to 32 bits. Wade (steam_76561197962020201) is 67D8D355 and Melly (steam_76561198653223616) is A3835C7B, and those
  characters exist.
- MystTiq's player registry shows the same accounts given other IDs in some sessions: Melly 014308E2 (2026-10-01 07:52),
  Wade E290DA9A ("WadeeRROR", 2026-10-03 23:32). Those players were sent to make a new character. The other wrong IDs in the
  world (1467C601, 84544311) are earlier cases. No form of the Steam ID hashes to them, so the server used another identity
  for those players, though REST still reported `steam_…` user IDs.
- The Steam client on the server machine is signed in as Wade's account. It was not running from the reboot (2026-09-30
  17:16) until 2026-10-01 07:57; Melly's wrong ID came at 07:52, inside that window; the correct IDs that morning came
  after. Wade's wrong ID on 2026-10-03 came while it was running, so that is not the whole story.
- The 2026-10-03 session was started on 2026-10-02 by the owner's v1.0.0.1 helper, which already launches the manual way,
  so the old launch flags alone do not explain it either.

The owner's answers (2026-10-04) narrowed it down: a server started by double-clicking `PalServer.exe` in its folder keeps
players' characters; one started from a script with the same arguments MystTiq passed gave the same wrong characters as
MystTiq. So the arguments are the cause, not how MystTiq starts the process. Every bad launch had `-port=8211`, `-stdout` and
`-FullStdOutLogOutput` in common (the old fixed flags also had `-unattended -useperfthreads -NoAsyncLoadingThread
-UseMultithreadForDS -logformat=text`; the first v1.0.0.1 default had `-log -abslog=…`); which one is responsible is not
known. What was done:

- **No arguments by default.** A profile without saved Launcher choices starts PalServer.exe with no arguments at all, like a
  double-click; `-port=` is added only for a server not on 8211 (which a double-click could not run correctly anyway). The
  stand-in server records its arguments, and the stuck-start smoke checks that nothing else reaches it.
- **The Like double-click preset** on Server > Launcher: no arguments, started through the Windows shell
  (`UseShellExecute`), a normal window, nothing hidden afterwards. The owner's main server has saved Launcher settings
  (Show Window, with `-port=8211 -log -stdout -FullStdOutLogOutput -abslog=…`), which win over the default; the owner applies
  this preset and saves.


- **The identity guard** (`HeadlessIdentityGuardService`, on by default): on every player poll, a Steam player whose
  expected ID has a character but who was given another ID, or the new-character screen ("None"), is recorded
  (`players/identity-guard-events.json`, with whether the Steam client was running), raised as a pinned Critical
  notification, and kicked before a duplicate character is made. A player whose expected character does not exist (new, or
  moved from co-op) is left alone. Like the whitelist, it runs while something polls (the desktop, also from the tray).
- The real characters were never touched; the extra ones (E290DA9A, 014308E2, 1467C601, 84544311) remain in the world for
  the owner to keep or delete.

Next evidence: each guard event records the launch time and Steam-client state. The question for the owner: which launch
works ("their application": Steam's library entry, or `PalServer.exe` by hand).

## Close to tray, and a full Exit (reported 2026-10-04)

Closing the window when nothing ran used to exit the GUI and leave `mysttiq-server.exe` (the helper) running. Now the close
button always hides to the tray (a reminder once per session). Exit and Force Exit stop every server the helper this desktop
owns runs (its whole fleet, via `/api/v1/servers`, gracefully or forced), then the helper, then the app. With no owned
helper (a Windows service, or one another program started) only the open tab's server is stopped, as before. Servers on
other computers are never stopped by closing the app. "Exit GUI only" and the close-confirm dialog are gone.

## Stuck starts (requested 2026-09-30)

On 2026-09-30 the main server spun one core for minutes without opening its port; the status said the port "has not been
confirmed". Now:

- `StartupWatch`: the status gives the process's start time (`NativeStartedAt`), says how long it has been starting, and
  calls it stuck (`StartupStuck`) after two minutes.
- The safe-start service has a test-load mode (one start with every MOD off, timed, then switched back on and stopped) next
  to the one-at-a-time test, can begin from a stuck start (it stops the stuck process first), checks every MOD switch (a
  refused switch ends the test and restores every MOD; v0.7.59.0 ignored refusals) and times every start.
- The Dashboard shows a panel when a start is stuck, with both tests, live progress and the outcome.
- The stand-in PalServer hangs while its "HangsStartup" MOD is enabled, so the smoke proves the whole path.

## Dashboard addresses (requested 2026-09-30)

`GET /network/addresses`: the machine's IPv4 addresses (the adapter with a gateway first; loopback and link-local left out)
and the public address, from the router over UPnP when it gives a public one, else api.ipify.org; kept an hour, shared by
every server on the machine. The Dashboard shows `address:port` for each, selectable. PRIVACY.md lists the lookup.
