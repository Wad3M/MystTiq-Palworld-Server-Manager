# v0.7.28.0 — New Ribbon Actions

## Goal

Fourth version in the GUI/workflow/UX overhaul roadmap, and the first that adds genuinely new capabilities to the ribbon rather than relocating buttons that already existed somewhere in-page. Items 7, 21, and 57 from the roadmap's findings log — all three were flagged during the original walkthrough as "the backend logic already exists, it's just never been exposed."

## What shipped

### Force Stop Server (item 7)

`ForceStopServerAsync` (`IMystTiqApiClient`) has existed since well before this roadmap, but the only caller anywhere in the codebase was `MainWindowViewModel.ShutdownForExitAsync(force: true)` — invoked automatically when the app closes while a server is running, never by direct user action. A new `ForceStopServerCommand` wraps it through the same `RunLifecycleAsync("Force stopping…", ...)` helper `StopServerAsync`/`RestartServerAsync` already use, giving it the same `BusyReason`/status-refresh/error-handling behavior for free. Its `CanExecute` (`!IsBusy && ManagementApiConnected && ServerIsRunning`) matches `StopCommand`'s exactly, and every place that already refreshed `StopCommand`'s/`RestartCommand`'s `CanExecute` state now also refreshes this one.

Surfaced as a new "Danger" ribbon group containing just this one button, appended **unconditionally** at the end of `BuildRibbonGroupsForActivePage()` — reachable from every page, not gated by `SelectedPage` like the per-page groups from v0.7.26.0/v0.7.27.0. Being appended last means it renders at the right edge of whatever else is currently visible in the ribbon, closest to the page header — the positioning the original request asked for ("just to the left of the page header").

### Install Missing (item 21)

`InstallMissingEnvironmentAsync` already existed (`MainWindowViewModel`), but was only reachable indirectly: the Server Setup component checklist's per-row "INSTALL"/"VERIFY" action dispatch would call it for the specific first-run "missing component" case, with no standalone way to trigger it directly. A new `InstallMissingEnvironmentCommand` (`AsyncCommand`, `CanExecute: !IsBusy`) wraps it directly, added as a second button to the "Environment" ribbon group v0.7.26.0 already created for "Verify Files" — no new group needed, just one more action in the existing one.

### Managed process list + Kill Processes (item 57)

This turned out to need far less new backend work than expected. `ServerStatusDto` (`Models/ServerStatusDto.cs`) already carried a full `Processes` list (`IReadOnlyList<ServerProcessDto>`, each with process ID, parent process ID, name, executable path, and a responding flag) — this data already flows end-to-end from `WindowsServerLifecycleService.FindManagedServerProcesses()` (server-side) through `ServerLifecycleSnapshot.Processes` and across the wire, but **nothing on the Desktop side ever read `status.Processes`** before this release; `ApplyStatus` only ever consumed `NativeProcessId`.

- `ServerProcessDto` gained one new computed `DisplayText` property (client-side only, not part of the JSON contract) formatting each process as `"{Name} (PID {Id})"`, with `" — not responding"` appended when `Responding` is false.
- New `MainWindowViewModel.ManagedProcesses` (`ObservableCollection<ServerProcessDto>`) and `HasManagedProcesses` bool, populated in `ApplyStatus` alongside the existing `NativePidText` assignment — matching this codebase's established convention for `Apply*` methods (unconditional clear-and-repopulate each poll, no change-detection, same pattern `ApplyLogs` already uses).
- Server Doctor's top status card (`MainWindow.axaml`) gained a second column ("MANAGED PROCESSES", visible only when `HasManagedProcesses`) listing each process's `DisplayText` — placed at the top-right of the page, as requested. This is the exact space v0.7.27.0 freed up when Run Doctor/Refresh and Export Diagnostic Report moved into the ribbon.
- **Kill Processes** was added to the Doctor ribbon group (alongside Run Doctor/Export Report), reusing `ForceStopServerCommand` rather than inventing a second, parallel kill mechanism — it's the exact same underlying action (force-terminate the managed process tree), just reachable here too since this is the page that actually shows which processes it would terminate.

## Explicit non-goals

- No new backend route or DTO — the process data was already flowing, just unread. If a future version needs richer process detail than what `ServerSessionProcessInfo`/`ServerProcessDto` already carry, that would be new backend work; this release didn't need any.
- Force Stop and Kill Processes are deliberately the *same* command, not two separate mechanisms — there was no reason to build a second kill path when the existing one already does exactly what both buttons need.
