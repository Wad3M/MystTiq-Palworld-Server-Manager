# v0.7.110.0 — Crash Recovery: Watching After a Give-Up

## Context

The last real gap named across this session's Alert Center/Doctor/Map work, and explicitly deferred every time
it came up as separate, larger scope: when automatic crash recovery gives up (too many restarts inside the
window) it pins a "server is DOWN, automatic recovery gave up" Critical notice — and, unlike the Alert Center's
own episode-based alerts (v0.7.104.0), that notice had no way to ever unpin itself. `HeadlessSupervisor
.RunCrashRecoveryLoopAsync` **returns** on give-up, by design (service-run relies on that exit code for the
OS's own recovery policy), so nothing was left watching the profile afterward — confirmed by reading the code,
not assumed, before building this.

## What changed

- New `SupervisorEventKind.ManualRecovery`, appended so existing numbering is unaffected: "the server is
  running again, started by something other than the automatic loop, since the loop itself had given up."
- `HeadlessFleetCrashRecoveryService` (the **api-run-only** wrapper `HeadlessFleetCrashRecoveryService`, used by
  the Desktop sidecar and every fleet profile — never `service-run`, whose own use of `HeadlessSupervisor
  .RunAsync`/`RunCrashRecoveryLoopAsync` and their return-on-give-up contract are completely untouched) now
  wraps the loop instead of running it once:
  - `RunWithGiveUpWatchAsync`: after the loop gives up, `WaitForManualRecoveryAsync` polls (the same
    `PollInterval`) purely for `lifecycle.GetStatusAsync().Processes.Count > 0` — the exact same signal a real
    crash or a real recovery already uses, so this needed no new capability from `IServerLifecycleService`.
  - Once seen, it notifies `ManualRecovery` and **resumes** `RunCrashRecoveryLoopAsync` on the very same
    `HeadlessSupervisor` instance. `CanRestart`'s existing restart-history window-aging already handles a
    stale attempt count safely — nothing needs to be reset by hand, confirmed with a scenario that forces a
    second, genuine crash immediately after the manual recovery and checks monitoring actually caught it.
- `CrashAlertText.Build` gained the `ManualRecovery` case: an unpinned Success "server is back up" notice.
- `CrashAlertObserver` now remembers the pinned give-up notice's own id (`pinnedGiveUpNotificationId`, the same
  single-field pattern `AlertEpisodeTracker.AlertNotificationId` established in v0.7.104.0, just without a
  tracker object — a crash give-up/recovery pair is one in-memory cycle here, not a persisted episode) and
  unpins that exact notification when `ManualRecovery` arrives, swallowing `KeyNotFoundException` if it was
  already dismissed.

## Deliberately not done

- `service-run`'s own supervisor loop (Windows service / systemd) is untouched. Its exit-on-give-up contract
  is what lets the OS's own service-recovery policy take over, and changing that was out of scope and would
  have been a real behavior change to a different, unrelated deployment mode.
- No change to how the *first* crash or a *successful automatic* restart are reported — only the post-give-up
  gap.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 2 new/extended scenarios: `HeadlessFleetCrashRecoveryService` against `ScriptedLifecycle`
  proves the watch-then-resume cycle end to end — give-up still reported exactly as before, no fabricated
  recovery while genuinely still down, `ManualRecovery` fires the moment the scripted process reappears, and a
  *second, real* crash afterward is caught by the resumed loop (not just one more event and then silence);
  `CrashAlertObserver`'s existing scenario extended to prove the pinned DOWN notice unpins itself on
  `ManualRecovery`, stays a single notification (not duplicated or removed), and a second `ManualRecovery` with
  nothing left to unpin does not throw.
- New live smoke `Test-v0.7.110.0-RouteSmoke.ps1` against the **real** Windows lifecycle service (not
  `ScriptedLifecycle`): the same crash fixture v0.7.101.0's smoke uses (a persisted lifecycle state claiming
  the server was running under a nonexistent PID), with default timings — give-up takes its own real ~90
  seconds, not artificially sped up, since the point was exercising the real cadence unmodified. A genuine
  process named `PalServer.exe` (a copy of Windows' own `waitfor.exe`, the only honest way to satisfy the real
  session inspector's name-AND-path match without fabricating data) is launched under the fixture's
  `ServerRoot` to stand in for a manually-started server: the real service reports it running, the DOWN notice
  unpins, and killing that same process afterward is caught as a genuine fresh crash — proving monitoring
  truly resumed, not just reacted once.
