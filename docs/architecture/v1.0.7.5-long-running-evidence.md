# v1.0.7.5 — Long-Running, Stress and Concurrency Evidence (internal)

Roadmap Q-10. The tests found three things to fix (below); then the evidence.

## Found and fixed

**1. A half-finished update was reported as installed.**
- `HeadlessServerDistributionService.GetStatus` called the server installed whenever `PalServer.exe` existed.
- SteamCMD or MystTiq stopping mid-update left that true with half-updated files, and a start was allowed.
- Now `ServerInstallIntegrity` (Core) has two signals:
  - a marker, `<ServerRoot>/.mysttiq-update-in-progress`, written before SteamCMD runs;
  - Steam's `steamapps/appmanifest_2394010.acf` `StateFlags` (4 = fully installed; all three real installs on the release
    machine read 4).
- `EndUpdate` removes the marker only when the executable exists and Steam reports 4 (or there is no manifest and the run
  succeeded). A SteamCMD that failed before touching anything leaves 4, so the marker goes.
- `Incomplete()` names a leftover marker (when no update runs in this process), or a manifest not at 4.
- The status reports `serverExecutableExists: false` with `IncompleteReason`, so older desktops show "Missing" rather
  than "Installed". Both lifecycle services refuse the start with the reason.

**2. A client disconnecting stopped SteamCMD half way.**
- Both update routes passed the request's `CancellationToken`. A desktop closing (or the network dropping) mid-update
  cancelled it, and `RunSteamCmdAsync` killed SteamCMD's process tree.
- They now pass `BackgroundWork.Shared.Stopping`: the update runs to its end, and only the service stopping cancels it,
  which the marker records.

**3. A backup failed at once on a held save file.**
- `ZipFile.CreateFromDirectory` threw on a sharing violation (the server writing `Level.sav`).
- Now: ten tries a second apart (`FileRetry.IsHeld`), the partial file removed between tries. If the file is still held,
  the message carries the file (from the exception) and its holders (`FileLockers`, Restart Manager).

## Evidence

**The long set** (`Test-v1.0.7.5-LongSet.ps1`, opt-in in the gate with `-RunLong`). It runs a real isolated service with
the stand-in PalServer and a stand-in SteamCMD (`FakeSteamCmd`: modes complete, hang, fail):
- **Interrupted update:** the service is killed while SteamCMD hangs with `StateFlags` 1026. The next service reports
  `serverExecutableExists=false` with "did not finish", and refuses the start ("Run Update again"). A finished update
  clears it. A SteamCMD failing first (exit 8) leaves the install as it was.
- **Simultaneous operations:** three rounds of 12 requests (4 backups, 2 starts, 2 stops, 2 updates, a poll, the backup
  list) sent at once, in-process. 36 answers: 10 × 200 and 26 × 409, with no 5xx, no `.partial` file, and every archive
  readable.
- **Held save file:** a file held for 2.5 s by another process is waited for (200). A file held throughout is refused
  after about 10 s, naming `Level.sav`.
- **10,000 console lines** written to `Pal.log` in 20 chunks while polling `/status/poll?lines=500`: the slowest poll was
  187 ms, with at most 290 lines.
- **Shutdown:** see the console stop below. The service exits in about 2 s with exit code 0. Its port can be bound again,
  every file under runtime, backups and fleet opens exclusively, and the stand-in PalServer keeps running. The next
  service reports it running (a second start is refused, 409).

**Rapid tab switching** (ArtworkHarness): three connected tabs whose status replies take 0–40 ms, in random order. After
300 switches (316 requests), the players and console lines shown are the active tab's own, and no unexpected error was
recorded.

**The idle soak** (`Measure-MystTiqIdleSoak.ps1`):
- **Windows:** an isolated `api-run` with the stand-in PalServer running, a 5-s status poll as a connected desktop does,
  and samples of private bytes, working set, handles and threads.
- **Linux:** the same service as `systemd-run --user` units (service, poller, sampler; no sudo, nothing installed, the
  production `mysttiq-palworld` unit untouched). Samples come from `/proc` (RSS, private, open files, threads).
- **The verdict:** memory may not grow over 30% and 50 MB after the warm-up, handles over 25% and 100, threads over 15;
  no poll may fail; the stop must finish within 15 s, leaving no process and a free port.
- **Trials (3 min each):** both passed. Windows stopped in 2.1 s with exit 0 and no files held. Linux stopped in 40 ms
  with exit 0.
- **The 24-hour runs:** started 2026-10-12 around 02:51 UTC on both, sampling every 30 min. They are recorded when
  collected; until then Q-10 stays `Built`.

## Notes

- **The console stop is Ctrl+Break, not Ctrl+C.** A process started from a parent that ignores Ctrl+C inherits that and
  never sees it. Running the long set from a bash-started pwsh, the service ignored Ctrl+C; Ctrl+Break worked.
  `Send-MystTiqConsoleStop.ps1` sends it from a separate pwsh (passed as `-EncodedCommand`; plain arguments were
  mangled), with a handler that keeps that pwsh alive.
- **A console stop reaches every process on the console.** With the default launch (no `createNoWindow`), PalServer
  shares the service's console. Running `api-run` in a terminal and pressing Ctrl+C would stop the game server too. The
  installed Windows service and the desktop's sidecar are not affected (no console stop reaches them). The tests start
  the stand-in with `@mysttiq:createNoWindow=true`. Open: give PalServer its own process group or no console by default.
- The desktop on Windows always uses the real per-user settings folders, so it is not part of the 24-hour soak. Its
  polling is covered by the v1.0.7.3 console measurements and the tab-switching check.
