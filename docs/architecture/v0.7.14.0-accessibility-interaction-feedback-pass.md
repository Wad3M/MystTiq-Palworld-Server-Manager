# v0.7.14.0 — Accessibility & Interaction Feedback Pass

## Background

This closes out the last unstarted third of a much earlier multi-part request: "Check to see if there are UI improvements that can be made based on best practices, Microsoft docs, and known good methods." Every UI pass since then addressed a narrower, separately-requested ask instead — v0.7.1.0 (page ordering), v0.7.4.0 (card flare), v0.7.5.0 (no-scroll density), v0.7.13.0 (new-server wizard redesign). None of those were a direct audit against Fluent/Avalonia best practices.

A dedicated audit read `Styles/DesignSystem.axaml`, `App.axaml`, and representative sections of `MainWindow.axaml`, then cross-checked against current Microsoft Fluent 2 guidance (typography, spacing, target size, focus visuals) and Avalonia's own accessibility documentation. It returned 5 findings; 4 were real and are fixed here, 1 was investigated and found not to hold (see below).

## What shipped

### `AutomationProperties.Name` on every genuinely icon-only control
The app had 50+ `ToolTip.Tip` usages but zero `AutomationProperties.Name` occurrences anywhere. A tooltip is not exposed as a control's accessible name to Narrator/NVDA/UIA — per Avalonia's own accessibility docs, icon-only controls need `AutomationProperties.Name` set explicitly. Added to all 16 controls in `MainWindow.axaml` whose `Content` carries no readable text on its own: the 3 window-chrome buttons (Minimize/Maximize/Close), the per-tab close button, the "+" add-tab button, the Notifications/Settings ghost buttons, the 7 ribbon action buttons (Refresh/Start/Restart/Stop/Backup/Console/Doctor — whose `Content` is a `StackPanel` of icon-tile + label, not plain text, so a default text-content fallback can't reliably resolve it), and the 2 dice-emoji random-name-generator buttons. Buttons whose `Content` is already real text (nav sidebar items like `TextBlock Text="Dashboard"`, most page-action buttons like `Content="Save Notes"`) were deliberately left alone — that text already serves as an accessible name without needing an explicit override.

### Restored the keyboard focus ring on ghost/ribbon/category-tab buttons
`App.axaml` defines `Button:focus-visible` (`BorderBrush="#75C8FF"`, `BorderThickness="2"`). `Button.ghost`, `Button.ribbon`, `Button.ribbonCompact`, `Button.ribbonMedium`, and `ToggleButton.categoryTab` each set their own always-on `BorderBrush` — at equal selector specificity to `:focus-visible` (one class/pseudo-class beyond the base type each), so Avalonia's tie-break rule (later declaration wins) let these classes' own color win over the focus ring, since they're loaded via `StyleInclude` in `DesignSystem.axaml` after `App.axaml`'s inline styles. Net effect: tabbing to any window-chrome button, the tab-close "x", Notifications/Settings, any ribbon action, or the 7 category tabs showed no visible focus indicator at all — a WCAG 2.4.7 (Focus Visible) gap, and one a keyboard-only or switch-access user would hit immediately. Fixed with 5 new `:focus-visible` style overrides in `DesignSystem.axaml`, each just re-asserting `BorderBrush="#75C8FF"` for that class (thickness already comes through unmodified from `App.axaml`'s base rule, since none of these classes override it).

### Tab-close button hit target: 20px → 28px
Fluent's control-size guidance targets ~32-40px minimum even for pointer-primary desktop controls. The per-tab close "x" was 20x20px — the smallest interactive element in the app, sitting inside a dense horizontal tab strip where mis-clicks become likely once several servers are open (exactly the multi-server scenario this app is built around). Bumped to 28x28, the smallest step that meaningfully helps without the tab row growing tall enough to visually compete with the category tabs above it.

### Tooltips on window-chrome buttons
Minimize/Maximize/Close had no `ToolTip.Tip`, unlike virtually every other icon-only control in the app (which otherwise does this consistently). Added, alongside their new `AutomationProperties.Name`.

## Explicit non-goals (investigated, not changed)

- **"No per-action busy/disabled feedback during async operations"** — the audit's 5th finding, naming Save Notes/Add Warning/Kick/Ban/Restart Server/Apply Migration/Apply-With-Fresh-Safety-Backup as examples of buttons with no protection against a double-click firing a duplicate destructive command. Checked each named command directly in `MainWindowViewModel.cs`: every one is an `AsyncCommand` whose `CanExecute` delegate already includes `!IsBusy` (e.g. `SavePlayerNotesCommand = new AsyncCommand(SaveSelectedPlayerNotesAsync, () => !IsBusy && SelectedPlayerRecord is not null)`), and Avalonia's standard `Button`/`ICommandSource` wiring already auto-disables a button whenever its bound command's `CanExecute` returns false — this is how `ICommand`-driven buttons behave by default in every XAML framework, not something requiring an explicit XAML attribute. The audit's methodology (grepping for a literal `IsEnabled="{Binding !Is*Busy...}"` XAML binding) returned zero hits and concluded the gap was real, but missed that this codebase's established pattern gates through `CanExecute` instead of a separate `IsEnabled` binding.
  - A first attempt at "fixing" this by adding an explicit `IsEnabled="{Binding !IsBusy}"` to the Save Notes/Add Warning buttons was caught and reverted during this same session before it shipped: doing so would have overridden the command's own more specific precondition (`SelectedPlayerRecord is not null`, or for Kick/Ban, `SelectedPlayerRecord?.Online == true`), re-enabling those buttons once `IsBusy` is false regardless of whether a valid/online player is actually selected — a real regression, not a fix. Nothing was changed for this finding.
  - A narrower, genuinely true observation buried in the same finding — "the only in-progress signal is one generic footer progress bar, with no indication of *which* action is running" — is real but minor, and would need a larger redesign (a per-action status label) to address properly; left as a future polish item rather than forced into this release.

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors, after fixing 4 instances of the recurring XML-comment-`--` AVLN1001 parse error introduced while writing this release's new XAML comments (same long-standing quirk documented in every prior release touching `.axaml` files).
- No GUI click-through capability in this environment (unchanged, disclosed every version) — these are style/markup-level accessibility and interaction-feedback fixes verifiable by static inspection of the resulting XAML/style rules and by direct reading of the `CanExecute` delegates they touch (or, for the one finding investigated and not changed, deliberately did not touch). No server-side (`MystTiq.Core`/`MystTiq.HeadlessHost`) code changed this release.
