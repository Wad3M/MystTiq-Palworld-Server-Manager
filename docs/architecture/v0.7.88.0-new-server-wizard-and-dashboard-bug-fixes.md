# v0.7.88.0 — New Server Wizard and Dashboard Bug Fixes

Direct live feedback with screenshots, against a running v0.7.87.0 build, surfaced five real bugs in
the New Server wizard and a real Dashboard state bug. All five are root-caused and fixed below.

## 1. Wizard jumps straight to Confirm & Finish

**Report**: "setting up a new server is still broken, it jumps right to this screen" (a screenshot of
Step 8 of 8 — Confirm & Finish, immediately after opening a brand-new "+ New Server" tab).

**Root cause**: `RefreshAsync`'s step-1 short-circuit (`if (IsCreatingNewProfile && NewServerWizardStep
== 1 && ServerIsRunning) NewServerWizardStep = IsNewServerSetupFlow ? 8 : 5;`, added in v0.7.64.0 for
the Connect flow, generalized to both flows in v0.7.83.0) assumes "step 1 detected a running server"
means "this wizard is resuming an already-configured server." That's true for Connect, but never true
for the New Server Setup flow: at step 1, before any new fleet profile is registered, the wizard's
connection is always to the shared default local management API -- the exact same one the always-open
"Local MystTiq" tab already uses. `ServerIsRunning` at that point reflects whatever the **default**
profile's server is doing, not "is the new server already set up" (which is nonsensical anyway, since
it doesn't exist yet). Any user who already has a running default server -- the common case -- hit
this short-circuit on every single "+ New Server" attempt, skipping World Source/Identity/Install/
MODs entirely.

**Fix**: scoped the short-circuit to `!IsNewServerSetupFlow` (Connect only). The New Server Setup flow
already had its own correct complementary branch right below it (auto-advance to World Source once
connected), which now always wins for that flow.

This single fix also explains two more of the reports below, since neither could ever be reached
while every wizard attempt was being redirected straight to Confirm:

- **"when i choose import a world it should load an option to actually import a world save"** -- the
  Install step's embedded Analyze/Apply import controls (`AnalyzeWorldArchive_Click` already opens a
  real file picker for the world-save ZIP) were simply never reached.
- Step 3's Game Port highlighting/note (below) was also never seen for the same reason.

## 2. Install Directory step has no field to see or change the path

**Report**: "when i hit back i see step 5 which is install directory. the user should be able to
change it" (a screenshot showing only a status sentence, a static warning box, and Back/Continue --
no path field at all).

**Root cause**: `NewServerInstallDirectoryEffectivePath` was already computed correctly (typical root
if free, an auto-derived sibling if occupied) but was never actually exposed as an editable field --
only folded into a sentence inside the status text when the default root happened to be occupied.

**Fix**: `NewServerInstallDirectoryEffectivePath`'s setter is now public (was computed/private-set),
and the step gained a real `TextBox` (`Mode=TwoWay`) plus a "Browse" button reusing the existing
`WorkspaceBrowse_Click` folder-picker pattern (new `Tag="installDirectory"` branch).
`ContinueFromInstallDirectoryAsync` already just reads this property for the actual `ServerRoot` sent
to `AddFleetProfileAsync`, so no further wiring was needed -- a manual edit flows straight through.

## 3. Game Port needs highlighting and an explanatory note

**Report**: "on step 3 it should highlight the game port and maybe have a note saying this must be
different if you run multiple servers on the same machine at the same time. otherwise default is
fine."

**Fix**: wrapped the Game Port field in an amber-bordered `Border` (matching the existing
unsaved-change highlight look) and added a permanent (not conflict-conditional) note beneath the
Players/Game Port/REST Port row. The pre-existing live conflict warning
(`SetupGamePortWarningText`/`HasSetupGamePortWarning`) is unchanged and still shows underneath when a
real conflict is detected.

## 4. Clone source list is missing "Local MystTiq"

**Report**: "when i choose to clone a world how come it is missing Local MystTiq?" (a screenshot of
the Clone step's dropdown showing only "Linux Test VM" and "Palworld Server 2 (Clone)").

**Root cause**: `CloneableSourceProfiles` reused the exact same filter as the "+" menu's own "Connect
to {profile}" list -- "any saved profile not currently open in a tab." That filter is correct for
*that* use case (don't open a redundant second tab to an already-open profile), but has no bearing on
whether a profile is valid to clone *from*. Cloning only requires the source's PalServer to be
stopped (already stated in the step's own instruction text) -- unrelated to whether its tab happens
to be open. Since "Local MystTiq" (the always-present default profile) is near-permanently open in
its own tab, it was excluded from every single Clone step.

**Fix**: `CloneableSourceProfiles` now returns all saved `Profiles` directly. The brand-new,
not-yet-saved profile being created can never appear here on its own (it has no real `Id` yet, so it
can't match anything in `Profiles`).

## 5. Dashboard stuck showing "Starting / Not Ready" with Start greyed out

**Report**: "i still have a bug where it says the server is stopped, the start button is greyed out
and lifecycle says it is stopped?" (a screenshot of the real Default Server's Dashboard: SERVER card
and OVERALL HEALTH both say "Starting / Not Ready"/"STARTING," Start is greyed, Stop is enabled, and
the LIFECYCLE banner reads "PalServer is already stopped.")

**Root cause, confirmed live** (queried `GET /api/v1/status` directly against the running local
sidecar): `{"phase":1,"nativeProcessId":15348,"ready":false,"detail":"PalServer is not running."}` --
`phase:1` is `ServerLifecyclePhase.Stopped`, but `nativeProcessId` still carries the *previous* run's
PID. Confirmed that PID no longer exists as an OS process. Both `WindowsServerLifecycleService` and
`LinuxServerLifecycleService` (`MystTiq.Core`) deliberately keep returning the last-known PID even
once the phase has genuinely gone to Stopped/Crashed, for reference display -- this is correct backend
behavior, not a bug. The bug was entirely in the Desktop client: `ApplyStatus` tested
`status.NativeProcessId.HasValue` directly as its "is a process alive" signal (added in v0.7.82.0 to
correctly show "Starting / Not Ready" instead of a false "Stopped" during the genuine mid-launch
window), which stays true forever once any server has ever run, regardless of whether it's since
genuinely stopped.

**Fix**: added `ServerStatusDto.IsProcessLive => Phase == 3` (mirrors
`MystTiq.Core.Models.ServerLifecyclePhase.Running`) -- the only phase where a process is actually
confirmed alive right now, including the genuine mid-launch window (the OS process is found and
reported as `Running` immediately once `StartAsync` spawns it, well before `Ready` flips true). All
three `ApplyStatus` call sites (`ServerIsRunning`, `ServerState`, `DashboardHealthText`) now use
`status.IsProcessLive` instead of `status.NativeProcessId.HasValue`. `NativePidText` (display-only)
is unchanged and still shows the last-known PID.

## Verification

- `dotnet build` on `MystTiq.Desktop` and the full solution -- clean, 0 warnings/errors.
- Live-queried the real running sidecar's `GET /api/v1/status` before and after the fix build to
  confirm the exact stale-PID scenario this targets, and independently confirmed the stale PID
  (15348) no longer exists as an OS process.
- Hand-traced `IsProcessLive`/`ServerIsRunning`/`ServerState`/`DashboardHealthText` against the
  confirmed-live status payload: `Phase=1` now correctly yields `IsProcessLive=false`, so
  `ServerIsRunning=false`, `ServerState="Stopped / Not ready"`, `DashboardHealthText="STOPPED"` --
  un-gating the Start button.
- Did **not** start the user's real Default Server as part of this verification (out of scope for a
  UI bug fix, and avoids touching their live production server); relied on the direct status-payload
  trace instead. There is no GUI automation tool for the native Avalonia desktop app in this
  environment, so the actual rendered Dashboard pill/Start button state was not visually confirmed
  this session -- flagging this explicitly rather than overclaiming a live UI test that didn't happen.
