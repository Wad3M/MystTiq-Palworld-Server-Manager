# v0.7.107.0 — Alert Center: Reminder Re-alerts

## Context

A named follow-up since v0.7.102.0 first introduced episode-based alerting, carried in every checkpoint since
as "not built": a condition that stayed true for a long time (days) sent exactly one alert at the start and
then nothing else until it cleared. A pinned Critical unpinning itself on recovery (v0.7.104.0) closed the
"stuck pinned forever" half of this; this version closes the "forgotten in the meantime" half.

## What changed

- `AlertEpisodeTracker.Observe` gained an opt-in `TimeSpan? reminderInterval = null` parameter (the default,
  `null`, exactly preserves every existing call site's behavior — including every harness scenario written
  before this version, none of which needed changes). When the condition has not transitioned this tick (still
  active, alert still open) and a full `reminderInterval` has passed since the alert (or since the last
  reminder, if one has already been sent), `Observe` returns the new `EpisodeAction.Reminder` instead of `None`.
- `EpisodeState` gained `LastReminderAt`. It is reset to `null` whenever a fresh episode opens (a new `Alert`),
  when the episode ends (`Recovered`), and when the rule is switched off (`Close`) — so a new episode always
  starts its own reminder clock from scratch and never inherits a stale timestamp from a previous one.
- `HeadlessAlertCenterService`: a new `ReminderInterval`, 1440 minutes (24 hours) by default, overridable with
  `MYSTTIQ_ALERT_REMINDER_MINUTES` (0 to 10080/one week; 0 disables reminders entirely) the same way
  `MYSTTIQ_ALERT_EVAL_SECONDS` already shortens the evaluation tick for live testing. `Track` passes it to
  `Observe` and handles `EpisodeAction.Reminder` by creating a plain notification titled `Still active: {title}`
  with the same severity and evidence as the original alert.
- The reminder is **never pinned**, even for a Critical condition. The original alert is already pinned (or
  isn't, for a Warning); pinning every reminder too would grow the pinned count without bound for a
  long-running condition, defeating the point of v0.7.104.0's unpin-on-recovery work. A reminder is a plain
  follow-up in the feed, not a second demand for attention.

## Deliberately not done

- No per-rule reminder interval. It is one global setting for every rule, matching `EvaluationInterval`'s own
  existing global-not-per-rule design, not a new field on each of the four `AlertRuleSet` rule types.
- No UI to change the interval from the Alert Center page. It is an environment variable, the same tier of
  control `MYSTTIQ_ALERT_EVAL_SECONDS` already has (a live-testing knob, not a documented user setting) — a
  proper Desktop setting is a larger, separate piece of work if wanted.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 2 new scenarios: a condition that stays true reminds exactly once per interval (verified past
  two full intervals, not just one), a fresh episode after a recovery starts its own reminder clock rather than
  inheriting the old episode's timestamp (a value chosen specifically to distinguish "reset" from "not reset" —
  a naive test could pass by coincidence otherwise), the disabled-by-default (`null`) and explicit
  `TimeSpan.Zero` cases send no reminders; and separately, that `Close` (switching a rule off) resets the clock
  the same way `Recovered` does.
- New live smoke `Test-v0.7.107.0-RouteSmoke.ps1` on a real sidecar (`MYSTTIQ_ALERT_EVAL_SECONDS=2`,
  `MYSTTIQ_ALERT_REMINDER_MINUTES=1` so a real interval elapses inside the smoke instead of 24 real hours): the
  original pinned alert arrives with no reminder yet; a reminder arrives once the interval elapses, unpinned,
  without touching the original; no second reminder before its own interval but one does after two intervals
  total; recovering stops reminders and the original alert has unpinned itself (confirming v0.7.104.0's
  behavior still holds alongside this new one). 4/4 passing under strict mode and on the final published
  binary.
