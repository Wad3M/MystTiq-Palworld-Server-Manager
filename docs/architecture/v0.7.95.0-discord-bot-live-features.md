# v0.7.95.0 — Discord Bot: Live Status, Join/Leave Feed, Autocomplete, More Commands

## Context

First of the "enhancements to features we already have" group, after the competitive feature review.
The review had noted the Discord bot as "exists, but less developed than PalSupervisor's". Reading the
actual service first corrected my own earlier backlog note: **per-Discord-role permission mapping already
exists** (Discord role id → MystTiq role via `RoleMappings`, plus an owner user id, with an
Operator/Admin/Viewer gate per command). So that is not built here. What genuinely was missing:

- The bot only ever *replied*; it never posted anything on its own (no live status, no join/leave feed).
- `/mysttiq-kick` and `/mysttiq-ban` required a raw player id typed by hand.
- No save, backup or unban command.
- Player names and broadcast text went into replies with mentions enabled (see Safety).

## What changed

- **Live status message.** Set a status channel id and the bot keeps ONE embed there up to date (state,
  player count and names, "last checked" as a Discord relative timestamp). Its message id is persisted, so it
  survives restarts and is edited rather than re-posted; if the message was deleted it posts a new one.
  It is only re-edited when the content changes, plus a forced refresh every 5 minutes.
- **Bot presence.** "Watching 3 players online" (toggle, on by default).
- **Events feed.** Optional events channel: players joining/leaving and server online/starting/stopped/crashed.
  The first observation is a silent baseline, and a stop or restart resets the baseline so it is never read
  as everyone leaving. A failed player read is never diffed. Stopping and Unknown are never announced.
- **Autocomplete for kick/ban.** The `player` option suggests the players online right now (name shown, id
  sent; same-named players are told apart by an id tail). A typed id still works for offline players. Only
  callers whose role could run the command see suggestions.
- **New commands:** `/mysttiq-save` and `/mysttiq-backup` (Operator, backup via the existing
  `HeadlessBackupService`), `/mysttiq-unban` (Admin).
- **Config:** `StatusChannelId`, `EventsChannelId`, `ShowPresence` (defaults keep an old `discord-bot.json`
  loading unchanged); `StatusMessageId` is internal and a save never wipes it, but changing the status channel
  drops it so a fresh message is posted there. Channel ids must be real 15-20 digit snowflakes: the server
  refuses anything else with a reason (HTTP 400) and the Desktop form checks first.

## Safety

- Player names are chosen by players and broadcast text by whoever runs the command, so **all bot replies and
  posts now send `AllowedMentions.None`** (an `@everyone` in a name can no longer ping the guild) and names are
  markdown-escaped in the messages we build. This also fixes the pre-existing `/mysttiq-players` and
  `/mysttiq-status` replies.
- A Discord-side problem (missing channel, missing permission) is logged once per distinct message, not per
  tick, so a misconfigured channel cannot flood the activity log.
- The live loop runs only while the gateway is connected, is cancelled on disconnect/re-save, and each tick
  swallows and logs its own errors so one failure cannot kill the loop.

## Design

The Discord-free half lives in `DiscordBotFormatting` (state keys, status text, presence text, transitions,
join/leave diff, autocomplete suggestions, command→role map, markdown escaping) plus `DiscordSnowflake` in
Core, so it is unit-tested; the gateway plumbing stays thin in `HeadlessDiscordBotService`
(`LiveTickAsync`, `UpdateStatusMessageAsync`, `PostEventsAsync`, `OnAutocompleteAsync`).

## Verification

- Solution and Desktop builds clean, 0 warnings/errors (the new Discord.Net calls compile against 3.20.1).
- Logic harness: 6 new scenarios pass (status text/escaping/truncation/change key, presence and transition
  rules, join/leave diff and baseline, autocomplete, command roles incl. "every command has an explicit role",
  snowflake/channel-id validation, and an old-format config loading with sensible defaults).
- Live: `GET/PUT /notifications/discord-bot` — on the scratch server a bad channel id returns HTTP 400 with the
  reason, a valid pair round-trips (whitespace trimmed, presence flag kept), and an old-style save falls back
  to defaults; cleared afterwards. The Default Server's bot is not configured and was only read.
- **NOT verified:** anything that needs a real Discord bot token — the gateway connection, that the status
  message actually posts/edits, autocomplete replies, presence, and the events feed. No token was available,
  and the Desktop has no GUI automation here. The message/embed/permission plumbing follows Discord.Net's API
  and compiles, but the first real run in a test server is the true test; the bot needs View Channel, Send
  Messages and Embed Links in the configured channels.
