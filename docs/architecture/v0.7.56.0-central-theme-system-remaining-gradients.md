# v0.7.56.0 — Central Theme System Completion, Remaining Decorative Gradients

## Goal

The rest of the theming gap deferred from v0.7.48.0's foundation pass. That version covered
`DesignSystem.axaml`'s opaque structural surfaces, page-accent card flares, status glows, and
button chrome via a formula-driven derivation engine (`ThemeColorMath`/`ThemeCatalog`/`ThemeApplier`).
It explicitly left ~240 hardcoded colors untouched — overwhelmingly the elaborate multi-stop
translucent "glass" gradients — because a translucent gradient behaves differently over a dark vs.
light background in a way a simple lighten/darken swap can't safely reproduce, and this session has
no way to render or screenshot the native Avalonia app to verify the result.

## Why this shipped as v0.7.56.0, not v0.7.57.0

The roadmap's own v0.7.56.0 slot ("Second Local Server + Remote Linux Server, Both Cloned") turned
out to be pure live-infrastructure work: a real second local server profile was successfully cloned
(5,683 files, 5.7GB) and registered in the fleet, but starting either the clone or the original
production server hit an unexplained, reproducible PalServer launch freeze on this machine (process
starts, engine process shows near-zero CPU growth indefinitely, UDP game port never binds, no crash,
no logged cause) — reproduced identically on a brand-new install at a different path/port, ruling out
anything specific to one server folder. Tabled by direct request pending a device restart; no code
changed for that item, so there is no "v0.7.56.0" software release to package for it. Following this
session's own established "no version-slot gaps" discipline (see v0.7.51.0's self-correction, where
a skipped slot was closed by renumbering the rest of the roadmap rather than leaving a gap), this
Theme Completion work fills the v0.7.56.0 slot instead. The Second Local Server / Remote Linux Server
item remains open and unscheduled, to resume once the local PalServer-launch issue is resolved.

## Approach: extend the existing formula-driven engine, don't hand-author

Same discipline as v0.7.48.0: ~30 gradient families × up to 5 stops × 4 themes × 2 variants has no
way to be manually tuned with any confidence without visual verification. Four new `ThemeApplier`
helper methods, each covering one structural category of gradient:

- **`BuildGraphFill(baseColor)`** — a simple top-to-bottom fade from `WithAlpha(base, 0x70)` through
  `WithAlpha(base, 0x28)` to full transparency. The lowest-risk family by construction: alpha-blending
  onto full transparency naturally reads correctly over any background color, so no separate
  Dark/Light tuning is needed at all — the same base color works for both variants. Computed inside
  the existing `DerivedColorNames` loop (all 11 names, for consistency with `Card{Name}Gradient`/
  `AccentBorderBrush`, even though only 5 have an existing XAML consumer today).
- **`BuildContextGradient(baseColor, variant)`** — a 2-stop diagonal fade. Dark darkens the base color
  toward a near-black tinted corner (mirroring the existing hand-authored `ContextBlueGradient` etc.
  structure); Light lightens toward a near-white tinted corner instead — fading toward black on a
  light background would read as a stray dark smear, the same reasoning `BuildCardGradient`'s own
  Light branch already established in v0.7.48.0.
- **`BuildGlassSheen(baseColor, variant, bright)`** — a 3-stop diagonal "bright lip → tinted mid →
  deeper face" gradient, matching the structure the app's own hand-authored `GlassOptionHoverGradient`/
  `PrimaryGlassGradient` already use. Dark stays close to that existing look (lip lightened, face
  darkened). Light pushes the lip brighter still and only lightly tints the face, rather than mirroring
  Dark's darken-toward-black direction — a literal Dark-formula inversion would produce a muddy
  mid-tone glass on a light backdrop instead of something that reads as glass. `bright` toggles the
  hover-state variant (higher alpha throughout, matching `PrimaryGlassHoverGradient` vs.
  `PrimaryGlassGradient`'s existing relationship).
- **`BuildNavGlass(variant, kind)`** — the nav sidebar's five structural (non-page-accent) glass
  states, keyed off `Structural.Border`/`Structural.Bg2` rather than an accent color, since these
  represent "this nav row/panel is selected/hovered," not a page identity. A `NavGlassKind` enum
  (`Surface`/`Selected`/`Hover`/`SelectedHover`/`Dashboard`) selects each state's own alpha/direction
  profile within one shared formula rather than five near-duplicate methods.

`Context{Amber}Gradient`/`BackupContextGradient` both tie to `Semantic.Amber`; `BackupProtectionGradient`/
`BackupStorageGradient`/`BackupRetentionGradient` reuse `BuildCardGradient` directly (the SAME
near-opaque 3-stop formula `Card{Name}Gradient` already uses) with Green/Blue/Orange as their base —
these don't need a new formula at all, just a new resource key pointing at the existing one with a
different base color.

`Border.dataRow`'s three states are `SolidColorBrush`/`BoxShadows` resources (`DataRowBg`,
`DataRowBorderBrush`, `DataRowHoverBg`, `DataRowHoverBorderBrush`, `DataRowSelectedBg`,
`DataRowSelectedBorderBrush`, `DataRowSelectedGlowShadow`), derived from `Structural.Bg2`/`Border`
blended with Blue (default/hover) and Amber (selected, matching the existing hardcoded box-shadow's
`#F4B83F` — an exact `Semantic.Amber` match).

## No `.axaml` structural changes needed for most of these

`ThemeApplier.Apply()` overwrites the exact same resource keys `DesignSystem.axaml` already declares
statically in `<Styles.Resources>` (`GlassOptionHoverGradient`, `ContextBlueGradient`, etc.) —
Application-level resource overrides already proven to win over `StyleInclude`-declared ones, the
same precedence `Card{Name}Gradient` already relies on since v0.7.48.0. Every existing
`{DynamicResource GlassOptionHoverGradient}`-style reference throughout `MainWindow.axaml`/
`DesignSystem.axaml` needed no change at all. Only `Border.dataRow`'s three states — previously
literal hex directly on the `Style` selector, with no named resource to override — needed real XAML
edits, routing `Background`/`BorderBrush`/`BoxShadow` through the new `DynamicResource` keys.

## Real-world consequence, disclosed (same as v0.7.48.0's own precedent)

`ThemeApplier.Apply()` runs unconditionally on every app start, so these newly-computed values
replace today's hand-tuned static ones immediately for every user, including Default+Dark. Unlike
`ThemeCatalog.GradientStops`/`Accent`/`Semantic` (which use `Combo()` to guarantee Default+Dark stays
byte-for-byte identical to legacy), this version's formulas were **not** hand-tuned to reproduce every
existing literal exactly — with ~30 families × up to 5 stops each, reverse-matching every value byte-
for-byte wasn't practical without visual verification. Each formula is designed to closely match the
existing structure and character (same "bright lip / tinted face" shape, same darken-vs-lighten
direction), matching v0.7.48.0's own disclosed precedent for its Card{Name}Gradient/border/glow set —
any visual difference from today's exact look should be minor, but this is disclosed rather than
silently glossed over.
