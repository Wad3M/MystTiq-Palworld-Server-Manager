# v0.7.103.0 — Doctor: Scheduled Backups and a One-Click Fix

## Context

Seventh of the "enhancements to features we already have". The Doctor already says whether a backup exists and how
long the world has gone unprotected (v0.7.98.0), and on the real Default Server it warns that the newest backup is
12 days old. That answers "is there a backup?" but not "will anything make the next one happen?". That server has
zero automation rules, so protection depends on someone pressing Backup. The Doctor also had no way to act on it:
its one existing fix button, "Fix Automatically", covered everything from creating a folder to downloading a server.

## What changed

- **A "Scheduled backups" finding** (Backups category), judged by a pure `DoctorHealthRules.ScheduledBackups`:
  - no rule creates backups: Warning, and the one-click fix is offered;
  - rules exist but all are switched off: Warning naming them, **no** fix (a second rule would be a duplicate);
  - enabled rules exist but none runs at least weekly (an idle-only rule, a daily rule on no days, an interval
    over 7 days): Warning, no fix;
  - every scheduled rule's last run failed: Warning quoting the reason, no fix; a missed run or a rule that has
    not run yet is not a failure, and one healthy rule is enough;
  - otherwise Pass: "Backups are scheduled: \"Nightly backup\" runs every day at 03:00 UTC".
- **A one-click fix, "Create Nightly Backup Rule".** It creates "Nightly backup (added by Doctor)": DailyTime 03:00
  UTC, every day, action CreateBackup, enabled. It is idempotent: the existence check is repeated under a lock, so
  two simultaneous clicks (or two clients) create exactly one rule, and a fix attempt when a rule already exists
  creates nothing. The message says what was created and that it can be changed or deleted in Automation.
- **Admin only.** Creating an automation rule is an Admin action everywhere else, but the Doctor's fix route only
  requires Operator, so the route now tells the service whether the caller is an admin and the service refuses
  otherwise with an explanation. Nothing else about the fix route changed.
- **Honest button labels.** The Doctor's button now says what it does: "Create Nightly Backup Rule", "Create Backup
  Folder", "Install / Repair Server Files" (it was "Fix Automatically" for all three, hiding that one of them
  downloads a server).
- Like every Doctor finding it feeds the Dashboard badge: on a running server a warning moves it to DEGRADED.

## Deliberately not done

- No rule is created without a click. Nothing changes on the real Default Server until you press the button.
- No cadence stricter than weekly: whether the backups actually keep up is Backup freshness's question, which
  judges real exposure. This finding only asks whether a schedule exists and is on.
- The fix does not enable a switched-off rule or edit an existing one: that is a decision for the admin.
- No confirmation dialog: the button names its effect, the result is one visible rule, and deleting it is one click
  in Automation.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 2 new scenarios covering every branch: none, switched off, idle-only, no days, monthly, daily,
  six-hourly, exactly weekly, selected days, a healthy rule beside a switched-off one, a failing last run with its
  reason, completed / not-yet-run / missed runs, and a failing rule beside a healthy one.
- New live smoke `Test-v0.7.103.0-RouteSmoke.ps1` on a real sidecar over a fixture with no rules: the finding warns
  and offers the fix; two simultaneous clicks leave exactly one rule; that rule is the documented nightly backup
  (name, enabled, CreateBackup, DailyTime, 03:00, next due set); the finding then passes and offers nothing and
  another attempt creates nothing; switching the rule off warns again without offering a second rule.
- **Seen on the running app** (the clone tab): the "Scheduled backups" row with its Warning badge, the evidence
  and recommendation text, and the green "Create Nightly Backup Rule" button next to Recheck; the disk row now shows
  its percentage. The button was deliberately not pressed on a real profile; its effect is covered by the smoke.
- **NOT verified:** the Admin-role refusal (auth is off in the desktop sidecar, so every caller is the Owner; the
  check is a direct comparison in the route, covered by reading, not by a live Operator token); the message shown on
  the Doctor page after pressing the button; the Linux paths.
- **A mistake caught on the way:** the first smoke run reported two failures. In this PowerShell a JSON array
  returned from a helper arrives as one nested object, so `@(Get-Rules).Count` was always 1, which also meant the
  "exactly one rule" check had passed vacuously. The helper now enumerates the rules explicitly, the counts are
  real, and a gate check makes sure that stays so.
