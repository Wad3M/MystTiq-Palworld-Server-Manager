# v0.7.92.0 — World Map: Guild Base Markers and Click-to-Select

## Context

First of the "real gaps" sequenced after the competitive feature review (see the Live-Session Backlog
in `docs/roadmap/PRODUCT_ROADMAP.md`). The live World Map already plotted online players
(`PlayerMapPointDto`, v0.6.16.0) with bundled Palpagos/World Tree backgrounds and an experimental
calibrated real-world-position mode (v0.7.21.0). Its own help text said "No Pal or base positions
yet -- see the roadmap." Competing panels (PalMap, PalSupervisor, xREALM) plot guild bases and let an
admin act on a player from the map. The user has already supplied their own map backgrounds, so no
bundled-image work was part of this.

## What was checked first

- **Base coordinates exist in the decoded save.** In the user's real `Level.sav.json`,
  `BaseCampSaveData` is a map keyed by base id; each entry's `WorkerDirector.RawData.value` carries
  `spawn_transform.translation.{x,y,z}`, in the same Unreal world units the calibrated map formula
  (`PalworldMapCoordinates`) consumes. No new decode step or dependency is needed.
- **Vanilla RCON cannot teleport to coordinates.** Palworld's RCON offers teleport-player-to-admin and
  teleport-admin-to-player only. So "click-to-teleport" on the map is honestly scoped to clicking a
  player: it selects that player for the existing Teleport To Me / Teleport To Player commands.
  Arbitrary click-anywhere teleport would need a companion mod and is not offered.

## Backend (`MystTiq.HeadlessHost`)

`HeadlessPlayerGuildExplorerService`:

- `FindAuthoritativeRoots` now also collects `BaseCampSaveData` roots during the same DOM walk that
  already finds `GroupSaveDataMap` (one traversal, no second parse of the file).
- `ReadBaseCoordinates` maps normalized base id to `(x, y)`; `TryFindNestedProperty` locates
  `spawn_transform` and `translation` with a bounded-depth search.
- `HeadlessPlayerGuildSnapshot` gains `BaseLocations` (`HeadlessBaseLocation`: base id, guild id, guild
  name, x, y). Each guild's `BaseIds` are matched to coordinates; a coordinate-bearing base no guild
  claims is still returned with guild name "Unowned" instead of being dropped.

## Desktop (`MystTiq.Desktop`)

- `PlayerMapPointDto` now carries `PlayerId`; new `BaseMapPointDto`; `BaseLocationDto` and
  `PlayerGuildSnapshotDto.BaseLocations` mirror the wire shape.
- `RebuildPlayerMapPoints` also builds `BaseMapPoints`, **only in the calibrated real-world mode**
  (`IsBaseMarkersActive`). Bases come from save coordinates and players from the REST location
  fields; only the calibrated formula treats them as one coordinate space. The default auto-fit view
  spreads dots relative to whoever is online, so mixing saved bases into it would be misleading.
  This inherits the Experimental status of that mode, and the panel text says so.
- Bases are fetched once when the markers first become visible (map expanded, calibrated mode) and
  on an explicit "Refresh Bases" button, never on the every-few-seconds status poll, since the server
  parses the whole decoded world for them.
- `SelectMapPlayerCommand`: each player dot is now a button; clicking it selects the matching
  `PlayerRecords` entry (IDs compared normalized) so the existing `TeleportPlayerToMeCommand` /
  `TeleportToPlayerCommand` work from the map. A small action row under the map shows the selection.
- Tab switches clear `_lastBaseLocations`/`BaseMapPoints` (per-server data, same stale-carryover
  class as the v0.7.89.0 Active World card fix).

## Verification

- `dotnet build` on the solution and `MystTiq.Desktop`: clean, 0 warnings/errors.
- Live: after relaunch, `GET /api/v1/world/players-guilds` against the real Default Server returned
  `baseLocations` with both bases, attributed to guild "MystTik", coordinates
  (-351088.73, 271805.20) and (-385074.78, 223931.92), matching the values read directly from the
  decoded JSON.
- Not visually confirmed: no GUI automation exists for the native Avalonia app in this environment,
  so marker placement on the Palpagos image and the click-to-select interaction were verified by
  build and control-flow trace, not by watching them. The user should enable the experimental
  real-world positions toggle and eyeball marker placement.
- Open caveat, inherited from v0.7.21.0: whether the REST player fields and the save-file base
  coordinates are the same axes is not independently confirmed; the calibrated toggle remains
  Experimental for that reason.
