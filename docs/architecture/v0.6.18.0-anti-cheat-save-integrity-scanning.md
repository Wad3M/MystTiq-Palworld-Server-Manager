# v0.6.18.0 — Anti-Cheat & Save-Integrity Scanning

## Goal

Fourth and final scheduled item in the roadmap sequence from the v0.6.15.0 competitive survey (`docs/architecture/v0.6.15-plus-competitive-survey.md`). The survey's Tier 1 finding #4 cites two real competitor mechanisms: PalSupervisor ("level-gap thresholds with configurable responses") and Sphere ("invalid Steam ID detection on join"). Neither the survey nor either competitor repo cites concrete numeric thresholds, so this pass grounds its own defaults in real, cited facts rather than guessing.

## Grounding

- **SteamID64 format**: always exactly 17 digits, always starting `7656119` (the minimum valid value is `76561197960265729`) — a hard, well-documented structural fact, not a guessed threshold.
- **Palworld's real level cap**: the 1.0 update (July 2026) raised the vanilla player/Pal level cap to 80 (previously 65). Nothing in Palworld's server configuration (`PalWorldSettings.ini`) or this codebase currently exposes a "max level" setting to read from — the cap is hardcoded into the game itself outside of mods — so this project's default (80) must stay admin-adjustable rather than presented as authoritative, since a modded server can legitimately raise it.
- Confirmed via direct code reading that no anti-cheat/anomaly-detection logic existed anywhere in the three current solution projects before this milestone. `PalworldManager/Services/WorldValidatorService.cs` (a separate, legacy WPF project) checks structural/ownership integrity, not player or Pal stat anomalies — no overlap.
- Also confirmed the roadmap doc's earlier claim that v0.6.15.0 extended to "player inventories" was never actually built (`HeadlessPalEditService.EnumeratePalEntries` explicitly skips every `IsPlayer == true` entry). That gap stays out of scope here too — this milestone adds detection, not new save-decode capability for players.

## What shipped

New `HeadlessAntiCheatService` (`MystTiq.HeadlessHost`), mirroring `HeadlessAlertCenterService`'s exact shape (rule records, persisted rule-set JSON, a `Fire`-equivalent with per-`(rule, player)` cooldown) but for player/Pal integrity rather than system-resource metrics. Three rules, each independently enabled/disabled with a configurable `Response` of `Flag | Kick | Ban` — **every rule defaults to `Flag`** (notify + log only; no player is ever auto-kicked/banned until an admin explicitly opts a rule into enforcement, matching this project's existing safety-first defaults):

- **Invalid Steam ID** — flags any online player whose Steam ID doesn't match the real SteamID64 format.
- **Impossible level** — flags any online player above a configurable `MaxAllowedLevel` (default 80).
- **Pal stat anomaly** — periodically (self-throttled to 10 minutes, since it requires a full `Level.sav` decode) scans every Pal via `HeadlessPalEditService.ListPalsAsync` (reused exactly as-is, **read-only** — this service never mutates a Pal or a save file) and flags any Pal with Level above the same configured maximum, or Talent/Rank outside the bounds `HeadlessPalEditService.ValidateChanges` already enforces on write (Talent 0-100, Rank 0-5) — reused as the read-side bounds, not redefined.

Two evaluation paths matched to cost: the two live per-player checks run on `HeadlessAutomationService`'s existing 15-second background timer loop (the same place `HeadlessAlertCenterService.EvaluateThrottledAsync` already runs), using `HeadlessMonitoringService.GetPlayersAsync` — no new polling infrastructure, and it runs independent of whether the Desktop is open. `Kick`/`Ban` responses call `PlayerModerationCoordinator.ExecuteAsync("kick"|"ban", playerId, message, ct)` — the exact mechanism the v0.6.17.0 Discord bot's `/mysttiq-kick`/`/mysttiq-ban` commands already use. A Pal-anomaly finding with no resolved owner can only ever be `Flag`ged, since there is no player to act against.

Rule configuration persisted per profile at `{ManagerRuntimeRoot}/anticheat/rules.json`; `GET`/`PUT /anticheat/rules` (`Admin`-gated, matching `/alerts/rules`) and `GET /anticheat/findings` (a bounded recent-findings list, mirroring `HeadlessPlayerRegistryService.RecentEvents`'s shape). New "Anti-Cheat & Save-Integrity Scanning" card on the Desktop's Alert Center page.

## Explicit non-goals (this pass)

- Player inventory/save decode — still doesn't exist anywhere in this codebase.
- Automatic Pal correction or deletion — anti-cheat only flags/kicks/bans; the Pal Editor (v0.6.15.0) remains the only way to actually fix a Pal.
- Behavioral/heuristic cheat detection (aim-bot-style analysis, etc.) — only structurally/numerically verifiable anomalies are detected.
- Configurable command→role mapping for who can edit anti-cheat rules — reuses the existing fixed `Admin` gate.
- Cross-profile/fleet-wide correlation — per-profile only.

## Verification

`dotnet build` (Release) across all three projects and the full solution — 0 warnings/0 errors. `scripts/Test-v0.6.18.0-Logic.ps1` (18 static contract checks) passes.

**Live, end-to-end, against an isolated `mysttiq-server.exe` instance** (real production install at `C:\GameServers\Palworld\Server` only ever read from via `robocopy`, never written to; no real production process touched):

- `GET /anticheat/rules` returned the safe, enabled, Flag-only defaults on first run.
- **Pal stat-anomaly scan**, against real production-derived save data: with the level threshold temporarily lowered to 1 (to guarantee real Pals would trip it), the very first scan after restart correctly found and flagged 5 real Pals with real species/levels/owners (e.g. `SheepBall` Level 4 owned by "Spiral", `Ganesha` Level 6 owned by "Wade", a `PinkCat` Level 15 with no resolved owner correctly handled as `"(unowned)"`, `playerId: null`). `Level.sav`'s SHA-256 hash was identical before and after the scan, confirming the scan is genuinely read-only.
- **Live player checks**, against a synthetic-but-schema-accurate fake Palworld REST server (honestly disclosed as synthetic, since no real cheater is available in this environment) returning three players — one with a malformed Steam ID, one with an impossible level (9001), one entirely normal: the very next automation tick correctly flagged the malformed Steam ID and both players above the (also lowered, to 1) level threshold, and correctly did *not* flag the two players with valid-format Steam IDs.
- **Cooldown suppression**: across two further automation ticks (~40 seconds), the finding count stayed fixed at 9 (5 Pal + 4 live-player) rather than growing — confirming the per-`(rule, player)` cooldown correctly suppresses repeat findings for the same persistent condition.
- All findings correctly recorded both a Desktop notification and an activity-log entry, matching the `HeadlessAlertCenterService.Fire` pattern this service deliberately mirrors.
