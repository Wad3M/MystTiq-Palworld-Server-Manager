# v0.7.7.0 — Fix: Backup/Restore & Lifecycle Locking Race Conditions

## Background

Second release from a broader review requested this session: a codebase-wide bug scan (two parallel agent passes) plus a competitive feature survey against other Palworld server-management tools, sequenced into versions from v0.7.6.0 onward (see `README.md`'s roadmap table). v0.7.6.0 fixed the Desktop-side scan's most severe finding; this release fixes every finding from the `MystTiq.Core`/`MystTiq.HeadlessHost` half.

## The locking discipline this fixes into

`IOperationCoordinator` (`MystTiq.Core/Operations/`) is the app's central mechanism for preventing two destructive operations from touching the same save data at once: `BeginAsync(profile, kind, source, resourceKeys, ...)` rejects immediately (`InvalidOperationException`) if any requested resource key (e.g. `"world-mutation"`) is already held for that profile, returning an `OperationHandle` whose `Dispose()` releases the held keys regardless of whether `Complete`/`Fail` was ever called. `HeadlessWorldTransactionService`, `HeadlessGuildOwnershipService`, `HeadlessBaseOwnershipService`, `HeadlessCharacterMigrationService`, and `HeadlessPalEditService` all correctly acquire this lock before mutating the save tree. Two places did not.

## Fix 1 — `HeadlessBackupService.RestoreAsync` now takes the `world-mutation` lock

Previously, `HeadlessBackupService`'s constructor took only `paths, lifecycle, activity`, and `RestoreAsync` — which moves `paths.SaveRoot` aside, extracts a backup archive into its place, and deletes the temporary rollback copy — was guarded only by the service's own local `backupGate` semaphore. `POST /backups/{fileName}/restore` called it with no coordinator involvement at all, so a restore could run concurrently with a Guild Ownership / Base Ownership / World Transaction Apply already mid-flight on the same `Level.sav`/save directory, each assuming (correctly, for every *other* caller) that holding the lock meant exclusive access.

`HeadlessBackupService` now takes `IOperationCoordinator coordinator, ServerProfileId profile` (mirroring the other four services' constructors exactly), and `RestoreAsync` acquires the `world-mutation` key before touching `SaveRoot`, releasing it via `operation.Dispose()` in its `finally` block alongside the existing `backupGate.Release()`. Every exit path (the three "soft failure" early returns, the extraction/swap exception path, and the success path) now also calls `coordinator.Fail`/`coordinator.Complete` so the operation's journal entry reflects the real outcome, not just "Running" forever.

`CreateAsync`/`DeleteAsync`/`VerifyAsync`/`VerifyAllAsync`/`ApplyRetentionAsync` deliberately do **not** take this lock. They don't mutate `SaveRoot` (they zip/read/delete backup *archive* files, not the live save tree), and critically, `CreateAsync` is called *by* `HeadlessWorldTransactionService` and its siblings for their own safety backups — while those services already hold the `world-mutation` key on the same profile. Adding the lock to `CreateAsync` would make those calls reject against their own caller's held lock (`IOperationCoordinator` has no reentrancy concept — it's "reject if any *other* caller holds the key," but a same-profile second `BeginAsync` call rejects regardless of who's asking).

## Fix 2 — `/diagnostics/network/restart` now takes the same lock as `/server/restart`

This route ran its own diagnostics-based decision (`RunAsync` recommends a restart) and, if so, called `p.Lifecycle.RestartAsync` directly — the only lifecycle-mutating route in the file that didn't go through `host.RunLifecycleActionAsync`'s `coordinator.BeginAsync(..., ["lifecycle", "world-mutation"], ...)` wrapper. Fixed by acquiring the same lock manually around the restart call (the route's existing pre/post-diagnostics response shape doesn't map onto `RunLifecycleActionAsync`'s generic result shape, so the lock is taken/released inline rather than reusing that helper) — a `409 Conflict` with `error: "lifecycle-operation-in-progress"` is now returned if a manual restart, an automation-triggered restart, or an in-flight world-mutation transaction already holds the lock.

## Fix 3 — a successful restore no longer reports "failed" because of a cleanup hiccup

`RestoreAsync`'s final steps used to be: move the extracted content into place, then delete the now-redundant `.restore-rollback-*` copy, all inside one try/catch. If the delete step threw (e.g. a transient AV-scanner file lock), the exception propagated to the method's outer `catch`, which returned `Failure(ex.Message)` — even though the restore itself had already fully succeeded (`SaveRoot` already held the newly-restored content by that point). The operator would see "restore failed" and might re-run the restore or distrust a perfectly good backup, while an orphaned rollback directory sat on disk with no explanation.

Fixed by moving the rollback-cleanup delete outside the restore's own try/catch, into its own best-effort block: a cleanup failure now produces a *successful* result whose message notes the leftover directory by name ("safe to delete manually") instead of reporting the whole restore as failed.

## Fix 4 — rollback-of-rollback no longer silently swallows its own failure

`HeadlessWorldTransactionService.ApplyAsync`'s failure-recovery path used to delete `explorer.Explore().ActiveWorldPath` (asking the world explorer "what does it currently think is the active world") before moving the pre-transaction rollback copy back into place. `ValidateWorldDirectory` (the transaction's own post-swap check) only verifies `Level.sav` exists and is non-empty — a narrower check than the explorer's own "is this recognizably a world" logic. Content that passed the former but failed the latter meant `ActiveWorldPath` came back empty, the corrupted directory at the real destination was never deleted, and the subsequent `Directory.Move(rollback, originalPath)` then threw (.NET requires the move destination not already exist) — caught by a bare `catch { rolledBack = false; }` that discarded the exception entirely. The result: `RolledBack=false`, the corrupted content stayed live, the good data sat stranded in the rollback folder, and the returned error message gave no hint that automatic recovery itself had failed.

Fixed two ways: the recovery path now deletes the actual, already-known destination path directly (computed the same way the subsequent `Directory.Move` computes it) instead of going through the explorer indirection, so the common case now succeeds outright; and if the rollback recovery still throws for some other reason, that exception's message is now appended to the reported failure detail ("Additionally, automatic rollback failed: ...") instead of being swallowed.

## Fix 5 — mod-snapshot rollback now uses the same ZIP path-traversal guard as everywhere else

`InstallZipAsync` established this file's pattern for extracting an archive safely: reject any entry path containing `..` or a rooted path, and verify the resolved destination stays under the intended root before writing. `RollbackAsync`'s snapshot-restore path (the "flat" `~mods` case) called `entry.ExtractToFile` directly with the raw `entry.FullName`, skipping that check. Snapshot ZIPs are normally self-generated by `CaptureSnapshot`, so exploitability requires a tampered or corrupted snapshot file already on disk — but a rollback path shouldn't trust that file any more than a fresh upload is trusted elsewhere in the same class. Now applies the identical guard.

## Explicit non-goals

- No change to `HeadlessGuildOwnershipService`/`HeadlessBaseOwnershipService`/`HeadlessCharacterMigrationService`/`HeadlessPalEditService` — all four were checked and already correctly hold the coordinator lock; the `explorer.Explore().ActiveWorldPath`-style rollback pattern from Fix 4 does not appear in any of them (confirmed via search — they use a different, simpler recovery mechanism).
- No change to `CreateAsync`/`DeleteAsync`/`VerifyAsync` locking — see Fix 1's reentrancy explanation for why that would be actively wrong, not just unnecessary.
