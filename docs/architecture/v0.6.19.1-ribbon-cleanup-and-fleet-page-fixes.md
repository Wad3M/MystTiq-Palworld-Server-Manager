# v0.6.19.1 — Ribbon Cleanup and Fleet Page Fixes

## Goal

Two items raised earlier this session and explicitly logged for later: "the ribbon tab items that mirror the navigation pane... we dont need both," and "the fleet navigation is missing other UI components."

## Grounding

**Ribbon duplication.** `MainWindow.axaml`'s ribbon (Grid.Row="2") had seven groups: two always-visible ("Server Control": Start/Stop/Restart/Refresh; "Quick Actions": Backup/Console/Doctor) and five category-conditional ones (World/Server/Mods/Tools/System), each shown only while that category tab was active. Comparing each category-conditional group against that same category's left nav sidebar list (Grid.Row="3", Grid.Column="0") showed they were exact, button-for-button duplicates — e.g. the "Server" ribbon group's Setup/Config/Console/Workspace buttons matched the Server category's nav sidebar 1:1, both firing the identical `NavigateCommand` with the identical `CommandParameter`. The two always-visible groups are not this kind of duplicate: "Server Control" has no nav-sidebar equivalent at all (lifecycle actions, not page navigation), and "Quick Actions" is a fixed, cross-category shortcut set rather than a mirror of the *currently active* category's own list.

**Fleet page.** Reading `MainWindow.axaml`'s Fleet section and the DTOs it binds (`FleetDtos.cs`) showed the page already has a header/refresh, Fleet Actions (Backup/Doctor/Update All), Clone World, a Server Profiles list, and a Last Fleet Action Results list. Two concrete gaps stood out: `ServerProfileSummaryDto.StatusText` was shown as plain text with no color cue, unlike every other status surface in the app (the v0.6.19.0 tab bar's status dot, the dashboard's glow cards); and `FleetActionResultDto.Error` — already returned by the API on a failed fleet-wide action — was never bound anywhere, so a failed Backup/Doctor/Update-All action showed only a bare `Success: False` with no indication of what went wrong. The user's feedback was broader than these two items ("missing other UI components," unscoped), but these are the concrete, unambiguous gaps the existing data model already exposes without inventing new server-side surface area.

## What shipped

- Removed the five category-conditional ribbon groups (World/Server/Mods/Tools/System) from `MainWindow.axaml`. The two always-visible groups (Server Control, Quick Actions) are untouched.
- `Models/FleetDtos.cs`: new `ServerProfileSummaryDto.StatusDotColor` (green running / red crash detected / grey stopped), mirroring the color scheme `TabSession.StatusDotColor` introduced in v0.6.19.0.
- `MainWindow.axaml`'s Fleet page: Server Profiles list rows now show a status dot bound to `StatusDotColor`; Last Fleet Action Results rows now show `Error` (red, wrapped, `IsVisible="{Binding !Success}"`) beneath a failed row.

## Explicit non-goals (this pass)

- Any other unspecified Fleet page additions — the feedback was broad and unscoped; only the concrete gaps found by inspecting the existing data model were addressed.
- Any server-side (`MystTiq.Core`/`MystTiq.HeadlessHost`) change — `ServerLifecycleStatusDto`/`FleetActionResultDto` already carried every field used here.

## Verification

`dotnet build` (Release) — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.6.19.0 regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. The ribbon's visual layout after removing five groups, and the Fleet page's new status dots/error text, are the user's to confirm once built.
