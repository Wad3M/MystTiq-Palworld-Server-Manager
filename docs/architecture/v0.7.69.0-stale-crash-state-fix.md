# v0.7.69.0 — Stale Crash-State Fix (Windows)

## Goal

Another item from the same roadmap audit that produced v0.7.64.0 through v0.7.68.0: *"a stale-crash-
state edge case where force-killing the MystTiq management process itself... leaves a stale
`NativeProcessId`/`crashDetected:true` that only an explicit `Start` (not `Stop`) clears"*
(v0.6.10.0's own session notes, never fixed).

## Root cause

`GetStatusAsync`'s crash-detection logic writes `Phase: Crashed` to the persisted state store once a
previously-`Running`/`Starting` managed process disappears without a requested stop. That check only
re-fires when `persisted.Phase is Running or Starting` — once it's already `Crashed`, the check is
permanently false until something else writes a different phase.

`LinuxServerLifecycleService.StopAsync`'s "nothing to stop" branch (reached when an admin presses
Stop while the server shows Crashed, or genuinely already stopped) already writes a fresh
`Stopped`/`StopRequested: true` state unconditionally — so pressing Stop naturally clears a stale
Crashed state on Linux. `WindowsServerLifecycleService.StopAsync`'s equivalent branch never wrote
anything to the state store at all — it just returned `NotRunning` with whatever
`GetStatusAsync` currently reported, leaving `Phase: Crashed` persisted forever. Only calling `Start`
(which does write a fresh state) ever cleared it on Windows — exactly the asymmetry the original
observation described, now confirmed to be a genuine Windows-vs-Linux inconsistency rather than an
unexplained edge case.

## The fix

`WindowsServerLifecycleService.StopAsync`'s "nothing to stop" branch now mirrors Linux's exactly:
writes a fresh `Stopped`/`StopRequested: true` state to the store before returning, and returns a
snapshot reflecting that (not the stale `Crashed` one). An admin who reacts to a crash by pressing
Stop — arguably the more natural reaction than pressing Start again — now actually clears it.

## Verification

- `dotnet build` on `MystTiq.Core.csproj` and the full solution: clean, 0 warnings/errors.
- New `scripts\Testing\MystTiq.LogicHarness` scenario (20/20 total, passing first run): constructs a
  **real** `WindowsServerLifecycleService` (not a stand-in) with a fake `IServerSessionInspector`
  reporting no processes/ports at all — exactly the "PalServer already gone" condition — and an
  isolated `ServerLifecycleStateStore` pre-seeded with a `Crashed` state. Calls the real `StopAsync`
  and asserts: the returned snapshot reports `Stopped`/`CrashDetected: false`, and — separately,
  re-reading from disk — the state actually persisted is `Stopped` with `StopRequested: true`, not
  left as the stale `Crashed` it started as. This exercises the real class end-to-end (constructor
  through the exact code path this fix changed), not a reimplementation of its logic.

## Known gaps (disclosed)

- Not verified against a real crash scenario on a live Windows host (killing a real PalServer
  process out-of-band, then observing the Desktop UI) — the harness scenario proves the state-store
  transition correctly, which is the entire mechanism this bug lived in; the GUI-visible effect
  (Dashboard health badge, etc.) already reads from this same state, so no separate GUI-level bug is
  expected, but this specific claim was not re-confirmed visually.
