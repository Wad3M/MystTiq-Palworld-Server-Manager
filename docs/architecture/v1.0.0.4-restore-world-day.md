# v1.0.0.4 — Restore Checked by the World's Day (internal)

Reported 2026-10-05: "the backup and restore function doesnt seem to work correctly. verify using the day of the game server
after a restoration."

## What the day showed

The world's day is `GameTimeSaveData.GameDateTimeTicks` (100 ns ticks; day = ticks / 864 000 000 000) inside `Level.sav`. On
current servers `Level.sav` is PlM (Oodle) compressed, which .NET cannot open, so MystTiq reads it from a decoded
`Level.sav.json` beside it, written by the PlM converter (`Tools\palworld-plm-tools\convert.py`, 0.8 s for this world).

Read straight from `Level.sav` with pyooz on 2026-10-05:

- Live world (`Level.sav`, 2026-10-04): **Day 248 21:08**. The Dashboard showed **Day 210 16:49**, from a `Level.sav.json`
  decoded on 2026-10-01 06:57. Nothing refreshed that copy after normal play; only a MystTiq world edit did
  (`RefreshExplorerSidecar`). The Dashboard still called it "exact".
- The 36 backups: each `Level.sav` holds its own day, rising from Day 109 (2026-08-25) to Day 211 (2026-10-01 07:57). Every
  backup since 2026-10-01 carries the same stale Day 210 `Level.sav.json`, so a restore could not change the day shown.
- On 2026-10-01 the world went from Day 211 (07:57) to Day 173 03:38 (10:24), consistent with the 2026-09-02 backup
  (Day 172 19:56) put in place and run a few game hours. No MystTiq restore succeeded that day, so it was not MystTiq.

## What the restores did

The operations journal (`fleet\operations\journals\default`) has four restores, all on 2026-10-01, all failed:

- 07:41:58 and 07:42:07: "Stop PalServer before restoring a backup."
- 07:42:43 and 07:58:15: "Access to the path '…\Pal\Saved\SaveGames' is denied."

`RestoreAsync` extracts the backup to a staging folder, then moves the whole `SaveGames` folder aside in one
`Directory.Move`. Windows refuses to move a folder while any file in it is open (seconds after the server stopped, an
Explorer window, a scanner). Nothing was changed, but nothing said what held it, and restores were not in the activity log.
Their safety backups (07:41:50 and 07:57:44 local) are in the backups list.

## The real cause: the save folder belonged to administrators (found 2026-10-05)

Testing the fix live, the decoded copy still would not refresh: writing `Level.sav.json` was denied. The ACLs:

- `Pal\Saved\SaveGames` and the world folder: owner `BUILTIN\Administrators`; Users have only read, add-file and
  add-subfolder rights (inherited from the C:\ defaults). `Pal\Saved` gives Users no delete-child.
- `Level.sav`: owner the user (PalServer, running as the user, writes it). `Level.sav.json`: owner Administrators, Users
  read-only.

Something that once ran as administrator created SaveGames. The Desktop's MystTiq service runs as the user without
administrator rights (UAC filters the Administrators group out of its token). It may read and add files there, but it may
not move or replace SaveGames: that needs DELETE on it, or delete-child on `Pal\Saved`. That, not a held file, is why both
2026-10-01 restores failed with "Access to the path …\SaveGames is denied". Windows reports a sharing violation and a
missing permission with the same message. `CreateFile(SaveGames, DELETE)` returns error 5 for this process and succeeds
for an ordinary folder.

The fix: `SaveFolderAccess.CanReplace` asks for DELETE (nothing is changed). The backups list reports it, and a restore
refuses up front with the way out. The Desktop's Fix Save Folder Access runs
`icacls <Pal\Saved> /grant *<user SID>:(OI)(CI)M /T /C /Q` through Windows' administrator prompt (`ElevatedPowerShell`,
shared with the firewall fix). It is offered only for a server on this computer and is never run without the owner's
click and Windows' consent. The world clock writes its own decoded copy
(`runtime\world-clock\decoded\<world>.Level.sav.json`) when the one beside `Level.sav` cannot be written, and reads the
newer of the two. The map and guild pages still read the one beside `Level.sav`, so they stay as old as it is until the
access is fixed.

The smoke reproduces it: it denies the user DELETE on its SaveGames and delete-child on its Saved (granting delete-child
on the parent would otherwise allow it), and makes its `Level.sav.json` read-only.

## What changed

- **The day:** `HeadlessWorldClockService` re-decodes a copy of `Level.sav` when it is newer than the decoded copy (the
  `/status/poll` cadence, at most every two minutes per world) and writes `Level.sav.json`. Both world views report whether
  the day is current and from when. The Desktop says "From the save as of …; the world has been saved since and is being
  read again" instead of "exact" in that case.
- **Restore:** the move is tried ten times, half a second apart. After that the Restart Manager names the holder
  ("Open in: … (pid N)"), and the message says nothing was restored. A PalServer process whose executable is under the
  server folder blocks a restore even when the lifecycle does not know it. After a restore, the restored world is decoded
  and its day reported against the backup's ("as in the backup", or both days when they differ). Restores are in the
  activity log as refused, failed or done.
- **Backups list:** each backup's day is read from its own `Level.sav` (the newest outside Palworld's `backup\`), one at a
  time in the background, cached in `backups\world-days.json`. A failure is retried after an hour.

## Tests

The restore smoke copies the newest real backups into an isolated server, links the real Tools folder (the link alone is
removed afterwards), and checks:

1. every backup's day is read;
2. a restore gives the backup's day and the Dashboard shows it as current;
3. a held `Level.sav` is named with nothing changed, and a brief hold is waited out;
4. a PalServer stand-in started from the server folder blocks a restore;
5. a touched `Level.sav` is reported as not current, then read again;
6. the activity log has every outcome.

It skips without the backups and tools (the release machine has them).

Not covered: a restore of the owner's live world (deliberately not done), and the in-game day after the server loads a
restored world. The day MystTiq reads is the one the server loads, but seeing it in the game needs the owner.
