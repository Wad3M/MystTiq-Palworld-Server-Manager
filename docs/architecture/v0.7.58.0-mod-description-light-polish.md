# v0.7.58.0 — Website-Sourced MOD Descriptions, Light Polish

## Goal

Direct request to polish v0.7.55.0's DESCRIPTION panel (MOD Library's MOD DETAILS side, the
Fetch/Refresh description feature). Reviewed the shipped XAML/ViewModel directly rather than
guessing at busywork, and found three real, concrete rough edges.

## What was found and fixed

1. **Long descriptions were silently clipped.** `MainWindow.axaml`'s description `TextBlock` had a
   bare `MaxHeight="220"` with no scroll container — any Steam Workshop description longer than
   that (common; many run several paragraphs) simply had its tail cut off with no way to read it.
   Fixed by wrapping the `TextBlock` in a `ScrollViewer MaxHeight="220"
   VerticalScrollBarVisibility="Auto"`.
2. **The Source URL was inert text.** Displayed as a plain `TextBlock`, giving the user no way to
   actually visit the mod's real page short of manually selecting and copying the text. Added an
   "Open" button next to it. Implementation reuses an already-established pattern rather than
   inventing a new one: `MainWindow.axaml.cs`'s `WorkspaceOpen_Click` already opens paths via
   `Process.Start(new ProcessStartInfo { FileName = ..., UseShellExecute = true })`; the new
   `OpenModDescriptionSource_Click` follows the identical shape, with an added scheme check
   (`http`/`https` only) before ever calling `Process.Start` — defense in depth, even though the
   backend's `SetModDescriptionSourceAsync` (v0.7.55.0) already rejects any non-http(s) URL before
   it can be persisted and shown here.
3. **The "No known Workshop match" guidance showed too early.** It was bound to
   `!HasSelectedModDescription`, a condition that's ALSO true before the user has ever clicked
   Fetch for the current selection — meaning a MOD the user simply hadn't checked yet displayed the
   same "no match" message as one that was actually looked up and confirmed absent. Added
   `MainWindowViewModel.ShowNoModDescriptionMatchMessage => HasModDescriptionResult &&
   !HasSelectedModDescription` — true only after a real fetch attempt completed and found nothing,
   raised alongside the two properties it derives from in `SelectedModDescription`'s setter.

## Verification

`dotnet build` on the full solution — clean, 0 warnings/errors. No behavioral change to the
backend (`HeadlessModManagementService`, the two v0.7.55.0 routes) — this version touches only
`MainWindow.axaml`, `MainWindow.axaml.cs`, and `MainWindowViewModel.cs`.
