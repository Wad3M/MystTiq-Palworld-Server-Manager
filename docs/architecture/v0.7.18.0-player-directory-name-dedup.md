# v0.7.18.0 — Player Directory Name Deduplication

## Background

Requested directly, the last item of a follow-up list raised earlier this session alongside the new-server wizard redesign and the tab-strip overflow work: "we should have a selectable feature to remove duplicate names for users."

The Players page's Directory list (`FilteredPlayerRecords`, backed by `PlayerExplorerItemDto`) is keyed by `PlayerId` — a real, distinct server-side identity per record. Two or more different `PlayerId`s can legitimately share the same display `PlayerName`: a player rejoining under a different platform ID than a previous session, or a stale record left behind from an older save that a current, correctly-identified record has since superseded. None of that is a data-quality bug — every one of those records is a real identity the server has actually reported at some point — but it clutters the list an operator is scanning for a specific person, and there was previously no way to declutter it short of manually cross-referencing IDs.

## What shipped

### `HideDuplicatePlayerNames` and the dedup step

A new `bool HideDuplicatePlayerNames` property on `MainWindowViewModel`, following the exact same pattern as the existing `SelectedPlayerViewFilter`/`SelectedPlayerAdminFilter`/`PlayerSearchText` filter properties — its setter calls `ApplyPlayerFilters()` on change, so toggling it re-applies immediately.

`ApplyPlayerFilters()` gained a dedup step, applied *after* the existing search/online/save-state/admin-review filtering (so it operates on whatever the operator has already narrowed the list down to, not the full unfiltered set):

```csharp
filtered = filtered
    .GroupBy(p => string.IsNullOrWhiteSpace(p.PlayerName) ? $"\0{p.PlayerId}" : p.PlayerName, StringComparer.OrdinalIgnoreCase)
    .Select(g => g
        .OrderByDescending(p => p.Online)
        .ThenByDescending(p => p.SaveExists)
        .ThenByDescending(p => p.SaveLastWriteUtc ?? DateTimeOffset.MinValue)
        .First())
    .ToArray();
```

Grouping is case-insensitive on `PlayerName`; a blank/whitespace name is keyed by its own `PlayerId` instead of an empty string, so multiple genuinely-nameless records don't all collapse into a single arbitrary survivor. The tie-break order (online first, then has-a-save, then most-recently-written) is deliberately the record an operator actually wants to find, not an arbitrary "first in the list" pick.

This is a pure view-side filter. `PlayerRecords` (the full, unfiltered source collection) is never touched, no record is deleted, no `PlayerId`s are merged or reassigned, and no server-side call is made — unchecking the box re-runs `ApplyPlayerFilters()` without the grouping step and every hidden record reappears immediately.

### Visible-count feedback

`PlayerVisibleCountText` now reports how many records the dedup step hid, whenever it hid at least one: `"{visible} visible / {known} known ({N} duplicate name(s) hidden)"`. Without this, a shorter list with the same underlying player count could easily read as "the server suddenly has fewer known players" rather than "some rows are intentionally hidden right now."

## Explicit non-goals

- **Actually merging or deleting duplicate identities.** Every `PlayerId` this feature can hide is a real identity the server itself has reported — collapsing or deleting them for real would be a destructive, much larger, and much riskier feature (and one this session's prior research into "Remove Admin"/give-items found no clean server-side precedent for). This is presentation-only, by design.
- **Persisting the toggle's state across sessions.** Matches every other filter on this page (`SelectedPlayerViewFilter`, `PlayerSearchText`, etc.), none of which are persisted either — resets to unchecked on next launch.
