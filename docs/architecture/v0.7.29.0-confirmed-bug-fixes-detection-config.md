# v0.7.29.0 — Confirmed Bug Fixes: Detection & Config

## Goal

Fifth version in the GUI/workflow/UX overhaul roadmap. Items 22 and 15 from the roadmap's findings log — both were confirmed, root-caused bugs identified during the original page-by-page walkthrough, not new feature work.

## What shipped

### Bug 1: Official/Vanilla preset wiping Server Name/Description/passwords (item 22)

**Root cause**: `ApplySelectedConfigurationPreset`'s Official branch reset every setting in `SimpleConfigurationNames` (`MainWindowViewModel.cs`) to its default value. That set is legitimately shared for a second purpose — deciding which fields the Simple Settings *view* shows (`SetConfigurationView`) — and includes `"ServerName"`, `"ServerDescription"`, `"ServerPassword"`, `"AdminPassword"` alongside genuine gameplay-rate fields, since those identity fields do belong on the Simple Settings page. But nothing about "which fields does Simple view show" implies "which fields should a QoL preset reset" — those are different questions that happened to share one `HashSet`.

**Fix**: new `GameplayRateConfigurationNames`, a proper subset of `SimpleConfigurationNames` containing only the rate-type fields (`DayTimeSpeedRate`, `ExpRate`, `PlayerAutoHPRegeneRate`, etc. — 23 fields total), explicitly excluding both identity fields and network/operational fields (`PublicPort`, `ServerPlayerMaxNum`, `RESTAPIEnabled`, `RESTAPIPort`, `RCONEnabled`, `RCONPort`). The Official branch now resets only this set — matching the scope the Balanced/Relaxed branch already had via `GetQolPreset`, which never touched identity or network settings either. `SimpleConfigurationNames` itself is unchanged; its view-filtering usage (`MainWindowViewModel.cs`, `SetConfigurationView`) was always correct and stays exactly as it was.

### Bug 2: genuinely-running server silently reported as "Stopped" (item 15)

**Root cause**: `WindowsServerLifecycleService.GetStatusAsync`'s "not running" fallback path always returned the same generic `"PalServer is not running."` detail, regardless of *why* `FindManagedServerProcesses()` found nothing — including the case where a real `PalServer.exe`/wrapper process genuinely is running, just at a path that doesn't start with the currently configured `ServerRoot` (a stale/edited path, a tab pointed at a different profile than the one actually running, etc.).

**Fix**: two changes, one in each layer:

- **Backend** (`WindowsServerLifecycleService.cs`): new `FindProcessesWithMismatchedPath()` — the exact inverse of the existing `FindManagedServerProcesses()`'s path filter, both now sharing a new `NormalizedServerRoot()` helper to avoid duplicating the path-normalization logic. `GetStatusAsync`'s "not running" fallback now checks this first (only when no crash was just detected, since a fresh crash is a more urgent, more specific signal): if any name-matching process exists at a different path, the snapshot's `Detail` names the expected `ServerRoot` and the actual process(es)/path(s) found, instead of the generic message. If nothing matches at all — genuinely not running — the message is unchanged.
- **Desktop** (`MainWindowViewModel.ApplyStatus`): fixing the backend alone wouldn't have been visible anywhere. `DashboardSessionText` and `DashboardHealthDetail` — the SERVER and OVERALL HEALTH cards' subtitle text on the Dashboard, the exact two fields the original bug report screenshot showed as unhelpfully generic ("No active PalServer session" / "Stopped intentionally or awaiting start.") — both previously **discarded `status.Detail` entirely** whenever the server wasn't Ready, always showing their own hardcoded string. Both now fall back to `status.Detail` (the now-improved backend message) instead of the generic literal, only using the hardcoded string as a last-resort fallback if `Detail` is somehow null.

## Explicit non-goals

- No new `ServerLifecyclePhase` enum value — the fix stays within the existing `Stopped` phase, just with a materially better `Detail` string. Adding a new phase value risked breaking other exhaustive-looking consumers of that enum for a benefit (a distinct phase) the original request didn't actually ask for; the ask was specifically about *why* it says Stopped, which `Detail` already solves.
- No change to `LifecycleStatusText` (the separate "LIFECYCLE" banner on the Dashboard) — that field is driven by explicit lifecycle *operations* (Start/Stop/Restart/connect), not routine background polling, and touching its semantics was out of scope for this fix.
