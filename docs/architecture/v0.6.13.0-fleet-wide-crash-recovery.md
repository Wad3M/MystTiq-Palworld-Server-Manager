# v0.6.13.0 — Fleet-Wide Crash Recovery

## Goal

Close the first of the v0.6.12.0 gap audit's real architectural findings: `HeadlessSupervisor` (crash-detect-and-auto-restart) only ever supervised the `default` profile, and only inside the installed OS service (`service-run`). Research this pass found the gap was bigger than that label suggested — `api-run`, the mode Desktop's own sidecar actually uses, had **zero** crash recovery for any profile, including default. Continues the same `v0.6.x.0` versioning convention.

## What shipped

### 1. api-run fleet-wide crash recovery

`HeadlessSupervisor.RunAsync` (used by `service-run`) previously combined two things: an "ensure started on launch" preamble (right for unattended-boot semantics) and a crash-detect/backoff/window polling loop. The loop was extracted unchanged into `RunCrashRecoveryLoopAsync` — `RunAsync` is now that preamble followed by a call to it, byte-identical behavior for every existing `service-run` caller.

New `HeadlessFleetCrashRecoveryService` (per profile, `MystTiq.HeadlessHost`) wraps one `HeadlessSupervisor` per profile and exposes an async `StartAsync`/`StopAsync` lifecycle matching `HeadlessAutomationService`'s exactly. `ServerProfileHost` gained a `CrashRecovery` property; `LocalManagementApiHost.Create` constructs it per profile (reusing that profile's already-built `IServerLifecycleService` and `LaunchArguments`, plus one `HeadlessSupervisorOptions` shared fleet-wide, built from the existing `HeadlessLifecycleConfiguration` — no new per-profile config surface this pass); `StartAsync`/`StopAsync` start and stop it right alongside `Automation`, the exact integration point that service already proved out.

Because it reuses `HeadlessSupervisor`'s existing logic verbatim, every profile under `api-run` now gets the same safety guarantee `service-run` already had: a profile an admin or Idle Auto-Stop intentionally stopped (`!CrashDetected && Phase == Stopped`) is never auto-restarted — only a genuine crash/disappearance is.

### 2. Per-profile installed OS services

`WindowsServiceManager` and `LinuxSystemdServiceManager` were both single-instance by construction (`const` `ServiceName`/`UnitName`). Both are now profile-aware: the **default profile's name is byte-identical to every prior version** (`MystTiqPalworld` / `mysttiq-palworld.service`) — critical so an upgrade never orphans an already-installed service — and a non-default profile gets a suffixed name (`MystTiqPalworld-{id}` / `mysttiq-palworld-{id}.service`). A true systemd `@`-template unit was considered and rejected: it needs a materially different install mechanism with its own escaping rules and has no clean Windows analog, while the suffixed-name approach is functionally equivalent and keeps both platforms' mental model identical.

New `--server-id <id>` CLI option resolves which profile `service-install`/`service-uninstall`/`service-status`/`service-run` and the direct single-server verbs (`status`/`start`/`stop`/`restart`) operate against — resolved once, in the single place every one of those commands already derived its profile from (`Program.cs`'s `defaultServerProfile` resolution), so it threads through automatically rather than needing per-command changes. Omitting it keeps the exact pre-v0.6.13.0 behavior. This closes the separately-disclosed "`--server-id` selection for direct verbs" gap as a direct side effect. Each installed per-profile service points at the same shared `mysttiq.json` (the fleet config already holds every profile) plus its own `--server-id`, not a separate config file.

Desktop GUI stays out of scope, matching the existing precedent: `service-install`/`service-uninstall`/`service-status` have been CLI-only since v0.6.3.0, even for the single-profile case.

## Explicit non-goals

- Per-profile recovery-policy overrides (poll interval/backoff/max-attempts/window) — one fleet-level setting shared by every profile's recovery loop this pass.
- A true systemd `@`-template unit.
- Desktop GUI for service install/uninstall/status.
- Cross-profile automation rules — a separate, already-disclosed gap.

## Verification

**Live, end-to-end, against two genuinely running PalServer instances** on an isolated, full-fidelity copy of the real production install (never the production directory or process): used Clone World to create a second profile, started both real PalServer processes via their per-profile lifecycle routes (confirmed distinct UDP ports, 8211/8311), then:
- Force-killed the non-default profile's process tree directly (both the `PalServer-Win64-Shipping-Cmd.exe` wrapper and its `PalServer.exe` child — killing only the child was not sufficient to register as "not running," since MystTiq's own process tracking considers the wrapper alone sufficient evidence a profile is up, a real behavior worth knowing for future crash simulations). Confirmed the new crash-recovery loop detected the loss and restarted it with a fresh PID within the configured `ServicePollSeconds`/`RecoveryBackoffSeconds` window (~15s), transitioning through `ready:false` → `ready:true` exactly as a real restart would.
- Confirmed the untouched sibling (default) profile's original PIDs were completely unaffected throughout.
- Explicitly stopped the non-default profile via its real Stop route, then polled repeatedly across multiple recovery-loop cycles and confirmed it was never auto-restarted — the "intentional stop" safety guard holds under `api-run` exactly as it always has under `service-run`.

**Static verification for per-profile OS services**: a throwaway harness instantiating `WindowsServiceManager` with both a default and non-default `ServerProfileId` confirmed the default profile's `ServiceName`/`DisplayName` are exactly `MystTiqPalworld` / `MystTiq Palworld Server Manager` (unchanged) and a non-default profile gets a distinct suffixed name. A live elevated install was not performed — this session has no Administrator elevation (confirmed via `whoami /groups`), the same carried-forward verification gap disclosed in every checkpoint since v0.6.3.0.

`dotnet build` (Release) across all three projects, and `scripts/Test-v0.6.13.0-Logic.ps1 -RunBuild` (16 static contract checks, the frozen v0.6.12.0 regression gate, and all 29 real v0.5.1.5 runtime-smoke checks) all pass.

## Notes for v0.6.14.0 (queued next)

A direct user report during this session: the Console page doesn't seem to load anything around a server start/stop transition. A bounded investigation (not a fix — that's v0.6.14.0's scope) found the write side is not simply missing: `WindowsServerLifecycleService.StartConsoleCapture` writes a session-start banner and redirects PalServer's real stdout/stderr into `MystTiq-PalServer-Console.log`, and a generic `AppendLifecycleConsoleLine` helper exists for MystTiq's own start/stop narrative lines. The separate `HeadlessConsoleLogWriter` class, however, is only ever called from MOD/UE4SS pre-start diagnostics — never from the plain Start/Stop lifecycle path. The likely culprits worth checking first: a `LogsRoot` path mismatch between what gets written and what the Desktop's log-tail read actually polls, or the Console page not being triggered to refresh right around the start/stop transition rather than waiting for the next passive poll tick.
