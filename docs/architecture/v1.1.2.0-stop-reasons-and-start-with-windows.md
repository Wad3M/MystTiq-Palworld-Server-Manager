# v1.1.2.0 — Stop reasons and start with Windows (internal)

Roadmap F-19 and F-20 (D-14, 2026-10-19).

## F-19: why a server stopped

The owner's server stopped cleanly on 2026-10-14, 10-16 and 10-19 with nothing saying why. A clean stop was recorded
as `Stopped` with `StopRequested`, but not who asked.

- `ServerStopReason` (Core) holds the reason in an `AsyncLocal<string?>`. A caller wraps its stop in
  `using var _ = ServerStopReason.Begin("...")`; nothing between the caller and the lifecycle passes it on. Reasons are
  one line of at most 200 characters (an API caller can send one). Without a reason the stop says
  "No reason was recorded for this stop", so an older reason is never shown for a newer stop.
- Both lifecycles read `ServerStopReason.Describe()` at the start of `StopAsync` and save it with every state the stop
  writes (already stopped, Stopping, Stopped). `PersistedServerLifecycleState.StopReason` is an optional last
  parameter, so older state files still read. `RestartAsync` sets "Restart" when its caller gave no reason.
- `GetStatusAsync`'s stopped result calls `WithLastStop(persisted)`: a stop the owner asked for adds `LastStopReason`
  and `LastStopAt`; a crash, or a running server, has none.
- Callers: the API routes take `?reason=` and add the principal ("<reason> (by <name>)"); automation names its rule;
  Discord names the user; MOD Safe Start, the character move, the CLI, the frozen-server restart and the service's
  shutdown each say what they are. `PolicyApplyingLifecycle.StopRecorded` writes "Server stopped: <reason>" to each
  server's activity log.
- The desktop sends its reasons (`MainWindowViewModel.StopReasons`, English: they are stored and read by others), and
  `LastStopLine` puts "Last stop: <reason> · <time>" (`dashboard.lastStop`) in the Overall Health card's detail, with
  the full text as its tooltip.

## F-20: start with Windows

- `StartWithSystem` (Desktop) writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\MystTiq` =
  `"<exe>" --tray` on Windows, or `$XDG_CONFIG_HOME/autostart/mysttiq.desktop` on Linux. The entry itself is the setting
  (nothing machine-wide, no administrator rights). An entry for a different copy is noticed and shown in Settings.
- `--tray`: `App` leaves `desktop.MainWindow` unset, so the window is not shown; start-up runs as usual
  (`InitializeLocalDashboardAsync` starts the helper). The tray's Show opens the window.
- Resume: a server that was running when the computer went down has `Running` persisted and no process, which reads as
  a crash; the helper's crash recovery starts it. One stopped on purpose is `Stopped` + `StopRequested` and is left alone.
- `MainWindow_Closing` lets `WindowCloseReason.OSShutdown` through (hiding to the tray held up Windows) after
  `SaveWorldsForSystemShutdown` asks each running server to save, waiting at most 4 seconds in all.

## Patch: ssh -n

The v1.1.1.3 gate waited eight hours on an `ssh` whose remote command had finished: the Windows ssh client waited on its
own input. Every non-interactive `ssh` call in the scripts passes `-n`; calls that pipe input in on purpose
(`... | ssh ... 'bash -s'`) and the interactive key set-up are left as they are.
