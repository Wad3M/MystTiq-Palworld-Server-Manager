# v0.6.11.0 — Stale-Instance Fix, UI Polish & WAN Reachability Diagnostics

## Goal

Three things accumulated in the working tree after v0.6.10.0 shipped, none of them released yet: a real bootstrap bug the user hit and reported directly from a screenshot, four small UI requests made in the same stretch, and a follow-on request for network/firewall tooling. Bundled into one release rather than three back-to-back release passes for changes made minutes apart. Continues the same `v0.6.x.0` grouped-milestone versioning convention as every prior milestone.

## What shipped

### Stale-instance bootstrap fix

The user reported, from a live run: the Palworld server console window appeared (not hidden), the Console page showed stale/old log entries with no new startup information, and status stayed "Stopped / Not ready" despite the server visibly running. Root cause: `LocalManagementBootstrapper`'s "reuse an already-running local instance" check (`EnsureAvailableAsync`) probed `/healthz` and treated any backend as compatible whenever `component == "mysttiq-headless"` and a coarse `apiVersion` integer (historically always `1`) matched — it never compared the actual semantic version string. A leftover v0.5.5.0 `mysttiq-server.exe` from an earlier, unrelated session was still listening on the default port (8213), pointed at the real production server root, and the freshly-launched v0.6.10.0 Desktop app silently attached to it instead of starting its own backend. Every symptom the user saw follows directly from that: the visible PalServer window belonged to the old process's own launch, the Console page was tailing the old process's log, and the new Desktop's own lifecycle/status views never matched what was actually running.

Fixed with a new `VersionMatches(string? probedVersion)` check, comparing the probed version against `Assembly.GetExecutingAssembly().GetName().Version?.ToString(4)`, lenient (returns true) when the probed version is missing (pre-version-reporting builds). Both existing reuse-check branches in `EnsureAvailableAsync` now additionally require a version match. On a mismatch, the bootstrapper does **not** kill the stale process — it falls through to the existing "port occupied → find a free loopback port → launch a fresh sidecar there" code path, and threads `StaleInstanceDetected`/`StaleInstanceEndpoint`/`StaleInstanceVersion` through the result so `MainWindowViewModel` can surface a clear message even on the success path: *"Started a fresh MystTiq {version} backend on {endpoint} because a different version ({staleVersion}) is already running at {staleEndpoint}. That older instance was left running -- close it manually if you don't need it."*

### WAN / External Reachability diagnostics

The user asked for "network checks, for firewall, local firewall, maybe a loopback that can test the external port." Investigation found local Windows Firewall inspection and repair for the game port **already existed and was already wired into the Desktop GUI** — `NetworkDiagnosticsService.RunAsync` (Windows Firewall check, via `WindowsNetworkDiagnosticsPlatformService.GetInboundFirewallRulesAsync`) and the "Add / Repair Firewall Rule" button on the Diagnostics Center page, both shipped in earlier v0.6.x work. Nothing to build there. The genuine gap, confirmed by grepping the whole repository, was external/WAN reachability: nothing anywhere tested whether the internet, or even the router, could actually reach the configured game port.

A true automated "is this UDP port reachable from the internet" test isn't honestly buildable without third-party server infrastructure this project doesn't own — proving unsolicited-inbound UDP reachability needs a cooperating external listener to bounce a packet back, unlike a TCP connect-back checker. Scoped instead to what's genuinely automatable, plus an honest manual hand-off for the rest:

- New `WanReachabilityService` (`MystTiq.Core.Services`, platform-independent — pure .NET networking, no OS-specific behavior, unlike the Windows/Linux-split `NetworkDiagnosticsService`):
  - **Public IP detection**: HTTPS GET to `api.ipify.org` (single well-known, no-auth, purpose-built endpoint — same trust tier as the existing `steamcdn-a.akamaihd.net` SteamCMD download dependency), short timeout, never a hard failure (renders `Skipped` on failure).
  - **Router UPnP port-mapping detection**: hand-rolled UPnP IGD client (no new NuGet dependency, matching this codebase's consistent pattern of hand-rolling OS/network integration) — SSDP M-SEARCH multicast discovery of the `InternetGatewayDevice`, fetch its device-description XML, locate the `WANIPConnection`/`WANPPPConnection` `controlURL`, then `GetSpecificPortMappingEntry` (read) and `AddPortMapping` (repair) SOAP calls for the configured game UDP port. A SOAP fault (router reachable, no such mapping — the expected outcome for an unmapped port) is distinguished from a genuine network-level failure (router unreachable) at the transport layer, not by exception-type sniffing.
  - `RepairUpnpMappingAsync` mirrors the existing `RepairInboundFirewallRuleAsync` detect/repair pair exactly, including the single-click "Add / Repair" UX convention (no extra confirmation dialog).
- New routes: `GET /diagnostics/network/wan`, `POST /diagnostics/network/wan/upnp/repair` (`RequireRole(Operator)` — mutates router state).
- New "WAN / External Reachability" card on the Diagnostics Center page, directly after the existing Network Diagnostics card: Public IP : Port, Router UPnP Mapping state, Router description, the check list, and a manual hand-off pair — "Copy IP:Port" (clipboard) and "Open Port Checker" (launches the browser to a well-known external checker homepage, no query-string prefill dependency on an undocumented third-party contract).

## Explicit non-goals

- True automated internet-side UDP reachability confirmation — no infrastructure owned to do this honestly; ships as the manual hand-off described above.
- TCP-based reachability for RCON/REST API ports — scoped to the game UDP port only, matching the existing Firewall check's own scope.
- IPv6 / Port Control Protocol as a UPnP alternative — UPnP IGDv1/v2 only.
- Walking a double-NAT chain (e.g. ISP modem then a separate router) — `RouterUnreachable`/`Unsupported` states surface honestly but don't attempt multi-hop discovery.

## Verification

- **Stale-instance fix**: mechanically confirmed against the user's actual real leftover process, not a synthetic stand-in. A read-only `GET /healthz` against the still-running stale process (PID 32300, `C:\GameServers\_Backups\MystTiqPalworldServer\v0.5.5.0\...\mysttiq-server.exe`, listening on port 8213) returned `"version":"0.5.5.0"`; traced by hand against the shipped `VersionMatches` comparison and the post-bump `Directory.Build.props` value (`0.6.11.0`), confirming the fix's precondition is genuinely exercised by this exact real instance and correctly evaluates to a mismatch. Full interactive GUI confirmation (clicking Start, watching the detail banner render) was not performed this session — no capability exists here to drive the native Avalonia window directly (a limitation disclosed consistently throughout this session); the user can confirm visually by rebuilding and relaunching, since the real stale process is still present on their machine.
- **WAN reachability — live, real, end-to-end**: a throwaway console harness referencing the built `MystTiq.Core` project called the exact shipped `WanReachabilityService.RunAsync` directly (read-only; no mutation, no server process required). Against this machine's real internet connection and real router: detected a real public IPv4; SSDP discovery found a real UPnP IGD ("Arcadyan OpenWrt Device"); `GetSpecificPortMappingEntry` correctly reported no existing mapping for the configured test port. `RepairUpnpMappingAsync` (the mutating action — adds a real port-forward on the user's actual router) was deliberately not exercised during this verification pass, consistent with never taking a shared-infrastructure-mutating action without the user's own explicit, in-app click.
- `dotnet build` (Release) across `MystTiq.Core`, `MystTiq.HeadlessHost`, `MystTiq.Desktop` — 0 warnings, 0 errors, post version bump.
