# v0.7.6.0 — Fix: Multi-Tab Stale Data (Wrong-Tab Actions)

## Background

Prompted by a broad request: review the codebase for logic/syntax bugs, research competing Palworld server-management tools for features worth adopting, and sequence findings into versions from v0.7.6.0 onward. Two independent research passes ran in parallel:

1. A competitive feature survey (PalSupervisor, na-ji/palworld-admin, PalAdmin, AMP/Pterodactyl) cross-checked against the actual codebase rather than taken at face value — several claimed gaps turned out to already be built (scheduled restarts with warnings, raw RCON console, RBAC, outbound Discord alerts), while several others were confirmed genuinely absent, including two the codebase's own comments already name as deferred roadmap items (whitelist, teleport).
2. Two parallel bug-scan agents — one over `MystTiq.Core`/`MystTiq.HeadlessHost`, one over `MystTiq.Desktop` — hunting for real logic bugs (null refs, race conditions, binding mismatches, copy-paste errors), not style nits.

This release fixes the single most severe finding from the Desktop-side scan. The remaining findings are sequenced into v0.7.7.0 (server-side locking races) and v0.7.8.0–v0.7.10.0 (verified competitive feature gaps) — see `README.md`'s roadmap table.

## The bug

`MainWindowViewModel`'s multi-tab architecture (v0.6.19.0) correctly scopes connection metadata (`SelectedProfile`, `BearerToken`, `ConnectionState`, `IsBusy`, etc.) per `TabSession` via `SetActiveTabField`/`RaiseActiveTabPropertiesChanged`. It does **not** scope the actual polled data — `OnlinePlayers`, `LogLines`, `ServerState`, dashboard/metrics fields — which remain plain app-level fields written only by `ApplyStatus`/`ApplyPlayers`/`ApplyLogs`/etc., called from whichever tab's own `DispatcherTimer` last ticked while it was the active tab.

Switching `ActiveTab` (bound directly to the tab bar's `ListBox.SelectedItem`) only replayed connection-metadata notifications; it never triggered a data refresh. The newly active tab kept displaying the previous tab's `OnlinePlayers`/logs/dashboard state until its own 5-second timer tick happened to fire. Within that window, `SelectedOnlinePlayer` was still the previous tab's selected player object, and `KickSelectedPlayerCommand`/`BanSelectedPlayerCommand` build their request from `BuildProfileFromEditor(SelectedProfile?.Id)` (the *new*, now-current tab's connection) combined with `SelectedOnlinePlayer.PlayerId` (the *old* tab's data) — a real risk for exactly the fleet-management use case this app's tab feature exists for.

A second, related gap: even outside the tab-switch window, a full refresh in flight for a tab the user has since navigated away from (e.g. a slow request from a background tab, or an in-flight `RefreshAsync`/`RefreshStatusPollingAsync` call from the tab that was active when it started) had no mechanism to detect that its target tab was no longer active before applying its result — a late-arriving response could silently stomp the now-active tab's freshly-displayed data.

## Fix

- **`ActiveTab`'s setter** (`MainWindowViewModel.cs`) now clears `SelectedOnlinePlayer`/`SelectedBackup`/`SelectedMod`/`SelectedExplorerPal`/`SelectedExplorerBase` immediately on every tab switch — before any new data has arrived, so no destructive action can be fired against a target left over from the previous tab — and fires an immediate `RefreshActiveTabDataAsync()` call (extracted from the timer tick's existing active-tab branch, now shared by both) instead of waiting up to 5 seconds for the next tick.
- **`RefreshAsync`/`RefreshStatusPollingAsync`** each now capture `var requestTab = ActiveTab;` before making their request and check `ReferenceEquals(requestTab, ActiveTab)` after it returns, before calling any `Apply*` method or updating `StatusBarText`/`ConnectionState`. A response for a tab that is no longer active is discarded rather than applied.
- **Wizard step per-tab**: `NewServerWizardStep` was a single `MainWindowViewModel` field; moved to `TabSession.WizardStep` and `NewServerWizardStep` now delegates through `SetActiveTabField`, matching every other per-tab property. Two tabs simultaneously mid-setup (or one abandoned mid-wizard) no longer corrupt each other's step.
- **Profile edit propagation**: `SaveProfile()` now updates `Profile`/`ProfileName`/`ServerUrl`/`CertificateSha256` on every *other* open tab already pointed at the same profile Id (deliberately leaving that tab's live `BearerToken`/`ConnectionState` untouched, rather than force-disconnecting a working background connection just because its profile was edited elsewhere).
- **Delete-in-use guard**: `DeleteSelectedProfile()` now checks whether another open tab is actively using the profile before deleting it, mirroring the existing duplicate-tab-open guard in `ConnectExistingProfileTab` rather than only checking at the point a new tab opens.
- **Minor**: `CloseTab` now sets `tab.Timer = null` after stopping it, not just `Stop()`.

## Explicit non-goals

- **Full per-tab data model migration**: the root architectural gap — `OnlinePlayers`/`LogLines`/`ServerState`/dashboard/metrics fields are not themselves `TabSession`-scoped — is not fixed here. Doing so properly means moving a large number of fields and every `Apply*` method into per-tab storage, which is a much larger, higher-risk change than a single release should safely absorb untested. This release closes the actual danger (a destructive action firing against a stale target) via the selection-clearing + stale-response-discard + immediate-refresh combination above, which together tightly close the exploit window without that larger rewrite. The underlying "data isn't tab-scoped yet" limitation remains and should inform any future work that adds more per-tab display state.
- `RefreshTabLightweightAsync`'s generic "Connection failed" message for background-tab auth/version errors (Low-confidence/severity finding) — not addressed this release.
- The two server-side locking-race findings (network-diagnostics restart bypassing the coordinator; backup restore never registering with it) — sequenced to v0.7.7.0, since they're `MystTiq.Core`/`MystTiq.HeadlessHost` changes and this release was scoped to Desktop-only.

## Verification

`dotnet build` (Release) — 0 warnings/0 errors. No server-side code touched, so the frozen v0.7.5.0 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged since v0.6.4.0**: no GUI click-through capability in this environment. The fix was traced by hand against the actual call graph (confirmed the new-tab-creation path never hits an unconstructed dependency during app startup, confirmed the stale-response guard's early return still runs the existing `finally { IsBusy = false; }`), but live multi-tab, multi-server click-through is the user's to confirm once run.
