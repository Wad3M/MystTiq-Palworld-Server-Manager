# v1.0.0.0 — The Stable Release (internal)

On 2026-09-30 the owner decided to publish v0.9.10.0's code as MystTiq 1.0, and to keep the open items and
verification notes in the internal docs rather than the public README, site and release notes.

## What changed for 1.0

- Version 1.0.0.0. No application code changed from v0.9.10.0.
- The release workflow makes a full release for v1 and later (`prerelease` only for a `v0.` tag). This matters to the
  app: from 1.0 on, `ReleaseChannel` counts only full releases, so a 1.0.x published as a prerelease would never be
  offered.
- Public docs present the release; the README's "Known limitations" and the site's "What still needs verification"
  section are gone, and the release notes have no limitations section.
- v1.0.0.0 is the accepted baseline (owner, 2026-09-30), replacing v0.8.25.0. This version's upgrade smokes still start
  from v0.8.25.0 (they cannot start from the release they test); from v1.0.1 on they also start from the v1.0.0.0
  checkpoint.

## Code signing

Requested on 2026-09-30. The release workflow signs through SignPath when the repository variable
`SIGNPATH_ORGANIZATION_ID` is set: it stages the Windows app (`Package-GitHubRelease.ps1 -StageOnly`), uploads it as a
GitHub artifact, submits it with the `windows-app` artifact configuration (`.signpath/artifact-configuration.xml`: the
seven MystTiq binaries, each required to carry the product name and the release version), waits up to 24 hours for the
approval, checks every MystTiq binary's Authenticode signature, and zips the signed folder (`-FromFolder`). Without the
variable nothing changes. For the metadata rule, `Directory.Build.props` sets one product name, company and copyright
and stops the SDK appending the commit to the product version; the native helper got a version resource.

v1.0.0.0 itself is published unsigned (the owner's decision, 2026-09-30); the first signed release is planned as v1.0.1.
Not done here, because it needs the owner's accounts: the SignPath Foundation application and the SignPath project
(`docs/release/CODE_SIGNING.md`). Third-party libraries that are not Authenticode-signed upstream (Avalonia, Discord.Net,
MicroCom.Runtime, Tmds.DBus.Protocol) are not signed; how the Foundation wants them handled is open.

## Open after 1.0 (kept here and in the roadmap)

The roadmap's v1.0 gate listed these; they were not met when 1.0 was published and stay open as post-1.0 work:

- **Translations:** the 11 non-English catalogs are drafts; no native-speaker review has been recorded. An outside
  review (2026-09-30) sampled them and applied label and wording fixes; it was not a native review.
- **Live integrations:** recorded in game on 2026-09-28: one Wood delivery through Give Item, and coordinates and a `tp`
  teleport matching MystTiq's conversion. Not yet recorded: a Pal delivery, a starter kit, refused gives, live player
  markers on the map, a chat-triggered teleport, real Discord and email delivery.
- **Accessibility:** accessible names and Tab reach are checked automatically; no pass with a real screen reader.
- **Linux:** the XFCE window, clipboard and tray checks passed (v0.9.8.0 gate); file pickers, scaling, other desktops and
  installed-service priority recovery are open. The Linux test VM did not answer during the v0.9.10.0 and v1.0.0.0
  gates, so those runs skipped the Linux checks. The Linux download is not published.
- **Firewall:** adding a rule live needs the owner's click; the Doctor's port-forwarding wording is untested on a real
  forwarded setup.
- **Known code limits:** a name in an unquoted message slot that does not follow a word such as "server" can still be
  translated if it equals a known status; a helper left by an older version is reported, not stopped; UE4SS builds older
  than the three newest releases read "check manually"; English keeps the system's number and date format.
