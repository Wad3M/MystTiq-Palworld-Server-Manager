# v0.6.3.0 — Windows Service Hardening, Character Migration & Setup/Update Cleanup

## Goal

Harden the Windows service/headless path, deliver character/account migration, and remove a real Setup/Update Center overlap bug.

## Windows service hardening

`WindowsServiceManager` (an `sc.exe` wrapper: `queryex`/`create`/`config`/`failure`/`delete`, plus recovery-policy args) has existed since v0.4.0.0 but was never called from anywhere — `Program.cs`'s `service-status`/`service-install`/`service-uninstall`/`service-run` commands were hard-gated to `OperatingSystem.IsLinux()` with no Windows branch. This milestone adds that branch, mirroring the Linux one exactly (`WindowsServiceManager` in place of `LinuxSystemdServiceManager`, `WindowsServerLifecycleService`/`WindowsServerSessionInspector` in place of the Linux equivalents).

`LinuxHeadlessSupervisor` (the auto-restart-on-crash loop) was found, on inspection, to contain zero Linux-specific code — it only ever used the shared `IServerLifecycleService` interface and platform-neutral models. Renamed to `HeadlessSupervisor` (`MystTiq.Core.Services`), with its options record renamed `LinuxServiceSupervisorOptions` → `HeadlessSupervisorOptions` (`MystTiq.Core.Models`), and reused unchanged by both platforms' `service-run` branches. This is what actually makes `RecoveryBackoffSeconds`/`MaximumRecoveryAttempts`/`RecoveryWindowSeconds` real on Windows for the first time — they were previously dead config with zero code path consulting them on that platform, the exact same "seam exists, nothing consults it" pattern `ServerProfileId` had before v0.6.2.0.

Registering `sc.exe create` against a plain console executable is not sufficient on its own: Windows SCM sends a `SERVICE_CONTROL_STOP` to a registered service control handler, which a bare console app never implements, so `sc.exe stop` would hang or force-kill rather than shut down gracefully. The Windows `service-run` branch adds the `Microsoft.Extensions.Hosting.WindowsServices` package and builds a minimal `IHost` via `Host.CreateApplicationBuilder().Services.AddWindowsService(...)`; its `IHostApplicationLifetime.ApplicationStopping` is registered to cancel the same `CancellationToken` the supervisor loop and API host already use, mirroring exactly what `PosixSignalRegistration`/SIGTERM already does for Linux `service-run`. `AddWindowsService()` degrades harmlessly to a no-op lifetime when the process isn't actually running under SCM (e.g. launched manually for testing) — verified live: running `service-run` in the foreground (not SCM-installed) against a scratch config correctly started the API host and supervisor, then shut down cleanly when the initial PalServer start failed, proving the host/supervisor/SCM-lifetime wiring is correct without requiring elevated `sc.exe install` to validate the core plumbing.

`WindowsSystemServiceStatusProvider` (new) queries `WindowsServiceManager.GetStatusAsync()` for real SCM-backed status on the `service-run` path, replacing `WindowsStandaloneManagementServiceStatusProvider`'s hardcoded-false stub there. The standalone stub itself is kept for `api-run --desktop-sidecar`, which genuinely isn't running as a service — that's a correct, honest answer, not a gap.

**Deferred**: a Desktop UI for install/uninstall/status (CLI-only this pass, matching the existing Linux systemd pattern, which is also CLI-only); fleet-aware crash-recovery supervision (the shared `HeadlessSupervisor` stays scoped to the `"default"` profile only, on both platforms, consistent with v0.6.2.0's own scoping of the Linux version); a full `sc.exe install`/`start`/`stop`/`uninstall` cycle against a real registered service, which needs Administrator elevation this session didn't have — the underlying host/supervisor/lifetime wiring was verified via foreground execution instead (see above).

## Character/account migration

Research confirmed the legacy WPF app's `PlayerRecoveryService`/`PlayerMappingEngine` (`src/PalworldManager/Services/`) never implemented a real migration mutation — it is scan/plan/backup/export scaffolding only, and its own `BuildPlan` method appends a hard warning every time: *"Player migration requires coordinated replacement of player, guild, ownership and Level.sav references. File renaming alone is intentionally blocked."* Full level/XP/inventory/equipped-item/Pal transplant (the original `PRODUCT_ROADMAP.md` v0.4.x wishlist's full scope) requires decoding an individual player `.sav` file's internal structure, which nothing in this codebase — legacy or new — has ever implemented; `HeadlessSaveCodecService`/`HeadlessGuildOwnershipService` only ever decode `Level.sav`.

This milestone ships a real, working slice instead: identity/guild-reference migration.

`MystTiq.Core.Migration.PlayerMappingEngine` ports the legacy engine's confidence-scoring ideas (exact GUID → platform ID → unique name → host-candidate fallback) as a single-pair `Assess(source, destination)` evaluator, adapted from the legacy `Suggest(imported, destination)` bulk-auto-matcher — that bulk API was built for a different scenario (matching many imported players against many existing ones, i.e. a "world import" feature) that doesn't fit this milestone's actual use case: an admin explicitly picks one source and one already-existing destination player within the same live world.

`HeadlessCharacterMigrationService` (new, `MystTiq.HeadlessHost`) follows `HeadlessGuildOwnershipService`'s exact shape: `PreviewAsync` re-explores current state via the existing `HeadlessPlayerGuildExplorerService`, runs the identity assessment (informational only — it does not gate `canApply`), checks for conflicts (destination already in a guild; source has no guild membership to migrate), hashes `Level.sav`, and issues a single-use preview token. `ApplyAsync` requires the server stopped, re-validates the token/hash, takes a fresh `HeadlessBackupService.CreateAsync(BackupClass.Safety, ...)`, decodes `Level.sav`, repoints the source player's `admin_player_uid`/`player_uid` guild references to the destination player, re-encodes to a staged file, independently re-decodes to verify the mutation landed, atomically replaces the live `Level.sav` (`File.Replace`), and rolls back from an original copy on any failure — reusing the exact `HeadlessWorldTransactionJournal`/`world-transactions/journals` store every other mutation service writes to, so migrations appear in Transaction Center with zero extra plumbing (`mode="character-migration"`).

`DisposeSourceCharacterAsync` is a post-commit-only step (only reachable after a successful, journaled migration): `Keep` no-ops, `Archive` moves the source `.sav`/`_dps.sav` into `ManagerRuntimeRoot/character-migration/archive/`, `Delete` removes them outright (safe — the pre-migration safety backup already exists). `Reset` (writing a fresh/blank player `.sav`) is not implemented — the route returns an explicit "not yet supported, needs a fresh-character encoder" error rather than silently no-op'ing or guessing; the Desktop UI still lets an operator select it, deliberately, so the server's real rejection message is what they see rather than a client-side substitution silently changing their choice.

**Two real bugs found via live verification against a real save** (a two-of-five-known-players guild, plus a synthetic guild-less destination created by copying an existing `.sav` under a new GUID — the migration only reads/writes guild references in `Level.sav`, never the destination's own save contents, so a copied file is a valid test destination): (1) `PreviewAsync`'s `canApply` computation initially counted the informational identity-match description as a blocking finding alongside real errors, making `canApply` permanently `false` even for a clean match — found because a real preview against real data returned `false` with only one, non-error finding present; fixed by separating `blockers` (gate `canApply`) from `findings` (full display list, blockers plus informational lines). (2) The new `CharacterDisposition` enum was initially missing `[JsonConverter(typeof(JsonStringEnumConverter))]` — the same bug class found in `ServerRuntimeKind` during v0.6.2.0 — causing request deserialization to fail; fixed the same way.

Live apply was verified end-to-end: safety backup created, `Level.sav` file hash changed (confirmed via diff against the safety backup's copy — proof the mutation was real, not a no-op), transaction journal appeared in `/api/v1/world/transactions` with `mode=character-migration`, and Archive/Reset disposition both behaved correctly (file moved to the archive directory; Reset correctly rejected with its explicit not-supported message). One caveat found and disclosed, not a regression: `/api/v1/world/players-guilds` reads a `Level.sav.json` sidecar that nothing in this codebase regenerates after any mutation (confirmed via code search — this is a pre-existing characteristic shared by `HeadlessGuildOwnershipService`/`HeadlessBaseOwnershipService` too, not introduced by this milestone), so the guild-explorer view can appear stale immediately after a successful migration until that sidecar is externally regenerated.

**Deferred**: full gameplay-state transplant (level/XP/inventory/equipped items/Pals/technology) — needs new individual-player-`.sav` decode/encode infrastructure. `Reset` source-character disposition — needs a fresh-character save encoder. Cross-server migration — this pass is single-server, matching every other `"world-mutation"`-scoped transaction service.

## Server Setup vs. Update Center cleanup

Confirmed real, functional duplication: `MainWindowViewModel.RunEnvironmentAction`'s handler for the "SteamCMD"/"Palworld Dedicated Server" checklist rows, and the page's own "↓ Install Missing" button, both called `InstallMissingEnvironmentAsync()` unconditionally — which directly invokes `UpdatePalworldServerAsync()` (`POST /api/v1/server/distribution/update`), the exact same mutating route Update Center's dedicated "Update Palworld Server" button calls. Because this fired even when clicked on an already-installed row reading **"Verify"**, it silently triggered a full SteamCMD update/reinstall on what looked like a read-only check — a real mislabeling bug, not just duplication.

Fixed Desktop-only (the underlying `/api/v1/server/distribution/update` route is correct and shared; the bug was only in which UI paths called it): `RunEnvironmentAction` now checks `item.IsMissing` before deciding what to do — genuinely missing (first-run) components still install directly, unchanged; already-installed components navigate to Update Center instead of mutating. `InstallMissingEnvironmentAsync` itself now checks whether anything is actually missing before calling `UpdatePalworldServerAsync`, so "Install Missing" can no longer silently re-trigger a full update when nothing is missing. "Update MystTiq" (self-update of the manager application) was confirmed to not exist as a feature anywhere in code — the roadmap's contrast against it was preventive framing, not a second flow needing disentangling.
