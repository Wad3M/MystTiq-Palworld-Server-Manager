# v0.7.85.0 — Import a World, Phase 2

## Context

The "Set Up New Server" wizard's Import a World path has been an honest interim placeholder since
v0.7.81.0: `HeadlessWorldTransactionService.ApplyCoreAsync` hard-requires an already-active world
(`explorer.Explore().Available == true`) because it's built as a safety-backed *replace* operation —
a real mismatch with a brand-new install, which has no world to replace. v0.7.81.0's own architecture
doc scoped this out explicitly as future work: "a genuinely new, simpler backend path."

## The real finding that made this safe to build

Before writing any code, this was tested empirically against a real, genuinely-fresh install on this
machine (a server that had never been started, SteamCMD-installed only): starting `PalServer.exe`
for the very first time generates a real world save folder,
`Pal/Saved/SaveGames/0/<32-hex-world-id>/Level.sav`, within a few minutes — confirmed by direct
filesystem inspection, not assumed. That means the *already-existing, already-proven*
`HeadlessWorldTransactionService` "world-import" flow (`AnalyzeArchiveAsync` → `ApplyAsync`, the same
safety-backed atomic swap with rollback used by the World Transactions page today) works completely
unmodified once a fresh install has been started once — no new backend method, no new route, no new
DTOs. This is why the originally-considered approach ("pre-seed a world folder before first launch")
was dropped: it would have relied on an unverified assumption about whether `PalServer.exe` honors a
pre-placed folder on a true first launch. Starting the server once and *replacing* what it generates
itself needs no such assumption.

## Changes

- **New: "Prepare for Import"** (Install step, Import path only) — starts the freshly-installed
  server once (reusing `StartServerAsync` unchanged), polls `GET /world/explorer` for
  `Available == true` (up to a 5-minute deadline, comfortably past the empirically-observed ~3
  minutes), then stops it (reusing `StopServerAsync` unchanged). Once ready, the wizard embeds the
  same Analyze/Apply controls the World Transactions page already uses
  (`WorldTransactionMode`/`WorldTransactionState`/`WorldTransactionPlanSteps`/
  `WorldTransactionConfirmed`/`ApplyWorldTransactionCommand`, plus the existing
  `AnalyzeWorldArchive_Click` file-picker handler) verbatim.
- **World Settings choice (step 4) is skipped for Import** — a preset/customize choice doesn't apply
  to a placeholder world that's about to be entirely replaced by the imported archive; Import now
  advances straight from Identity & Ports to Install Directory.
- **Fixed a real bug found while wiring this in**: `AnalyzeWorldArchiveAsync`/`ApplyWorldTransactionAsync`
  hard-required `SelectedProfile` directly and silently no-op'd otherwise — the same bug class as
  `RefreshEnvironmentAsync`'s v0.7.81.0 fix, since `SelectedProfile` is always null for the entire
  "Set Up New Server" wizard (`IsCreatingNewProfile` literally means that). Both now use
  `BuildProfileFromEditor(SelectedProfile?.Id)`, the same established pattern every other wizard-time
  method already uses (matching `RefreshWorldExplorerAsync`, which already had it right).
- **Fresh state on entry**: choosing the Import card resets `WorldTransactionMode` to `"world-import"`
  and clears any stale preview token/confirmation left over from an earlier World Transactions page
  visit in the same session (these are shared, not wizard-scoped, properties).

## Verification

`dotnet build` on `MystTiq.Desktop` and the full solution — clean, 0 warnings/errors. **Live
end-to-end verification against a real server** (not just contract checks): started the genuinely
fresh "MystTiqClaude" install (created during v0.7.83.0's own live verification) for the first time,
confirmed via `GET /world/explorer` that a real world (`Level.sav`, `Available: true`) had been
generated, stopped the server, built a real test archive from that same world's own save data,
`POST`ed it to `/world/import/analyze` (accepted, real preview token returned), then `POST`ed
`/world/import/apply` with that token — result: `"success": true, "state": "Completed"`, a real
safety backup was created (`Palworld_2026-09-17_13-45-15-743.zip`), and the world folder was left in
a clean, valid state. This proves the entire Phase 2 mechanism end-to-end using zero new,
previously-unexercised backend code.
