# v0.8.15.0 — A Real Remote Sign-In

This is the sixth item of the automated run. v0.8.14.0 made the Desktop's cards follow the signed-in role, but that
was checked offline only, with the principal set directly. This version signs in for real: the Desktop's own code,
over the network, to a remote MystTiq with remote access switched on the documented way.

## The test

`scripts/Test-v0.8.15.0-RemoteSignIn.ps1` (Windows) drives it; the Linux test VM is the remote machine.

1. **Publish** MystTiq for linux-x64 and copy it to `/tmp/mysttiq-v0815-remote` on the VM. The VM's installed
   `mysttiq-palworld` service and `/etc/mysttiq` are never touched.
2. **Switch remote access on** (`Test-v0.8.15.0-RemoteSignIn.setup.sh`), exactly as the documentation says:
   - `api-token-create`, `api-tls-create` (a self-signed certificate), `api-remote-enable`, then `api-run`;
   - three accounts, **Viewer**, **Operator** and **Admin**, created through `/api/v1/security/users` with the Owner
     token. Their passwords are generated for this run and never printed or stored.
   - The setup prints the certificate's SHA-256 pin, which the Desktop pins.
3. **Sign in** with `scripts/Testing/MystTiq.RemoteSignInHarness`: the Desktop's real `MainWindowViewModel`,
   `MainWindow` and `MystTiqApiClient`, headless. Every local store is isolated in a temp folder or in memory; no
   local sidecar is started and nothing in this PC's real Desktop setup is read or written.
4. **Tear down** (`teardown.sh`, always, in `finally`): the instance is stopped and its folder, token, certificate
   and accounts deleted.

## What is checked (19 checks)

- A **wrong certificate pin** is refused before any sign-in is attempted.
- For each role:
  - a **wrong password** is refused by the server itself, and nobody is signed in;
  - the **Sign In** command signs in over TLS, and the server reports the role;
  - the Desktop **shows, disables and hides cards** as the v0.8.14.0 table says, and the role notice shows;
  - **the server agrees**: reading kits and the whitelist gives 200 for Operator and up and 403 for Viewer; saving
    the whitelist gives 200 for Admin and 403 below;
  - **Sign Out** forgets the role and ends the session on the server: the old token gets 401 afterwards.
- The Security and Players pages are rendered for each role (`artifacts/remote-signin/remote-<role>-*.png`).

## What it found

- **A refused save looked saved.** The server refuses a route above the role with
  `403 {"error":"insufficient-role"}`, and a missing or expired sign-in with `401 {"error":"..."}`. The Desktop's
  `ReadOperationAsync`, used by about 90 client calls, parsed that body as the route's own result type. A refusal
  therefore came back as an empty "result": for the whitelist, an empty whitelist, reported as saved.
  - The server was right all along; the Desktop hid the refusal.
  - **Fixed:** `AccessRefusal.Describe` recognises a 401 or 403 carrying `error` (or an empty or non-JSON body), and
    the client throws it with the status code and a plain message, for example "MystTiq refused this: it needs the
    Admin role or higher."
  - The sign-in route's own 401 is a result with a message and no `error`. It still comes back as a result, so a
    wrong password still says "The username or password is not right".
  - The cards v0.8.14.0 hides already keep a role away from most of these, but a scoped account (one limited to
    another server) or an expired token could still reach them.
- The harness itself first deadlocked: awaiting on the main thread while the Avalonia dispatcher was not running. It
  now runs inside the dispatcher loop, as the real app does, with a 10-minute watchdog.

## Gate

- The contracts check the setup (documented switch-on, `/tmp` only, teardown always), the harness checks, and the
  refusal handling.
- `-RunBuild` runs the live test when the VM answers on SSH (`MYSTTIQ_LINUX_HOST` overrides the address). Otherwise
  it is reported as **SKIP**, because the VM is a separate machine on DHCP.
- The ArtworkHarness checks `AccessRefusal` offline (442 checks).

## Not done

- The Owner role was not signed in as a user account. The test uses the Owner token only to create the accounts, and
  the Owner-only cards were covered offline in v0.8.14.0.
- Ribbon buttons are still not role-gated (the server refuses them).
- Signing in from the Linux Desktop itself (the Avalonia app running on Linux) was not tested; this test signs in
  from Windows to a Linux server.
