# v0.7.41.0 — MOD Update Detection

## Goal

Seventeenth version in the GUI/workflow/UX overhaul roadmap. Roadmap item 52 — per-MOD "check for a newer version"/"update" actions in MOD Library, with MODs deliberately kept out of the Update Center per that finding's own instruction: "MODs should NOT be listed in the Update Center — MOD update-detection belongs on the MOD Library page instead."

## Investigation before building

Before writing any code, checked whether real update-detection infrastructure already existed anywhere in the codebase. It doesn't: `HeadlessModManagementService.ScanWorkshopAsync` (the existing Steam Workshop scanner) only discovers Workshop content already downloaded to the local Steam client's cache — it has never queried Steam's servers for whether a newer version exists. There is no version-comparison, no timestamp-tracking, no Steam Web API integration anywhere in `MystTiq.HeadlessHost`.

Building genuine "is there a newer version on Steam's servers" detection would require a live Steam Web API integration (an API key, outbound network calls, response parsing, and the same kind of scope/rate-limiting/ToS considerations already disclosed for item 40's deferred website-description work) — substantial new infrastructure on the same scale as item 45's UE4SS Release Catalog Backend, which the roadmap explicitly deferred as its own multi-version "+"-suffixed item rather than something to improvise inside a single UI-overhaul version. Faking that capability with a placeholder or a hardcoded "up to date" response would violate this session's established discipline (verify against primary sources, disclose real gaps rather than force a feature past what the evidence supports — the same standard applied to v0.7.30.0's item 48 correction).

## What's actually real and buildable

One genuine, fully local, network-free signal exists: whether **Steam's own local Workshop content cache** for a MOD's matching Workshop item is newer than what's **currently installed** in the server's mod folder. Steam periodically re-downloads subscribed Workshop items in the background regardless of whether MystTiq has re-imported them — if the cached copy's files are newer than the installed copy's files, that's real, on-disk evidence an update is sitting there unapplied, discoverable with zero network calls.

## What shipped

### Server: `HeadlessModManagementService.CheckModUpdateAsync(type, package, cancellationToken)`

1. `FindMatchingWorkshopItem(package)` — reuses the existing `DiscoverWorkshopContentRoots()`/`DescribeWorkshopItem()` machinery already built for `ScanWorkshopAsync`, scanning for a local Workshop item whose `SuggestedPackage` or `WorkshopId` matches the installed MOD's package name.
2. If no match: returns `HasKnownSource: false` with an honest "no known update source for this MOD" message — the same disclosed-gap pattern as the pre-existing "Legacy Migration — BACKEND REQUIRED"/"Workshop Information — BACKEND REQUIRED" buttons already sitting on this exact page.
3. If matched: `GetInstalledModLastWriteUtc(type, package)` (reusing the same PAK-flat/PAK-nested/UE4SS-folder location logic already established in `DeleteAsync`/`CaptureSnapshot`) computes the newest `LastWriteTimeUtc` among the installed MOD's own files; compared against the newest `LastWriteTimeUtc` among the matched Workshop item's local content folder files (a 2-second tolerance absorbs filesystem/copy timing jitter).
4. Returns `HeadlessModUpdateCheckResult(HasKnownSource, UpdateAvailable, WorkshopId, Detail)` — `WorkshopId` is populated only when `UpdateAvailable` is true, so the client's Update action always has exactly what it needs to call the existing import route.

New route: `GET /mods/{type}/{package}/check-update` (`LocalManagementApiHost.cs`), following the same pattern as every other MOD route.

### Client: wired into the v0.7.40.0 MOD DETAILS panel

New `ModUpdateCheckResultDto` (client-side mirror of the server record), `IMystTiqApiClient.CheckModUpdateAsync`/`MystTiqApiClient` implementation, and `MainWindowViewModel.CheckSelectedModUpdateCommand`/`UpdateSelectedModCommand`/`SelectedModUpdateText`. A new "UPDATE" section in the MOD DETAILS panel (built in v0.7.40.0) holds both buttons and the result text, scoped to whichever MOD is currently selected — switching selection clears the stale result via `SelectedMod`'s setter, so a check result never appears to apply to the wrong MOD.

**Update** doesn't duplicate any install logic — it calls the same `ImportWorkshopItemAsync(workshopId)` route that already powers "Import Selected" on the Available Local Steam Workshop Mods list, reusing its existing, already-tested overwrite-safe copy logic unchanged.

## Explicit non-goals

- No live Steam Web API integration, no "latest published version" comparison against Steam's servers — deferred, same category of work as item 45.
- No update-detection path for non-Workshop-matched MODs (most UE4SS/Lua content from other sources) — no known source to check, honestly disclosed rather than guessed at.
- No change to `ImportWorkshopItemAsync`'s own import logic.
