# v0.7.67.0 — Tray Reminder Toast: Layout Timing Fix (completes v0.7.66.0)

## Goal

The user asked to "try it out on the real hardware" after v0.7.66.0 shipped its fix for the tray
toast positioning bug. That hardware — this machine — turned out to have exactly the multi-monitor
layout described in the original report (confirmed via `System.Windows.Forms.Screen.AllScreens`:
primary 2048×1152 at (0,0), secondary 1920×1080 at (383,-1080)), so this pass actually drove the real
`TrayReminderToast` class on real hardware instead of reasoning about it statically, and found a
second, independent bug the first pass missed.

## How this was tested

Built a small standalone Avalonia harness (`TrayToastVerify`, scratch project referencing
`MystTiq.Desktop.csproj` directly, not part of the shipped solution) that:
- Creates a stand-in "MainWindow" positioned well inside the real secondary monitor (this machine's
  actual negative-Y monitor), matching the real bug scenario.
- Constructs a `TrayReminderToast` the OLD way (no owner — the exact pre-v0.7.66.0 code path, since
  the owner parameter defaults to `null`) and logs its final settled position.
- Constructs a second `TrayReminderToast` the NEW way (owner = the stand-in MainWindow) and logs
  every `PositionChanged` event with a timestamp and the `Bounds` at that moment.
- Compares the final position against the mathematically-expected bottom-right corner of the
  secondary monitor's `WorkingArea`.

This is a real, mechanical test of the actual shipped classes and the actual `Avalonia.Controls.
Screens` API against the actual OS window manager on the actual reported hardware — not a screenshot
eyeballed for "looks about right," but an exact pixel-coordinate comparison.

## What the first run (v0.7.66.0's fix, as shipped) found

```
OLD (no-owner) toast final position: 1023, 594        <- lands near center of the PRIMARY monitor
NEW (owner) toast final position:    766, -834         <- correct monitor, wrong corner
Expected bottom-right of SECONDARY:  1972, -127
MISMATCH -- investigate.
```

The owner fix correctly put the toast on the *secondary* monitor (`Y=-834` falls inside that
monitor's `[-1080, 0]` range) — but not at the bottom-right corner. Adding a `PositionChanged`
logger to the harness (not the shipped code) revealed why:

```
[event] PositionChanged -> 160, 160   (Bounds 1521.6x770.4)
[event] PositionChanged -> 160, 160   (Bounds 1521.6x770.4)
[event] PositionChanged -> 766, -834  (Bounds 1521.6x770.4)
```

`PositionBottomRight()`'s own fallback logic — `Bounds.Width > 0 ? Bounds.Width : 320` — assumes a
non-zero `Bounds` means "the real, final, content-measured size." At the moment `Opened` fires,
`Bounds` was already non-zero, but reporting **1521.6×770.4** — nowhere near the toast's real small
content size (its `<Border MaxWidth="320">` should settle around ~315×63). That's not a screen
problem; it's a `Window.SizeToContent="WidthAndHeight"` timing problem: content hasn't been
measured/arranged yet when `Opened` fires, and the placeholder size present at that instant is large
enough to slip straight past the `> 0` guard, corrupting the bottom-right math on both axes.

Doing the arithmetic confirms this exactly: `383 + 1920 - 1521.6 - 16 = 765.4 ≈ 766`,
`-1080 + 1032 - 770.4 - 16 = -834.4 ≈ -834` — both match the wrong observed position to the pixel.

## The fix

`TrayReminderToast`'s constructor now also subscribes to `LayoutUpdated` (in addition to the
existing `Opened` subscription), calling `PositionBottomRight()` again every time it fires.
`LayoutUpdated` fires after each real Avalonia layout pass, so once `SizeToContent` has actually
settled on the toast's true small content size, the next `LayoutUpdated` firing recomputes and
re-applies the correct position using the now-accurate `Bounds`. Re-running `PositionBottomRight()`
on every firing (rather than once) is deliberate: it's cheap and idempotent once the size stabilizes,
and recovers automatically from any further late layout pass (e.g., font metrics resolving) rather
than needing to guess how many passes are "enough."

## Verification (re-run with the fix in place)

```
OLD (no-owner) toast final position: 2291, 1301        <- still wrong (unowned path unchanged, as designed)
  [event] PositionChanged -> 766, -834    (Bounds 1521.6x770.4)
  [event] PositionChanged -> 766, -834    (Bounds 1521.6x770.4)
  [event] PositionChanged -> 751, -872    (Bounds 1536x808)
  [event] PositionChanged -> 1972, -834   (Bounds 315x770)
  [event] PositionChanged -> 1972, -127   (Bounds 315.2x63.2)
  [event] PositionChanged -> 1972, -127   (Bounds 315x63)
NEW (owner) toast final position: 1972, -127
Expected bottom-right of SECONDARY monitor: 1972, -127
MATCH: NEW toast lands exactly at secondary monitor's bottom-right.
```

An exact pixel match, converging through several `LayoutUpdated` corrections as `Bounds` settled
from the placeholder size down to the real content size. The OLD (no-owner) path was re-run in the
same harness invocation and landed at yet another different wrong position (`2291, 1301`, not the
`1023, 594` from the very first run) — confirming that path's screen resolution really is
non-deterministic run-to-run, exactly the "sometimes mid-screen, sometimes somewhere else" shape of
the original bug report, and that it's the owner-based fix (not this layout-timing fix alone) that
makes the screen choice deterministic. Both fixes are independently necessary and jointly
sufficient: v0.7.66.0 picks the *right monitor*; v0.7.67.0 makes the *position on that monitor*
converge to the intended corner instead of stopping at a stale, oversized `Bounds` reading.

- `dotnet build` on `MystTiq.Desktop.csproj` and the full solution: clean, 0 warnings/errors.
- The harness itself is scratch-only (not part of the shipped solution) — its role was to drive the
  real production code on real hardware, not to become permanent test infrastructure. The observed
  behavior (and the exact before/after logs above) is preserved here since this environment has no
  other way to re-run a live GUI check later.
- `scripts\Test-v0.7.67.0-Logic.ps1` — static contract-presence checks confirming the `LayoutUpdated`
  subscription exists alongside the `Opened` one.

## Known gaps (disclosed)

- The harness proved the fix using a stand-in window, not the full running Desktop application with
  a real hidden `MainWindow` and a real "server still running" trigger condition — reproducing that
  exact end-to-end user flow (which needs a tracked running server) was out of scope for this
  targeted check. The `TrayReminderToast`/`PositionBottomRight` code path exercised is identical
  either way; only the *trigger* (hiding a real main window with a server running vs. a stand-in
  window shown directly) differs.
- The no-owner fallback path (`Screens.ScreenFromWindow(this)`) remains unreliable, as documented in
  v0.7.66.0 — still not a live bug today since the one real call site always supplies an owner, but
  confirmed once again here to genuinely vary run-to-run if anything ever constructs this toast
  without one.
