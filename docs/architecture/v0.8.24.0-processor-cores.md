# v0.8.24.0 — Processor Cores, and the Policy Applied at Start

Two follow-ups from v0.8.17.0's HOST tab.

## Processor cores (affinity)

The priority card on the HOST tab has a **Processor cores** field: `0-3, 6`, or empty for every core. A server pinned
to some cores leaves the others to other servers and programs on the same machine.

- **The list** (`CoreSelection` in `ServerResourcePolicy.cs`):
  - cores are numbered from 0, as Task Manager and `/proc/cpuinfo` number them;
  - ranges and single cores can be mixed;
  - the list is checked against the machine: a core that does not exist, a backwards range, a word or an empty
    selection is refused with the reason (HTTP 400; the saved policy stays).
  - At most 64 cores: Windows sets affinity within one processor group of 64, and MystTiq does not spread a server
    over groups.
- **Applying it**, like priority and efficiency mode:
  - it is applied to every managed process on save and on every automation tick, and changed only where it differs;
  - each change is logged once;
  - **clearing the list gives every core back only where MystTiq had pinned the process**, so pinning done elsewhere
    is left alone;
  - eco mode does not change the cores;
  - the HOST tab lists each process's cores, and the machine's count in the hint.
- **Windows:** the process's affinity mask.
- **Linux:** `sched_setaffinity` on **every thread** (`/proc/<pid>/task`), because affinity, like niceness, is per
  thread and existing threads keep theirs. Unlike niceness, a process's owner may widen it again without any privilege.
- **Older policies:** a policy saved before this version has no cores and loads as every core. A saved list naming
  cores this machine does not have falls back to changing nothing.

## Applied at start, instead of `Nice=` in the systemd unit

v0.8.17.0 listed "a systemd unit's own `Nice=` is not set" as not done. **This version does not add it**:
- `Nice=` applies to the MystTiq service itself, so the management API and its sign-ins would run at the server's
  priority too;
- it would take effect only after `service-install` is run again;
- it would set one niceness for a whole fleet.

What it would have bought is the server starting at its priority, instead of waiting up to 15 seconds for the next tick.
That is what this version does, on both platforms. `PolicyApplyingLifecycle` wraps each server's lifecycle, so
**every start and restart through MystTiq applies the policy as soon as it succeeds**: the API, automation, the
Discord bot and mod safe start.
- A failed start applies nothing.
- A failing apply never turns a successful start into a failure.
- The service supervisor's crash recovery (`service-run`) uses its own lifecycle and is picked up by the tick, as
  before.

## Crash signatures: no new evidence

Checked read-only on this machine's servers: no Unreal crash report newer than 2026-09-16. The clone
("Palworld Server 2 (Clone)") has five reports:
- four are the TArray resize assert;
- one is an access violation reading an address.

Both kinds are already covered by the signatures added from real evidence in v0.8.9.0, so none was added.

## Verification

- **Logic harness:**
  - the list: parsing, the machine check, the 64-core limit, masks, descriptions;
  - the decision: chosen cores, every core again only where MystTiq pinned, otherwise left alone;
  - the service: pins only what differs, gives cores back, leaves outside pinning alone, logs, reports a refusal,
    keeps the policy, and loads a pre-v0.8.24.0 policy;
  - the start wrapper: a successful start or restart applies once, a failed start or a stop does not, and a failing
    apply keeps the start successful.
- **Windows smoke (6/6)**, on the real stand-in process in service mode:
  - every core by default;
  - pinned to 0-1 at once;
  - a missing core refused;
  - **a restart through MystTiq: the new process has the priority and cores as soon as the restart returns**;
  - every core given back;
  - the activity log.
- **Linux VM, isolated:** every thread of a 4-thread stand-in pinned to core 1 and given every core back without
  privilege; a missing core refused.
