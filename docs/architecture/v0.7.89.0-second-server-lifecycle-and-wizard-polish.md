# v0.7.89.0 — Second-Server Lifecycle Fixes and Wizard Polish

Direct live feedback, against a running v0.7.88.0 build, while the user drove a genuine second
local server ("Moonlit Sanctuary 2235" / fleet id `frostbound-pal-realm-1069`) all the way through
setup and Start. Surfaced a cluster of real bugs, all stemming from the same architectural blind
spot introduced across v0.7.82.0-v0.7.83.0: code that special-cased "the literal default profile" as
a proxy for "a local, desktop-owned server," which silently breaks now that genuine *second* local
servers exist. Plus four smaller, independently-reported UX/data bugs.

## 1. Server "did not start and i have no messages as to why"

**Root cause, confirmed live**: `EnsureManagementConnectionForLifecycleAsync` (gates Start/Stop/
Restart) only attempted local reconnection when `SelectedProfile.Id == ConnectionProfile.LocalDefault.Id`.
For any other profile -- including a genuine second local server -- it returned `false` immediately
with **no status text set at all**. Confirmed the backend itself works fine: calling
`POST /server/start` directly against the new profile's scoped route succeeded and produced a real
running `PalServer.exe`. The bug was entirely client-side: Start silently did nothing whenever this
tab's `ManagementApiConnected` was momentarily false (e.g., right after the wizard finishes, before
the first poll lands).

**Fix**: replaced the `Id == "default"` check with an actual loopback-address check on
`SelectedProfile.BaseAddress.Host` (`IPAddress.IsLoopback`) -- the real signal for "this is the
desktop's own owned sidecar, which `LocalManagementBootstrapper` can help reconnect." A genuinely
remote, non-loopback profile now gets an explicit status message instead of silent failure.

## 2. Tab labeled "Remote" for a genuinely local second server

Same root cause as #1: `TabSession.ConnectionKindText` used the identical `Id == "default"` proxy.
Fixed with the same loopback-address check.

## 3. Dashboard showed a different server's world data

**Report**: "why is the active world the same without a clone?" -- the brand-new server's Dashboard
showed the exact same Active World ID, player-save count, and size as the Default Server.

**Root cause, confirmed live** (compared `GET /world/explorer` across profiles directly): the new
server's own world genuinely wasn't ready yet (`available: false` -- expected, it had just started).
`ApplyDashboardSupport`'s `else` branch (the "world not available" case) only ever reset the
clock/save-age text; `ActiveWorldIdText`/`DashboardWorldNicknameText`/`DashboardWorldText`/
`WorldPlayerSaveCountText`/`WorldSizeText`/`DashboardWorldPulseText` are plain top-level ViewModel
properties (not per-tab), so they kept whatever the *previously active tab's* last successful poll
had set -- in this case, the Default Server's own real data.

**Fix**: the `else` branch now resets all six fields to explicit "not available" placeholders.

## 4. "how is this overall progress at 100% when there are missing items?"

Server Setup's "OVERALL PROGRESS" bar was never actually tied to environment readiness -- it only
ever tracked the most recently run *operation's* own completion (e.g., Create Default Settings
finishing = 100%), a completely different thing from the READY/ATTENTION cards right above it, which
correctly showed 8/13 ready. The label wrongly implied it summarized the whole environment.

**Fix**: relabeled to "OPERATION PROGRESS." No behavior change -- the bar's actual meaning (progress
of the current/last operation) is useful and stays, it just no longer claims to be something it
isn't.

## 5. Install step didn't auto-refresh or show progress detail

**Report**: "after we install palworld it should install all the items we require and then
automatically refresh. The installation should probably have more information as to what step it is
on."

The wizard's "Install Palworld Dedicated Server" button called `UpdatePalworldServerCommand`
directly, which updates Distribution/SteamCmd state but never refreshes `EnvironmentItems` -- so the
Server Environment table kept showing the pre-install "MISSING" row until a manual Refresh click.

Investigated whether "install all the items we require" could reasonably mean auto-installing UE4SS
Runtime/Palworld Save Tools/PIM-Oodle Decoder too: confirmed via `RunEnvironmentAction` that none of
these three has a one-click install path anywhere in the app today (UE4SS needs its own page's
version picker; the other two are explicitly `actionSupported: false` with "BACKEND REQUIRED" --
no management API exists for them yet). Building that is a real, separate feature, not a bug fix, so
it's out of scope here.

**Fix**: new `InstallPalworldServerFromWizardCommand` wraps the existing install call with an
automatic `RefreshEnvironmentAsync()` afterward. The install status text now sets an honest
expectation up front ("can take several minutes on first install" -- there's no incremental
progress API to report real percentages from), and the wizard's Install step now also shows
SteamCMD's own captured output tail (`DistributionOutputText`, already existed, already shown on the
Update Center page, just not here) for real detail instead of a flat "Complete."

## 6. MODs step required a manual scan

**Report**: "step 7 should automatically search for workshop mods."

**Fix**: `FinishInstallAndAdvanceAsync` (the "Next: MODs" handler) now auto-triggers
`ScanWorkshopModsAsync()` on arrival, mirroring the MOD Library page's own v0.7.78.0
auto-scan-on-first-visit behavior verbatim (same `WorkshopItems.Count == 0` guard).

## 7. MODs step had no way to install a local MOD ZIP

**Report**: "have a different colour button to allow for the installation of mod zip or pak files."

**Fix**: added a green "Install MOD ZIP…" button reusing `InstallModZip_Click` verbatim -- the exact
picker + `InstallModZipAsync` path the MOD Library page's own "Choose ZIP and Install" button already
uses. Scoped to ZIP only, matching MOD Library: a bare `.pak` file has no install path anywhere in
this app today; adding one would be a new backend capability, not a button-wiring fix.
