# v0.6.18.4 — Server Control Button State

## Goal

Direct user feedback: the Start/Restart/Stop ribbon buttons stayed clickable regardless of whether the server was actually running or stopped — Start should grey out while already running (same for Restart), and Stop should grey out while already stopped.

## Grounding

The buttons' `CanExecute` predicates only checked `ManagementApiConnected`/`IsBusy` — never the server's actual lifecycle phase. The real "is the server running" signal already exists on every status poll (`ServerStatusDto.Ready`/`NativeProcessId`) and is already used for exactly this purpose elsewhere: `HeadlessPalEditService.ApplyAsync`'s precondition for refusing to apply a Pal edit while the server is running checks `status.NativeProcessId.HasValue || status.Ready` — `NativeProcessId` alone catches "process launched but not yet Ready" during startup, which `Ready` alone would miss.

## What shipped

New `ServerIsRunning` bindable property, set inside `ApplyStatus` using that same, already-proven definition. `StartCommand`'s `CanExecute` gained `&& !ServerIsRunning`; `StopCommand`/`RestartCommand` gained `&& ServerIsRunning`. `ServerIsRunning`'s setter raises `RaiseCanExecuteChanged` for all three commands, mirroring the existing pattern `ManagementApiConnected`'s setter already uses.

## Explicit non-goals (this pass)

- No change to what happens when Start/Stop/Restart actually run — only when the buttons are enabled.
- No server-side change.

## Verification

`dotnet build` (Release) across all three projects and the full solution — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.6.18.3 regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. The actual button greying behavior against a real running/stopped server is the user's to confirm once built.
