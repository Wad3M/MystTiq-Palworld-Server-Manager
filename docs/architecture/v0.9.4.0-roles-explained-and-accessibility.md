# v0.9.4.0 — roles explained, and accessibility

## Required roles on disabled controls

Since v0.8.23.0 every command that reaches a route needing more than Viewer is listed with its role
(`MainWindowViewModel.CommandRoles.cs`), and cannot run below it, so every button bound to it is disabled. The Ribbon
already said which role (v0.8.19.0); page buttons and menu items did not.

`Services/RoleHint.cs` closes that gap for every `Button` and `MenuItem`:

- Each gated command now knows the role it needs and how to read the signed-in role (`IRoleGatedCommand.RequiredRole`,
  `SignedInRole`, set by `InstallCommandRoleGates`). Commands belong to a tab's view model, so a hint is always about
  that tab's sign-in.
- Class handlers on `Button.Command`, `MenuItem.Command` and `IsEffectivelyEnabled` look at the control whenever its
  command or enabled state changes; a role change (`RaiseCommandRoleGatesChanged`) and a language change refresh every
  control bound to a gated command.
- When the role blocks the command, the control gets "Needs the Admin role. You are signed in as Viewer." (translated;
  role names too) as its tooltip, shown while disabled (`ToolTip.ShowOnDisabled`), with its own tooltip after it, and as
  its accessible help text. Both are set at Animation priority, above the control's own value or binding, so removing
  them restores what was there untouched.
- Ribbon buttons (class `ribbon`) keep their own "(needs the … role)" tooltip. Local use without sign-in is never
  blocked, so nothing changes there.

## Accessible names

Every list, text box, drop-down, number box, slider and check box in the Desktop now has a name a screen reader can say:
its text, an `AutomationProperties.Name`, a tooltip or a watermark. About 150 names were added, almost all from the
label or heading the control already sits under (the same translated key), the rest chosen by hand: filters ("Severity
filter", "Player filter"), lists whose heading is a sentence, and boxes whose label follows them ("Mbit/s per player").
Setting rows are named after the setting: a check box with the translated name (`{services:TrText DisplayName}`), a
text box with the setting's own name (`{Binding DisplayName}`), because an editable field never goes through the catalog
(the v0.9.1.0 rule). 21 new keys, translated in every language.

The release gate checks the XAML statically (a new unnamed control fails it), and the ArtworkHarness checks the running
window: on every page, every visible control has a name, and every enabled button, toggle, text box, drop-down and slider
can take focus and is in the Tab order. (A list passes focus to its items and a number box to its own text box.)

## More in the chosen language

- The health states the Dashboard and the service use (STOPPED, DEGRADED, STARTING, TRANSITIONING, UNKNOWN, INCOMPLETE,
  MISSING) are in the catalog.
- `{services:TrFormat key, Path=…}` (a translated label with a value, "Health: {0}") now shows a text value through the
  catalog too, like `{services:TrText}`, so "Health: Healthy" becomes 状態：正常. Numbers and names match nothing and stay
  as they are.
