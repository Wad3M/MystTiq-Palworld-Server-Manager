# v0.7.114.0 — Multi-User Login

## Why

Pulled into 0.7.x by the user on 2026-09-22 (it had been parked for v0.8.x). Until now every caller was a
*token*: the shared legacy bearer token (always Owner) or an RBAC principal token (v0.6.x). Tokens scope
access for scripts and integrations, but they are not people. There was no username, no password, no
sign-out, and the audit log said "local-management-api" for everything.

## Design

Named accounts sit *on top of* the existing model rather than beside it. The existing auth middleware and
`RequireRole` are unchanged, and so is the Desktop's role gating. The shared token and principal tokens
still work exactly as before.

- `HeadlessUserAccountService` is fleet-level, like `HeadlessRbacService`, and lives in
  `<FleetRoot>/security/users.json` and `sessions.json`.
  - **Passwords**: PBKDF2-HMAC-SHA256, 210,000 iterations, 16-byte random salt, stored as
    `pbkdf2-sha256$iter$salt$hash`. Verification is a fixed-time comparison. The minimum length is 10.
  - **Sessions**: 32 random bytes returned once at sign-in. Only the SHA-256 is persisted, so a copied
    `sessions.json` cannot be replayed. Sessions last 12 hours and survive a MystTiq restart.
  - **Live account**: every request re-reads the account, so a role or scope change applies to open
    sessions at once. Disable, password reset and delete end the account's sessions.
  - **Lockout**: 5 failed sign-ins in a row lock the account for 15 minutes, on top of the existing
    per-IP guard (8 failures), which sign-in failures also feed. A missing username costs the same PBKDF2
    work and gets the same message as a wrong password.
  - **Principal**: `Id = "user:<id>"`, `Name` = display name, the account's role and optional
    single-server scope, and `ExpiresUtc` = the session's end.
- Middleware: `rbac.Authenticate(token) ?? userAccounts.Authenticate(token)`. Exactly one path is
  anonymous, `/api/v1/auth/login`.
- Routes:
  - `POST /api/v1/auth/login`. Returns 409 when authentication is off, because then everyone is already
    Owner.
  - `POST /api/v1/auth/logout`
  - `POST /api/v1/auth/password` (own password; needs the current one)
  - `GET/POST /api/v1/security/users`, and `PUT`, `DELETE` and `POST .../password` on
    `/api/v1/security/users/{id}`. All are Owner-only.
- **Audit**: the fleet API activity line now records the caller's name as the actor.

## Desktop

- **Settings, connection card**: "Sign in with a user account" (username, password, Sign In, Sign Out).
  - Sign In puts the session token in the tab's Bearer token and connects, which saves the token encrypted
    the same way a pasted token is. The password is never stored.
  - Sign Out ends the session on the server and forgets the saved token.
- **Connect now loads `whoami`** when authentication is on. So `CanManageAdmin` and `CanManagePrincipals`
  reflect the real role on every page from the start; before, the principal was only loaded on the
  Security page.
- **Security page**: a "User Accounts" card (Owner) to create accounts (username, display name, role,
  optional server id, password), list them (role, active/disabled/locked, last sign-in), and reset a
  password, enable/disable or delete.
- `/api/v1/auth/` was added to the Desktop's fleet-only route list, so a per-server tab never rewrites
  sign-in to a server-scoped path.

## Verification

- Logic harness: 3 new scenarios. They cover hashing, validation, sessions, live role change, the lockout
  and its end, disable, password reset, restart persistence, expiry, sign-out, delete, and changing your
  own password.
- `scripts/Test-v0.7.114.0-RouteSmoke.ps1` (11 checks) runs against the published exe with authentication
  really on (loopback, a shared token from `api-token-create`). It covers:
  - anonymous 401, account creation and bad input
  - the same message for a wrong password and an unknown user
  - sign-in → `whoami` as Alice/Operator
  - Operator route 200 while Admin/Owner routes return 403
  - promotion applying to the open session
  - an audit entry naming "Alice A"
  - disable → 401, sign-out → 401, lockout
  - no password or token in the files on disk
- Live Desktop: the Sign In block and the User Accounts card render. A real Desktop sign-in was not
  exercised: the local sidecar on this machine runs with authentication off (where sign-in correctly
  answers 409).

## Found and fixed while testing

The first smoke run used the default `FleetRoot`, which is machine-wide (`C:\ProgramData\MystTiqPalworldServer\fleet`)
and shared with the real app. So its test accounts landed in the real store. They were removed at once:
the file had only the two test accounts, and the feature was minutes old. The smoke now uses its own
FleetRoot, and the gate checks that it does. Its API calls were also appended to the shared fleet audit
log; that append-only history was left as is, the same as the older v0.7.17.0 smoke's.

Also fixed in this version: the v0.7.113.0 teleport service sent its reply to the player *before* recording
the use. A status read landing between the two missed the record, and this version's full gate hit exactly
that window once (the carried v0.7.113.0 smoke's "recent uses" check). Uses are now recorded before any reply.

## Not done

- A web (browser) sign-in page. MystTiq has no browser UI; sign-in is from the Desktop or the REST API.
- Hiding cards per role beyond the existing Admin/Owner gating (the server enforces every route
  regardless).
