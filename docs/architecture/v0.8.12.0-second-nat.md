# v0.8.12.0 — Second-NAT Check, and UPnP That Works

This is the third item of the user's automated run (remaining roadmap in reverse order). The roadmap item was "checking
ports from outside". Checking it on real machines (this Windows server and the Linux test VM) turned up two long-standing
UPnP bugs, and they are fixed here too.

## What can and cannot be checked

A true outside-in test of a Palworld server needs a real game packet (UDP) sent from somewhere on the internet by a
peer that speaks the game's protocol, and MystTiq has none. Port-checker websites mostly test TCP.

What can be checked is the common blocker the WAN check did not see: **a second NAT**. A port forward on the home router
only helps when that router holds the address the internet sees. It does not when:
- the ISP uses carrier-grade NAT, giving the router a 100.64.0.0/10 address (RFC 6598);
- the router sits behind another router (double NAT), so its internet (WAN) address is itself private.

## What changed

- **`NatTopology.Classify(publicIp, routerWanIp)`** (Core, pure) decides on the router's own WAN address, from UPnP
  `GetExternalIPAddress`:

  | Router's WAN address | Result |
  |---|---|
  | In 100.64/10 | **Fail**, CGNAT |
  | Private | **Fail**, double NAT |
  | Public, but not the address the internet sees | **Warning** |
  | The same public address | **Pass** |
  | Not reported | Skipped |

  Each result has its own fix.
- **`NatTopology.ClassifyRoute(hops, routerRefused)`** is used only when the router gives no WAN address. It looks at
  the first answering hop after the home router, from ICMP with a rising TTL (like `tracert -d -h 4`). It is weak
  evidence and is treated that way:

  | Route | Result |
  |---|---|
  | The very next hop is public | Pass |
  | A 100.64/10 hop | a cautious Warning |
  | A private next hop | **Skipped, "cannot tell"**, with how to find out on the router's status page |
  | A silent hop 2 | no verdict (it could be the second NAT) |

  It never gives a Fail.
- **The first draft was wrong on the real network, and was corrected.** It read a private hop 2 as "likely double NAT"
  and said so to the user. On the Linux VM the same router then reported its WAN address, and it was **the public
  address**. Hop 2 (10.x) is the ISP's own equipment. A private hop therefore now means "cannot tell". The draft also
  treated the router refusing its WAN address (UPnP error 501) as a hint of a private address. That was also wrong: the
  refusal is intermittent, and the router is asked again once.
- **An "Outside-in test" entry** is always added, as Skipped. It says MystTiq cannot prove outside reachability,
  suggests a friend joining `<public IP>:<port>`, and notes that TCP port checkers are unreliable for Palworld.
- **UPnP fixed on Linux.** A router's control URL such as `/ctl/IPConn` parses on Linux as an absolute `file://` URI,
  so every UPnP call failed there with "The 'file' scheme is not supported". Control URLs now count as absolute only
  when they are http(s) (`ResolveControlUrl`). On the test VM, UPnP now finds the router and reads its mappings.
- **UPnP fixed on a multi-interface Windows host.** This project's own server has a second interface on the same subnet
  (the Hyper-V switch for the test VM). The SSDP search from an unbound socket never reached the router, so UPnP had
  always shown "Unsupported" there. Probing showed the router answers at once when the search is sent from either LAN
  interface. The search now goes out from every LAN interface that has a gateway, in parallel, and is also sent
  straight to the gateway.
- **Route trace on Linux.** An unprivileged process can only ping there through the system `ping` tool, which accepts
  the default payload only (a custom one threw), and a hop answers as `TimeExceeded` rather than `TtlExpired`. Both are
  handled.
- `WanReachabilityReport` gains an optional `RouterWanIPv4`. The Desktop shows the router's internet address beside its
  name and explains the checks in the WAN section's intro.

## Verification

- **Logic harness.** The "Second NAT" scenario covers:
  - every WAN-address branch and the range edges;
  - every route case, including a silent hop 2 and a refused WAN address;
  - `ResolveControlUrl` for a relative and an absolute control URL.
- **Route smoke** (`Test-v0.8.12.0-RouteSmoke.ps1`), on the published exe. It checks the contract (a verdict with a
  reason, `routerWanIPv4` present, the outside-in entry Skipped), since the verdict depends on the network.
- **Real network, Windows (this server).** Before the fixes: "no UPnP router", then the route draft's false double-NAT
  warning. After the fixes, the router (Arcadyan OpenWrt) is found:
  - "no UPnP mapping for UDP 8211";
  - **second NAT: Pass**, because the router holds the public address the internet sees.
- **Linux** (test VM 192.168.1.122, Ubuntu kernel 6.8). `Test-v0.8.12.0-LinuxIsolated.ps1` publishes the linux-x64
  headless and runs it isolated: its own config, FleetRoot and port 18412, a synthetic server folder, and the
  installed service untouched. It passes 5/5:
  - v0.8.9.0: the crash report is read and classified (engine-array-size);
  - v0.8.11.0: Pal positions (base worker, party alpha; the Palbox Pal only counted);
  - v0.8.12.0: the WAN report, twice. One run got the router's public address (Pass). The other got the router's
    intermittent refusal plus a private hop 2 ("cannot tell"). UPnP works, with no "'file' scheme" error.

## Not done

- A real outside-in UDP probe needs a server outside the user's network.
- The router's refusal of `GetExternalIPAddress` is intermittent (miniupnpd), so on some runs the check can only say
  "cannot tell".
