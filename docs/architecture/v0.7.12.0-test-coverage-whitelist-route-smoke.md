# v0.7.12.0 — Test Coverage: Whitelist Enforcement & Route Smoke

## Background

Requested directly, following the v0.7.6.0–v0.7.10.0 sequence: check for other tests worth running. A dedicated audit compared the 28-check frozen `Test-v0.5.1.5-RuntimeSmoke.ps1` baseline and every version-specific `Test-vX.Y.Z.W-Logic.ps1`'s `-RunBuild` block against the full REST route surface (`LocalManagementApiHost.cs` maps roughly 95 routes). The finding: everything shipped from v0.7.8.0 onward had regex-on-source contract checks only — proving the code *pattern* exists, never that the *endpoint* behaves correctly — and the one genuinely new piece of business logic added in that window (`HeadlessWhitelistService.EnforceAsync`'s kick-a-non-whitelisted-player behavior) had never executed at all, since verifying it live would need a real online player against a real Palworld server, which this environment cannot provide.

The audit also confirmed both of the following are true, which shaped what got built here:
- `HeadlessWhitelistService.EnforceAsync`'s dependencies are all plain interfaces (`IServerPathProfile`, `IPlayerModerationProvider` via `PlayerModerationCoordinator`) — fully fakeable without any real server, RCON connection, or HTTP round-trip.
- `MainWindowViewModel`'s constructor takes only interfaces too, and its base class is plain `INotifyPropertyChanged`, not an Avalonia type — in principle testable the same way, but doing so needs the Avalonia `Dispatcher` (the constructor posts to it), which needs either `Avalonia.Headless` (a new dependency) or careful avoidance — deferred here as bigger infrastructure investment than this release's two "quick win" items.

## What shipped

### `scripts/Testing/MystTiq.LogicHarness/` — a real object-graph test for whitelist enforcement
A standalone, throwaway C# console project (`MystTiq.LogicHarness.csproj`), referencing `MystTiq.Core` and `MystTiq.HeadlessHost` directly via `ProjectReference`, deliberately **not** added to `PalworldServerManager.slnx` or `Build.ps1`'s normal build/validate pipeline — it's invoked with `dotnet run` from a test script, matching this project's existing script-as-test philosophy rather than introducing xunit/nunit as a new dependency for one test file.

It fakes exactly one thing — `IPlayerModerationProvider`, recording every `ExecuteAsync` call — and a minimal `IServerPathProfile` pointed at a scratch temp directory, then constructs and exercises the real `HeadlessWhitelistService` against real `HeadlessPlayersSnapshot`/`HeadlessPlayerSnapshot` data. Six scenarios:

1. A disabled config takes no action at all.
2. An enabled config kicks a non-whitelisted online player and leaves an allowed one alone.
3. The same still-online non-whitelisted player is *not* re-kicked on a second poll (the `recentlyEnforced` dedup set doing its job).
4. A player *is* re-kicked after leaving (dropping off the online list) and rejoining.
5. Saving a new config resets the dedup set, so a still-online, already-kicked-once player gets re-evaluated (and kicked again) after a config change.
6. An unavailable `HeadlessPlayersSnapshot` (the REST API itself unreachable) is ignored entirely, not misinterpreted as "everyone kicked."

All six ran and passed against the real service before this was wired into the release pipeline.

### `scripts/Test-v0.7.12.0-RouteSmoke.ps1` — permanent route coverage for v0.7.8.0–v0.7.10.0
Same isolated-sidecar bootstrap pattern as `Test-v0.5.1.5-RuntimeSmoke.ps1` (a fresh temp server root, no real `PalWorldSettings.ini`, `--desktop-sidecar` mode). Covers every route added in that window that had zero prior live coverage:

- `GET /players/ban-list`, `POST /world/save-now`, `POST /players/{id}/teleport-to-me`, `POST /players/{id}/teleport-to-player` — each checked for reachability, the correct graceful-failure shape (RCON genuinely unconfigured in this environment returns a structured `409` with a real explanatory message, not a crash), and — for the three RCON-command routes — that the exact command text built (`Save`, `TeleportToMe <id>`, `TeleportToPlayer <id>`) matches what Palworld's RCON protocol expects.
- `POST /players/{id}/action` with `action=unban` — confirms it resolves to `providerId: "rcon"`, proving the v0.7.8.0 routing fix (unban going through the moderation coordinator, not the REST-only admin provider that doesn't support it) still holds.
- `GET`/`PUT /players/whitelist` — the full round trip: default state, persisting a new config, and a subsequent `GET` reflecting exactly what was saved (proving real file persistence, not an in-memory echo).
- `GET /metrics` — confirms the v0.7.9.0 `serverFps`/`serverFrameTimeMs` fields are present in the response shape.

`Invoke-RestMethod` throws on non-2xx responses in PowerShell, so every check expecting a graceful `409` reads the response body from `$_.ErrorDetails.Message` in a `catch` block rather than a direct return value — a real bug in the first draft of this script (it initially tried the PowerShell 5.1-era `$_.Exception.Response.GetResponseStream()` API, which doesn't exist on the `HttpResponseMessage` that PowerShell 7's `Invoke-RestMethod` actually throws) was caught and fixed before this shipped, by actually running the script and reading its failures rather than trusting it unverified.

### Stale comment fix
`src/MystTiq.Core/Providers/ProviderModels.cs`'s header comment still described whitelist and teleport as part of an undifferentiated "explicit deferred list" — both shipped (v0.7.10.0 and v0.7.8.0 respectively) since that comment was written. Noticed while re-reading this file's context for the harness's `IPlayerModerationProvider` fake; updated to name what's shipped versus what's still deferred (presence/world-data/chat/generic-commands).

## Explicit non-goals

- **A `MainWindowViewModel` stale-tab-logic harness** — identified by the audit as feasible in principle (the VM's dependencies are all interfaces), but doing so cleanly needs `Avalonia.Headless` or equivalent care around the `Dispatcher.UIThread.Post` call in its constructor. That's a real new-infrastructure decision (a new test-only package dependency, possibly a new test project) rather than a quick addition, so it's deferred rather than built without flagging the tradeoff.
- **Broad route coverage beyond v0.7.8.0–v0.7.10.0** — the audit found roughly 90 routes total with no live coverage (most of them long-standing, predating this session's work: `/automation/*`, `/alerts/*`, `/anticheat/*`, `/diagnostics/*`, `/guilds/*`, `/pals/*`, `/bases/*`, etc.). This release deliberately scoped to just the routes added in the immediately preceding three versions, not a full backfill.
- **A CI runner** — every test in this project, old and new, is manually invoked. Nothing structurally guarantees the two additions here run before a future release; they rely on the same discipline that has kept `Test-v0.5.1.5-RuntimeSmoke.ps1` wired into every `-RunBuild` block so far.
