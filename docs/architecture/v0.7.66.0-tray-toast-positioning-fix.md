# v0.7.66.0 — Tray Reminder Toast Positioning Fix

## Goal

Direct bug report: on a real multi-monitor layout (primary 2048×1152 at (0,0), secondary 1920×1080
at (383,-1080), stacked above the primary; 100% display scaling on both), the "MystTiq is still
running" tray reminder toast (`TrayReminderToast`, v0.7.11.0) rendered far from its intended
bottom-right anchor — roughly mid-screen — instead of tucked near the tray icon.

## Root cause

`TrayReminderToast.PositionBottomRight()` resolved its target monitor via
`Screens.ScreenFromWindow(this)` — asking Avalonia which screen the toast window itself currently
overlaps. The problem: this call happens from the `Opened` event handler, at the exact moment the
window has just been created with `WindowStartupLocation="Manual"` and **no `Position` ever
explicitly set** — so at that instant, `this` is still sitting wherever the OS/window manager
defaulted a brand-new manually-positioned window to, not yet the corner `PositionBottomRight` is
about to move it to. `ScreenFromWindow` reliably resolving to the *intended* monitor depends on that
default position happening to already overlap it, which is not guaranteed — least of all on a layout
where the secondary monitor sits at a *negative* Y origin, since a naive default position (e.g. near
the origin) can straddle or land squarely on the wrong monitor entirely. The window doesn't need to
be full-DPI-scaled or misconfigured for this to happen — it's a timing/reference problem, not a
coordinate-math problem, which is why 100% scaling didn't prevent it.

Once the wrong screen's `WorkingArea` feeds the bottom-right calculation, the resulting `Position` is
a real, validly-computed bottom-right corner — just of the wrong monitor, which from the user's
actual seat (looking at the *intended* monitor) reads as "renders mid-screen" or in an arbitrary spot
relative to what they're looking at.

## The fix

`TrayReminderToast` now accepts an optional owner `Window` (`TrayReminderToast(string message,
Window? owner = null)`). `PositionBottomRight()` resolves the target screen from that owner first
(`Screens.ScreenFromWindow(owner)`), falling back to the previous `Screens.ScreenFromWindow(this)` /
`Screens.Primary` / `Screens.All.FirstOrDefault()` chain only if no owner was supplied. `App.
ShowTrayStillRunningReminder` now passes `mainWindow` as that owner — the one window in this app
whose position is always real and already-settled at the moment the toast appears, since this
reminder only ever fires immediately after `HideMainWindowToTray`'s own `mainWindow.Hide()` call
(the main window is hidden, not disposed — it's still a fully valid, positioned `Window` instance for
`Screens.ScreenFromWindow` to query).

## Verification

- `dotnet build` on `MystTiq.Desktop.csproj` and the full solution: clean, 0 warnings/errors.
- Confirmed `TrayReminderToast` has no other construction sites needing the same fix (only
  `App.ShowTrayStillRunningReminder` constructs it).
- `scripts\Test-v0.7.66.0-Logic.ps1` — contract-presence checks confirming the owner parameter,
  screen-resolution-from-owner logic, and the call site both exist.
- **Not verified visually** — same disclosed limitation as every other Desktop/GUI change this
  session: no way to render or click-test the native Avalonia window in this environment, and
  specifically no way to reproduce a real dual-monitor layout with a negative-Y-origin secondary
  monitor to confirm the toast now lands correctly. The fix directly targets the mechanism identified
  in the bug report (screen resolved from an unsettled window instead of a settled one) rather than
  guessing at a workaround, but a live check on the actual reported hardware is the only way to fully
  close this out.

## Update: this fix was real but incomplete

Live testing on the actual reported hardware in v0.7.67.0 (the very next version, same session)
found a **second, independent** positioning bug this pass didn't catch — see
[`v0.7.67.0-tray-toast-layout-timing-fix.md`](v0.7.67.0-tray-toast-layout-timing-fix.md) for the
full account. The owner-based screen resolution documented above is still correct and necessary;
it was one of two bugs, not the whole story.

## Known gaps (disclosed)

- No live multi-monitor visual verification performed (see above) — the highest-priority follow-up
  for whoever can run the actual Desktop app on that hardware.
- The underlying `Screens.ScreenFromWindow(this)` fallback path (used when no owner is supplied)
  still has the same timing weakness described above — not a live bug today since the one real call
  site always supplies `mainWindow`, but worth remembering if a future caller ever constructs this
  toast without an owner.
