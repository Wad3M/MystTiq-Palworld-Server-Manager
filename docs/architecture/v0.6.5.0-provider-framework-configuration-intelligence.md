# v0.6.5.0 — Provider Framework & Configuration Intelligence

## Goal

Per the roadmap: "Decouple features from individual Palworld interfaces and make configuration schema-driven, version-aware and safe." This milestone ships a real, working slice of both halves rather than the full surface, matching the roadmap's own "real foundation per named area, explicit deferrals" discipline.

## What shipped

### Provider Framework — player moderation

Before this milestone, kick/ban had exactly one implementation path: `HeadlessPalworldAdminService`, calling Palworld's REST API directly. If `RESTAPIEnabled=False` in `PalWorldSettings.ini` — a common real-world configuration for admins who only run RCON — kick/ban had no working path at all.

- `MystTiq.Core.Providers.IPlayerModerationProvider` — the first real provider contract: `ProviderId`, `DisplayName`, `GetHealthAsync` (returns a `ProviderDescriptor` with a `ProviderHealth`: `Unknown`/`Healthy`/`Degraded`/`Unavailable`/`Misconfigured`/`Unsupported`), `SupportsAction`, `ExecuteAsync`.
- `HeadlessPalworldAdminService` now implements this interface directly (composition, not duplication — the existing REST kick/ban logic is completely unchanged; the interface methods are thin adapters over the existing `ExecuteAsync(action, playerId, message, item, token)`).
- `RconPlayerModerationProvider` (new) — issues Palworld's Source RCON `KickPlayer <id>`/`BanPlayer <id>` commands via the existing `PalworldRconService.ExecuteAsync`, which already has its own internal try/catch returning a graceful failure result.
- `PlayerModerationCoordinator` (new, in Core) — tries each provider that supports the action, in registration order (REST first, matching pre-v0.6.5.0 default behavior for REST-only servers), skipping any provider whose health is `Unavailable`/`Misconfigured` without attempting it, and falling through to the next provider on a genuine execution failure. Returns the first success, or the most recent real failure if every provider fails — never a silent no-op.
- Wired per-profile in `ServerProfileHost`/`LocalManagementApiHost.Create`: `new PlayerModerationCoordinator([playerAdmin, rconModeration])`.
- `POST /api/v1/players/{playerId}/action` now dispatches `kick`/`ban` through the coordinator; every other action (`whisper`/`promote`/`give-item`, still honestly unsupported by either interface) is completely unchanged, going straight to `HeadlessPalworldAdminService.ExecuteAsync` as before.
- New `GET /api/v1/players/moderation/providers` returns each provider's current health. Surfaced on the Desktop Players page as a compact status line (`ModerationProviderStatusText`), fetched alongside the existing player-page refresh, non-fatal on failure.

**Real bug found and fixed during live verification, load-bearing for the whole feature**: `HeadlessPalworldAdminService.ExecuteAsync`'s REST HTTP call (`client.SendAsync`) had no exception handling. A connection-refused failure (REST enabled per config, but the port not actually listening) threw an unhandled `HttpRequestException` straight out of `PlayerModerationCoordinator`'s `foreach` loop — the exception propagated past the coordinator entirely, so RCON was never attempted, and the client received an empty-body HTTP 500 instead of a fallback attempt or an honest error. This is exactly the failure mode the coordinator exists to handle, and it was silently defeated by the missing try/catch. Fixed by catching `HttpRequestException`/`TaskCanceledException`/`IOException` around the REST call and returning a normal `HeadlessPlayerAdminResult(false, Supported: true, ...)`, restoring the intended fallback behavior.

### Configuration Intelligence — first real slice

The roadmap calls for a full central configuration schema (types, defaults, ranges, tooltips, version metadata, dependencies) and cross-setting validation. This milestone ships the cross-setting validation half's first concrete case: port-conflict detection.

- `HeadlessDiagnosticsService.BuildConfigurationFindings()` (new) reads `PalWorldSettingsConfigurationService.Load()` and checks whether the Game (`PublicPort`), REST API (`RESTAPIPort`, only if `RESTAPIEnabled`), and RCON (`RCONPort`, only if `RCONEnabled`) ports collide — a real misconfiguration neither `HeadlessDoctorService` nor `HeadlessEnvironmentChecklistService` has ever checked, since both validate individual settings, not settings against each other.
- The result is a single `DiagnosticFinding` with `Category: "Configuration"`, merged into the same `GetUnifiedReportAsync` list the v0.6.4.0 Diagnostics Platform already produces — so it appears on both the Desktop Doctor page and the Dashboard health badge with **zero Desktop code changes**, since both already render the unified finding list generically without filtering by category.
- No fix action exists yet (`ActionSupported: false`) — resolving a port conflict requires editing `PalWorldSettings.ini` and restarting the server, which stays a manual action via the existing Configuration page.

## Explicit deferrals (not silently dropped)

- Provider types beyond moderation: presence, world data, chat, whitelist, teleport, commands.
- Provider implementations beyond REST/RCON: GameData, save/world, PalDefender, MOD.
- Typed command schema, RCON catalog, advanced API/command explorer.
- The full central configuration schema (types/defaults/ranges/enums/tooltips/restart requirements/version metadata/deprecated-reserved state/dependencies).
- Minimal configuration writes, presets, import/export, secret-safe portable profile packages.

## Verification

Live, against a real isolated instance (a scratch copy of the real `PalWorldSettings.ini`, never the production save/config, on a throwaway port):

- `GET /players/moderation/providers` with both REST and RCON enabled in the ini: both reported `Healthy`, matching the ini's actual `RESTAPIEnabled=True`/`RCONEnabled=True`/non-empty `AdminPassword`.
- Induced a real port collision (set `RCONPort` equal to `RESTAPIPort` in the scratch ini): `POST /diagnostics/configuration-port-conflicts/recheck` correctly flipped to `Fail` with evidence `"REST API Port and RCON Port are both set to port 8212."`; reverted the ini and rechecked back to `Pass`.
- `POST /players/{id}/action` with `action=kick` against a nonexistent player with no live PalServer process running (both ports closed): before the exception-handling fix, this returned an unhandled HTTP 500 with an empty body. After the fix, returns `{"success":false,"supported":true,"providerId":"rcon","message":"No connection could be made because the target machine actively refused it."}` (HTTP 409) — proving the coordinator genuinely attempted REST, caught its real failure, and fell through to RCON, surfacing the real underlying network error rather than crashing or silently reporting success.
- Disabled REST in the scratch ini (`RESTAPIEnabled=False`): `GET /players/moderation/providers` correctly reported REST `Unavailable`; a subsequent `ban` action skipped straight to RCON per the health check (no REST HTTP attempt), still correctly failing honestly since no live server was reachable.
- Confirmed `whisper` still returns the exact same pre-v0.6.5.0 "Vanilla Palworld REST does not expose..." unsupported response (HTTP 422) — the non-kick/ban path is untouched.

Not performed this session (no live PalServer process was started — verification stayed inside the "never touch/never risk the production save or an actual running server" constraint): a real successful kick/ban against an actually-running PalServer instance. The failure-path fallback chain above is the practically verifiable scope without standing up a live game server, and mirrors how prior milestones' RCON/REST integration was verified.
