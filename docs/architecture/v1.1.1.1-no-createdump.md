# v1.1.1.1 — Packages without .NET's createdump helper (internal)

Roadmap F-15. Owner, 2026-10-17, with a VirusTotal behaviour report of the v1.1.1.0 Windows ZIP: "Is there a way to adapt
our coding so that this detected issue does not come up?"

## What the report showed

- 0 antivirus detections. One crowdsourced Sigma rule matched: "Potential Vcruntime140 DLL Sideloading" (a
  `vcruntime140.dll` loaded from outside System32 or Program Files).
- The sandbox (CAPE, Jujubox) unpacked the ZIP and ran `createdump.exe`, the crash-dump helper a self-contained .NET
  publish places beside the app (twice in MystTiq: the app folder and `headless\`). The only modules listed were the
  sandbox's own Python 3.8 (`...\AppData\Local\Programs\Python\Python38`, which ships its own `vcruntime140.dll`);
  `createdump` wrote `dump.1064.dmp`. The rule's event context was empty.
- MystTiq ships no `vcruntime140.dll` (checked in the publish folder and the ZIP), and nothing in MystTiq calls
  `createdump` or sets `DOTNET_DbgEnableMiniDump`.

## What changed

- `Directory.Build.targets`, target `MystTiqLeaveOutCreateDump` after `ComputeResolvedFilesToPublishList`: removes
  `createdump` from `ResolvedFileToPublish`, so it is never copied. Being in the repository root, it applies to every
  project and every publish: `Build-AvaloniaDesktop.ps1`, `Package-GitHubRelease.ps1`, the release workflow and the Docker
  build.
- `Package-GitHubRelease.ps1` refuses a package (or a signed `-FromFolder` folder) holding `createdump`;
  `Build-DockerImage.ps1` refuses an image whose `app/` holds it.
- The cost: .NET cannot write an on-demand dump of a crashed MystTiq process. MystTiq's crash records (its own logs) are
  unchanged.

Retaken (asked 2026-10-18): `docs/images/01-dashboard.png`, `03-players.png`, `06-backups.png`, `07-mods.png`. The real
`MainWindow` rendered headlessly at 1920x1080 (the ArtworkHarness's Avalonia setup, with the real API client) against a

Taking them found F-16 (pages reading a stale decoded save).

## Evidence

- A Windows and a Linux self-contained publish of the service hold no `createdump`, and the Windows one starts (gate,
  with `-RunBuild`); the release ZIPs and the image checked after packaging.
- Not provable here: what a third-party sandbox does with the next upload. Code signing (E-14) remains the broader fix
  for reputation.
