# v0.7.36.0 — Theme System Audit

## Goal

Twelfth version in the GUI/workflow/UX overhaul roadmap. Roadmap item 50 — with Light mode enabled, the main content area lightened correctly but the title bar, category tab row, and ribbon area all stayed the same dark navy as before.

## Two distinct gaps, correctly separated

Grounding for this item split it into two separate issues during the original walkthrough, and this release confirms and closes only one of them:

### 1. Already disclosed, not attempted (out of scope by design)

`Services/ThemeCatalog.cs`'s own header comment already explains: the catalog covers structural surfaces, the five accent hues, three semantic colors, and roughly 20 chrome gradients — but explicitly **not** the smaller decorative `BorderBrush`/`BoxShadow`/`Effect` colors scattered through individual `<Style>` selectors elsewhere in `DesignSystem.axaml`. The reason is a real Avalonia platform limitation: `BoxShadow`'s shorthand string syntax cannot bind to `DynamicResource` at all. This stays as-is — a genuine, previously-disclosed ceiling, not something this release attempts to work around.

### 2. Real, fixable gap — closed this release

Separately from the BoxShadow limitation, two **structural chrome containers** — not decorative accents — were using hardcoded hex literals instead of any theme resource at all:

- The title bar `Border` (`MainWindow.axaml`, `Grid.Row="0"`): `Background="#F1081422" BorderBrush="#28445D"`.
- The footer status bar `Border` (`MainWindow.axaml`, `Grid.Row="4"`): the identical `Background="#F1081422" BorderBrush="#28445D"`.

Both sat hardcoded while the nav pane container right beside them correctly used `Background="{DynamicResource NavGlassSurfaceGradient}"` (now `GlassOptionHoverGradient` as of v0.7.34.0) and the ribbon/category-tab row correctly used `Background="{DynamicResource CommandSurfaceGradient}"` — this is exactly why the title bar and footer visibly stayed dark in the reported screenshot while the surrounding chrome lightened.

## Fix

Rather than inventing new resources, found that `DesignSystem.axaml` already defines a `StatusSurfaceGradient` — a `LinearGradientBrush` whose name and Dark/Default color stops (`#F1112639`/`#F0091725`/`#F00C1A2A`) are a near-exact visual match for the hardcoded `#F1081422` the title bar and footer were using — and it's already fully registered in every `ThemeCatalog.GradientStops["StatusSurfaceGradientStop0/1/2"]` combination (all four accent themes × both variants). It simply had zero consumers in `MainWindow.axaml` before this release. Likewise, `BorderSoftBrush` (Dark `#223D55`, close to the hardcoded `#28445D`) was already defined and theme-registered via `ThemeCatalog.Structural["BorderSoft"]`.

Both hardcoded literal pairs were replaced with `Background="{DynamicResource StatusSurfaceGradient}" BorderBrush="{DynamicResource BorderSoftBrush}"` — a single `replace_all` edit (the two occurrences were byte-identical). No new `Color`/`LinearGradientBrush`/`ThemeCatalog` entries were needed; this was pure `MainWindow.axaml` rewiring to resources that already existed and were already theme-aware.

## Audit of the rest of MainWindow.axaml

Catalogued every remaining hardcoded `Background="#..."` literal in `MainWindow.axaml` to check for other primary-chrome-scale gaps. None were found at the title-bar/footer/nav-pane scale — the remaining hardcoded values are:

- Thin 1px divider lines (`Width="1"` separator `Border`s).
- Per-value status badges and small accent fills local to one card.
- Table-header row background tints (Server Environment, Network diagnostics grids).
- Deliberately theme-independent terminal-style console/RCON output panes (`#07110A`/`#0A1118`, near-black with green monospace text) — a common, intentional UX convention for log/console views that should read as a terminal regardless of the app's own theme, not a gap.

All of these fall into the same "secondary decorative accent" category `ThemeCatalog`'s own header comment already disclaims for the BoxShadow limitation — left untouched, consistent with that existing, disclosed scope boundary rather than expanding this release into an unbounded full-app color audit.

## Explicit non-goals

- No attempt to make `BoxShadow`/`Effect` colors theme-aware — the documented Avalonia platform limitation stands.
- No restyling of console/RCON output panes, table headers, or thin divider lines — decorative/secondary, not structural chrome.
- No new `ThemeCatalog` resources — both fixes reuse resources that already existed and were already fully theme-registered.
