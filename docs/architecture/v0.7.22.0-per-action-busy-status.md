# v0.7.22.0 — Per-Action Busy Status

## Background

Third of the planned backlog sequence approved this session. A code-level audit during planning confirmed a real, if minor, gap: `IsBusy` (`MainWindowViewModel.cs` ~1591) is a per-tab bool with no accompanying "what's running" string, and the footer's `ProgressBar`/`StatusBarText` pair (`MainWindow.axaml` ~2288-2289) sits behind a single hardcoded `"Working…"` literal in `RaiseIsBusyDependents`, regardless of which of the app's many possible async operations actually triggered it. Many *page-scoped* status strings already exist (`PlayerAdminStatusText`, `LifecycleStatusText`, `BackupDetail`, etc.) but nothing global that the always-visible footer could read regardless of which page happens to be active.

## What shipped

### `BusyReason`

A single new nullable string property on `MainWindowViewModel`. `RaiseIsBusyDependents` (the one place `StatusBarText` gets its busy-state value) now reads it: `StatusBarText = value ? (BusyReason ?? "Working…") : ...`. No XAML change was needed at all — `MainWindow.axaml`'s footer `TextBlock` was already bound to `StatusBarText`, so it started showing real reasons the moment operations began setting `BusyReason` before their own `IsBusy = true`.

### Where it's threaded through

Deliberately scoped to the highest-value operations, not a blanket sweep of every `IsBusy = true` site in the file (there are roughly 90):

- **Server start/stop/restart** — all three already funnel through one shared helper, `RunLifecycleAsync(string activity, Func<...> operation)`, which already receives a distinct `activity` string per caller (`"Starting…"`, `"Stopping…"`, `"Restarting…"`) used elsewhere in the same method for `ConnectionState`/`LifecycleStatusText`. One `BusyReason = activity;` insertion at the top (alongside the existing `IsBusy = true;`) and one `BusyReason = null;` in the shared `finally` block covers all three commands at once.
- **Backup create** (`CreateBackupAsync`) and **backup restore** (`RestoreBackupAsync`) — each gained `BusyReason = "Creating backup…"` / `"Restoring backup…"` alongside their existing `IsBusy = true`/`false` lines.
- **World transaction apply** (`ApplyWorldTransactionAsync`) — gained `BusyReason = "Applying world transaction…"` the same way.

## Explicit non-goals

- **Full coverage of every busy operation in the app.** Deliberately out of scope this pass, matching the approved plan's own framing ("call out remaining un-labeled operations as a known, disclosed gap rather than claiming full coverage"). An operation that hasn't been threaded through yet falls back to exactly the same generic `"Working…"` text the footer has always shown — never worse, just not yet improved.
- **Persisting or logging busy reasons.** This is a live UI-state string, not an audit trail (the existing Activity/Audit log already covers that separately, for the operations that write to it).

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors. No XAML changes this release, so no recurring comment-parsing issue to watch for.
- No GUI click-through capability in this environment (unchanged, disclosed every version) — confirmed by direct code review that `BusyReason` is set before and cleared after each of the 4 targeted operations (including in their `catch`/`finally` paths, so a reason never gets stuck showing after an operation fails), and that the footer's existing `StatusBarText` binding requires no XAML change to pick it up. Seeing the actual text change on screen during a real Start/Stop/Backup/Restore/World-transaction is left to the user.
