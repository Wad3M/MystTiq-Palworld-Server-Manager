# v0.7.81.0 — "Set Up New Server" Wizard Rework

Direct live feedback: "When i setup a new server it should always be a local install. It should
not be trying to connect to a previously installed version as we already have an option to connect
to a local server or remote server from the plus... It should have the option to clone an existing
server, setup a new world, import a world, and then move onto the specific settings. Finally ask
about MODs... then setup the new server. If another service is detected it should flag that when
selecting the ports to run on." Follow-up in the same round: "please create a logic test to create
a new server with all the steps, it should also have the option to setup a new world or clone,
choose one of the preset settings like vanilla or quality of life, and choose a new port."

## The real gap

`OpenNewServerTab()` and the shared wizard step machine
(`BeginNewProfile`/`ChooseLocalConnection`/`IsWizardStep1-3`) never actually distinguished "install
a fresh local server" from "connect to an already-running one" — both paths landed on the identical
Local/Remote choice screen, then the identical "find or start a MystTiq service" Connection Details
step. This was already disclosed in the code's own comment (`MainWindowViewModel.cs`, now removed):
"MystTiq's wizard doesn't actually distinguish 'install a fresh local server' from 'connect to an
already-running one' as different code paths... only the framing text below differs." This version
closes that gap for real rather than continuing to disclose it.

## What changed

- **`OpenNewServerTab()` always local, no Local/Remote choice.** Mirrors
  `OpenConnectLocalServerTab()`'s existing pattern: calls `ChooseLocalConnection()` immediately,
  sets a new per-tab `IsNewServerSetupFlow` flag. The old Step 0 (Local/Remote choice cards) is
  fully removed from the XAML — every "+"-menu entry point now resolves Local vs. Remote itself
  before reaching Step 1, so that screen had become unreachable, dead UI.
- **Step machine renumbered and now branches by flow**: 1 (Connect, unchanged) → 2 (World Source
  choice, install-wizard only) → 3 (Clone Source or Install, branches on the World Source choice) →
  4 (Settings, was "Step 2") → 5 (Confirm, was "Step 3"). Connect to Local/Remote Server skips
  straight from 1 to 4, exactly matching its pre-this-version behavior — nothing changed for that
  flow. `AdvanceWizardStep`/`GoBackWizardStep` now switch on the current step number and
  `IsNewServerSetupFlow`/`NewServerWorldSource` instead of blindly incrementing/decrementing.
- **New Step 2: World Source choice** — three cards (Clone an Existing Server / Set Up a New World /
  Import a World), matching the same card-choice visual pattern the old Step 0 used.
- **New Step 3, Clone branch**: a dropdown of already-saved profiles (excluding ones already open in
  a tab, same filter the "+" menu's own "Connect to {profile}" list uses) as the clone source, reusing
  `CloneWorldPortOffsetOptions`/`CloneWorldPortOffset` already added to Fleet's own Clone World card
  this session. New `CloneIntoNewServerAsync` calls the existing `CloneWorldAsync` API method with
  the *source* profile (not `SelectedProfile`, which is this in-progress, not-yet-saved profile) and
  `CredentialStore.TryLoad(sourceProfile.Id)` for its token — both already general enough to support
  this without any backend change. On success, jumps straight to Confirm (Settings/MODs don't apply
  to an already-fully-configured clone).
- **New Step 3, Install branch**: reuses `UpdatePalworldServerCommand` unchanged (the same SteamCMD
  install/validate flow Update Center already exposes) — it already bootstraps a fresh, nonexistent
  `ServerRoot`, no new backend needed. Below it, a **read-only** embed of the Server Setup page's own
  environment checklist (`EnvironmentItems`), auto-loaded when this step is reached. Read-only
  deliberately: several rows' actions navigate to other pages (Configuration/UE4SS/Update Center),
  which the wizard's full-screen overlay hides while `IsCreatingNewProfile` is true — those stay
  reachable from the real Server Setup page after finishing setup.
  - **Real bug found and fixed along the way**: `RefreshEnvironmentAsync` had a hard
    `if (SelectedProfile is null) return;` — since `SelectedProfile` is null for the *entire*
    wizard by definition (`IsCreatingNewProfile => SelectedProfile is null`), the checklist could
    never have loaded here at all. Switched to the same `BuildProfileFromEditor(SelectedProfile?.Id)`
    pattern `UpdatePalworldServerAsync`/`CheckSetupPortAsync` already use.
  - Import a World's own card shows an honest interim message ("not yet available inline here...")
    rather than a half-built import flow — `HeadlessWorldTransactionService.ApplyCoreAsync` hard-requires
    an already-active world to replace (a real architectural mismatch with a brand-new install that
    has none yet), confirmed via direct investigation; a real fix needs a new, simpler backend path
    that skips the swap/rollback machinery entirely, scoped as a separate future version.
- **Settings step (Step 4) gained a starter preset picker** ("choose one of the preset settings like
  vanilla or quality of life"): a dropdown of `PalworldConfigPresets` (Official/Balanced/Relaxed/
  custom, already built for the Configuration page) plus a new `ApplyStarterPresetCommand` that
  chains `LoadPalworldConfigurationAsync` → `ApplySelectedConfigurationPreset` → `SavePalworldConfigurationAsync`
  in one action — the same three-button sequence the Configuration page already does manually, just
  orchestrated here since the wizard only needs "apply this preset to the server I just created."
  No new backend; both load/save methods already used `BuildProfileFromEditor(SelectedProfile?.Id)`.
- **Port selection ("choose a new port")** was already covered by Step 4's existing `SetupGamePort`/
  `SetupRestPort` fields with live conflict detection (`CheckSetupPortAsync`, backed by
  `/api/v1/diagnostics/port-check`) — no new work needed, just kept in the renumbered step order.
- **MODs step**: not built this version. Scoped as a separate future version (embedding the existing
  MOD Library Workshop-scan machinery as a wizard step) rather than rushed in alongside everything
  else above.

## New automated test

`scripts/Test-v0.7.81.0-RouteSmoke.ps1` — live HTTP coverage against a genuinely fresh,
empty `ServerRoot` (no pre-existing Palworld install, matching what "Set Up a New World" actually
targets), following the same isolated-sidecar pattern as `Test-v0.7.12.0/15.0/64.0-RouteSmoke.ps1`.
Covers: Connect (`/healthz`), live port-conflict detection (both an occupied and a free port),
Install's status route on an honestly-empty root, Create Default Settings on that fresh root, the
Load→apply→Save starter-preset chain (verified a mutated `DayTimeSpeedRate` value survives a
save+reload), and Clone (verified files copied and the cloned `PublicPort` correctly offset from the
source's). Deliberately does **not** run a real SteamCMD install (multi-GB download, too slow/heavy
for a repeatable test) — a minimal stand-in `DefaultPalWorldSettings.ini` fixture is created instead,
matching the same "minimal realistic fixture over a full real install" pattern
`Test-v0.7.64.0-RouteSmoke.ps1`'s own fixture already uses for its own scenario.

Found and fixed two real route-name mistakes while first running this test against the live
service: `GET /server/distribution/status` doesn't exist (the real route is `/server/distribution`
with no `/status` suffix), and `CreateDefault` genuinely requires `ServerRoot/DefaultPalWorldSettings.ini`
to already exist (confirming the Install-before-Settings step order in the wizard is not just a nice
default, it's load-bearing).
