# v0.7.76.0 — Base/Guild Right-Click Workflow

## What this ships

The deferred half of the previous version's request: right-click convenience for the Bases and
Guilds pages, matching the workflow shape asked for directly — pick a target from a populated
dropdown, review real findings, a mandatory safety backup, then a confirm button (this app's
existing "I'm sure" checkbox pattern, expressed as an explicit confirm dialog here instead of an
inline checkbox, since a right-click quick action has no persistent in-page card to hold one).

**Deliberately reuses 100% existing, already-shipped backend** — `HeadlessBaseOwnershipService`
(Transfer, Recovery/wipe) and `HeadlessGuildOwnershipService` (Claim, Transfer Leadership, Add
Player, Remove Broken Member) were already real, working, Preview → Safety Backup → Apply
operations before this version, reachable only through the in-page "Base Ownership Transfer,"
"Base Recovery," and "Guild Ownership Operations" cards with hand-typed 32-hex IDs. No new
server-side mutation code was written this version — only new Desktop-side orchestration calling
the same, already-verified API endpoints.

## New Desktop pieces

- `SelectGuildDialog` — a populated dropdown of real guilds (mirrors v0.7.75.0's `SelectPlayerDialog`
  exactly), used for "Transfer base to guild."
- `ConfirmOperationDialog` — one reusable findings-list confirm dialog (title, real server-reported
  findings, safety-backup notice, Cancel/Confirm with the confirm button's label and danger-styling
  set per call site) instead of building near-duplicate dialogs per operation. Used by all four new
  flows below.
- `MainWindowViewModel` gained parallel Preview/Apply method pairs
  (`PreviewTransferBaseAsync`/`ApplyTransferBaseAsync`, `PreviewWipeBaseAsync`/`ApplyWipeBaseAsync`,
  `PreviewGuildOperationForRowAsync`/`ApplyGuildOperationForRowAsync`) that call the exact same
  `_api.PreviewBaseOwnershipTransferAsync`/`ApplyBaseOwnershipTransferAsync`/etc. the in-page cards
  already use. Deliberately parallel rather than reusing the cards' own bound properties (e.g.
  `BaseTransferTargetGuildId`) — that would couple this flow's state to whatever the user happens to
  have typed into the card at the time. Each writes its result into the *same* status-text
  properties those cards already display (`BaseTransferStatusText`, `BaseRecoveryStatusText`,
  `GuildOperationStatusText`), so both entry points stay in sync regardless of which one ran.

## Right-click menus

- **Bases**: "Copy Base Info" (full details to clipboard — ID, guild, leader, health, evidence;
  the existing "Copy Base ID" button on the details card is unchanged and still copies just the
  ID), "Transfer to Guild…", "Wipe Base Completely…".
- **Guilds**: "Transfer Leadership To…", "Add Player…", "Remove Broken Member…", "Claim Orphaned
  Guild…" — all four operation types the existing card's own dropdown already supports, each
  driving the same real `PreviewGuildOwnershipAsync`/`ApplyGuildOwnershipAsync` calls.

Guild operations' player picker offers every player currently loaded into `FilteredPlayerRecords`
(populated once the Players page has been visited this session) rather than trying to
client-side-filter which players make sense for which operation (e.g. "only players not already a
member" for Add Player, "only members with no save file" for Remove Broken Member) — the backend's
own `PreviewAsync` already validates this and returns a clear, real finding/blocker if the choice
doesn't make sense (e.g. "Destination already belongs to guild X"), so client-side pre-filtering
would just be duplicating validation the server already does authoritatively.

## Verification

`dotnet build src/MystTiq.Desktop/MystTiq.Desktop.csproj` — clean, 0 warnings/errors. No new
server-side mutation logic was written this version (see above) — the underlying Base/Guild
operations were already live-verified against real save data in this project's earlier history. No
live GUI click-testing was possible in this environment (no GUI-automation capability, a disclosed
limitation consistent with the rest of this project) — code-reviewed against the exact same dialog
shapes and ViewModel-method pattern already proven working for Player Delete/Copy (v0.7.75.0).
