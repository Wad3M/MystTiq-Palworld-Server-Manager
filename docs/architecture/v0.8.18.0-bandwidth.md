# v0.8.18.0 — Bandwidth

This is the second version of the optimisation line ("process priority/eco mode, bandwidth, and a HOST tab"). It adds
per-server bandwidth limits to the HOST tab.

## What the game actually does (read from its pak)

A Palworld server's network limits are Unreal engine settings in the server's own `Engine.ini`
(`Pal/Saved/Config/WindowsServer/` or `LinuxServer/`), section `[/Script/OnlineSubsystemUtils.IpNetDriver]`:

| Key | Meaning | Unit |
|---|---|---|
| `MaxClientRate`, `MaxInternetClientRate` | the most the server sends to one player | bytes per second |
| `NetServerMaxTickRate` | how often the server sends network updates | per second |

What the game ships, read (read-only) from the installed game's pak, `Pal-WindowsServer.pak` (game v1.0.4), with
MystTiq's own pak reader:

| Source | Per player | Updates per second |
|---|---|---|
| Unreal engine `BaseEngine.ini` | 100000 B/s (0.8 Mbit/s) | 30 |
| **Palworld `Pal/Config/DefaultEngine.ini`** | **8000000 B/s (64 Mbit/s)** | **60** |
| **Palworld `Pal/Config/LinuxServer/LinuxServerEngine.ini`** | (not changed) | **20** |

So:
- a Windows server runs at 60 updates per second and a Linux server at 20;
- both allow 64 Mbit/s per player.

Hosting guides widely recommend `MaxClientRate=100000`. That **lowers** the per-player limit to about 0.8 Mbit/s,
about one eightieth of what the game ships with.

The `Engine.ini` MystTiq finds on a real server is the one the engine writes itself: `[Core.System]` content paths.
The engine rewrites that file from memory when it exits. **A change made while the server runs is lost at its next
exit.**

## Design

- **The policy** (`ServerNetworkPolicy`, Core) is kept per server in its runtime folder (`network-policy.json`):
  - **the game's own limits** (the default): MystTiq writes nothing;
  - or **my limits**: 0.25–100 Mbit/s per player and 10–120 network updates per second;
  - optionally, the connection's upload speed, for the estimate.
- **Writing** (`EngineNetworkSettings.ApplyBeforeStart`, Core):
  - MystTiq's three keys are set, or removed for game defaults, in the network section, matched in any case;
  - every other line, section and line ending is kept;
  - a second copy of the section loses its old keys, so one value of each is left;
  - the first time MystTiq changes the file, the original is kept once as `Engine.ini.mysttiq-original`;
  - nothing is written when the file already matches;
  - a failed write is reported and never blocks the start.
- **When.** It runs inside both lifecycles' own start (Windows and Linux), just before the process is launched. So it
  covers **every start path**: the Desktop, service mode's supervisor, crash recovery, the Discord bot and the CLI. It
  also puts the limits back if the engine dropped them on exit.
  - Saving while the server is **stopped** writes at once.
  - Saving while it **runs** waits for the next start, and the card says a restart is needed.
- **The estimate** (`BandwidthPlanner`):
  - worst case = the maximum player count (from PalWorldSettings.ini) × the per-player limit;
  - above 80 % of the given upload it warns;
  - it suggests the largest quarter-Mbit/s limit that fits, and "Use It" fills it in.

## The card

On the HOST tab, after the priority card, titled **Bandwidth limits**. It shows:
- the game's own limits for this platform;
- what `Engine.ini` sets now, and whether those are MystTiq's limits or set outside MystTiq;
- the mode and limits, and the upload;
- the worst case, the warning and the suggestion;
- a note on the update rate;
- a restart note when one is needed.

As with the priority card, everyone reads it and only Admin and above change it. Unsaved edits are not overwritten by
the 5-second refresh.

Routes, scoped per server:
- `GET /network/policy`: Viewer;
- `PUT /network/policy`: Admin; out of range gives 400;
- the `/host` snapshot carries the same data.

## Verification

- **Logic harness**, two scenarios:
  - **The text edit:** the engine's lines kept; CRLF and LF kept; a lower-case section from a guide read and reused;
    duplicate sections left with one value; an empty file; idempotent.
  - **The rules:** validation, the real defaults, the planner, write-before-start once with the original kept, and a
    damaged policy file.
- **Windows route smoke** (8 checks, service mode, stand-in server). The restarts come from the supervisor:
  - the defaults are shown and nothing is written;
  - saving while running waits and says so;
  - a restart writes the limits and keeps `[Core.System]`;
  - **after the engine drops them, the next start puts them back**;
  - `/host` carries the data;
  - game defaults written at once while stopped, removing only the three keys;
  - out of range gives 400;
  - each save is logged.
- **Linux, isolated on the VM** (8 checks). MystTiq itself starts and stops the stand-in through a real
  `PalServer.sh`:
  - the Linux defaults are shown (20 updates per second);
  - a save while stopped is written to `LinuxServer/Engine.ini` at once;
  - a save while running waits;
  - the Linux start path writes the new limits and logs them.
- **ArtworkHarness: 502 checks.** The card's texts, fields, estimate, warning, suggestion and "Use It"; unsaved edits
  kept; validation before sending; the role table entry; width at 950x650. Render: `host-bandwidth`.

## Not done

- **No operating-system traffic shaping.** Windows QoS policies and Linux `tc` need admin rights on the machine, and
  would cap the whole server instead of each player.
- **The server's own traffic is not measured apart from the machine's.** Neither Windows nor Linux counts UDP traffic
  per process without tracing; the Network card shows each adapter.
- The client-side speed setting (`ConfiguredInternetSpeed`) is not written; it belongs to the players' games.
