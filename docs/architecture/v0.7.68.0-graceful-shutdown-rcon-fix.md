# v0.7.68.0 — Graceful Shutdown: RCON-First Fix

## Goal

The roadmap audit that kicked off this session's v0.7.64.0 work flagged an item nobody had ever
chased down: *"graceful shutdown consistently fell back to forced termination — observed 4/4 times
this session, never chased down (v0.6.10.0's own session notes)."* With the RCON wire-protocol
testing technique already built for this session's other fixes, this was tractable to actually
diagnose rather than leave flagged.

## Root cause

`WindowsServerLifecycleService.StopAsync` asks PalServer to exit gracefully via
`Process.CloseMainWindow()` — sending a `WM_CLOSE` message to the process's main window. This
silently does nothing whenever the target process has no window `.NET` considers "the main window":
internally, `Process.MainWindowHandle` (which `CloseMainWindow()` depends on) only resolves a handle
for a window that is currently **visible** — a real `HWND` existing isn't enough if Windows'
`IsWindowVisible` reports false for it, .NET's own window-enumeration logic filters it out entirely.

`WindowsServerLifecycleService` has its own `ApplyPostLaunchWindowPolicyAsync`, running on a 500ms
loop for `startupTimeout + 30s` after every single launch, which explicitly calls
`ShowWindow(handle, SW_HIDE)` on every visible top-level window belonging to a managed PalServer
process — deliberate, documented behavior ("MystTiq is headless-first"). By the time an admin (or
automation) actually calls Stop, minutes or hours after launch, that window has long since been
hidden by MystTiq's own policy. `CloseMainWindow()` then has no visible window to find, does nothing,
and `StopAsync` always falls through to the force-kill escalation after waiting out the full
`gracefulTimeout` for nothing. MystTiq's own "stay headless" feature was silently defeating its own
graceful-shutdown feature, on effectively every real stop — exactly matching the 4/4 observed rate
from v0.6.10.0's session, which was never diagnosed because that session had no reason to inspect the
window-hiding policy while investigating shutdown timing.

## The fix

Palworld's dedicated server RCON protocol supports a native `Shutdown <seconds> <message>` admin
command — the game's own real graceful-exit path (broadcasts the message, saves the world, then
exits cleanly), with no dependency on window visibility, Win32 messages, or process signals at all.
Both `WindowsServerLifecycleService.StopAsync` and `LinuxServerLifecycleService.StopAsync` now try
`rcon.ExecuteAsync("Shutdown 1 MystTiq requested a graceful shutdown.")` first, when RCON is actually
enabled and a password is configured (read the same way `PalworldRconService` already does
everywhere else in this codebase). This is purely additive: every existing step after it —
`CloseMainWindow()` then force-kill on Windows, `SIGTERM` then `SIGKILL` on Linux — still runs
completely unchanged regardless of whether the RCON attempt succeeds, so this can only improve the
outcome (a real chance at a clean, saved exit when RCON is configured) and can never regress it (the
exact same safety net as before still catches every failure case).

Linux's `SIGTERM` was not found to be broken the way `CloseMainWindow()` is confirmed broken on
Windows — this is a genuine reliability improvement there (RCON's native path saves the world before
exiting; a raw signal depends on the engine's own signal handler doing the same), not a bug fix.

## Verification

- `dotnet build` on `MystTiq.Core.csproj` and the full solution: clean, 0 warnings/errors.
- New `scripts\Testing\MystTiq.LogicHarness` scenarios (19/19 total, both new ones passing on first
  run): a minimal, real Source RCON protocol stub server (just enough of the wire format —
  authenticate, receive one `EXECCOMMAND`, respond) proves `PalworldRconService.ExecuteAsync` sends
  the *exact* `"Shutdown 1 MystTiq requested a graceful shutdown."` command text the fix uses, over
  the real wire protocol, and correctly surfaces both success (with the server's real response body)
  and a rejected-password failure. This exercises the actual risk surface of the change (does the
  RCON client correctly transmit this specific command and parse the response) without needing a
  real PalServer process to be "found" by the lifecycle service's own OS-level process detection.
- **Update, same session**: end-to-end confirmed live against a real PalServer. Cloned the real
  production install (robocopy, ~11 GB, never touching the live `ServerRoot`/process — the same
  isolation technique already used for v0.7.65.0's Linux verification) to
  `C:\GameServers\_TestClones\PalServer-diag-v0.7.70`, offset its game/RCON/REST ports and gave it a
  throwaway `AdminPassword` distinct from production's real one, and ran it under an isolated
  `mysttiq-server api-run` instance on a throwaway API port. Ran a direct A/B comparison on the exact
  same real, real-modded PalServer binary:
  - **RCON enabled**: `POST /server/stop` returned in **~4 seconds**, `forced: false`,
    `"PalServer stopped cleanly."`
  - **RCON disabled** (`RCONEnabled=False` in the clone's ini, otherwise identical): the *same* Stop
    call took **~31 seconds** and returned `forced: true`,
    `"PalServer required forced termination after the graceful shutdown timeout."` — the exact
    pre-fix behavior, reproduced on demand by simply removing the one thing this fix added.

  This is a clean, controlled, conclusive confirmation: RCON's `Shutdown` command is genuinely what
  turns a ~31-second forced-kill into a ~4-second clean exit on this real server. Five additional
  start/stop cycles with RCON enabled all landed in the same fast, clean pattern. The clone and its
  isolated `mysttiq-server` instance were fully torn down afterward
  (`taskkill`, `rm -rf` on the ~11 GB clone); the real production install and its `PalWorldSettings.ini`
  (including its real `AdminPassword`) were confirmed byte-for-byte unchanged throughout.

## Known gaps (disclosed)

- This fix does not change `HeadlessAutomationService`'s own separate warning-countdown-then-stop
  flow's *broadcast* mechanism (still `Broadcast <message>` at intervals, unchanged) — only the
  underlying `StopAsync` call it eventually makes benefits from this fix, automatically, with no
  changes needed in the automation service itself.
- The A/B test above was run on Windows only (the platform where `CloseMainWindow` was confirmed
  broken); the equivalent Linux `SIGTERM`-vs-RCON comparison was not separately re-run this pass,
  since Linux's fallback was never confirmed broken in the first place (see "The fix" above).
