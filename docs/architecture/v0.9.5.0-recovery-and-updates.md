# v0.9.5.0 — recovery and updates

Everything here was found on 2026-09-28, during a live join to the clone server, and fixed in this version.

## Servers started each other

**What happened.** The machine had five server profiles. Whenever a PalServer process started or exited — the clone's,
or one MystTiq had just stopped — the other profiles logged "server crashed, restarting" within a second and started
their own servers. That included one stopped on purpose a minute earlier. Two of those could never become ready, kept
retrying (one used a full CPU core), and a player on the same machine kept timing out.

**Why.** `WindowsServerSessionInspector` read each process's path through `Process.MainModule`, which needs full access
and fails while a process is starting or exiting; the path was then empty. `FindManagedServerProcesses` counted a
process with an empty path as the profile's own (`return true`). So for a moment every profile saw that process as its
running server and recorded "Running" (overwriting a deliberate stop). A poll later the process was readable (not
theirs) or gone, and each profile concluded its server had crashed, then "recovered" it.

**Fix.**

- Paths are read with `QueryFullProcessImageName`, which needs only limited query access and works for the whole life
  of a process; `MainModule` is only a fallback.
- A process whose path still cannot be read belongs to a server only when that server started it: its launcher
  process, or the game process it last recorded. Linux applies the same rule to an unreadable `/proc/<pid>/exe`.

**Evidence.** The logic harness drives a real `WindowsServerLifecycleService` with a fake inspector: another server's
process with an empty path leaves a stopped server stopped, and its exit is not a crash; the server's own recorded
process still counts. Live under the new build, stopping and starting the real clone server started no other server
and logged no crash. The new fleet smoke (two stand-in servers in one service) passes, but it passes on the old build
too — the stand-in's path is readable at once — so it is a guard, not the proof.

## Readiness waited for the wrong port

Readiness waited for PalWorldSettings.ini's `PublicPort`. That setting only advertises a port; PalServer binds the
port its `-port=` argument names, or 8211. Two profiles were launched with `-port=8211` while their ini said 8219 and
8213, so they could never be ready. `ServerGamePort.Expected` now returns the `-port=` value (8211 without one), and
PublicPort only when the arguments are unusable (a bad value, or two different ports).

## The update check could never report an update

The Update Center asked the Steam Web API's `ISteamApps/UpToDateCheck` whether the installed build was current. That
endpoint compares against a minimum version the developer sets (1000 for this app), not the build, so any build above
it was "up to date". The server stayed on build 25080279 while Steam published 25247047, and a v1.0.5 game could not
join the v1.0.4 server.

The latest build now comes from SteamCMD's app info for the public branch (`+app_info_print 2394010`), cached for 15
minutes per SteamCMD install, because SteamCMD takes 10–30 seconds to answer. The Doctor uses only the cached value
(`PeekPublicBuild`) and starts a refresh in the background, so its report never waits on Steam.

## PalDefender after a game update

After the game update, PalDefender v1.8.3 logged that it "hasn't yet updated to the latest version of the game", and
the server stopped about 40 seconds after each player joined, with no crash report and nothing in the Windows event
log. PalDefender v1.9.2 fixed it. The Update Center now has a PalDefender row (the DLL's product version against the
latest GitHub release), and the Doctor warns while PalDefender's newest session log contains that warning. Updating
PalDefender stays a manual step.

## A refused manifest stopped every update

Updating the clone failed twice with exit code 8. SteamCMD's content log said "Failed to get manifest request code,
'Access Denied'" for the installed build's manifest, which SteamCMD downloads to work out what changed. With the app
manifest moved aside, SteamCMD treated the folder as a fresh install, checked every file against the new build and
replaced only the 103 that differed. MystTiq now does that itself when it sees that failure: it keeps the old manifest
(`appmanifest_2394010.acf.before-update-<time>`), retries with validation, and puts the manifest back if the retry
fails too. Every failed update names SteamCMD's reason, from its output and the lines it added to its content log.

## Upgrade and recovery

`scripts/Test-v0.9.5.0-Upgrade.ps1` runs on isolated data with the stand-in server:

1. The accepted baseline (v0.8.25.0) writes its configuration and is given process priority, bandwidth, teleport
   points, the whitelist, an automation rule, a kit, alert rules and a backup through its API.
2. This version starts on the same data and returns every value the baseline returned (new fields may be added; the
   bandwidth policy is compared as saved, since starting the server applies it to Engine.ini).
3. The baseline's backup is listed and verifies; a world changed after it is restored byte for byte.
4. The baseline starts again on the data this version used and still reads every value.
5. This version writes a new configuration in an empty folder, starts, and creates the server settings from the game's
   defaults.

Not covered yet: accounts (the test runs without sign-in).
