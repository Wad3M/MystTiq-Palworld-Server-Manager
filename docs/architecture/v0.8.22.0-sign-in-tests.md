# v0.8.22.0 — The Remaining Sign-In Tests: Owner, the Ribbon, and the Desktop on Linux

v0.8.15.0 signed the real Desktop in to a real remote MystTiq (an isolated instance on the Linux test VM) as Viewer,
Operator and Admin. Three things were still untested:
- an **Owner** account;
- the v0.8.19.0 **Ribbon gating** in a real signed-in window;
- the **Desktop itself running on Linux**.

`scripts/Test-v0.8.22.0-RemoteSignIn.ps1` covers all three. It uses the same isolated instance, the same
setup/teardown scripts and the same harness (`scripts/Testing/MystTiq.RemoteSignInHarness`) as v0.8.15.0.

## Four roles

The instance gets a fourth account, `rs-owner` (role 3). As before, each account's password is generated for the run,
and the account is deleted with the instance.

For Owner, the harness expects:
- every card shown and usable, including Create Principal, User Accounts and Clone World;
- the role notice hidden.

## The Ribbon gating in the signed-in window

For each role, the harness goes through **every page** and checks every Ribbon button whose route needs a role:
- the button is marked allowed exactly when the role is high enough;
- when it is not allowed:
  - its tooltip names the role it needs;
  - the button drawn in the window is disabled.

It also checks the page buttons bound to the role (`CanOperate`, `CanManageAdmin`, `CanManagePrincipals`: save-now,
kick/ban/teleport/RCON, and the user and principal cards).

**The server agrees.** One route behind each kind of gated button, all harmless on this empty instance:

| Route | Needs | Viewer | Operator | Admin | Owner |
|---|---|---|---|---|---|
| Mark all notifications read | Operator | 403 | 200 | 200 | 200 |
| Save the priority policy, unchanged | Admin | 403 | 403 | 200 | 200 |
| List user accounts | Owner | 403 | 403 | 403 | 200 |

## The Desktop on Linux

The harness is published for `linux-x64` (self-contained) and copied into the instance's `/tmp` folder on the VM. It
runs there headless and signs in over TLS, with certificate pinning, to the instance on the VM's own address, running
every check above.
- **Home folder.** It runs with `HOME`, `XDG_CONFIG_HOME` and `XDG_DATA_HOME` pointing into that `/tmp` folder, so
  nothing lands in the VM user's real settings.
- **Settings check.** The script lists the VM user's MystTiq settings folders before and after the run and requires
  them to be identical.
- **Renders.** The Linux run's screenshots are copied back as `linux-*.png`.

### Found and fixed: empty boxes instead of icons

The first Linux run passed every check, but its renders showed **empty boxes** where these icons should be:
- the tab's close ×;
- the settings gear;
- minimize, maximize and close.

They were glyphs of the **Segoe Fluent Icons** font. Linux does not have that font, and neither does Windows 10, which
ships Segoe MDL2 Assets instead.

The fix: the five icons are now drawn (`PathIcon` with vector geometry), and the maximize/restore swap sets the
geometry. They take the button's text colour, as the glyphs did, so hover and themes are unchanged.

The harness checks that each of those five buttons draws its icon and that no text in the window uses the icon font.
The gate checks that `MainWindow.axaml` no longer names that font.

## Verification

- **Windows and Linux Desktop: 38/38 checks each** against the same instance:
  - a wrong pin is refused;
  - the window controls draw their icons;
  - per role (9 checks each):
    - a wrong password is refused, and the real sign-in works;
    - the cards and the role notice;
    - the Ribbon on every page, and the role-bound page buttons;
    - both server-agreement checks;
    - sign-out.
- The VM user's settings folders were unchanged, and the instance was torn down.
- The renders were inspected on both platforms, before and after the icon fix.
- The gate runs this test in `-RunBuild` when the VM answers, in place of the v0.8.15.0 one (SKIP otherwise).
