# v0.7.65.0 — Linux Console Capture Fix

## Goal

Close the gap surfaced (but not fixed) during v0.7.64.0's log-rotation work, at the user's direct
follow-up request: `LinuxServerLifecycleService` was believed to have no PalServer stdout/stderr
console capture at all, unlike `WindowsServerLifecycleService`.

## What was actually wrong

Re-tracing it more carefully than the v0.7.64.0 pass did turned up a more precise diagnosis than
"missing entirely": Linux **was** capturing PalServer's raw stdout/stderr all along, via the detached
launch script's own shell redirect —

```
exec /usr/bin/setsid -f <PalServer.sh args...> >> <ManagerRuntimeRoot>/palserver-console.log 2>&1 < /dev/null
```

— but into `ManagerRuntimeRoot/palserver-console.log`, a location nothing on the read side ever
looked at:

- `HeadlessMonitoringService.ResolveActiveLogPath` (the Live Console page's log source) only checks
  `LogsRoot/MystTiq-PalServer-Console.log`, then `LogsRoot/Pal.log`, then any `*.log` directly under
  `LogsRoot` — never `ManagerRuntimeRoot`.
- `HeadlessMonitoringService`'s Doctor/monitoring log-source list has the identical hardcoded
  `LogsRoot/MystTiq-PalServer-Console.log` path.
- `LogsRoot` (`ServerRoot/Pal/Saved/Logs`) and `ManagerRuntimeRoot` (e.g. `/opt/mysttiq/runtime`) are
  two entirely different directories on a real install.

So the capture existed and worked, but its output was invisible everywhere the app actually reads
console output from. `grep`-ing the codebase for the exact filename `MystTiq-PalServer-Console.log`
(what v0.7.64.0's audit should have done, and what surfaced this) versus "any console capture at all"
(what it actually did) would have caught this distinction immediately.

## The fix

`LinuxServerLifecycleService.LaunchDetached` now:

1. Resolves the target log directory as `paths.LogsRoot`, falling back to
   `ManagerRuntimeRoot/logs` on a `CreateDirectory` failure — the exact same
   try/create/fallback shape `WindowsServerLifecycleService.StartConsoleCapture` already uses.
2. Targets `MystTiq-PalServer-Console.log` inside that directory — the identical filename Windows
   captures into, so every existing read-side consumer (Live Console, `HeadlessMonitoringService`,
   Doctor) picks it up with zero changes on the read side.
3. Immediately before the detached process opens its own long-lived shell redirect handle, calls
   `ConsoleLogRotation.RotateIfNeeded` (the same helper v0.7.64.0 added for the Windows writers) and
   writes a MystTiq-owned `===== MystTiq PalServer detached console session starting ... =====`
   marker line, matching the banner line Windows writes at the same point.

### Why rotation only works here, and only here, on this platform

Windows' two writers (`HeadlessConsoleLogWriter`, `WindowsServerLifecycleService`'s own stream
capture) are both long-lived C# code running inside the MystTiq process itself, calling
`File.AppendAllText` (which opens, writes, and closes the file) on every single line — so calling
`ConsoleLogRotation.RotateIfNeeded` immediately before *each* append is safe and effective there.

Linux's `setsid -f ... >> file` is architecturally different: bash opens the file's handle **once**,
when the detached process starts, and holds it open for the process's *entire* lifetime — potentially
hours or days. Renaming the file out from under that handle mid-session (the way Windows rotates)
would not stop the growth; Unix file-descriptor semantics mean the shell keeps writing to the
now-renamed `.1` generation under its stale handle forever, and the live-named file would just sit
empty. The **only** point in this architecture where a brand-new file handle is about to be opened is
right before `LaunchDetached` spawns the process — which is exactly where the rotation call was
placed. This means rotation on Linux only takes effect at server (re)start boundaries, not
continuously mid-session the way it does on Windows; a single very long-running session without a
restart could still grow past 25 MB. That's a real, disclosed, accepted trade-off of this platform's
detached-process design, not an oversight.

## Known gaps (disclosed)

- Rotation on Linux only takes effect at server-start boundaries, not continuously — a disclosed,
  accepted trade-off of the detached-process architecture, not a bug (see above).
- Unlike Windows, the Linux capture is a single merged, untagged stdout+stderr stream (no `[OUT]`/
  `[ERR]` per-line prefixing) — deliberately not attempted this pass, since adding per-line tagging
  would mean piping the shell redirect through `sed`/`awk`, a materially higher-risk change. A
  lower-risk future improvement, not attempted here.
