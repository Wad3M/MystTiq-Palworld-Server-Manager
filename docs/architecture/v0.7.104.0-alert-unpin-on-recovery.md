# v0.7.104.0 — Alert Center: Unpinning a Pinned Alert on Recovery

## Context

A named gap carried since v0.7.102.0 ("Alert episodes" — `docs/architecture/v0.7.102.0-deficiency-fixes.md`,
"Deliberately not done"): a pinned Critical alert stayed pinned forever, even after its own "Resolved: ..."
notice had already been sent. Worse, switching the rule off mid-episode (which sends no notice at all, by
design — `AlertEpisodeTracker.Close`) left the pinned alert stuck with no follow-up whatsoever. This version
closes both.

## What changed

- `AlertEpisodeTracker` now records which notification an open alert created
  (`SetAlertNotificationId`, `EpisodeState.AlertNotificationId`, persisted in `alerts/episodes.json` like the
  rest of the episode state) and hands that id back to the caller when the episode ends:
  - `Observe(...)` gained an `out string? recoveredNotificationId` overload (the original 4-argument signature
    is unchanged and now just calls the new one, discarding the id, so every existing call site and harness
    scenario compiles and behaves exactly as before).
  - `Close(ruleKey)` now returns the id (`string?`) instead of `void`, for the same reason: switching a rule
    off is the other way an episode ends.
- `HeadlessNotificationService.Create(...)` gained an `out string id` overload so a caller can learn the new
  notification's id without a second lookup (the original signature is unchanged and calls the new one).
- `HeadlessAlertCenterService`:
  - `Track(...)`: on `EpisodeAction.Alert`, records the new notification's id against the rule
    (`episodes.SetAlertNotificationId`). On `EpisodeAction.Recovered`, still sends the "Resolved: ..." notice,
    then unpins the id `Observe` handed back.
  - Every `else episodes.Close("...")` branch (one per rule, run when that rule is switched off) now unpins
    whatever id `Close` hands back too — no "Resolved" notice is invented for this path; only the pin clears,
    so the alert stays in the notification history unpinned rather than as a permanent pinned artifact.
  - A private `Unpin(string? notificationId)` helper: a no-op when there was nothing to unpin (`null`), and
    swallows `KeyNotFoundException` from `SetPinned` — the notification may already have been dismissed by the
    time the episode ends, and that must not fail the evaluation tick.

## Deliberately not done

- No reminder re-alerts for a long-running Critical (the recovery notice, or now the unpin, remains the only
  follow-up).
- Crash alerts (`CrashAlertText`/`CrashAlertObserver`) are untouched: they are not episode-tracked (a crash is
  a point-in-time event, not an ongoing condition monitored by `AlertEpisodeTracker`), and the pinned
  "server is DOWN, automatic recovery gave up" notice has no corresponding "back up" signal in the codebase
  today — the crash-recovery loop (`HeadlessSupervisor.RunCrashRecoveryLoopAsync`) returns entirely once it
  gives up, so there is nothing that would ever observe the server coming back up to unpin it. Out of scope for
  this version.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness, 2 new scenarios: `AlertEpisodeTracker` hands back the correct notification id from `Observe`
  on recovery and `null` everywhere else (still open, already recovered, never alerted, closed before an id was
  ever recorded), and `Close` hands back the id for a pinned-and-switched-off rule while returning `null` for
  an already-closed or never-alerted one; `HeadlessNotificationService.Create`'s new id overload, unpinning by
  id, and unpinning an already-unpinned or already-dismissed notification (the latter throws
  `KeyNotFoundException`, which the Alert Center is expected to catch).
- New live smoke `Test-v0.7.104.0-RouteSmoke.ps1` against two isolated sidecars (a real low-disk Critical
  forced via a 99% threshold, `MYSTTIQ_ALERT_EVAL_SECONDS=2`): the pinned alert unpins itself once the
  condition clears and the Resolved notice arrives, and it stays unpinned and still on record afterward; on a
  second fixture, switching the rule off while the alert is still pinned unpins it too, with no Resolved notice
  fabricated for that path. Both pass under strict mode and on the final published binary.
