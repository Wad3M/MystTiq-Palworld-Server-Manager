# v0.7.74.0 — Close-Dialog Exit Shortcuts & Tab-Restore Exception Isolation

Direct live report from actually clicking through the v0.7.73.0 build, plus a real screenshot-driven
tab-strip color question. Three things were checked; two were real, fixable gaps in this codebase and
are fixed here, one was already fixed by other work already landed in the source tree.

## 1. Close-confirm dialog only offered Cancel/Minimize — fixed

`ConfirmMinimizeToTrayDialog` (the "Server is running" dialog shown by the window's own close
button when something's running, and now also by "Exit GUI Only" as of v0.7.73.0) only ever offered
Cancel or Minimize to Tray, with a text hint pointing at the tray icon's own Safe Exit/Force Exit for
anyone who actually wanted to stop the server from there — an extra, avoidable round-trip reported
directly.

Fix: `SafeExit_OnClick`/`ForceExit_OnClick` in `App.axaml.cs` were split into public
`SafeExitAsync()`/`ForceExitAsync()` (the tray menu's own click handlers now just call these), and
the dialog gained two more buttons wired to two new `ConfirmMinimizeToTrayResult` values
(`SafeExit`/`ForceExit`), handled in `MainWindow_Closing` by calling the same public methods. Both
paths — tray menu and close dialog — now run through identical shutdown logic; nothing was
duplicated.

## 2. Tab-restore only reopened 1 of 3 saved tabs — fixed

Directly reported live: after relaunching, only the default local tab reopened, not the two other
tabs (a remote profile and a local clone) that were open before. Confirmed the saved session data
itself was intact — `%APPDATA%\MystTiq\open-tabs.json` had all three profile IDs, and
`connections.json` still had matching entries for all three. So the bug wasn't data loss.

Root cause: `MainWindowViewModel`'s startup continuation ran
`await InitializeLocalDashboardAsync(); await RestoreTabSessionAsync();` as one unguarded async
lambda. `InitializeLocalDashboardAsync` does local-installation discovery/bootstrap — logic that can
plausibly behave differently depending on exactly where the running executable and its sidecar
happen to sit (the user had, separately, tried running from a different install location than usual
while investigating another issue, which is a reasonable thing to suspect and was worth checking).
An unhandled exception anywhere inside it would silently abort the whole continuation *before
`RestoreTabSessionAsync` ever ran*, dropping every remembered tab beyond the first with no error
shown anywhere.

Fix: each phase now runs in its own `try`/`catch`, surfacing any failure to `StatusBarText` instead
of swallowing it silently and instead of letting one phase's failure take the other down with it.
This closes the bug class regardless of what specifically threw in any given environment — the real
defect was the missing isolation, not one specific exception.

**Answering the user's own diagnostic question directly**: no, the *tab session storage itself*
isn't tied to which copy of the exe is running (`%APPDATA%\MystTiq\open-tabs.json`/`connections.json`
are per-user-profile, not per-install-location) — that wasn't the mechanism. But the underlying
suspicion wasn't unreasonable: running from a different location absolutely could change what
`InitializeLocalDashboardAsync`'s discovery step finds or how it behaves, and because of the missing
exception isolation, a failure there really could cascade into "my other tabs didn't come back." The
real fix removes that cascade regardless of the specific trigger.

## 3. Per-tab title colors bleeding between tabs — already fixed, not by this version

The reported symptom (switching tabs, chrome staying tinted like the *previous* tab rather than the
newly active one) was checked directly against the live source tree. `TabSession.AccentBrush` is
computed per-tab from whichever theme resources are *currently globally applied*
(`Application.Current`'s live resources, rewritten by `ThemeApplier.Apply()` whenever the active tab
changes) — so every open tab's own color needs re-computing after any such global switch, not just
the newly active one's. That refresh (`RefreshTabAccentVisuals()` iterating every tab, not just
`ActiveTab`) was already present and already wired into every call site that applies a theme
(`ActiveTab`'s setter, `ApplyProfileTheme`, `SelectedProfile`'s setter) — evidently added by other
work already landed in this source tree since this session's own v0.7.73.0 checkpoint, alongside a
separate, related fix making each tab's own `AccentBrush` take precedence over the shared selected-
state style so every tab's border reflects its own identity color rather than a generic highlight.

Not re-implemented here since it was already correct in the tree this version builds from — the
user's screenshots were taken running the older, frozen v0.7.73.0 checkpoint build, which predates
that fix. Flagged here for the record rather than silently taking credit for someone else's landed
work; re-verify live with the current build once the app is open again.
