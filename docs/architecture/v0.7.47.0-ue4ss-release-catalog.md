# v0.7.47.0 — UE4SS Release Catalog

## Goal

Continue the roadmap after v0.7.46.0's live bug report. That checkpoint's own "Next steps" pointed
at Native Console Capture — this version investigates that first (see below), rules out every fast
option, and scopes the real fix as its own future project rather than attempting it here. It then
picks up the next item already in the roadmap: item 45, the UE4SS page's "Release source" dropdown,
which has been a client-side-only stub since it was first built.

## Console capture: investigated, not fixed here

Per direct instruction ("go ahead and start on the console-capture fix"), three candidate fixes
were tested **live, against an isolated robocopy of the user's real server** (never the live one),
before any code was written:

1. **`-ABSLOG="path"`** — a real, documented, standard Unreal Engine command-line flag that writes
   the engine's full log to a file, independent of console ownership. Added to the isolated
   server's launch arguments, launched, and polled for up to 4 minutes (past the point UE4SS
   finished loading all 6 of the user's real mods, confirmed via `UE4SS.log` reaching its
   steady-state size). No file was ever created. Palworld's build appears to have this Unreal
   subsystem compiled out, not just defaulted off — matching the independently-sourced research
   finding that Pocket Pair "ships the dedicated server binary without enabling Unreal's standard
   log output."
2. **Launching `PalServer-Win64-Shipping-Cmd.exe` directly**, bypassing the `PalServer.exe`
   wrapper MystTiq normally launches — the theory being that the grandchild allocates its own
   console specifically because it never inherits redirectable handles through the wrapper.
   Launched directly with the exact same `ProcessStartInfo` shape MystTiq's own
   `WindowsServerLifecycleService.StartAsync` uses (`RedirectStandardOutput`/`RedirectStandardError`
   = true, `CreateNoWindow` = true). Polled for 140+ seconds while `UE4SS.log` confirmed real,
   ongoing engine activity (hook registration, mod loading) — zero lines were captured via the
   redirected stdout the entire time. This is the more important negative result: it rules out
   "wrong process in the launch tree" as a fixable root cause. Palworld's engine appears to
   allocate and write to its own console object internally, regardless of which process launches
   it or how its stdio handles were set up beforehand.
3. **UE4SS's own Lua API** — confirmed via UE4SS's documentation (fetched directly, not assumed)
   that no hook exists for Unreal's own engine log output; only UE4SS's own mod-loading diagnostics
   are exposed to Lua. A native UE4SS extension could theoretically add one, but that's a much
   larger, separate undertaking than a Lua mod.
4. **Existing third-party tools**, investigated per direct instruction before proposing to build
   anything new. "PalServerLogger" (Nexus Mods) is a real, working solution — described as using a
   DLL proxy technique (`d3d9.dll`, the same category of proxy-DLL loading UE4SS's own loaders
   already use) to inject into the PalServer process and hook its console output, writing
   timestamped files to a `PalServerLogs` folder. Not safely integrable as-is: it requires
   PalDefender (a separate anti-cheat mod) already installed as its own proxy-loading base, and its
   license/redistribution terms could not be confirmed — Nexus Mods returned HTTP 403 to automated
   access, and no GitHub source or license file was found. Bundling an unverified-license binary
   that gets injected into the user's live game process is not something to do without the user
   explicitly choosing that specific tool and reading its terms themselves.

**Conclusion**: the real, working technique for this problem is native DLL proxy injection — the
same pattern UE4SS/PalDefender/PalServerLogger all independently converged on. The correct fix is
MystTiq's own small, first-party proxy DLL, not a bundled third party's. This is genuinely large:
it needs a C++ toolchain (this project is otherwise entirely .NET), real Win32 DLL-proxy/injection
code, a hook into Unreal's print/log function, and the same careful isolated-copy testing used to
rule out the three options above before it could ever touch a real server. Scoped in the roadmap as
its own future project (v0.7.49.0+) rather than rushed into this version.

## What shipped: UE4SS Release Catalog (item 45, listing half)

The UE4SS page's "Release source" dropdown (`Ue4ssForkOptions`: "Palworld Fork" / "Official
Upstream") has always been client-side-only, with a permanent `TextBlock` reading "Release catalog
and install/rollback controls require a dedicated headless release service. BACKEND REQUIRED."
next to it. This version gives it real data for the first time.

### Grounding: real release data for both sources

Fetched directly from the GitHub API before writing any code:

- **`Okaetsu/RE-UE4SS`** (the Palworld-specific fork this project targets): exactly 2 releases — a
  legacy rolling `experimental-palworld` tag (published 2025-02-20) and a new-style discrete
  `2281fa31` release (published 2026-09-03). The release notes on the newer one state "Future
  releases will be a new release instead of updating the old one" — a real, recent strategy change.
  **This means v0.7.45.0's Update Center UE4SS row, which reads the old `experimental-palworld` tag
  by name, is now looking at stale data** — worth a follow-up fix, not addressed in this version
  since it's Update Center's own concern, not this feature's.
- **`UE4SS-RE/RE-UE4SS`** (the general, non-Palworld-specific upstream project): a real, proper
  multi-release history — v2.5.1, v2.5.2, v3.0.0, v3.0.1, plus an `experimental-latest` prerelease.

### Asset selection

Each release attaches multiple downloadable files. Verified against both repos' actual (and
differently-styled) asset sets:

- Palworld Fork's `2281fa31` release: `UE4SS-Palworld-g2281fa31.zip` (correct) vs.
  `UE4SS-Palworld-g2281fa31-zDev.zip` (developer build, for mod authors).
- Official Upstream's `v3.0.1` release: `UE4SS_v3.0.1.zip` (correct) vs. `zDEV-UE4SS_v3.0.1.zip`
  (developer build), `zCustomGameConfigs.zip` and `zMapGenBP.zip` (unrelated optional extras).

The rule — asset name contains `"UE4SS"` (case-insensitive) and does not contain `"dev"`
(case-insensitive) — correctly identifies the right file in both real cases, confirmed by direct
inspection of the actual GitHub API asset lists, not assumed. When no asset matches, the
recommended asset is left null and the UI discloses "no clear primary asset" rather than guessing.

### Implementation

- `HeadlessUe4ssReleaseCatalogService` (new, `MystTiq.HeadlessHost`) — queries both repos'
  `/releases` endpoints, applies the asset-selection rule per release, returns
  `Ue4ssReleaseCatalog(PalworldForkReleases, OfficialUpstreamReleases, ObservedAt)`.
- New fleet-level route `GET /api/v1/ue4ss/releases`, registered the same way as the existing
  `/api/v1/diagnostics/port-check` route: no per-profile state needed (it's a pure, read-only
  GitHub query independent of any specific server's install), no `RequireRole` beyond default
  authentication (matches that same low-risk, read-only tier).
- Desktop: `Ue4ssReleaseDto`/`Ue4ssReleaseCatalogDto` (new), `IMystTiqApiClient.
  GetUe4ssReleaseCatalogAsync` + client implementation, `MainWindowViewModel`'s new
  `Ue4ssPalworldForkReleases`/`Ue4ssOfficialUpstreamReleases` collections with a computed
  `Ue4ssVisibleReleases` that switches based on `SelectedUe4ssFork`. Wired into the existing
  "Refresh Runtime" ribbon button (`RefreshModsCommand`/`RefreshModsAsync`), gated to only fire the
  extra GitHub call while `IsUe4ssPage` is true — that same command also serves MOD Dashboard/
  Library's plain "Refresh MODs," which has no reason to hit GitHub.
- XAML: the permanent "BACKEND REQUIRED" stub text is replaced with a live status line plus a real
  release list (reusing the established card-per-row `ItemsControl` pattern), each row showing the
  release name, recommended asset (or the "no clear primary asset" disclosure), channel
  (Stable/Prerelease), and publish date.

### Why install/rollback is deferred

Inspecting the actual downloaded release zip's contents against the user's real installed UE4SS
layout surfaced real complexity that makes a naive "extract over the existing install" genuinely
unsafe:

- The zip's own `ue4ss/Mods/` folder contains UE4SS's bundled *default* mods (BPModLoaderMod,
  ConsoleCommandsMod, ConsoleEnablerMod, etc.) and `mods.txt`/`mods.json` — extracting it directly
  over an existing install would silently overwrite the user's real enabled-mod state.
- The user's real server has UE4SS's legacy root-level file layout (`dwmapi.dll`/`UE4SS.dll`/
  `UE4SS-settings.ini` directly under `Pal/Binaries/Win64/`) coexisting with the modern `ue4ss/`
  subfolder layout — matching a warning MystTiq's own detection already logs ("Both modern and
  legacy UE4SS Mods roots exist. Modern root is active."). A correct installer must target only the
  active layout.
- A correct install must only replace UE4SS's own core engine files (the proxy DLL, `UE4SS.dll`,
  `UE4SS_SDK_Backends/`, `LICENSE`, `MemberVariableLayout.ini`) and must never touch `Mods/` or an
  already-present `UE4SS-settings.ini` — preserving the user's customization, matching the real
  v3.0.1 release notes' own stated design ("replacing files while preserving custom configuration
  settings").

This needs the same Preview → Safety Backup → Apply → rollback discipline as every other mutating
operation in this codebase, plus live isolated-copy verification before it could ever touch a real
server — tracked as its own version, v0.7.48.0+.
