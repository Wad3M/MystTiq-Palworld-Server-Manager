# v0.6.2.0 — Multi-Server Fleet (Runtime Providers deferred)

## Goal

Remove the single-server assumption baked into `HeadlessConfiguration`, the composition root, every REST route, `OperationCoordinator`, and RBAC — while keeping every pre-fleet client (an existing single-server deployment, the existing Desktop app) working with zero behavior change.

## Scope decision

The roadmap's literal v0.6.2.0 scope bundles two largely orthogonal bodies of work: (a) server/profile identity, and (b) a runtime-provider abstraction covering Docker and Wine-on-Linux. This milestone ships (a) in full, plus a genuine seam for (b) (`ServerRuntimeKind`, two real implementations wrapping the existing lifecycle services), explicitly deferring actual Docker/Wine implementations — they need real environments to verify against, and this project does not ship unverified "decorative" code.

## Config schema v3

`HeadlessConfiguration.Server` (one `HeadlessServerConfiguration`) becomes `Servers` (`IReadOnlyList<HeadlessServerProfileConfiguration>`), each entry carrying its own `Id`/`Name`/`ServerRoot`/`SteamCmdPath`/`BackupRoot`/`RuntimeRoot`/`LaunchArguments`/`Runtime`. A new top-level `FleetRoot` field backs the three fleet-level singletons' shared state. `HeadlessConfigurationService.MigrateV2` wraps an old single-`Server` config into one `"default"` entry; `MigrateV1` now converges through `MigrateV2` rather than building the current shape directly, so both migration paths share one v2→v3 step.

## Composition root: one service graph per profile, not a rewrite

Every `Headless*Service` already took `IServerPathProfile` (and sometimes `IServerLifecycleService`) via constructor injection — none reached for global/static config. `LocalManagementApiHost.Create` loops over `configuration.Servers`, constructing one full existing service graph per profile (`ServerProfileHost`), each with its own `ServerPathProfile.ForCurrentPlatform(...)` and its own `IServerLifecycleService` (via a `lifecycleFactory` delegate now passed in from `Program.cs` instead of a single pre-built instance). No internal service class was rewritten.

Three services are fleet-level singletons instead: `OperationCoordinator` (fleet-wide operation visibility), `HeadlessRbacService` and `HeadlessAuthAbuseGuardService` (one principal/auth surface for the whole app). A dedicated fleet-rooted `HeadlessActivityLogService` backs HTTP-request logging and auth-abuse auditing; each profile keeps its own separate activity log for domain events.

## Routes

`MapProfileRoutes(IEndpointRouteBuilder routes, ServerProfileHost p, ...)` holds every profile-scoped route body, unchanged business logic from the pre-fleet single-server host. It is called twice per profile: once via `app.MapGroup($"/api/v1/servers/{id}")` (every profile) and once via `app.MapGroup("/api/v1")` for the `"default"` profile only (backward compatibility — a pre-fleet client never sees a path change). Route literals inside `MapProfileRoutes` are relative (`"/backups"`, not `"/api/v1/backups"`) since the `MapGroup` prefix supplies the `/api/v1` segment — an early implementation mistakenly kept the full literal path on both the handler and the group prefix, producing a doubled `/api/v1/servers/{id}/api/v1/backups`; caught by manually curling the new routes against a real two-profile instance.

Fleet-only routes (`GET /api/v1/servers`, `POST/DELETE` for profile membership, `POST /api/v1/fleet/{backup,doctor,update}-all`, `/healthz`, `/api/v1/security/*`, `/api/v1/operations*`, `/api/v1/service`) are registered once directly on `app`, not through `MapProfileRoutes`.

## OperationCoordinator

`resourceLocks` changed from `Dictionary<string, OperationId>` to `Dictionary<(ServerProfileId Profile, string Key), OperationId>` (key strings still normalized case-insensitively via `NormalizeKey`). Journal paths gained a profile segment: `operations/journals/{profileId}/operation-{id}.json`. `ListRecent` gained an optional `ServerProfileId?` filter for per-profile listing while still supporting fleet-wide listing (`null`). `OperationHandle` now carries its profile so `ReleaseLocks` can address the composite key correctly.

Every mutation service that begins an operation (`HeadlessWorldTransactionService`, `HeadlessGuildOwnershipService`, `HeadlessBaseOwnershipService`, `HeadlessAutomationService`, the manual lifecycle routes) now takes its owning `ServerProfileId` via constructor injection (or, for the manual routes, as a `RunLifecycleActionAsync` parameter) instead of the previous hardcoded `ServerProfileId.Default`.

## Compound process identity

`/healthz` gained `serverProfileIds` (every profile a given `mysttiq-server` process manages). `LocalManagementBootstrapper.EnsureAvailableAsync` (Desktop) gained an `expectedServerProfileId` parameter (default `"default"`); its "already reachable, reuse it" fast path now additionally checks `HasExpectedProfile`, which requires the expected id to appear in the probed instance's `serverProfileIds` — unless that field is absent entirely (an older, pre-v0.6.2.0 sidecar), treated as compatible to avoid regressing against an already-deployed older instance. This closes a real cross-talk bug found during the v0.6.1.0 screenshot session, where the old identity-blind check (`component == "mysttiq-headless" && apiVersion >= 1`) let a "local" connection profile silently attach to a different already-running instance.

## RBAC

`MystTiqPrincipal.ScopedServerProfileId` (nullable string; null = full-fleet access). `RequireRole` gained an optional `ServerProfileId? profile` parameter — since each route registration already knows which profile it belongs to (a closure capture at `MapProfileRoutes` call time, not something resolved from the request), no runtime route-value lookup is needed. A principal scoped to one profile is rejected (403, `server-scope-mismatch`) on any other profile's gated route. Only routes that already carried a `RequireRole` call in v0.6.1.0 gained profile-scope checking — matching the existing (not every route is role-gated) precedent rather than expanding gating depth in this pass.

## Fleet bulk actions

New `HeadlessFleetConfigurationService` (add/remove server profiles — always requires a process restart to take effect, matching the existing "restart required" convention for other config edits). `LocalManagementApiHost.RunFleetActionAsync` iterates every profile, staggering by `configuration.FleetStaggerSeconds` (new top-level config field, default 5), used by the three `/api/v1/fleet/*` routes.

## Deferred (documented, not dropped)

- Docker and Wine-on-Linux runtime provider implementations.
- Docker-specific health/config checks.
- Per-page "current server" selector on existing Desktop pages (the new Fleet page is the only fleet-aware Desktop surface this pass; threading `ServerProfileId` through 90+ existing API-client call sites in `MainWindowViewModel` is a separate, large mechanical pass).
- Direct single-server CLI verbs (`status`/`start`/`stop`/`restart`/`service-*`) stay scoped to the `"default"` profile only; no `--server-id` flag was added to them this pass.
- `LinuxHeadlessSupervisor`'s crash-recovery auto-restart loop stays scoped to the `"default"` profile only.
- Cross-profile automation rules.

## Verification

Manual verification against a real two-server isolated instance (throwaway ports/directories) found and fixed two real bugs beyond the route double-prefix above: `ServerRuntimeKind` lacked a `JsonStringEnumConverter` attribute (config load failed on any non-default `Runtime` value), and the computed `HeadlessConfiguration.DefaultServer` property was serializing into the persisted JSON file (missing `[JsonIgnore]`). Both are the kind of bug contract-presence regex checks cannot catch — see `scripts/Test-v0.6.2.0-Logic.ps1` for the static checks and `release-notes/v0.6.2.0.md` for the live-verification narrative.
