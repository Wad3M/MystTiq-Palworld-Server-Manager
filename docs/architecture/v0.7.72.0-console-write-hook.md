# v0.7.72.0 — Console-Write Hook (Native Console Capture, completed)

## What this closes

v0.7.57.0 built the DSOUND.dll proxy foundation (`native/MystTiqConsoleProxy/`, injected into
`PalServer-Win64-Shipping-Cmd.exe` via the well-established DLL-proxy technique UE4SS/PalDefender
already use) but deliberately left the actual capture hook unimplemented — the originally-scoped
target, Unreal's `FOutputDevice::LogfImpl`, isn't exported, its offset isn't stable across builds,
and there was no live PalServer process available that session to safely verify a memory patch
against.

## The hook: WriteConsoleA/WriteConsoleW, not LogfImpl

Re-checked the same `dumpbin /imports` data v0.7.57.0's own DSOUND target was picked from:
`PalServer-Win64-Shipping-Cmd.exe` imports **`WriteConsoleA` and `WriteConsoleW` directly, by
name, from `KERNEL32.dll`**, in its own import table. Unreal's Windows console output device
writes the visible console window's text through exactly this API — independent of the
file-logging subsystem — and it's the same low-level path anything else in the process ultimately
goes through to put text on screen. This is a better target than `LogfImpl` on every axis: it's a
real, named, always-resolvable import (no signature scanning needed), and hooking it in the main
EXE's own Import Address Table — not a shared kernel32 export patch, which would affect every DLL
in the process — has minimal blast radius: only this one importer is touched.

Implementation (`native/MystTiqConsoleProxy/dllmain.cpp`):
- `PatchKernel32Import` walks the target module's own PE import directory, finds the
  `IMAGE_THUNK_DATA` slot for a named KERNEL32.dll import, and overwrites just that slot's function
  pointer via a `VirtualProtect`/write/`VirtualProtect`-restore sequence.
- The *real* function is resolved independently via `GetProcAddress(GetModuleHandleW(L"kernel32.dll"), ...)`
  rather than read back out of the IAT slot — safe regardless of what order the loader processed
  this EXE's own imports in, since kernel32 is always fully loaded before any other DLL's `DllMain`
  (including this proxy's own) ever runs.
- `HookedWriteConsoleA`/`HookedWriteConsoleW` capture the bytes (UTF-16→UTF-8 conversion for the W
  variant), append them verbatim to `MystTiqConsoleProxy-Capture.log` (guarded by a
  `CRITICAL_SECTION`, since the game can call these from multiple threads), then always forward to
  the real function — so the game's own console behaves exactly as before.
- **Real bug found and fixed during live testing**: the log files were opened with plain
  `_wfopen_s`, which on the Windows UCRT opens with no sharing at all — MystTiq's own concurrent
  tail-read failed with a sharing violation for the entire life of the game process. Fixed by
  switching to `_wfsopen(..., _SH_DENYWR)`, which keeps this process the only writer while letting
  any number of readers open the file concurrently — confirmed live, reading the file successfully
  while PalServer was still running.

## Live verification (isolated clone, never touching the real production server)

Robocopy-cloned the real production install to `C:\GameServers\_TestClones\ConsoleProxyTest`
(offset ports, throwaway admin password, per this project's established clone-and-isolate
recipe), deployed the rebuilt proxy as `dsound.dll`, and launched PalServer directly first (raw
process launch, to isolate the native mechanism from the .NET integration):

- Process launched, ran, and reached full readiness (UDP port bound) without incident. No crash,
  no hang attributable to the hook.
- `MystTiqConsoleProxy.log` confirmed both hooks installed cleanly.
- `MystTiqConsoleProxy-Capture.log` contained **real, genuine Unreal engine console output that no
  other source anywhere in this app has ever captured**: `LogMemory` platform memory-stats lines
  and console-variable echoes (`r.NGX.DLSS.AutoExposure = "0"`, `net.ParallelTickNetConnection =
  "1"`), all from the first ~5 seconds after launch.
- **The file stayed readable while PalServer was still running**, confirming the sharing-mode fix.

Then re-tested through the *real* shipped code path, not a manual launch: published via
`Build.ps1 DesktopWindows` (which now also stages `MystTiqConsoleProxy.dll` into the headless
sidecar's `native/` folder), stood up a fully isolated `mysttiq-server api-run` instance against
the clone (isolated API port, isolated fleet root, so it could never register into the real
production fleet config), called the new install route, started PalServer through MystTiq's own
lifecycle service, and confirmed `/logs/tail` reported a new `"PalServer console capture (native
hook)"` source carrying the same real `LogMemory` content — the full backend capability works
end-to-end, not just the raw native mechanism.

## Honest finding: the marginal value is exactly as small as v0.7.57.0 predicted

Let the isolated test server run for several more minutes after reaching full readiness (UDP port
bound, confirmed via `Get-NetUDPEndpoint`). **The capture log stayed at exactly the same handful of
startup-only lines for the entire remaining run — nothing further was ever written.** This
empirically confirms, rather than merely predicts from static binary analysis, that Palworld's
Windows dedicated server build genuinely does not write anything to console during normal
steady-state operation (consistent with the earlier `NO_LOGGING` finding). The hook is real, safe,
and correctly captures everything the process *does* write — there just isn't much of it. What
this version delivers is a handful of genuine engine diagnostic lines (memory stats, cvar state)
at startup that were never visible anywhere before, not the "console goes silent during actual
gameplay" fix the original v0.7.46.0 bug report was really asking for. That deeper problem has no
further remaining fix available short of Palworld's own build re-enabling logging.

## What shipped

- `native/MystTiqConsoleProxy/dllmain.cpp` — the real hook (was a disclosed no-op scaffold).
- `HeadlessConsoleCaptureProxyService` (`MystTiq.HeadlessHost`) — install/uninstall/status for the
  proxy DLL, Windows-only, refuses to overwrite a foreign `dsound.dll`, refuses to touch a locked
  file (server must be stopped to install/uninstall).
- Three new routes: `GET /server/console-capture`, `POST /server/console-capture/install`,
  `POST /server/console-capture/uninstall` — mutation-gated the same way `/server/distribution/update`
  already is; nothing in the lifecycle/launch path calls Install automatically.
- `HeadlessMonitoringService.ResolveConsoleSources` reads `MystTiqConsoleProxy-Capture.log` as a new
  merged console source when present — harmless no-op when the proxy isn't installed.
- `Build-AvaloniaDesktop.ps1`/`Build-WindowsHeadless.ps1` stage the native proxy DLL (built
  separately via `scripts/Build-ConsoleProxy.ps1`, which needs the MSVC toolchain) into the
  published headless host's `native/` folder — best-effort, never fails the .NET publish if the
  native artifact hasn't been built yet.

## Deliberately NOT done this version

- **Not installed on this machine's real production server.** Every risky step was proven safe on
  an isolated clone first; actually placing a native DLL next to the real, live PalServer
  executable is a materially different risk category than any prior console-source change (all of
  which only ever read pre-existing files) and needs the user's own explicit go-ahead, asked for
  separately from this build/verification work.
- No Desktop GUI (Environment Checklist row, install button) — API-level only for now, matching how
  several other backend-first capabilities have shipped in this project (e.g. Email notification
  dispatch, v0.7.70.0) before their own Desktop UI pass.
- Linux: not applicable. DLL proxying is a Windows PE/loader technique with no equivalent on Linux;
  `HeadlessConsoleCaptureProxyService` reports `PlatformId != "windows"` honestly rather than
  attempting anything.
