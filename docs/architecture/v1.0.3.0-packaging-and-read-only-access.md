# v1.0.3.0 — Packaging and Read-only Access (internal)

The owner's roadmap milestone v1.0.3.0: P-1 Docker image, W-1 read-only browser view (decision D-1: no write routes in
the browser), X-1 Xbox player discovery (decision D-5).

## W-1 Read-only browser view

- `BrowserView` serves one static page (`/web`, `/web/app.js`, `/web/app.css`) with
  `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; ...`,
  `nosniff`, no referrer and no caching.
  - The page holds no data, so the auth middleware lets these three GETs through.
  - Everything shown comes from the ordinary read routes, with the session token in `Authorization`; roles apply as
    for the desktop.
  - Values are written with `textContent` only (no `innerHTML`). Player IP addresses are not shown.
- `POST /api/v1/auth/browser-login` signs in with an existing account (same per-IP failure guard as `auth/login`) and
  records the token's SHA-256 in `BrowserSessionRegistry` until it expires or is signed out.
- In the auth middleware, after the principal is resolved, a browser session may only `GET`/`HEAD` and
  `auth/logout`. Anything else is answered `403 read-only-browser-session` before the route runs.
- With authentication off, browser sign-in is refused (409): there would be no account to sign in with. Remote use
  needs authentication and TLS as before.
- The desktop's Security page shows the address (the API's own, under `/web`).
- Tests: `Test-v1.0.3.0-RouteSmoke.ps1`, against an isolated service with authentication on:
  - the page has no token and no data;
  - browser sign-in reads status, players and backups;
  - all 114 change routes (every POST, PUT and DELETE in the source) are refused with 403;
  - the same account signed in the desktop's way still writes;
  - a Viewer cannot read the account list;
  - sign-out ends the session.
- Live 2026-10-05: isolated service for the clone, test account, page signed in. A Start sent from the page's own
  session got 403, and reads got 200. A session from another computer over TLS is owed (the browser rejects a
  self-signed certificate, and MystTiq does not install certificates into Windows' trust store).

## P-1 Docker image

- `deploy/docker/Dockerfile` (`runtime-deps:10.0-noble`, i386 libs for SteamCMD, python3, a non-root `mysttiq` user,
  `VOLUME /data`, a healthcheck on `/healthz`, labelled with the version) and `entrypoint.sh`. On the first start
  `entrypoint.sh`:
  - writes a configuration with every path under `/data`;
  - creates an API token and a self-signed certificate;
  - switches the API on for `0.0.0.0:8213` (`api-remote-enable`, which requires authentication and TLS);
  - then runs `api-run`.
- `scripts/Test-v1.0.3.0-Docker.ps1` builds `mysttiq-headless:<version>` from the linux-x64 publish and runs it with its own
  Docker volume as `/data`. With a folder bind-mounted from Windows the server exited before it was ready; on a volume it
  ran. It checks healthz, that a request without the token gets 401, the status with the token,
  and the paths. `-RunServer` installs the Linux server through `server/distribution/update`, copies the clone's world
  (SaveGames and its two ini files, into `Config/LinuxServer`), starts it, waits for ready and stops it.
- Found doing it: SteamCMD's first app install after installing itself failed with "Missing configuration".
  `HeadlessServerDistributionService` now runs it once more (`SteamCmdFailure.IsMissingConfiguration`).
- Evidence: Recorded 2026-10-05 (v1.0.3.0) on Docker Desktop: the image built and labelled with the version, the server installed in the container through MystTiq, the clone's world run there (REST answering, Day 173 11:02 read from its save) and stopped cleanly.
