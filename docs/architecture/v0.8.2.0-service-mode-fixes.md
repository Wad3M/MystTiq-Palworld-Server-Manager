# v0.8.2.0 — Service Mode Fixes

First release after the user set **v0.8.1.0 as the accepted baseline** (2026-09-23). It fixes service mode:
`service-run`, the command an installed Windows service or systemd unit runs. A reproduction with a stand-in
PalServer on a non-default game port found three faults that api-run (the Desktop's own sidecar) does not have.

## What was wrong

1. **Wrong game port.** Both `service-run` branches (Windows and Linux) built the supervisor's lifecycle without
   the profile's configured game port, so it always waited for UDP 8211. A server on any other port ran fine but
   was reported as `StartupTimeout`. The initial start then "failed", and the service shut itself down.
2. **Two supervisors.** `service-run` also starts the embedded management API. That API host started its own
   `HeadlessFleetCrashRecoveryService` for every profile, including the one the service supervisor already
   watches. So one crash had two supervisors racing to restart the same server.
3. **No alerts or memory.** The service supervisor had no observer, so crashes, recoveries and give-ups sent no
   notifications. It also had no persisted state. After it gave up and the OS restarted the service, nothing said
   the server was back, and nothing unpinned the DOWN notice.

## What changed

- `Program.cs`: both branches now build the lifecycle through the same per-profile factory that the API host uses
  (`WindowsServiceRunLifecycleFactory` / `ServiceRunLifecycleFactory`). That factory carries the configured port.
- `LocalManagementApiHost.TakeOverCrashRecovery(profileId)`: marks the profile as externally supervised and
  returns that profile's `CrashAlertObserver` and `SupervisorRecoveryStateStore`. `StartAsync` skips
  `CrashRecovery.StartAsync` for externally supervised profiles. The service supervisor is built with the returned
  observer and store, so alerts, mute rules and persisted state match api-run exactly. Without the API, it falls
  back to `SupervisorRecoveryStateStore.ForProfile(paths)`.
- `HeadlessSupervisor`:
  - It now records `GaveUpAtUtc` itself, at the moment it gives up. Before, only the api-run wrapper recorded it.
  - `RunAsync` handles a start with a give-up still recorded. Once the server is READY, it clears the give-up and
    raises `ManualRecovery` ("PalServer is running again after the MystTiq service restarted."). Through the
    observer, that sends the "back up" notice and unpins the DOWN notice.
- `HeadlessFleetCrashRecoveryService`: its duplicate give-up record is removed. It still resumes watching from the
  stored give-up.
- `CrashAlertObserver`: pinning a new DOWN notice first unpins the previous one. A service that gives up, is
  restarted by the OS, and gives up again never leaves several DOWN notices pinned.

The exit code on give-up is unchanged: `CrashDetected` (16). That is the signal the OS service recovery policy
acts on.

## Verification

- Logic harness has two new scenarios:
  - the supervisor records its own give-up, and a later `RunAsync` announces the recovery once ready;
  - a second give-up replaces the pinned DOWN notice.
- `scripts/Test-v0.8.2.0-RouteSmoke.ps1` runs the **published** `mysttiq-server.exe service-run` in the
  foreground. It uses its own FleetRoot, ports and fixture, with the new stand-in
  `scripts/Testing/FakePalServer`: process name `PalServer`, which binds its `-port=N` UDP port. It checks:
  1. the server starts on port 18482 and the service stays up past the startup timeout;
  2. one crash gives exactly one detection, one relaunch, one "server crashed" alert and a "back up" alert;
  3. a give-up exits with 16 and records `GaveUpAtUtc` and the pinned id in `state.json`;
  4. a new `service-run` announces the recovery, unpins that DOWN notice and clears the give-up.
- Against the v0.8.1.0 exe, check 1 fails ("UDP 8211 was not confirmed"), and the API host restarts the server
  on its own.
- The smoke builds FakePalServer into its temp folder and removes the project's bin/obj afterwards. The Clean
  step also removes them.
