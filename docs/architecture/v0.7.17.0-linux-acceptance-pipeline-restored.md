# v0.7.17.0 — Linux Acceptance Pipeline Restored

## Background

While closing the disclosed Linux-verification gap on the `api-remote-enable` CLI fix (see `docs/architecture/v0.7.17.0-api-remote-enable-cli-fix.md`), running `Build.ps1 LinuxHeadless` for the first time in a while threw immediately:

```
Required Linux publish script was not found: C:\GameServers\Claude\scripts\Test-v0.7.17.0-LinuxAcceptance.sh
```

`scripts/Build-LinuxHeadless.ps1` hard-requires a version-specific `Test-v{version}-LinuxAcceptance.sh` and `Test-v{version}-ProductionReadiness.sh` pair to exist before it will publish anything (it bundles them into the shipped archive). The last version either file exists for is **v0.6.1.0** — every release since (v0.6.2.0 through v0.7.17.0, ~15 releases) is missing both, so `Build.ps1 LinuxHeadless` and its caller `Deploy-Test-MystTiqLinux.ps1` have been unusable for the entire lifetime of those releases. This had been a known, disclosed, carried-forward gap since v0.6.2.0's own checkpoint notes ("`Build-LinuxHeadless.ps1` needs a version-specific `Test-v0.6.2.0-LinuxAcceptance.sh` that doesn't exist yet") but was never actually closed.

## What shipped

- `scripts/Test-v0.7.17.0-LinuxAcceptance.sh` and `scripts/Test-v0.7.17.0-ProductionReadiness.sh`, adapted from the v0.6.1.0 originals (the last working copies):
  - `SchemaVersion` check updated from `2` to `3` (v0.6.2.0's Multi-Server Fleet migration bumped it; `Api.*` itself stayed a top-level singleton so no other `jq` path needed to change).
  - Reference kernel string refreshed to match the VM's current `6.8.0-138-generic` (a routine kernel bump; this check only ever `WARN`s, never blocks).
- **A real, previously-undiscovered bug fixed in both scripts along the way**: every ephemeral CLI invocation the scripts made against the live config (`status --config $CONFIG --json`, `production-doctor --config $CONFIG --json`, and the temporary authenticated loopback `api-run` instance) crashed with an unhandled `System.UnauthorizedAccessException` trying to write `lifecycle-state.json.tmp` under the live config's `RuntimeRoot` (`/opt/mysttiq/runtime`, root-owned by the `User=root` systemd unit — a gap already documented in v0.6.1.0's own memory notes, but the acceptance script itself was never actually updated to work around it). Fixed by giving every such ephemeral invocation its own isolated, self-owned `--runtime-root` (a `mktemp -d` scratch directory) instead of reusing the live one — the documented workaround, now actually applied in the script rather than just written down as a note for next time.
- **A second real, pre-existing design flaw fixed**: both scripts scanned the systemd unit's entire *current-boot* journal for fatal-looking lines. On a long-uptime host (this VM: 5+ days since its last reboot), one old, already-resolved crash-loop event from days earlier keeps re-triggering the check indefinitely — a production-readiness gate that can never recover without an unrelated reboot is a design flaw independent of anything in this release. Changed both to scan only the last 30 minutes (`--since "-30 minutes"` instead of `-b`) — "is anything wrong right now," not "has anything ever gone wrong since the last reboot."
- **Coverage then expanded from the v0.6.1.0-era subset to essentially the full current API surface**, at the user's explicit request to go beyond just restoring the mechanism. Catalogued every route in `LocalManagementApiHost.cs` (~125 profile-scoped + fleet-level routes) and classified each by safety against real production data:
  - **~30 previously-untested read-only GET endpoints** added (players/registry, diagnostics, world/validate, world/transactions, pals, anticheat, mods/workshop, server/environment, palworld/config, raw config, notifications/*, RCON status/doctor, ban-list, whitelist, temp-bans, moderation providers, fleet servers/principals/port-check, etc.) — each just needs a 200 without crashing.
  - **Safe POST/self-test/re-run endpoints** added with reachability checks accepting any non-5xx status (diagnostics network re-run, crash analyzer analyze, save-tools self-test — all confirmed read-only/introspection-only by reading their implementations first; world save-now and RCON command exercised as graceful-failure checks since PalServer is currently stopped; notifications self-test/mark-all-read).
  - **Six preview-only endpoints** (world/import/analyze, guilds/ownership/preview, pals/edit/preview, bases/ownership/preview, bases/recovery/preview, players/migration/preview — never their `*-apply` counterparts) exercised with garbage identifiers, accepting any non-5xx response as proof the endpoint validates input rather than crashing on a nonexistent target.
  - **Fully reversible create-then-delete roundtrips** for automation rules (a once-a-year-interval, disabled-immediately-after-creation, harmless-SendNotification-action rule) and security principals (Viewer role) — pure metadata, never touching real save/world data, cleaned up within the same test run and confirmed via a 200 delete response.
  - **No-op PUT roundtrips** (GET the real current value, PUT it back unchanged) for whitelist, notification channels/templates/discord-bot settings, alert rules, and anticheat rules — proves the write path works without altering live behavior.
  - **Explicitly still excluded**, documented in a block comment near the end of the script: every `*-apply` endpoint, per-player mutations (`action`/`teleport-*`/`warnings`/`flag`), backup restore/reclassify/retention-apply, diagnostics auto-fix and network firewall/UPnP repair, all MOD mutation routes, server clone, SteamCMD distribution update, `palworld/config`/`config/editable` PUT, fleet server add/remove, `fleet/backup-all` (non-destructive but a real, potentially large/slow full save copy — excluded for run-time boundedness, not safety), `fleet/update-all`, and the lifecycle start/stop/restart routes (already correctly gated by the pre-existing "Extended API lifecycle" guard, unchanged).
- **A second real, previously-undiscovered bug found and fixed by this expanded pass**: `PalworldSettingsConfigurationService.ValidateDefaultRequest` threw an unhandled `System.NullReferenceException` (`request.ServerName.Length`, `request.ServerDescription.Length`, and a `.Contains('\r')` loop over four string fields, none null-checked) whenever a `POST /api/v1/palworld/config/defaults` request omitted an optional string field — turning what should be a clean 400 validation response into a 500 crash of that request. `PalworldDefaultConfigurationRequest`'s properties are plain (non-nullable) `string`, but System.Text.Json's default model binding does not enforce that at runtime, so any caller (a real API client included, not just this test) sending an incomplete request would hit this. Fixed with null-safe checks (`?.Length ?? 0`, `value is not null &&`); verified the endpoint now correctly returns 400 with a clean `validationErrors` list (including the pre-existing "PalWorldSettings.ini already exists" refusal, since the real production config already exists) instead of crashing.

## Manual mutation-path verification (not part of the permanent script)

The automated acceptance script above deliberately excludes every endpoint that mutates real save/world/guild/base/player/backup/mod data, because this VM's actual live world had never had a real player join it — no guilds, bases, or characters existed to mutate safely or meaningfully. At the user's explicit request to verify this path too, a one-time **manual** pass exercised the excluded mutation endpoints for real, against a fully isolated environment, using this machine's real Windows Palworld save (which does have real guild/base/player data) copied in as fixture data:

- Built an isolated copy of the real Linux `ServerRoot` (`cp -r /opt/mysttiq/palserver`, 4.9 GB, `mystroth`-owned scratch dir, never touching the live install), then replaced its save slot with a zipped copy of the real Windows server's save (`C:\GameServers\Palworld\Server\Pal\Saved\SaveGames\...`, 5 real players/2 real guilds/2 real bases) — the Windows original was only ever read from, never modified.
- Wired in the already-installed PlM/Oodle converter (`~/palsav-src/convert.py`, per prior session notes) at the path MystTiq's save codec expects (`ServerRoot/Tools/palworld-plm-tools/convert.py`) — without it, every mutation correctly refused with "Save codec unavailable," itself a legitimate finding, not a bug.
- **Verified for real, with full preview→apply→re-verify cycles, restoring original state where the change wasn't self-reverting**: guild leadership transfer (`TransferLeadership`, applied then reverted, confirmed via re-read both times); base ownership transfer (`113 owning-guild tag(s) updated`, applied then reverted); `RemoveBrokenMember` correctly refuses against a member who still has a valid save (`"only offered for a dangling reference with no matching save"`); character-migration preview between two real distinct players (correctly reported `Unmatched`, 0% confidence, and a guild-membership conflict — real identity-matching logic working); backup create → verify → **restore** (Kestrel actually overwrote the live save from the backup, and itself took a fresh safety backup first); `backups/verify-all` (6 real archives, all checksums clean); `backups/retention/preview`+`apply` full roundtrip; MOD install-zip → disable → **rollback** (correctly *removed* the freshly-installed mod rather than "restoring" it — the exact `install-then-rollback` distinction v0.6.8.0's own notes flagged as easy to get backwards) and separately install → **delete**; `palworld/config/defaults` actually creating a real `PalWorldSettings.ini` from scratch (119 real settings, config-backup written) after a stray 1-byte placeholder file was removed; `palworld/config` PUT and `config/editable` PUT round-trips (both wrote real timestamped rollback/backup copies); a full **world/import** self-cycle — zipped the isolated save's own `Level.sav`/`LevelMeta.sav`/`Players`, analyzed it, applied it (`Stop PalServer → safety backup → staged extract → validate → atomic swap → validate`, all real steps), and confirmed the guild/player data read back identically afterward; and **`pals/edit/preview`+`apply`** on a real pal (a nickname change, applied and confirmed via re-read) — a first pass had wrongly concluded there were no pals to edit (the `/pals` endpoint was tested before the PlM converter was wired in, so it silently returned `[]` per `HeadlessPalEditService.ListPalsAsync`'s `if (converterMatch is null) return [];` guard; once the converter was in place from the start of a rebuilt isolated copy, `/pals` correctly returned 85 real pals).
- **Found and fixed a second real bug this way**: `HeadlessBackupRetentionRequest.IncludeClasses` was typed `IReadOnlySet<BackupClass>?` — `System.Text.Json`'s default deserializer cannot populate an `IReadOnlySet<T>` from a JSON array (throws `NotSupportedException`, surfaced as an unhandled 500), so any real caller that ever passed `includeClasses` (a real, documented, non-default field — the whole point of the retention tool's class-scoping design) would crash the request instead of getting filtered results. Changed to `IReadOnlyCollection<BackupClass>?` (JSON-deserializable, same consumption semantics); reran the check afterward and it correctly returned 200 with an accurately-filtered (empty, since nothing was old enough) result.
- **Explicitly not exercised even in this manual pass, and why**: `players/migration/apply` and `RemoveBrokenMember`'s actual-deletion path (would have required deleting a real player's `.sav` to engineer a genuinely broken reference — the session's own permission classifier declined that file-deletion action over SSH, and rather than route around it, real players' character data was left untouched; the healthy-member refusal path above was verified instead); `players/{id}/action`/`teleport-*`/`warnings`/`flag` (need either a genuinely running PalServer or would leave permanent notes/flags on a real person's character record); `server/clone` and `server/distribution/update` (heavy — a full second multi-GB copy or a real SteamCMD download, not attempted given the scope already covered); `api/v1/servers` fleet add/remove; `diagnostics/{id}/fix`/network firewall/UPnP repair (mutate host-level system state, out of scope regardless of data isolation, consistent with this project's existing sudoers-scope philosophy).
- **The real save data itself was never committed anywhere** — copied only into a throwaway scratch directory on the Linux VM (`rm -rf`'d after this pass) and a local scratchpad temp file (also deleted), never into the repo or either script. Bundling real, identifying player-name save data into a permanent automated test fixture would need the user's explicit sign-off first; this was a one-time manual verification, not new permanent coverage.

## Explicit non-goals

- **The permanent automated script is still not a mutation-behavior audit.** Every endpoint that would touch real save/world/guild/base/player/backup/mod/network/system state on this live production install is deliberately not exercised there — see the exclusion list above and the matching block comment in the script itself. The manual pass above closed most of that gap once, empirically, but did not change what the script itself runs automatically.
- **No change to `Deploy-Test-MystTiqLinux.ps1` itself.** The wrapper script was already correct; it was blocked entirely by the missing version-specific files it depends on.

- `Deploy-Test-MystTiqLinux.ps1 -LinuxHost 192.168.1.144 -SkipBuild -Extended` against the real VM, iterated to green through several real findings (each fixed, not worked around in the test): the `RuntimeRoot` permission crash; the unrecoverable stale-journal gate; three checks that expected HTTP 200 where the real, correct behavior is a documented non-2xx graceful-failure/rejection status (RCON doctor 424, ban-list 409, palworld-config-defaults 400 — all confirmed correct by reading the actual handler code, not assumed); an automation-rule-create test body that didn't match the real `AutomationRuleRequest`/`AutomationTrigger`/`AutomationAction` shape; and the real `ValidateDefaultRequest` NullReferenceException described above. Final clean run: **118 passed, 0 failed, 2 warnings** (PalServer intentionally stopped; UDP 8211 not listening as a result), **1 skip** (extended lifecycle mutation correctly declines since the live instance is already TLS/auth-secured on a non-default bind — its own guard, unchanged). Includes the `Production readiness integration` gate passing clean.
- Confirmed the real `mysttiq-palworld.service` was `active` before, during, and after every run, and still reports its actual pre-existing version (`0.5.2.0` — this VM's live systemd service has never been promoted past that; deploying a build under `~/mysttiq-builds/v{version}` is intentionally separate from making it live, per this project's own established `Upgrade-MystTiqLinux.sh` workflow). Nothing in this pass touches the live install's config or persistent data — every ephemeral instance used its own scratch config/token/certificate/runtime-root under `mktemp -d`, and the automation-rule/security-principal roundtrips were created against the newly-built v0.7.17.0 candidate's own temporary loopback instance and confirmed deleted (HTTP 200) within the same run.
