# v0.7.9.0 — Real Server FPS/Frame Time

## Background

Fourth release from the broader review requested this session: a codebase-wide bug scan plus a competitive feature survey against other Palworld server-management tools. The survey (and independent verification against Palworld's own official documentation at `docs.palworldgame.com`) confirmed `/v1/api/metrics` is a real, documented endpoint returning:

```json
{ "serverfps": 57, "currentplayernum": 10, "serverframetime": 16.7671, "maxplayernum": 32, "uptime": 3600, "days": 1 }
```

`currentplayernum`/`maxplayernum`/`uptime`/`days` overlap with data MystTiq already tracks via other means (the players endpoint, process lifecycle, in-game day tracking). `serverfps`/`serverframetime` do not — MystTiq's existing `HeadlessMonitoringService.GetMetricsAsync` only ever samples host-level process CPU%/working-set/thread-count via `System.Diagnostics.Process`, which cannot see the game's own simulation performance. A dedicated server can show low host CPU% while the actual game tick rate has collapsed under base/Pal count — the thing operators actually watch for lag — and MystTiq had no way to show that at all before this release.

## What shipped

### `HeadlessMonitoringService.GetGamePerformanceAsync` (new, private)

Reuses `GetPlayersAsync`'s exact REST client construction rather than introducing a second copy of that setup: same `PalWorldSettings.ini` path resolution, same `RESTAPIEnabled`/`RESTAPIPort`/`AdminPassword` reads, same `SocketsHttpHandler`/`HttpClient` configuration, same HTTP Basic `admin:{password}` auth header. Calls `GET metrics` instead of `GET players`, parses `serverfps`/`serverframetime` from the JSON body (tolerant of either being absent), and returns `(double? Fps, double? FrameTimeMs)` — both null on any failure (REST disabled, no `AdminPassword` configured, unreachable, non-success HTTP status, malformed JSON). This is deliberately best-effort: a failure here must never affect `GetMetricsAsync`'s existing host-level metrics, so every failure path is swallowed to `(null, null)` rather than thrown.

### `HeadlessRuntimeMetricsSnapshot` extended

Two new optional trailing fields, `ServerFps`/`ServerFrameTimeMs`, both nullable — following the exact "null means unavailable, not zero" convention the existing `CpuPercent` field already established on this same record. `GetGamePerformanceAsync` is called once at the top of `GetMetricsAsync`, before the host-level process-discovery branching, and its result is threaded into **every** return path in that method (including the "PalServer is not currently running" and "processes exited before sampling" branches) — the Palworld REST API's own reachability is independent of whether MystTiq's own process-lifecycle tracking currently sees a managed PalServer process, so a real FPS reading should still surface even in states where the host-level metrics are unavailable.

### Desktop wiring

`RuntimeMetricsSnapshotDto` gained matching `serverFps`/`serverFrameTimeMs` properties (camelCase JSON, matching the DTO's existing convention). `MainWindowViewModel` gained `ServerFpsText`/`ServerFrameTimeText` (formatted "—" when null, matching `CpuText`'s existing "Baseline"/"—" pattern), populated in `ApplyMetrics` independently of the `snapshot.Available` early-return branch (since FPS availability doesn't depend on process discovery the way CPU/RAM/thread sampling does).

Surfaced on the Monitoring page's Activity & Audit stat row (`MainWindow.axaml`), widened from a 3-column to a 5-column grid to add "Server FPS" and "Frame Time" cards alongside the existing CPU/RAM/Threads cards — same row, same card styling, no new page height. The Dashboard's existing compact CPU/Memory tile (already visually dense, using `ClipToBounds`/`TextTrimming` defensively) was deliberately left untouched rather than cramming two more values into an already-tight fixed layout; the Monitoring page was judged the better home since it has room and is where CPU/RAM/Threads already live.

## Explicit non-goals

- **`currentplayernum`/`maxplayernum`/`uptime`/`days`** from the same `/v1/api/metrics` response are not consumed — MystTiq already tracks player counts and uptime through its existing player/lifecycle endpoints, and duplicating them from a second source risks the two disagreeing rather than adding value.
- **Historical FPS charting** (extending `MetricHistoryPoint`/the resource history graph to include FPS over time, matching what CPU/RAM already get) was considered but deferred — this release ships the current-value display first; charting is a natural, separately-scoped follow-up if the current-value display proves useful.
- **Auto-restart-on-FPS-collapse** (an Automation trigger keyed on low FPS, mentioned as a monitoring use case in Palworld's own REST API documentation) is not part of this release — Automation's existing trigger types would need a new "metric threshold" kind, a larger change than this release's scope.

## Verification

`dotnet build` (full solution, Release) — 0 warnings/0 errors.

**Live check**: started a real sidecar and confirmed `GET /api/v1/metrics` includes `serverFps`/`serverFrameTimeMs` in its response shape, correctly `null` both with no `PalWorldSettings.ini` present at all and with `RESTAPIEnabled=True` pointed at a port nothing is listening on (confirming the best-effort failure handling doesn't crash or hang). A real Palworld dedicated server with the REST API actually serving `/v1/api/metrics` would be needed to verify the positive-path values arrive and display correctly — outside what this environment can run, the same disclosed limitation as every RCON/REST-touching feature added this session (v0.7.8.0's teleport/unban/ban-list/save-now).
