# v0.6.8.0 — MOD/UE4SS Platform & Monitoring

## Goal

Per the roadmap: "Manage extension lifecycles safely, building on the analytics/monitoring foundation shipped in v0.6.1.0." Research at the start of this milestone found `HeadlessModManagementService` already far more mature than expected — install/delete/enable-disable/repair, PAK + UE4SS scanning, real UE4SS.log runtime-load evidence, and Steam Workshop scan/import all pre-existed and needed no rework. This milestone's real, scoped job was to close the two gaps that genuinely remained: backup/rollback safety, and Alert Center awareness.

## What shipped

### MOD backup, staged install & rollback

- Before this milestone, `InstallZipAsync` (staged extraction, then commit) and `DeleteAsync` had no safety net: a bad install or an accidental delete had no built-in undo path. The roadmap's "staged install" and "runtime verification" halves already existed; "backup" and "rollback" did not.
- `HeadlessModManagementService.CaptureSnapshot(type, package)` (new) — called at the start of both `InstallZipAsync` and `DeleteAsync`, before any mutation. Takes a lightweight, package-scoped snapshot: for a flat PAK deployment, zips just that package's own files; for a nested Workshop/LogicMods PAK folder or a UE4SS mod folder, zips the whole folder. One snapshot is kept per `(type, package)`, overwritten on the next mutation of that same package — "undo my last change to this MOD," not a full history, matching the actual failure mode this protects against (a bad update, an accidental delete) rather than inventing a versioned archive system.
- **Absent-marker distinction**: if nothing existed for the package before the mutation (a brand-new install), a sidecar `.absent` marker is written instead of a snapshot zip. `RollbackAsync` checks for this explicitly — a package that didn't exist before its last install must be *deleted* on rollback, not left in place. Without this distinction, rolling back a fresh install would silently no-op instead of undoing it.
- A companion `.meta` file (not embedded in the zip, to avoid ambiguity between a flat file-set and a nested folder's own internal structure) records exactly how to restore: `"flat|{root}"` for loose files, `"folder|{path}"` for a folder snapshot with its own real restore target path (so a Workshop-nested mod correctly restores back under the *same* Workshop/LogicMods root it came from, not a hardcoded default).
- `RollbackAsync` requires PalServer stopped, same as every other MOD mutation; honestly reports "No rollback snapshot is available" rather than pretending success when nothing was ever captured for that package.
- New `POST /api/v1/mods/{type}/{package}/rollback` route (same auth posture as the neighboring install/delete/enable routes — none of them currently require an elevated role, so rollback doesn't introduce an inconsistent restriction). Desktop: "Rollback Selected" button on the MOD Dashboard, next to Delete.

### Alert Center integration for MOD/UE4SS-specific health

- The one specifically-named roadmap bullet ("Alert Center integration for MOD/UE4SS-specific health") not covered by anything else in this milestone.
- `HeadlessAlertCenterService` gains a `HeadlessModManagementService` dependency and a new `ModHealthDegraded` rule (`AlertSimpleRule`: `Enabled`, `CooldownMinutes`, default enabled with a 60-minute cooldown). Evaluated inside the service's existing `EvaluateThrottledAsync` — already self-throttled to a 60-second minimum interval and already driven by `HeadlessAutomationService`'s existing background tick — so this adds zero new timers or polling loops.
- When the existing MOD inventory computation (`HeadlessModManagementService.GetInventoryAsync`, unchanged) reports `OverallHealth == "Degraded"`, a real notification fires naming up to 5 of the specific MOD(s) and their health state (e.g. `"BrokenMod (Misconfigured)"`), with a `+N more` suffix for larger counts — not a generic "a mod has a problem" message.
- Surfaced on the Desktop Alert Center page as a new toggle row alongside the four existing threshold rules.

## Explicit deferrals (not silently dropped)

- Mod load order, dependencies and profiles.
- Release discovery and one-click update (checking Nexus/Workshop for a newer version than what's installed).
- Nexus integration.
- Latest vs. tested/recommended vs. installed version tracking.
- PalDefender-specific lifecycle handling — confirmed via research this is really "special-case one well-known third-party UE4SS mod by filename" (the legacy WPF app's `ModScannerService` detected it by checking for a literal `PalDefender.dll`). Since the current generic UE4SS scanner already surfaces PalDefender as a regular MOD entry with real health/runtime evidence like any other, adding filename-specific special-casing was judged low value relative to the mechanism already being generic — deferred rather than built as a one-off.
- MOD runtime-state *providers* in the v0.6.5.0 Provider Framework sense (a formal `IModRuntimeProvider` abstraction) — the existing UE4SS.log evidence-reading approach stays as direct logic inside `HeadlessModManagementService`, not generalized into the provider pattern this pass.
- The explainable/reversible/audited optimization advisor.

## Verification

Live, against a real isolated instance (no real save/config touched — MOD operations work entirely off `ServerRoot/Pal/Content/Paks` and the UE4SS mods root, independent of world/save state):

- Installed a fake PAK MOD (`TestMod`, v1 content) — confirmed an `.absent` marker was written (nothing existed before).
- Installed v2 content over it — confirmed the pre-mutation snapshot now held v1's exact content (`.meta` recorded `flat|...`), and the file on disk was genuinely v2.
- Rolled back — confirmed the file on disk was restored to v1's exact content, byte-for-byte.
- Installed a brand-new package (`FreshMod`) for the first time, then rolled it back — confirmed the file was deleted entirely, correctly following the absent-marker path rather than leaving it in place.
- Attempted rollback of a package that was never touched (`NeverTouched`) — confirmed an honest `409` failure naming the missing snapshot, not a silent success.
- Deleted an existing MOD (`TestMod`, restored to v1 from the prior step), then rolled back the delete — confirmed the file was restored.
- Induced a real `Misconfigured` MOD health state (a `.ucas` file with no matching `.pak`/`.utoc`) and confirmed `GET /mods` correctly reported it as `Misconfigured` with `overallHealth: "Degraded"`.
- Confirmed the default `ModHealthDegraded` rule is enabled out of the box (`GET /alerts/rules`), then polled `GET /notifications` and confirmed a real notification appeared within the automation tick's cadence, correctly naming `"BrokenMod (Misconfigured)"` — not a placeholder or generic message.

Not performed this session: rollback of a nested Workshop-folder-installed PAK MOD or a UE4SS folder-based MOD specifically (only the flat-file PAK path and the absent-marker path were exercised against real files; the folder-restore code path shares the same `ZipFile.CreateFromDirectory`/`ExtractToDirectory` calls already proven correct elsewhere in this codebase, but wasn't separately exercised this session) — a reasonable follow-up for a future verification pass, not a known defect.
