# v1.0.7.2 — Progress You Can See (internal)

Roadmap items Q-8, Q-12, Q-13 and Q-7 from the outside review (`docs/roadmap/ANALYSIS_REVIEW_2026-10-07.md`).

**Reproduced first** (2026-10-08): `scripts/Test-v1.0.7.2-RouteSmoke.ps1` against the published v1.0.7.1 service. The
status had no start step, and the backup list had no scan, so both checks failed.

## Q-8 — Server start-up shows its steps

- `StartupProgress` (Core) holds the step, since when, and when the start began.
- `WindowsServerLifecycleService` and `LinuxServerLifecycleService` wrap their start (`StartCoreAsync`) in
  `Begin` / `Conclude` / `End` and enter `Launching` before the process is created and `WaitingForGamePort` before the
  readiness loop.
- `GetStatusAsync` decorates every status read (`StartupStage`, `StartupStageSinceUtc`, `StartupBeganUtc`).
- `Conclude` prefixes a failed result with `The start stopped at "<step>": `. A duplicate start (AlreadyRunning) is not
  prefixed.
- **No "checking REST" step**, unlike the roadmap's list. The start's readiness is the game port. A REST API that does
  not answer is shown by Q-7's connection cause and handled by the frozen-server watchdog (R-1), so a step for it would
  only delay the start.
- Desktop: `ServerStatusDto.StartupStageText(now)` on the Dashboard's server tile (`StartupStageText`).

## Q-12 — Backup scans show progress and can be cancelled

- `HeadlessBackupService` keeps one scan state (`BackupScanProgress`: kind, done, total, the archive in hand, unreadable
  archives with the reason, started and finished, cancelled). It is part of the backup list.
- Each scan has an id, and only the newest writes its progress. The world-day read does not start while Verify All
  runs; Verify All takes the slot from a running world-day read.
- **World days:** the backups to read are listed first (the total), the read goes through the `BackgroundWork`
  token, and the list is saved every `WorldDaySaveEvery` (10) backups and at the end.
- **Verify All:** steps through the archives with a linked cancellation. Cancel (`POST /backups/scan/cancel`, Operator)
  stops it after the archive in hand. The results so far are kept and saved, and the answer says "Cancelled after N of
  M".
- Desktop: the Backups page's scan card, with progress, Cancel (enabled while Verify All keeps the window busy) and
  the archives it could not read. While Verify All runs, the desktop reads the backup list every 1.5 s for the
  progress.

## Q-13 — Opening a page while busy says so

`RefreshPageForNavigationAsync` used to poll `IsBusy` every 500 ms for up to a minute (Map and Players). Now:
- `RaiseIsBusyDependents` signals a `TaskCompletionSource` when the busy state clears.
- `WaitUntilNotBusyAsync` shows `PageWaitText` at once, naming `BusyReason` when there is one, and waits on the signal
  (up to `PageWaitLimit`).
- `PerformNavigation` cancels the wait when the owner moves to another page.

## Q-7 — Connection status names the cause

`ConnectionCause.ForFailure` (no Avalonia dependency, compiled into the LogicHarness) maps a failed call to one of:

| Failure | State and what it says |
| --- | --- |
| HTTP 401 or 403 | Sign-in rejected: sign in again, or check the token |
| HTTP 5xx | Service error, with the code |
| A TLS authentication failure | Certificate rejected: check the pinned fingerprint |
| No answer (socket error, timeout, a request with no status) | Reconnecting, with the attempt, when this tab was connected before; otherwise Service unreachable, with the address |

`ForConnected` names a running Palworld whose REST API does not answer.

The recurring status poll and the full refresh both use it (`NoteConnected`, `NoteConnectionFailure`). The tab dot
(amber for Reconnecting, red for the others) and the status tags know the new states. A stopped Palworld was already
told apart by the server state.
