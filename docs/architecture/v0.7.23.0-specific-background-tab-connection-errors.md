# v0.7.23.0 — Specific Background-Tab Connection Errors

## Background

Fourth of the planned backlog sequence approved this session. A code-level audit during planning found a real, if minor, bug: `RefreshTabLightweightAsync` (`MainWindowViewModel.cs`) — the lightweight health check background tabs run on their own cadence, distinct from the active tab's full `RefreshAsync` — had a bare `catch { }` that discarded whatever exception `GetHealthAsync` actually threw and always set `tab.ConnectionState = "Connection failed"`, whether the real cause was a genuinely unreachable server, a version mismatch, or a missing bearer token.

The active tab's own connection check, `RefreshAsync` (hitting the identical `_api.GetHealthAsync(profile, ...)` call), already had this exactly right: it explicitly checks the health response's `Component`/`ApiVersion` and throws `InvalidOperationException` naming the actual mismatched values, and checks `health.Authentication` against a blank bearer token, throwing `UnauthorizedAccessException`. `RefreshTabLightweightAsync` simply never read any of that — the fix is entirely a matter of reusing logic that already existed one method away, not inventing anything new.

## What shipped

`RefreshTabLightweightAsync` now performs the identical two checks `RefreshAsync` already does, throwing the same two exception types under the same conditions, then classifies the catch accordingly:

- Component/API-version mismatch → `tab.ConnectionState = "Incompatible API version"`
- Missing bearer token when the endpoint requires one → `tab.ConnectionState = "Needs bearer token"`
- Anything else (genuinely unreachable, network error, etc.) → `tab.ConnectionState = "Connection failed"` (the original, now-accurate catch-all)

`ConnectionState` was already rendered as visible text in two places in `MainWindow.axaml` once a tab becomes the active one — a status badge (`Border Classes="badge"`) and a status card (`TextBlock ... StringFormat='Connection: {0}'`), both already bound to the (per-tab-delegated) `ConnectionState` property. No XAML change was needed for the more specific text to actually reach the screen.

`TabSession.StatusDotColor`'s switch expression (which drives the tab strip's colored status dot — green/amber/red/grey) gained the two new strings alongside the pre-existing `"Connection failed"`/`"Invalid profile"` red cases, so a background tab that failed for one of these newly-specific reasons still shows the same red failure dot it always did, rather than silently falling through to the neutral grey "not yet connected" default (which would have been a real visual regression if this switch hadn't also been updated).

## Explicit non-goals

- **Surfacing the specific reason without switching to the tab.** This release makes the reason visible once a background tab becomes active (via the existing `ConnectionState` bindings); a tooltip or other always-visible indicator on the tab strip item itself was not part of the scoped fix and would be a separate, additive UI change.
- **Classifying network-level failures more granularly** (DNS failure vs. TLS failure vs. timeout, etc.). Out of scope — this release specifically mirrors what the foreground path already distinguishes, not a broader exception-taxonomy expansion.

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors. No XAML changes this release, so no recurring comment-parsing issue to watch for.
- No GUI click-through capability in this environment (unchanged, disclosed every version) — confirmed by direct code review that the new exception classification exactly mirrors `RefreshAsync`'s existing, already-correct logic (same conditions, same exception types, same triggering `GetHealthAsync` call), and that `StatusDotColor`'s red-case list was updated in lockstep so the new strings don't silently lose their error-color signal. Seeing the actual text/dot-color change on screen for a real background tab in one of these three states is left to the user.
