# v0.7.21.0 — Experimental Real-World Map Positions

## Background

Second of a two-part World Map sequence (v0.7.20.0 shipped bundled preset backgrounds first, deliberately decoupled from this higher-risk work). The user's actual goal for the two provided map images was real coordinate calibration — player dots at their true in-game position, not just relative spread among currently-online players.

This exact idea was attempted once before and abandoned: a `v0.7.0.2` comment in `RebuildPlayerMapPoints` records that a fetched community-wiki formula "didn't reconcile with the wiki's own worked example (off by several orders of magnitude)" and concluded "a coordinate transform that can't be verified numerically correct is worse than the existing, already-correct auto-fit behavior." This pass treats that as the design constraint to satisfy, not just a warning to note.

## What research found, and how it was verified

The open-source `palworld-coord` project (github.com/palworldlol/palworld-coord) has already reverse-engineered Palworld's `.sav`-file-coordinate-to-map-UI conversion. Two independent web lookups of that project's *documentation* returned the formula with the axes in different orders from each other — precisely the kind of unreconciled-source problem that sank the earlier attempt. Rather than pick one and hope, this pass fetched the project's actual source file (`src/palworld_coord/__init__.py`) directly:

```python
__transl_x = 123888
__transl_y = 158000
__scale = 459

def sav_to_map(x: float, y: float) -> Point:
    newX = x + __transl_x
    newY = y - __transl_y
    return Point(x=round(newY/__scale), y=round(newX/__scale))
```

This resolves to `mapX = (worldY - 158000) / 459`, `mapY = (worldX + 123888) / 459` — an axis swap (map X derives from world Y and vice versa).

Two independent checks confirm this is correct, not just plausible:
1. **The project's own README worked example**: `sav_to_map(-167230, 96430)` is documented as returning `Point(x=-134, y=-94)`. Plugging those inputs into the formula above (both by hand and via a standalone PowerShell calculation during this release's verification) reproduces `(-134, -94)` exactly.
2. **Internal consistency with the documented `.sav` coordinate bounds** `(-582888, -301000)` to `(335112, 617000)`: both axes span exactly `459000` units — exactly `1000 × 459` — landing precisely on the map coordinate space's own `-1000..1000` range with zero residual error. A formula with a lost scale/division step (the specific failure mode of the v0.7.0.2 attempt) would not reconcile this cleanly.

## What shipped

### `PalworldMapCoordinates` (new, `MystTiq.Desktop/Services`)

`ToMapUnits(worldX, worldY)` implements the verified formula directly. `ToCanvasPosition(worldX, worldY, canvasSize)` normalizes the resulting `-1000..1000` map-unit space to a `0..canvasSize` pixel position, assuming a center-origin, non-inverted mapping (see "What's still unverified" below for why this specific assumption isn't treated as confirmed).

### Opt-in toggle, gated to the Palpagos preset specifically

`MainWindowViewModel` gained:
- `IsPalpagosMapActive` — a computed property, `true` only when the currently-loaded background's real file path matches the Palpagos preset's own extracted path (`MapPresetService.TryGetPresetForPath`, new). Derived from the actual loaded path rather than a separately-tracked "which preset is active" flag, so it can't drift out of sync with what's really on screen.
- `UseCalibratedWorldPositions` — a plain opt-in bool, off by default, not persisted across restarts (deliberately — this is explicitly experimental, not a setting worth remembering yet).
- `RebuildPlayerMapPoints` gained a calibrated branch, taken only when both are true; every other case (World Tree preset, a browsed custom image, no background at all, or the toggle simply off) is byte-identical to the existing auto-fit relative-spread logic.

`MainWindow.axaml`'s World Map card gained a `CheckBox`, visible only when `IsPalpagosMapActive`, labeled "Experimental: real-world positions (Palpagos only)" with a tooltip stating outright that dots may appear mirrored or offset pending real-server confirmation.

## What's still unverified, and why this isn't the default

The conversion *math* (translate/scale constants, axis swap) is now numerically confirmed against an independent worked example and internally self-consistent with the documented `.sav` bounds. What is **not** confirmed by any source found during this research:

- Which corner of the specific `palpagos.png` image the map coordinate space's origin corresponds to.
- Whether the map's Y-axis needs an additional inversion for screen/canvas rendering (Y-down), the way the existing auto-fit path already inverts world-Y for exactly this reason.
- Whether the REST API's live `LocationX`/`LocationY` fields are guaranteed to be in the same coordinate space as the `.sav`-file `x`/`y` the source project's formula was built against (a reasonable assumption — both ultimately read the same underlying Unreal Engine world-transform state — but not independently proven here).

`ToCanvasPosition`'s current center-origin, non-inverted choice is a reasoned best guess (documented in the class's own header comment), not a confirmed one. Shipping this as an explicit, off-by-default, clearly-labeled toggle — rather than silently replacing the existing, already-correct relative-spread default — means a wrong guess here degrades nothing for anyone who doesn't opt in, and gives a path to promote it to default-on in a later release once a user can confirm it against a real server.

## Explicit non-goals

- **World Tree calibration.** No coverage for a second/DLC map was found anywhere in the source research. The toggle is deliberately gated to Palpagos only.
- **Persisting the toggle's state.** Matches its "experimental, not yet trustworthy enough to remember" framing.
- **Base or Pal positions.** Out of scope, unrelated to this release — still tracked as its own separate, longstanding gap (`docs/architecture/v0.6.16.0-live-world-map-player-positions.md`).

## Verification

- Full solution `dotnet build` (Release) — 0 warnings/0 errors, after fixing one instance of the recurring XML-comment-`--` AVLN1001 parse error in a new comment.
- The formula was independently re-derived and checked against the source project's own worked example via a standalone PowerShell calculation (not just eyeballed against the fetched web content) — confirmed exact match: `(-134, -94)`.
- No GUI click-through capability in this environment, and no live Palworld server to test real player positions against (unchanged, disclosed every version) — this is exactly why the feature ships opt-in with an explicit "may be mirrored or offset" disclosure rather than as a claimed-verified default. Confirming the image-orientation assumption against a real server is left to the user, and is the actual gate for whether this could become the default in a future release.
