# v0.7.51.0 — Per-Tab Color Coding

## Goal

Item 2 from the original GUI walkthrough findings log: tabs need a persistent identity color so
it's obvious at a glance which server a tab points at, once several are open. Three open questions
were left for implementation time; resolved as follows.

## Design decisions

**Auto-assigned, not user-assigned.** Round-robin over a fixed 10-color palette
(`ThemeCatalog.TabIdentityColorNames`), keyed by `Profiles.Count` at the moment a genuinely new
profile is created. No new settings surface, works immediately for every profile without requiring
the user to configure anything.

**Tab strip only, not the nav pane or main content.** Those other surfaces already carry *page*
identity from v0.7.48.0's accent system (Server=blue, World=cyan, Mods=magenta, etc.) — tinting them
again with a *server*-identity color would make the two signals indistinguishable from each other.
The tab strip itself was the one surface not already claimed.

**Kept separate from `StatusDotColor`.** The existing status dot is a live health signal
(green/amber/red/grey, derived from `ConnectionState`). The new stripe is a fixed identity marker,
independent of health. Both render side by side in the tab template rather than merging into one
color.

## Implementation

- `ConnectionProfile.AccentColorKey` (new optional record parameter, defaults to `"Blue"` — older
  persisted profile JSON without this field deserializes safely to the default).
- `ThemeCatalog.TabIdentityColorNames`: the same 10 base names (`Blue`, `Cyan`, `Violet`, `Magenta`,
  `Orange`, `Green`, `Amber`, `Red`, `Purple`, `DarkGreen`) `DerivedColorNames` already produces
  brushes for, minus `Neutral` (too muted to read as a distinct identity marker).
- `MainWindowViewModel.ResolveAccentColorKey(existingId, tabProfile)`: reuses an already-known
  profile's color (looked up by id in `Profiles`, or from the tab's current `Profile` directly) so
  it survives edits/reconnects; only assigns a fresh color when neither source has one. Both
  `BuildProfileFromEditor` and `BuildProfileFromTab` — which already construct a brand-new
  `ConnectionProfile` record on every save/reconnect, an existing pattern unrelated to this feature
  — call through this before constructing the record.
- `TabSession.AccentBrush`: resolves `Profile.AccentColorKey` to the live
  `{Name}AccentBorderBrush` resource via `Application.Current.TryGetResource`. This is a plain
  bound value, not `{DynamicResource}` in XAML, because the tab template is a dynamic
  `ItemsSource`/`DataTemplate` over `TabSession` objects rather than a fixed page element — so it
  does not auto-refresh when `ThemeApplier` rewrites the resource's value on a theme switch.
  `RefreshAccentVisual()` re-resolves and re-raises change notification; called from `Profile`'s own
  setter (a tab getting/losing its profile) and from `MainWindowViewModel.RefreshTabAccentVisuals()`
  (all open tabs, called right after each of the two existing `ThemeApplier.Apply` call sites).
- `MainWindow.axaml`: the tab template's `Grid` gained a new first column (`4,10,*,Auto`, was
  `12,*,Auto`) holding a thin colored `Rectangle` bound to `AccentBrush`; the status dot, name text,
  and close button all shifted one column over. The existing selected-tab highlight style
  (`ListBoxItem:selected Border.serverTabSurface`) is untouched.

## Verification

`dotnet build` on `MystTiq.Desktop` and the full solution — clean. One AVLN1001 `--` XML-comment
error hit and fixed in this version's own new comment (the same recurring pattern this session has
hit repeatedly whenever touching XAML comments).

## Known gaps (disclosed)

- No visual verification possible in this environment — same limitation as every prior version
  touching the UI. The stripe's actual rendered appearance, spacing, and whether 3px reads clearly
  at the tab strip's compact size were not confirmed visually.
- The palette is a fixed round-robin; no way to manually reassign a color if two profiles happen to
  land on similar-looking adjacent hues, or to intentionally color-code servers by role (e.g. "all
  production servers red"). Not requested in the original finding — flagged here in case it comes up.
