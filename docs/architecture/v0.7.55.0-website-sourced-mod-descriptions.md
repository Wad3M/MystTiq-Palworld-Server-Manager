# v0.7.55.0 — Website-Sourced MOD Descriptions

## Goal

Item 40's deferred half: MOD Library's MOD DETAILS panel (v0.7.40.0) shows real, locally-derived
evidence about an installed MOD's health/runtime state, but never a description of what the MOD
actually *does* — the kind of text a user would normally read on the MOD's own Steam Workshop or
GitHub page before installing it. Deferred at the time because it needed its own design pass: MODs
in this app come from genuinely different sources (Steam Workshop items with a numeric ID, UE4SS/Lua
content typically from GitHub or Nexus Mods with no uniform ID scheme), and fetching arbitrary web
content from an admin tool deserved a scope/security decision before any code was written.

## Scope decision, made before writing any fetch code

Asked directly how to scope this; the answer was to design for multiple sources up front (Steam
Workshop plus at least one more, e.g. Nexus Mods) rather than shipping Workshop-only and bolting on
a second source later.

Nexus Mods was investigated and set aside for this version, honestly rather than silently: it has no
public, keyless API — fetching from it would mean either scraping HTML (fragile, against most sites'
terms, and this project already treats "no reliable API" as a real "Unavailable" case rather than a
thing to work around, per `HeadlessComponentUpdateService`'s own established convention for
Python/VC++/MSVC) or requiring the user's own Nexus API key (a real option, but a bigger scope
decision than this version needed to make on its own). Instead, the second source is GitHub — the
actual origin of most of the installed UE4SS/Lua content in this project's own test environment
(AntiDupe, AdminCommands, etc. are GitHub-hosted), reachable via a genuinely public, keyless,
well-documented REST API. This satisfies the "design for multiple sources" instruction with two real
sources rather than one real source and one placeholder.

## The two sources

### Steam Workshop (automatic match, no user input needed)

Reuses `HeadlessModManagementService.FindMatchingWorkshopItem` — the exact same local-Workshop-cache
match `CheckModUpdateAsync` (v0.7.41.0) already performs, so a MOD that's already known to have a
Workshop match for update-checking purposes needs no separate configuration here. Once a
`WorkshopId` is known, a real Steam Web API call
(`POST https://api.steampowered.com/ISteamRemoteStorage/GetPublishedFileDetails/v1/`,
`itemcount=1&publishedfileids[0]=<id>`, no key required for public items) returns the item's title
and `file_description`.

Steam Workshop descriptions use the platform's own lightweight BBCode dialect (`[h1]`, `[list]`,
`[*]`, `[url=...]`, `[b]`/`[i]`, etc.). `StripBasicBbCode` strips tag markup with a single regex
rather than rendering it — a disclosed, deliberate simplification (see Known gaps) rather than
building a second markup renderer into an admin tool for one text field.

### GitHub (manual opt-in, for MODs with no Workshop match)

When `FindMatchingWorkshopItem` finds nothing, the panel offers a Source URL text box instead of
failing silently. Setting a `github.com/<owner>/<repo>` URL persists it (`SetModDescriptionSourceAsync`)
and, from then on, `GetModDescriptionAsync` fetches that repository's real `description` field via
`GET https://api.github.com/repos/{owner}/{repo}` (public, unauthenticated, rate-limited but fine for
an on-demand per-MOD lookup, matching the same GitHub REST usage already established by
`HeadlessComponentUpdateService`/`HeadlessUe4ssReleaseCatalogService`). A Source URL that isn't a
recognized `github.com` repository (or that GitHub can't resolve) is still saved and shown as a plain
link — "open it yourself" rather than pretending a description was fetched.

## Security/scope discipline

- **Every fetch is on-click only.** Neither selecting a MOD in the list nor navigating to MOD Library
  triggers a network call — only the panel's own Fetch/Refresh button does, and only for the
  currently selected MOD. `MainWindowViewModel.FetchSelectedModDescriptionAsync` is the sole caller
  of the description-fetching route on the client.
- **Results are cached to disk**, one JSON file per MOD under
  `{ManagerRuntimeRoot}/mod-descriptions/{TYPE}_{package}.json` (mirroring the existing
  `mod-snapshots`/`ue4ss-snapshots` naming convention), so repeat views of the same MOD don't
  re-fetch — only an explicit Refresh (a description already showing) forces a new outbound call.
- **Outbound calls are limited to two public, unauthenticated, read-only endpoints** (Steam Web API,
  GitHub REST API) — no credentials are sent, no write access is requested of either service, and no
  other domain is ever contacted. A manually-set Source URL is validated as an absolute `http(s)`
  address before being stored; a non-GitHub URL is never auto-fetched, only displayed.

## Implementation

- **Backend** (`HeadlessModManagementService.cs`): `GetModDescriptionAsync(type, package,
  forceRefresh, ct)` and `SetModDescriptionSourceAsync(type, package, sourceUrl, ct)`, plus private
  helpers `TryFetchSteamWorkshopAsync`, `TryFetchGitHubAsync`, `TryParseGitHubRepo`,
  `StripBasicBbCode`, and disk cache read/write/delete helpers. New DTOs:
  `HeadlessModDescriptionResult`, `ModDescriptionCacheEntry` (the cache file's own shape), plus
  private Steam/GitHub response DTOs. New static `DescriptionHttp` client (10s timeout, MystTiq user
  agent), mirroring `HeadlessComponentUpdateService.BuildHttpClient`'s existing pattern rather than
  inventing a new HttpClient convention.
- **Routes** (`LocalManagementApiHost.cs`): `GET /mods/{type}/{package}/description?refresh=` (always
  safe — only reads cache unless `refresh=true`), `POST /mods/{type}/{package}/description/source`
  (`ModDescriptionSourceRequest(string SourceUrl)`).
- **Desktop client**: `ModDescriptionResultDto`, `ModDescriptionSourceRequestDto` in
  `ModManagementDtos.cs`; `IMystTiqApiClient.GetModDescriptionAsync`/`SetModDescriptionSourceAsync`
  and their `MystTiqApiClient` implementations, matching `CheckModUpdateAsync`'s existing
  GET-with-query-string / POST-with-body shapes.
- **ViewModel**: `SelectedModDescription` (nullable DTO, null until fetched), `HasSelectedModDescription`
  (true only when `Available`), `HasModDescriptionResult` (true once any fetch attempt has completed,
  success or not — drives the status-detail line), `SelectedModDescriptionSourceInput` (bound
  TextBox), `FetchSelectedModDescriptionCommand`, `SetSelectedModDescriptionSourceCommand`. All reset
  to empty in `SelectedMod`'s setter — the same "stale result from a different MOD" discipline
  `SelectedModUpdateText`/`_selectedModUpdateWorkshopId` already established in v0.7.41.0.
- **XAML**: a new DESCRIPTION section in MOD DETAILS (`MainWindow.axaml`, MOD Library page), below the
  existing UPDATE section — a Fetch/Refresh button, conditional Source/Title/Description/link display,
  a status-detail line, and a Source URL text box + Set Source button for the manual-source path.

## Verification

`dotnet build` on the full solution — clean, 0 warnings/errors.

## Known gaps (disclosed)

- **BBCode is stripped, not rendered.** Steam Workshop descriptions with embedded images
  (`[img]...[/img]`), tables, or nested lists will read as slightly flattened plain text. A real
  BBCode-to-Avalonia-markup renderer is a meaningfully bigger piece of work for a marginal display
  improvement on one text field — not attempted here.
- **Nexus Mods is not a supported source.** No public, keyless API exists for it; adding real support
  means either scraping (fragile, likely against Nexus's terms) or asking the user for their own API
  key — both bigger decisions than this version's own scope. MODs sourced from Nexus can still use
  the manual Source URL field; they just won't get an auto-fetched description, the same honest
  "Manual Link" treatment any unrecognized source URL gets.
- **No visual verification possible in this environment** — same standing limitation as every version
  touching the UI in this session; the new panel section's exact layout/spacing is not confirmed
  against a rendered window.
- **The Steam Web API call is unauthenticated and rate-limited by Steam, not by this project** — Steam
  may throttle or reject a burst of requests from the same IP; since fetches are strictly on-click and
  cached, this is expected to stay well under any real limit in normal use.
