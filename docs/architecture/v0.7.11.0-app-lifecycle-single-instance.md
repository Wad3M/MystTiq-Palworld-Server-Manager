# v0.7.11.0 — App Lifecycle: Single-Instance, Tab-Close Confirmation, Tray Reminder

## Background

Direct request, distinct from the prior bug-scan/competitive-survey sequence (v0.7.6.0–v0.7.10.0): verify multi-server operation actually works, confirm before closing a running tab, remind the user MystTiq is still running when minimized to tray, only fully close when nothing is running, and block a second instance from launching. A documentation consistency audit was also requested and folded in here since its findings were small.

Before writing any code, the existing infrastructure was checked first — much of the tray/exit surface already existed (`App.axaml`'s `TrayIcon`/`NativeMenu` with Show/Start/Restart/Stop/Safe Exit/Force Exit/Exit GUI Only, `App.axaml.cs`'s `HideMainWindowToTray`/`ShowMainWindow`/`RequestExplicitExit`, `ShutdownMode.OnExplicitShutdown`). The actual gaps were narrower than they first appeared: the close button's behavior was unconditional (always minimize, never fully exit), there was no tray notification of any kind, no tab-close confirmation existed, and there was no single-instance guard at all.

## What shipped

### Window close (X) behavior now depends on whether anything is running
`MainWindow_Closing` previously always cancelled the close and hid to tray, checking nothing. It now checks `Tabs.Any(t => t.ServerIsRunning)` — every open tab, not just the currently-focused one, since Fleet allows several servers to run at once and the previously-active tab is not necessarily representative. If nothing is running, `App.ExitGuiOnlyIfNothingIsRunning()` (a thin wrapper around the existing `RequestExplicitExit()`, the same method the tray menu's "Exit GUI Only — keep services running" item already calls) performs a real, clean exit — there was previously no way to fully quit via the window's own close button at all, ever, regardless of state. If something is running, the existing hide-to-tray behavior is preserved, now paired with a visible reminder (below).

### Tray reminder toast
Avalonia's `TrayIcon` control was checked against its current documentation and source (`Avalonia.Controls.TrayIcon`) before building anything — it exposes `Icon`/`ToolTipText`/`Menu`/`Command`/`IsVisible`/a `Clicked` event, and explicitly no balloon or toast notification API. `TrayReminderToast` (`Views/`) is a small, `SystemDecorations="None"`, `Topmost`, non-taskbar window that self-positions to the bottom-right of the current screen's working area and auto-closes after 5 seconds, standing in for the missing native capability. Shown via a new `App.ShowTrayStillRunningReminder(string message)`, called from `MainWindow_Closing` only on the "something is still running" branch.

### Tab-close confirmation
Closing a tab whose server is running previously left it running with no confirmation of any kind and no way to stop it from that interaction. `Views/ConfirmCloseTabDialog` is a small modal (`ShowDialog<ConfirmCloseTabResult>`) offering **Stop & Close**, **Leave Running**, or **Cancel**. The close button in the tab bar (`MainWindow.axaml`) moved from `Command="{Binding CloseTabCommand}" CommandParameter="{Binding}"` to a code-behind `Click` handler (`CloseTabButton_OnClick`) carrying the `TabSession` via `Tag="{Binding}"` — consistent with this codebase's existing pattern of code-behind owning anything that needs a native dialog or window, rather than giving the ViewModel a View reference or building a request/response event for what is otherwise a one-off interaction. A new `MainWindowViewModel.StopTabServerAsync(TabSession tab)` stops the *specific* tab chosen — built the same way `RefreshTabLightweightAsync`/`BuildProfileFromTab` already operate directly on a background tab's own fields, never through the `ActiveTab`-delegated properties (which would silently target whichever tab is currently focused, not necessarily the one being closed).

### Single-instance enforcement
`Program.Main` now acquires a named `Mutex` (`MystTiq.Desktop.SingleInstance`, no `Global\` prefix — that convention is Windows-only, and a plain named Mutex is supported cross-platform in .NET) before starting the Avalonia classic desktop lifetime. If the mutex already exists, the second launch shows a native `MessageBox` (Windows, via a direct `user32.dll` P/Invoke — the simplest way to notify a user who just double-clicked the exe with no attached console) or writes to stderr on other platforms, then exits immediately without starting any UI.

## Multi-server simultaneous operation — verified live, not just re-read from the architecture

Rather than assume the existing v0.6.2.0 fleet architecture (each profile gets its own `IServerPathProfile`/`IServerLifecycleService`/lock scope) was sufficient evidence, two full sidecar instances were actually started at once, on two different ports (18230/18231), against two separate isolated server roots. Both reported healthy (`/healthz`) simultaneously under distinct process IDs; each independently created a real backup via `/api/v1/backups/create`, and each instance's `/api/v1/backups` listing contained only its own file — zero cross-contamination confirmed. No code changes were required; this was a verification pass proving the existing design, not a fix for a found bug.

## Documentation consistency audit

A dedicated pass checked README's roadmap table, `docs/index.html`, `CHANGELOG.md`, and every v0.7.6.0–v0.7.10.0 architecture/release-notes file for internal consistency — all confirmed already correct. Four stale labels were found and fixed in `docs/roadmap/`, all predating this session and unrelated to the v0.7.x line: two roadmap-doc headers still marked long-shipped v0.3.1.0/v0.5.1.1 milestones "(Current Candidate)"/"(Current Release Candidate)", a backport-tracking registry table still showing "In progress"/"Planned" for now-shipped v0.3/v0.4 rows, and three "(planned)" tags on v0.6.16.0–v0.6.18.0 that were never updated after those milestones actually shipped.

## Explicit non-goals

- **Bringing an already-running instance's window to the foreground** when a second launch is blocked — the single-instance guard currently just notifies and exits; activating the existing window from a second process would need inter-process signaling (a named pipe, per Avalonia's own community-documented pattern for this), which is a reasonable future enhancement but wasn't requested and adds real complexity for a secondary convenience.
- **A persistent/dismissable tray notification** — the toast is a fixed 5-second auto-dismiss; no "don't show this again" preference was added, since the request was for a reminder on every close-to-tray, not a one-time notice.
- **Documentation fixes beyond what the audit specifically flagged** — `WINDOWS_BACKPORT_REGISTRY.md`'s two "Discovery backlog" rows were left untouched since the audit did not find them contradicted by anything shipped.

## Verification

`dotnet build` (full solution, Release) — 0 warnings/0 errors. No server-side code touched, so the frozen v0.7.10.0 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected. Multi-server simultaneous operation verified live (above).

**Disclosed verification gap, unchanged since v0.6.4.0**: no GUI click-through capability in this environment. The close/tray/dialog/single-instance logic was traced by hand against the actual call graph and Avalonia's documented API surface, but the toast's exact on-screen position, the dialog's visual layout, and the native message box's appearance are the user's to confirm once run.
