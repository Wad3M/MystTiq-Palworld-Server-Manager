# v0.7.31.0 — Duplicate-Install Prevention

## Goal

Seventh version in the GUI/workflow/UX overhaul roadmap. Item 3 from the roadmap's findings log, requested directly: "there should be no reason to have multiple tabs connecting to the same server. They can have the same port, but the location of the install should be different." Two connections are the same server if their install directories match — not if their host/port match, since two genuinely different remote servers can coincidentally share a port.

## What was investigated first

Before implementing, the existing duplicate-tab guard was checked: `ConnectExistingProfileTab` (`MainWindowViewModel.cs`) already blocks re-opening a tab for a profile already open, but only by matching `profile.Id` — a persisted `ConnectionProfile` record's own identity, not the server's install location. It also only runs when reconnecting to an *already-saved* profile, never during the "Set Up New Server" wizard.

The deeper constraint found: `ConnectionProfile` (the record that actually gets persisted — `Models/ConnectionProfile.cs`) has no install-location field at all. It's just `Id`, `Name`, `BaseAddress`, and an optional certificate pin. The install directory (`ServerRoot`) is something the *server itself* reports about its own configuration — it can only become knowable after a connection already succeeds and the client asks. This rules out blocking the setup wizard *before* a connection exists (there's nothing to compare yet); the check can only run *after* connecting, as a warning once the match is discovered.

## What shipped

### Capturing each tab's install location for free

`RefreshDashboardBackendAsync` already calls `_api.GetServerDistributionStatusAsync(profile, BearerToken)` on every routine Dashboard refresh for the active tab, and that response (`ServerDistributionStatusDto`) already carries a `ServerRoot` field — used elsewhere for install-existence checks, but never previously cached anywhere per-tab. New `TabSession.ServerRoot` stores it; the existing distribution-status call in `RefreshDashboardBackendAsync` now also writes `ActiveTab.ServerRoot = distribution.ServerRoot` when non-empty. No new network calls were needed — this is data already being fetched, just not kept.

### Detecting the duplicate

New `MainWindowViewModel.RecomputeDuplicateInstallWarnings()`: groups every open tab by `ServerRoot` (case-insensitive), and for any group with more than one tab, sets a `TabSession.DuplicateInstallWarning` message on each member naming the shared path; tabs not in a duplicated group get their warning cleared. It's recomputed from scratch on every call rather than tracking which specific pair triggered it — simpler, and correctly self-heals if a tab closes or a later poll finds the roots actually differ, without needing separate invalidation logic. Called after every successful distribution-status refresh, and again when a tab closes (`CloseTab`), so a warning clears promptly once the conflict is gone.

### Surfacing it

A new amber warning banner on the Dashboard page, `IsVisible="{Binding ActiveTab.HasDuplicateInstallWarning}"`, showing `ActiveTab.DuplicateInstallWarning`'s text (which names the actual shared install path). Placed above the existing "LIFECYCLE" card, only visible while the active tab genuinely has an unresolved conflict.

## Explicit non-goals

- No hard block on the setup wizard — the install location genuinely can't be known before connecting, so this is a post-connection warning by necessity, not a design choice to make it less strict than requested.
- No change to `ConnectExistingProfileTab`'s existing `profile.Id`-based guard — that's a different, still-valid check (don't open two tabs for the literal same saved profile) that this doesn't replace, just complements.
- No attempt to auto-close or auto-merge duplicate tabs — the warning informs the user, who decides what to do about it (close one, or knowingly keep both, e.g. while migrating a server).
