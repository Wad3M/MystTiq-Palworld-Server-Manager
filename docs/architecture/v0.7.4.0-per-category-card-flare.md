# v0.7.4.0 — Per-Category Card Flare

## Goal

Fourth slice of the v0.7.x UX plan: "add some flare to the different cards." Investigation during v0.7.1.0's planning found 172 of 176 total card-styled panels (`Border.card`/`Border.statuscard`) across the app were completely plain, with color accents concentrated almost entirely on the Dashboard (3 elements). Asked the user whether to extend the existing status-glow pattern to a few more high-value cards, or go broader — the user chose the broader decorative pass.

## Grounding

The app already has a proven visual language for card accents: `Border.card.glowGreen`/`glowRed`/`glowAmber`/`glowPurple`/`glowDarkGreen`/`glowNeutral` (a swapped gradient background + a colored `BoxShadow` glow), used today only for genuinely status-driven signals (the Dashboard's SERVER/health cards, dynamically toggled based on real state). The 7 nav categories (Home/Server/World/Backups/Mods/Tools/System) already each have their own established accent color, visible today on the category tabs themselves (`ToggleButton.categoryTab.server:checked` → `#52C4FF`, `.world` → `#B87BFF`, `.backups` → `#F4B83F`, `.mods` → `#E676FF`, `.tools` → `#FF9558`, `.system` → `#72C8E8`; Home uses the tab's own default `#5AD4FF`).

Rather than reuse those exact tab colors (some are visually very close to each other) or invent an entirely new background-swap treatment for ~169 cards (too loud applied that broadly), each category was assigned one of the theme's existing accent hues (Blue/Cyan/Violet/Amber/Magenta/Orange/Green) and given a **much softer** treatment than the status glows: a blended (not fully saturated) border color plus a low-alpha (~0x30 vs the status glows' ~0x5A) ambient glow, keeping the existing `CardGradient` background untouched. This keeps the effect present but calm across dozens of cards on one page, rather than competing with the existing dynamic status glows for visual attention.

## What shipped

- **`Styles/DesignSystem.axaml`**: 7 new style pairs — `Border.card.accentHome`/`Border.statuscard.accentHome` (Blue), `accentServer` (Cyan), `accentWorld` (Violet), `accentBackups` (Amber), `accentMods` (Magenta), `accentTools` (Orange), `accentSystem` (Green) — each setting only `BorderBrush` (a blended tone) and `BoxShadow` (a soft, low-alpha glow in the category's hue). Declared immediately before the existing `Border.card.glowGreen` etc. selectors: both are 2-class selectors of equal specificity, so Avalonia's declaration-order tiebreaker means a genuine status glow always wins over a decorative category accent on the rare element that could carry both.
- **`MainWindow.axaml`**: every page's `Classes="card"`/`Classes="statuscard"` `Border` was tagged with its category's accent class (mechanically, via a line-range-aware script matching each page's `IsVisible="{Binding IsXxxPage}"` boundaries against the existing category groupings from v0.6.19.1's ribbon-cleanup investigation) — 129 `card` + 40 `statuscard` = 169 elements tagged. The Monitoring page (which multiplexes Console [Server category] and Activity & Audit [System category] content in one shared `IsVisible="{Binding IsMonitoringPage}"` block) was handled specially, tagging each card by its own inner `IsConsolePage`/`IsActivityAuditPage` visibility rather than a single fixed line range. The 3 Dashboard cards that already carry a dynamic status-glow toggle (`Classes.glowGreen="{Binding IsServerGlowGreen}"` etc.) were explicitly excluded to avoid any visual competition between the two systems on the same element; the always-visible nav-sidebar status footer (not tied to any one category) was left untouched.
- Verified visually before committing: rendered all 7 accent treatments (border + glow, over the same card background/gradient used in the real app) as HTML in the Browser pane and inspected an actual screenshot — confirmed each category reads as clearly distinct from its neighbors and none overwhelm the card's own content, the same verification technique introduced for the v0.7.0.0 theme colors and v0.7.1.0's icon.

## Explicit non-goals

- No change to the 3 Dashboard cards' existing dynamic status-glow behavior, or to the always-visible nav-sidebar status footer.
- The no-scroll initiative (the other half of v0.7.4.x) — explicitly deferred, framed as an ongoing multi-release effort rather than a single deliverable, per the approved plan.
- No new gradient/background treatment — only `BorderBrush`/`BoxShadow`, keeping every card's existing background untouched.
- No server-side change.

## Verification

`dotnet build` (Release) — 0 warnings/0 errors. This release touches zero server-side code, so the frozen v0.7.3.0 checkpoint regression gate and the full v0.5.1.5 runtime smoke suite are expected — and confirmed — fully unaffected.

**Disclosed verification gap, unchanged from every checkpoint since v0.6.4.0**: no GUI click-through capability in this environment. The 7 accent color/glow combinations were rendered as standalone HTML swatches and visually inspected via screenshot before being written into the real stylesheet — a genuine, if partial, mitigation of the usual gap — but the actual on-screen result of ~169 tagged cards across the real running app, at real card sizes and real page layouts, is the user's to confirm once built.
