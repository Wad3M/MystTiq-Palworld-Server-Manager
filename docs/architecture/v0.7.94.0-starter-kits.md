# v0.7.94.0 — Starter Kits

## Context

Third and last of the "real gaps" sequenced after the competitive feature review: a kit/starter-package
system (a named item/Pal loadout that can be given by hand, or automatically to new players). It is
sequenced before the v0.8.x give-item work, so it had to be built around the one hard constraint that
work shares.

## The constraint

Vanilla Palworld has no give command (that is why the Players page's Give Item button is hard-wired
disabled). PalDefender, a server mod, adds `giveitems <UserId> <ItemId>[:<Amount>] ...` and
`givepal <UserId> <PalId> [Level]`, documented as runnable over RCON
(ultimeit.github.io/PalDefender/Commands). So kits deliver only when PalDefender is installed and RCON is
usable, and say so plainly when not. The user's Default Server has PalDefender (folder present, and it
already logs into the Dashboard); freshly created servers do not.

Delivery sits behind `IKitCommandRunner` with an RCON-backed production runner, so the v0.8 give-item
decision (which provider) can slot in without touching kit storage, claim tracking or auto-gift.

## Design (`HeadlessKitService`, server-side, like the whitelist)

- **Storage:** `players/kits.json` (kits + auto-gift settings) and `players/kit-claims.json`, atomic
  writes. Config is read/replaced as a whole (the whitelist convention).
- **Validation (pure, unit-tested):** ids are letters/digits/underscore only, amounts 1..1,000,000, Pal
  levels 1..100, at most 50 kits and 100 entries each, unique kit ids, non-empty kits, and auto-gift must
  name an existing kit. Because ids are interpolated into RCON text, the strict id and UserId patterns are
  also the injection guard (no spaces, no newlines).
- **Commands (pure, tested):** items grouped 20 per `giveitems`, each Pal its own `givepal`; a UserId that
  is not `[A-Za-z0-9_-]{3,64}` produces no commands.
- **Success is not trusted blindly:** the reply text of these commands is not formally specified, so a
  reply that reads as an error ("unknown", "invalid", "failed"...) counts as a failed delivery and is not
  recorded as a claim.
- **Auto-gift semantics — the important safety decision.** Only a player the player registry **first saw at
  or after the moment auto-gift was enabled** is gifted, once, and never a player already known. Enabling
  it therefore never mass-gifts everyone who already plays here. The cutoff is stamped when auto-gift is
  switched on, kept on an unchanged re-save, moved forward if the auto-gift kit changes, and cleared when
  it is turned off. Definition disclosed in the UI: "first seen by MystTiq", not "new to the server".
- **No spam:** at most 3 delivery attempts per player (then it logs and gives up; Give Kit and Reset Claims
  retry by hand), one enforcement pass at a time, and nothing is attempted while the provider cannot
  deliver or the player is offline.
- **Hook:** `EnforceAsync` runs from the same `/status/poll` cadence as the registry and whitelist,
  after the registry's `Observe`.
- **Routes:** `GET /players/kits` (Operator), and Admin-only `PUT /players/kits`,
  `POST /players/kits/test-provider` (sends `version`, returns the raw reply), `POST
  /players/kits/{id}/give`, `DELETE /players/kits/claims/{playerId}`.

## Desktop

A collapsed "Starter Kits" card on the Players page (next to Whitelist): provider status and a **Test
PalDefender** button, kit list, name, and an entries editor with one entry per line (`item PalSphere 10`,
`pal WeaselDragon 5`; shorthand `Money 500`; `#` comments). `KitEntryText` (Core, tested) parses it and
names the offending line. Edits sync live into the selected kit; Save refuses while a line does not parse.
Also: auto-gift checkbox and kit picker with the cutoff explained, **Give Kit To Selected Player**
(online players only; uses the directory or map selection), **Reset Player's Claims**, and recent claims.

## Verification

- Solution and Desktop builds clean, 0 warnings/errors.
- Logic harness: 9 new scenarios pass — validation, command grouping/UserId refusal, failure-text
  detection, and the enforcement rules end to end with a fake runner and a real registry (existing players
  never gifted; a new player gifted exactly once; nothing while disabled; retries capped at 3 and not
  recorded as claimed; a claim reset allows a retry; no provider means no commands; offline manual give
  refused; cutoff stamping), plus `KitEntryText` parse/round-trip/errors.
- Live: after relaunch, `GET /players/kits` on the real Default Server (read-only) reports PalDefender +
  RCON detected. On the scratch server (`mysttiqclaude`, since cleared): a valid `PUT` saved and stamped the
  cutoff, an invalid one returned HTTP 400, provider status and `test-provider` honestly reported
  PalDefender missing, and a manual give to an absent player returned 409.
- **Not verified:** PalDefender's actual reply/syntax was not exercised live. Confirming it needs the
  Default Server running with an online player, and starting your production server was out of scope. The
  syntax follows PalDefender's published docs; the **Test PalDefender** button and the error-text check
  exist precisely so a mismatch shows up as a clear message instead of a silent non-delivery. No GUI
  automation exists for the native app, so the card was verified by build and control-flow trace.
