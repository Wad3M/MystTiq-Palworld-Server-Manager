# v0.7.77.0 — MOD/Workshop Detection Fixes, UE4SS Version via Hash, Per-MOD Repair

Direct live investigation, prompted by three real observations against the user's actual
production install: (1) Steam Workshop items reported "NOT INSTALLED" when the user believed they
were, (2) UE4SS's own page showed "Installed — version metadata unavailable" despite an ask for
*some* real version signal, and (3) a real discrepancy between the currently-detected 6 installed
MODs and a remembered "8" from an earlier build (v0.2.16.4).

## Investigation, not guesswork

Before writing any code, inspected the real file system directly:
- The real Steam Workshop content lives on a **second** Steam library (`E:\SteamLibrary`), not the
  default `C:\Program Files (x86)\Steam` — confirmed present, not missing.
- **QualityOfLife**'s `.pak` files physically existed but were renamed to
  `*.pak.quarantined-slow-start-cause` (dated Aug 9) — manually disabled at some point, almost
  certainly during a past startup-freeze investigation, and never restored. Unreal never loads a
  file with that extension.
- **PalSchema** only existed in inert staging folders (`Server\Mods\...`) that UE4SS never reads
  from — an import that started but was never finished.
- **UE4SS Experimental (Palworld)**'s bundled `UE4SS.dll` is **SHA-256 identical** to the real,
  actively-loaded `UE4SS.dll` — confirmed via a direct hash comparison. This Workshop item isn't a
  mod at all; its own manifest declares an `InstallRule` of type `"UE4SS"` — it's a full runtime
  distribution, and the currently-running UE4SS almost certainly came from installing it.

## Fix 1: Workshop "installed" detection for runtime-type items

`DescribeWorkshopItem` always checked a Workshop item's package name against the *mod* inventory —
correct for PalSchema/QualityOfLife (real mods, genuinely absent), but wrong for a Workshop item
whose manifest declares itself as the UE4SS runtime, since the mod inventory by definition never
contains the runtime itself. `DescribeWorkshopItem` now takes a `ue4ssInstalled` flag
(`Directory.Exists(paths.Ue4ssRoot)`) and uses that instead of the mod-inventory check when
`hasRuntime` is true.

## Fix 2: UE4SS version via local-Workshop-copy hash match

New `TryDetectVersionFromLocalWorkshopHash()`, added as a step in `DetectUe4ssVersion()` before the
final "version metadata unavailable" fallback: hashes the real active `UE4SS.dll`, then hashes every
locally-discoverable Workshop item's own bundled `UE4SS.dll` (for items whose manifest declares a
`"UE4SS"`-type rule); on a SHA-256 match, reports that item's own declared `Info.json` `Version`
field, clearly labeled as hash-matched rather than presented as unconditional fact:
`"2281fa31 (matched via local Workshop item 3625223587, SHA-256 identical)"`.

**A second real bug found live while wiring this up**: the real install has *two* different
`UE4SS.dll` files side by side — a stale one at the legacy root-level location
(`Pal/Binaries/Win64/UE4SS.dll`, 16 MB, dated Feb 2024) and the real active one at the modern
location (`Pal/Binaries/Win64/ue4ss/UE4SS.dll`, 20 MB, dated Sept 2026). The naive candidate order
checked the legacy path first, silently hashing the wrong file. New `ResolveActiveUe4ssDllPath()`
mirrors `ResolveUe4ss()`'s own modern-vs-legacy preference instead of guessing by fixed order, and
is now the only place this version's own new code resolves "the active UE4SS.dll" from. (The
pre-existing `FileVersionInfo` loop earlier in `DetectUe4ssVersion()` still uses its own original
candidate order — left untouched, since it only ever returns on a genuinely *meaningful*, non-zero
stamped version, a narrower and lower-risk case than this session's own new hash-comparison code.)

## Real data restored (direct user request, live action against the real server)

With the user's explicit go-ahead, actually imported PalSchema and QualityOfLife into the real
active mods folder via the already-existing, already-proven `ImportWorkshopItemAsync` — no new
mutation logic needed for this part. `mods.txt` now lists exactly 8 mods, matching what the user
remembered from v0.2.16.4. The old orphaned `.quarantined-slow-start-cause` files are still present
(owned by `BUILTIN\Administrators`; this session's non-elevated process couldn't remove them,
consistent with this project's standing practice of never elevating itself) but are harmless — the
invalid extension means Unreal will never load them regardless.

## New: per-MOD Repair / Re-install

Direct request: "if a MOD is incomplete there should be an option for repair/re-install." Distinct
from two things that already existed and could be mistaken for it: `CheckModUpdateAsync`/Update
(only offers a re-import when Steam's local copy is *newer* than what's installed — an incomplete
install isn't necessarily older) and the existing global "Repair" button (`RepairAsync`, which only
neutralizes legacy `enabled.txt` overrides and ensures `mods.txt` exists — it never touches a MOD's
own file content).

New `HeadlessModManagementService.RepairModAsync(type, package)`: finds a matching local Workshop
item via the already-existing `FindMatchingWorkshopItem`; if none is known, fails honestly rather
than guessing at a source. If found, **deletes the existing install first, then re-imports fresh** —
found live that a naive straight re-import fails outright (`InstallUe4ssFiles` correctly refuses to
overwrite an existing MOD folder, by design, to protect a normal Import from silently clobbering
something). Reusing the existing `DeleteAsync` (which already captures a pre-delete snapshot via
`CaptureSnapshot`) rather than adding a new overwrite code path to the shared install method means
Repair gets the exact same Rollback safety net every other MOD delete already has, with no new risk
introduced to that shared, sensitive install logic. New route:
`POST /mods/{type}/{package}/repair`. Desktop: a new "Repair / Re-install Selected" button next to
Rollback Selected on the MOD Library page.

## Verification

Everything in this version was live-verified against the real production install (no isolated
clone needed — none of this touches player save data, only mod files and read-only detection
logic): the Workshop-runtime detection fix, the hash-based version match (confirmed exact string
match), PalSchema/QualityOfLife import (confirmed real files present, `mods.txt` count now 8), the
repair flow's success path (re-ran repair on the freshly-imported PalSchema, confirmed it survived

attempted).
