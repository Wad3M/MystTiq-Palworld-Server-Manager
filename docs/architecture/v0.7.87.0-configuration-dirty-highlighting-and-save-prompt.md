# v0.7.87.0 — Configuration: Advanced Dirty Highlighting, Save/Discard Prompt, Default Tab

## Direct live feedback (queued in the Live-Session Backlog, now addressed)

> "When i change items on this page they should highlight so that we know what has been changed in
> both simple and advanced settings. If I do not save the changes and click away it should ask if I
> want to save changes or discard. when i load up configuration it should always start with the
> servers settings."

Three asks, addressed in order below. Simple Settings already had unsaved-edit highlighting
(`Border.statuscard.dirty`, shipped in v0.7.82.0); Advanced Settings did not.

## 1. Advanced Settings dirty highlighting

`PalworldSettingDto.IsDirty` (`src/MystTiq.Desktop/Models/PalworldConfigurationDtos.cs:50`) already
existed and already drove the STATE column's "Unsaved" text — it was just never bound to a visual
highlight on the Advanced table's rows, unlike Simple's cards. Added:

- A new local style `Border.rowDirty` in the Advanced `ListBox`'s own `<ListBox.Styles>` block
  (`MainWindow.axaml`), matching `Border.statuscard.dirty`'s amber border/gradient/glow, declared
  alongside the existing `Border.differsFromDefault` style (which flags active value against
  Palworld's factory default, not against the last-saved value — both can apply to the same row at
  once, e.g. a QoL rate that's both non-default and freshly edited).
- `Classes.rowDirty="{Binding IsDirty}"` on the row `Border`, and `Classes.dirty="{Binding IsDirty}"`
  on the Active Value `TextBox` (reusing the existing global `TextBox.dirty` style unchanged).

No ViewModel changes needed — `PalworldSettingDto.IsDirty` already existed and already raised
`PropertyChanged` correctly (confirmed by the STATE column already reacting live).

## 2. Save/Discard prompt on navigating away with unsaved changes

Previously, leaving Configuration with unsaved changes (via any nav button, sidebar link, or
in-page shortcut) silently discarded them with no warning.

`Navigate(string? pageName)` (`MainWindowViewModel.cs`) is the single funnel every navigation
call site already goes through — confirmed dozens of XAML bindings point at the same
`NavigateCommand`, so the guard was added there once rather than at each call site:

```csharp
if (SelectedPage == NavigationPage.Configuration && page != NavigationPage.Configuration && PalworldConfigIsDirty)
{
    _pendingNavigationAfterConfigPrompt = page;
    ConfigurationUnsavedChangesNavigationBlocked?.Invoke();
    return;
}
```

The ViewModel has no `Window` reference for a confirm dialog — the same constraint the Close Tab and
Delete Player flows already work around (dialogs are owned by `MainWindow.axaml.cs`'s code-behind).
So the guard raises a new parameterless event, `ConfigurationUnsavedChangesNavigationBlocked`, which
`MainWindow`'s constructor subscribes to reactively (DataContext is assigned *after* the constructor
runs via `App.axaml.cs`'s `new MainWindow { DataContext = viewModel }`, so the subscription happens
inside the existing `PropertyChanged` handler when `DataContextProperty` changes, not inline).

The handler shows a new `Views.ConfirmSaveDiscardDialog` (Cancel / Discard / Save Changes — mirrors
`ConfirmCloseTabDialog`'s own three-button shape) and calls back into whichever of three new
ViewModel continuation methods matches the user's choice:

- `ContinuePendingNavigationSavingConfigurationAsync()` — awaits the existing
  `SavePalworldConfigurationAsync()`, then completes navigation.
- `ContinuePendingNavigationDiscardingConfigurationChanges()` — calls the existing
  `ResetPalworldConfigurationChanges()`, then completes navigation.
- `CancelPendingConfigurationNavigation()` — clears the pending target; the user stays on
  Configuration.

The original `Navigate()` body (set `SelectedPage`, post `RefreshPageForNavigationAsync`) was
extracted into a new `PerformNavigation(NavigationPage page)` helper, shared by the direct path and
all three continuations, so behavior is identical whichever path completes it.

## 3. Configuration always starts on Server Settings

`RefreshPageForNavigationAsync`'s `NavigationPage.Configuration` case now calls
`SetConfigurationView(true)` (the existing private method backing the Simple/Advanced toggle) before
loading, so every navigation onto Configuration resets to Simple Settings — it no longer silently
remembers Advanced from an earlier visit in the same session.
