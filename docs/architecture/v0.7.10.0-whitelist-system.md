# v0.7.10.0 — Whitelist System

## Background

Fifth and final release from the broader review requested this session: a codebase-wide bug scan (v0.7.6.0/v0.7.7.0) plus a competitive feature survey against other Palworld server-management tools (v0.7.8.0/v0.7.9.0). This release ships the last verified gap: a whitelist/allow-list, named explicitly in the codebase's own comments as a deferred roadmap item before this release (`src/MystTiq.Core/Providers/ProviderModels.cs`'s comment listing "presence, world data, chat, whitelist, teleport, commands" as the full capability list MystTiq's Provider Framework was scoped down from — teleport shipped in v0.7.8.0, whitelist ships here).

Unlike v0.7.8.0's teleport/unban/ban-list/save-now (each a thin wrapper around an existing RCON command), Palworld has no native "whitelist" concept at the protocol level — this had to be built as app-level state (a persisted allow-list) plus an enforcement loop, not a command wrapper.

## Design decisions

**Enforcement cadence**: MystTiq's entire player-observation architecture (`HeadlessPlayerRegistryService`, v0.6.6.0) is poll-driven, not event-driven — `Observe()` is called once per `/status/poll` request with the current online-player list, diffing against previous state to detect join/leave transitions. "Observation only happens while something is actively polling" is an already-accepted limitation for that service. Whitelist enforcement follows the identical pattern rather than introducing a second background timer: `HeadlessWhitelistService.EnforceAsync` is called from the same `/status/poll` handler, immediately after `HeadlessPlayerRegistryService.Observe`, using the players snapshot already fetched for that request.

**Kick mechanism**: reuses `PlayerModerationCoordinator.ExecuteAsync("kick", ...)` — the same REST-first-RCON-fallback coordinator every other kick already goes through (manual UI, Discord bot, anti-cheat) — rather than a whitelist-specific moderation path. This keeps exactly one kick implementation in the codebase.

**Debounce**: without one, a not-whitelisted player still connected would be re-kicked on every single 5-second poll tick until the kick actually takes effect and they leave the online list (kicking isn't necessarily instantaneous from the game server's perspective). `HeadlessWhitelistService` tracks a per-player "already handled this session" set, cleared when that player is no longer in the online list (they left) or when the whitelist config changes (a re-enable should re-evaluate everyone fresh).

**Config shape**: `GET`/`PUT /players/whitelist`, config read/replaced as a whole — matching the existing Discord Bot config's established GET+PUT convention (`HeadlessDiscordBotService.GetConfigView`/`SaveConfigAsync`) rather than inventing granular per-entry add/remove REST endpoints. The Desktop mutates a local `ObservableCollection` (add/remove buttons) and an explicit "Save Whitelist" button persists the full list at once — identical UX to the Discord Bot role-mapping list already shipped in v0.6.17.0.

## What shipped

- **`src/MystTiq.Core/Models/WhitelistModels.cs`** (new): `WhitelistEntry(string PlayerId, string Label)`, `WhitelistConfig(bool Enabled, IReadOnlyList<WhitelistEntry> Entries)` with a `Default` (disabled, empty).
- **`src/MystTiq.HeadlessHost/HeadlessWhitelistService.cs`** (new): JSON persistence under `ManagerRuntimeRoot/players/whitelist.json` (atomic write-then-move, matching every other JSON-config service in this codebase), `GetConfig()`/`SaveConfig()` (normalizes/dedupes entries by PlayerId on save), `EnforceAsync(HeadlessPlayersSnapshot, CancellationToken)`.
- **`ServerProfileHost`** gained a `Whitelist` property; `LocalManagementApiHost`'s per-profile service construction wires `PlayerModerationCoordinator` into the new service (already available at that point in the constructor sequence, no new dependency needed).
- **New routes**: `GET /players/whitelist` (Operator role), `PUT /players/whitelist` (Admin role — a stricter gate than most player-moderation routes, since misconfiguring this can lock out the whole player base).
- **`/status/poll`** now calls `p.Whitelist.EnforceAsync(players, token)` immediately after the existing `p.PlayerRegistry.Observe(players, ...)` call.
- **Desktop**: `WhitelistConfigDto`/`WhitelistEntryDto` (`Models/WhitelistDtos.cs`), `GetWhitelistAsync`/`SaveWhitelistAsync` on `IMystTiqApiClient`, and a full ViewModel/XAML wiring mirroring the Discord Bot role-mapping pattern exactly (`WhitelistConfig`, `WhitelistEntries` collection, `NewWhitelistPlayerId`/`NewWhitelistLabel`, `SelectedWhitelistEntry`, `AddWhitelistEntryCommand`/`RemoveWhitelistEntryCommand`/`SaveWhitelistCommand`/`RefreshWhitelistCommand`). New collapsible "Whitelist" card on the Players page (collapsed by default, following the v0.7.5.0 no-scroll pattern and sitting alongside v0.7.8.0's Ban List card).

## Explicit non-goals

- **Whitelist requests** (a no-login link players can use to ask for access, per PalAdmin's feature list) — not part of this release; the current scope is admin-managed entries only.
- **Per-entry granular REST endpoints** — deliberately not built; see the config-shape decision above.
- **A dedicated "Set up whitelist" wizard step** during new-server creation (v0.7.3.0's wizard) — whitelist remains a Players-page feature, not part of initial server setup.

## Verification

`dotnet build` (full solution, Release) — 0 warnings/0 errors.

**Live check**: started a real sidecar and confirmed the full round trip — `GET /players/whitelist` returns the correct default (`{enabled: false, entries: []}`), `PUT` with an enabled config and one entry persists successfully, a subsequent `GET` reflects the saved state (proving real file persistence, not just an in-memory echo), and `GET /status/poll` continues to respond correctly with the new `EnforceAsync` call wired into its handler (confirming the early `if (!players.Available) return;` guard behaves correctly when no real Palworld server is present). Testing the actual auto-kick behavior requires real online players against a real running Palworld server with RCON/REST configured, which is outside what this environment can run — the same disclosed limitation as every RCON/REST-touching feature added this session (v0.7.8.0, v0.7.9.0).

This closes out the full v0.7.6.0→v0.7.10.0 sequence from this session's codebase bug scan and competitive feature survey.
