# v1.0.0.3 — NATIVE MODs and the MOD Drop Zone (internal)

## PalDefender on the MODs page (reported 2026-10-05)

"So Pal Defender does not show up in the MODs. It has a different installation"
(https://ultimeit.github.io/PalDefender/Installation/). PalDefender is a DLL, not PAK or UE4SS content. Its GitHub release
(v1.9.3, 2026-10-03) ships `PalDefender.dll` and `d3d9.dll`. `d3d9.dll` is a general proxy loader that loads the DLLs listed in
`d3d9_config.json` (`{"load_dlls": ["PalDefender.dll"]}` on the owner's server). The wiki shows `version.dll` instead. Both
go into `Pal\Binaries\Win64`. MystTiq only scanned `~mods`/Workshop PAK folders and UE4SS `Mods`, so PalDefender was invisible.

### What was found on the owner's server

- `d3d9.dll` (PalDefender's loader) and `dwmapi.dll` (UE4SS 3.x's loader) had both been renamed to `*.disabled-test` by hand,
  most likely during the 2026-10-01 stuck-start troubleshooting. No session transcript records it, and MystTiq never writes
  that suffix. PalDefender's newest log was 2026-10-01 09:40, so it had not loaded since. That means Give Item, kits and
  teleports were not working, and no UE4SS MOD loaded (the console showed "ENABLED - LOAD NOT CONFIRMED").
- `dsound.dll` is MystTiq's own console-capture proxy (MystTiqConsoleProxy), not a MOD loader.
- An older `dwmapi.dll.myst-disabled` (July, 61 KB) sits beside the August `dwmapi.dll.disabled-test` (279 KB).
- The owner chose to switch both back on (2026-10-05). They were renamed back with the server stopped. The July copy was left alone.

### Design

- `NativeModCatalog` (pure) recognises PalDefender (installed when `PalDefender.dll` exists; on when `d3d9.dll` that loads
  it per the config, or `version.dll`, is present) and the UE4SS loader (when UE4SS.dll exists at the root or in `ue4ss\`).
- **Switching off** renames the active loader to `<loader>.mysttiq-disabled`. The game then loads the real system DLL and
  none of the MOD. Renaming the loader, not the MOD's DLL, keeps the game away from a half-configured proxy.
- **Switching on** restores MystTiq's own copy first, otherwise the newest switched-off copy, so the July UE4SS loader is
  never preferred over the August one.
- Disabling `d3d9.dll` also stops anything else its config lists. That is accepted: on this server it lists only PalDefender.
- Misconfigured states are reported, not guessed: a config that does not list PalDefender, no loader at all, or
  `PalDefender.dll` itself renamed.
- "Loaded" means the MOD's log (`PalDefender\Logs`, `UE4SS.log`) was written after the current server process started.
- With the UE4SS loader off, enabled UE4SS MODs are shown as Attention ("UE4SS loader is off").
- Delete, rollback and repair refuse NATIVE MODs. A ZIP containing `PalDefender.dll` is refused with where the files go,
  instead of becoming a UE4SS folder. Updating PalDefender stays in the Update Center (which already compares it with
  GitHub). The owner asked for an update button for every component in v1.0.1.0.
- The stuck-start tests take NATIVE MODs like any other (they sort first), so "test without MODs" now also leaves
  PalDefender's hooks and UE4SS out. That is the same test that was done by hand on 2026-10-01.

## The MOD drop zone (reported 2026-10-05)

"the drag and drop did not work for installing MODs". The drop zone was a `Border` without a background. In Avalonia only
painted areas take input, so a drop on the zone's empty area went to the card behind it. Only a drop exactly on the button
or caption worked. The fix gives it `Background="Transparent"` and handles drag-enter too.

The ArtworkHarness drops a real ZIP (Avalonia's own file object, the kind an Explorer drop carries) on the zone's empty
corner through the headless drag-and-drop input. It failed before the fix and passes after. Not covered: an elevated
MystTiq ("Run as administrator") cannot receive drops from a normal Explorer window (Windows blocks it). The app asks for
normal rights (`asInvoker`).
