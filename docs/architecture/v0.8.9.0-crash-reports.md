# v0.8.9.0 — Crash Reports in the Crash Analyzer

This is the first item of the user's automated run, which works through the remaining roadmap in reverse order.
It closes the v0.7.97.0 Crash Analyzer follow-ups:
- Palworld-specific signatures, "add only from real log evidence";
- alerting on a new critical crash finding.

## What was missing

Unreal Engine writes a crash report folder for every crash: `Pal\Saved\Crashes\UECC-<platform>-<id>_<n>\`. Its
`CrashContext.runtime-xml` names:
- the error;
- the crash type (Crash / Assert);
- the engine version.

It is the most exact crash evidence a Palworld server leaves. The Crash Analyzer only ever read the `*.log` files.

This project's real server has three such reports, all on UE 5.1.1:

| Date | Error |
|---|---|
| 2026-09-12 | `EXCEPTION_ACCESS_VIOLATION reading address 0xffffffffffffffff` |
| 2026-09-13 | `EXCEPTION_ACCESS_VIOLATION writing address …` |
| 2026-09-16 | `LowLevelFatalError … Containers\Array.cpp … Trying to resize TArray to an invalid size of 1` (an assertion) |

## What changed

- **`UnrealCrashReportParser`** (Core, pure).
  - Reads `FGenericCrashContext/RuntimeProperties`, taking ErrorMessage, CrashType and EngineVersion.
  - Produces one evidence line: `[yyyy.MM.dd-HH.mm.ss] Unreal crash report <folder>: <error> (<type>, engine <version>)`.
  - The time is the report's write time, in local time like the game's own log stamps, so the catalog reads it back.
  - Garbage, other XML documents and empty errors are ignored.
- **New signature `engine-array-size`**, placed ahead of the fatal-error catch-all.
  - It matches the one Palworld-specific message the real evidence supports.
  - It claims only what the report states: an engine safety check on an internal array size, which points to a
    programming error in the game or a native mod. The report names the check, not the feature that hit it.
  - The fixes are to note circumstances, test without native mods, and keep the report folder (it includes a
    minidump) for Pocketpair.
  - The two access violations already match the existing `access-violation` signature, so nothing was invented for
    them.
- **`HeadlessCrashAndSaveToolsService`.**
  - Reads the newest 20 report folders and adds their lines after the (already capped) log lines, so a busy log can
    never push a report out of a finding's evidence.
  - Counts them in `CrashReportsRead`, and the summary says how many were read.
  - Runs one analysis at a time, because two concurrent analyses could each mark the same crash as newly reported.
- **`HeadlessCrashReportWatcher`**, run on the automation tick (every 15 s) for every profile, in api-run and in
  service mode.
  - The first check ever records the reports already on disk **without alerting**, so an upgrade does not announce old
    crashes. An unreadable record is treated as a first run too, never as "every report is new".
  - A new report runs the analysis. It alerts (Critical, "<server>: new crash report") only on new critical findings
    **whose evidence is one of the new reports**. The harness caught an earlier draft presenting an older, never
    analysed report's finding as the new crash's cause.
  - While alerts are **muted**, nothing is marked seen, so the report is announced when the mute ends.
  - With crash alerts **switched off**, the report is marked seen and only the Activity log records it.
  - A crash the recovery loop alerted about in the last 10 minutes is not announced twice. `CrashAlertObserver` now
    exposes `LastCrashDetectedUtc`.
  - The watcher also covers crashes that happened while MystTiq was not running or not supervising.

## Verification

- **Logic harness, 3 scenarios.**
  - The parser: fields, flattening, rejects, and the stamp read back; classification of the TArray check, an access
    violation, and another fatal error.
  - The analyzer reading a fixture `Saved\Crashes`: newest first, skipping an empty folder and a broken file, the
    summary, and not new on a second run.
  - Every watcher case: first-run baseline, a new report alerting once and naming its own finding, a mute held back
    then announced, a recent crash alert suppressing the announcement, crash alerts off, and a corrupt record.
- **Route smoke** (`scripts/Test-v0.8.9.0-RouteSmoke.ps1`), on the published exe with synthetic reports.
  - An existing report is recorded silently.
  - The analyze route reads and classifies it.
  - A new report is announced exactly once, naming the right finding.
  - A report written during a mute is held back and announced after it.
- **Real data** (read-only copies of the three real crash contexts, in an isolated instance):
  - all 3 were read;
  - the two access violations are grouped under "Access violation (native crash)";
  - the TArray crash has its own "Engine stopped on an invalid array size" finding;
  - all carry their correct local times.
